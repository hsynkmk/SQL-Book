# Data Types

## 🧠 Intuition

Every column has a **type** that declares what it can hold — a whole number, a decimal amount,
text, a date, true/false. The type is a contract the database enforces: try to put `'hello'` in an
`INT` column and it's rejected. Choosing the right type matters for **correctness** (no rounding a
currency), **storage** (don't use 8 bytes where 4 will do), and **performance** (smaller types =
more rows per page = faster).

> 💡 **Analogy — labeled containers.** A type is the label on a container: "liquids only,"
> "integers only," "dates only." It stops you from pouring the wrong thing in, and it tells the
> database exactly how much space to reserve and how to compare values.

This is one of the biggest areas where **🟦 SQL Server and 🐘 PostgreSQL diverge** — different type
names, different defaults. Here's the side-by-side map.

## 🟦 SQL Server vs 🐘 PostgreSQL — the type map

### Numbers

| Need | 🟦 SQL Server | 🐘 PostgreSQL | Notes |
|------|--------------|---------------|-------|
| Small/whole integer | `TINYINT` (0-255), `SMALLINT`, `INT`, `BIGINT` | `SMALLINT`, `INT`/`INTEGER`, `BIGINT` | 🐘 has no 1-byte `TINYINT` |
| Exact decimal (money!) | `DECIMAL(p,s)` / `NUMERIC(p,s)` | `NUMERIC(p,s)` / `DECIMAL(p,s)` | **Use this for currency** |
| Money (special) | `MONEY`, `SMALLMONEY` | *(none — use `NUMERIC`)* | 🟦 `MONEY` is discouraged; prefer `DECIMAL` |
| Floating point | `FLOAT`, `REAL` | `DOUBLE PRECISION`, `REAL` | Approximate — never for currency |
| Auto-increment | `INT IDENTITY` | `INT GENERATED ... AS IDENTITY` / `SERIAL` | See [Identity & Sequences](../03-Modifying-Data-and-DDL/04.Identity-and-Sequences.md) |

> ⚠️ **Never store money in `FLOAT`/`DOUBLE`.** `0.1 + 0.2 ≠ 0.3` in binary floating point. Use
> `DECIMAL`/`NUMERIC` with explicit precision (e.g. `DECIMAL(10,2)`).

### Text

| Need | 🟦 SQL Server | 🐘 PostgreSQL | Notes |
|------|--------------|---------------|-------|
| Variable-length, Unicode | `NVARCHAR(n)` / `NVARCHAR(MAX)` | `VARCHAR(n)` / `text` | 🐘 text is **always** Unicode (UTF-8); 🟦 needs the `N` prefix |
| Variable-length, non-Unicode | `VARCHAR(n)` | `VARCHAR(n)` | 🟦 distinguishes; 🐘 doesn't |
| Fixed-length | `CHAR(n)` / `NCHAR(n)` | `CHAR(n)` | Pads with spaces; rarely what you want |
| Unbounded | `NVARCHAR(MAX)` | `text` | 🐘 `text` has no length limit by design |

> 🐘 In PostgreSQL, **`text` and `varchar` are equally fast** — `text` (unbounded) is the idiomatic
> default. In 🟦 SQL Server, prefer **`NVARCHAR`** for Unicode safety and **set a length** (`MAX`
> only when truly needed — it's stored off-row).

### Dates & times

| Need | 🟦 SQL Server | 🐘 PostgreSQL | Notes |
|------|--------------|---------------|-------|
| Date only | `DATE` | `DATE` | Same |
| Time only | `TIME` | `TIME` | Same |
| Date + time | `DATETIME2` (preferred), `DATETIME` (legacy) | `TIMESTAMP` | Use `DATETIME2`, not `DATETIME` |
| With timezone | `DATETIMEOFFSET` | `TIMESTAMPTZ` (`TIMESTAMP WITH TIME ZONE`) | **Prefer these for global apps** |
| Interval/duration | *(none — compute)* | `INTERVAL` | 🐘 has a first-class duration type |
| "Now" | `SYSDATETIME()`, `GETDATE()`, `SYSUTCDATETIME()` | `now()`, `CURRENT_TIMESTAMP` | UTC: `SYSUTCDATETIME()` (🟦) / `now() AT TIME ZONE 'UTC'` (🐘) |

### Boolean

| 🟦 SQL Server | 🐘 PostgreSQL |
|--------------|---------------|
| `BIT` (0/1, or NULL) | `BOOLEAN` (`TRUE`/`FALSE`/`NULL`) |

> 🟦 has no real boolean — use `BIT`. 🐘 has a proper `BOOLEAN` you can write `WHERE is_active`
> against directly.

### Binary, UUID, and specialized

| Need | 🟦 SQL Server | 🐘 PostgreSQL |
|------|--------------|---------------|
| Binary blob | `VARBINARY(MAX)` | `BYTEA` |
| Globally-unique ID | `UNIQUEIDENTIFIER` (`NEWID()`) | `UUID` (`gen_random_uuid()`) |
| JSON | `NVARCHAR` + JSON functions / `JSON` type (SQL 2025) | `JSON` / **`JSONB`** (binary, indexable) |
| XML | `XML` | `XML` |
| Spatial | `GEOGRAPHY`, `GEOMETRY` | PostGIS `geometry`/`geography` |
| Array | *(none — use JSON/table)* | **native arrays** (`int[]`, `text[]`) |
| Row-versioning token | `ROWVERSION` / `TIMESTAMP` | system `xmin` column |

Specialized types get their own chapters in [Module 08](../08-Specialized-Data/README.md).

## 💻 Same table, two dialects

```sql
-- 🟦 SQL Server
CREATE TABLE products (
    product_id  INT IDENTITY PRIMARY KEY,
    name        NVARCHAR(100) NOT NULL,
    unit_price  DECIMAL(10,2) NOT NULL,
    created_at  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    is_active   BIT NOT NULL DEFAULT 1
);
```
```sql
-- 🐘 PostgreSQL
CREATE TABLE products (
    product_id  INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        text NOT NULL,
    unit_price  NUMERIC(10,2) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    is_active   BOOLEAN NOT NULL DEFAULT TRUE
);
```

Six columns, six small dialect differences — that's the whole game.

## ⚖️ Choosing well

- **Currency → `DECIMAL`/`NUMERIC`** with explicit scale. Never float.
- **Text → 🟦 `NVARCHAR(n)` / 🐘 `text`.** Size 🟦 columns sensibly; `MAX`/unbounded only when needed.
- **Timestamps → prefer timezone-aware** (`DATETIMEOFFSET` / `TIMESTAMPTZ`) and store **UTC**.
- **IDs → integer surrogate** for most tables; `UUID` when you need globally-unique/unguessable IDs
  (distributed systems), accepting larger size and random-insert index cost.
- **Smaller is better** — narrower types pack more rows per page → less I/O. But don't
  micro-optimize at the cost of correctness.

## 🚫 Common mistakes

```sql
-- ❌ Money in float → rounding errors
price FLOAT            -- 19.99 might store as 19.989999...
-- ✅
price DECIMAL(10,2)

-- ❌ 🟦 forgetting N-prefix on Unicode literals → silent data loss for non-ASCII
INSERT INTO t (name) VALUES ('Łukasz');     -- may corrupt without N''
-- ✅
INSERT INTO t (name) VALUES (N'Łukasz');

-- ❌ Storing dates as strings → can't sort/compare/index correctly
order_date VARCHAR(10)  -- '2025-13-99' is "valid" text!
-- ✅
order_date DATE

-- ❌ 🟦 using deprecated TEXT/NTEXT or DATETIME
-- ✅ use NVARCHAR(MAX) and DATETIME2
```

## 🎯 Practice (with full solutions)

### 1. Pick the right types — `Easy`
**Task:** Choose types (both engines) for: a product price, a customer's display name (may contain
accents), an order's exact timestamp in a global app, and an "is shipped" flag.
**Solution:**
| Column | 🟦 SQL Server | 🐘 PostgreSQL |
|--------|--------------|---------------|
| price | `DECIMAL(10,2)` | `NUMERIC(10,2)` |
| name (Unicode) | `NVARCHAR(100)` | `text` |
| timestamp (global) | `DATETIMEOFFSET` | `TIMESTAMPTZ` |
| is_shipped | `BIT` | `BOOLEAN` |
**Why it works:** exact decimal for money, Unicode-safe text, timezone-aware timestamps for a
global app, native/closest boolean.

### 2. Fix the broken column types — `Medium`
**Smelly DDL:** `CREATE TABLE payments (amount FLOAT, paid_at VARCHAR(20), currency CHAR(50));`
**Task:** correct it.
**Solution:**
```sql
-- 🟦 SQL Server
CREATE TABLE payments (
    amount   DECIMAL(12,2) NOT NULL,      -- exact money
    paid_at  DATETIMEOFFSET NOT NULL,     -- real timezone-aware timestamp
    currency CHAR(3) NOT NULL             -- ISO codes are exactly 3 chars
);
```
```sql
-- 🐘 PostgreSQL
CREATE TABLE payments (
    amount   NUMERIC(12,2) NOT NULL,
    paid_at  TIMESTAMPTZ NOT NULL,
    currency CHAR(3) NOT NULL
);
```
**Why it works:** money is exact, the timestamp sorts/compares correctly, and the currency code is
right-sized to its actual domain (3-letter ISO) instead of a wasteful `CHAR(50)`.

## ✅ Key Takeaways

- A column's **type** enforces a contract and drives correctness, storage, and speed.
- **Currency → `DECIMAL`/`NUMERIC`**, never float. **Timestamps → timezone-aware + UTC.**
- Text: **🟦 `NVARCHAR`** (Unicode, sized) vs **🐘 `text`** (Unicode by default, idiomatic).
- 🟦 has **`BIT`**; 🐘 has a real **`BOOLEAN`**. 🐘 has **native arrays** and **`JSONB`**; 🟦 leans on
  JSON functions + `VARBINARY`.
- Right-size types — smaller is faster — but never trade correctness for bytes.
