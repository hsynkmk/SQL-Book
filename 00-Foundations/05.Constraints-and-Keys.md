# Constraints & Keys

## 🧠 Intuition

A **constraint** is a rule the database enforces on your data, automatically, on every insert and
update. Types catch "wrong kind of value"; constraints catch "wrong *value*" — a negative price, a
duplicate email, an order for a non-existent customer, a missing required field. Put the rules in
the **database** and they hold no matter which app, script, or person writes the data.

> 💡 **Analogy — a bouncer at the door.** The database is a club; constraints are the bouncer
> checking IDs at the entrance. It doesn't matter how someone tries to get in (your web app, a
> migration script, a DBA typing by hand) — bad data is turned away at the door. Application-only
> validation is a bouncer who only checks *some* doors.

The two engines agree on constraints almost completely — this is well-standardized SQL.

## 📐 The constraint family

| Constraint | Enforces | Example |
|------------|----------|---------|
| **PRIMARY KEY** | Unique + not null row identifier | `customer_id INT PRIMARY KEY` |
| **FOREIGN KEY** | Referential integrity (value exists in another table) | `customer_id INT REFERENCES customers(...)` |
| **UNIQUE** | No duplicate values (an alternate key) | `email VARCHAR(255) UNIQUE` |
| **CHECK** | A custom rule on values | `CHECK (unit_price >= 0)` |
| **NOT NULL** | A value is required | `name VARCHAR(100) NOT NULL` |
| **DEFAULT** | A fallback value when none supplied | `status VARCHAR(20) DEFAULT 'Pending'` |

## 💻 Declaring constraints (works on both engines)

```sql
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,                         -- PK: unique + not null
    email       VARCHAR(255) NOT NULL UNIQUE,            -- required + no duplicates
    country     VARCHAR(50) NOT NULL DEFAULT 'Unknown',  -- required, with a fallback
    age         INT CHECK (age >= 0 AND age < 150)       -- custom domain rule
);

CREATE TABLE orders (
    order_id    INT PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(customer_id),   -- FK
    total       DECIMAL(10,2) NOT NULL CHECK (total >= 0),
    order_date  DATE NOT NULL DEFAULT CURRENT_DATE
);
```

### Named constraints (recommended)

Naming constraints makes errors readable and lets you `ALTER` them later:

```sql
ALTER TABLE products
    ADD CONSTRAINT chk_products_price_nonneg CHECK (unit_price >= 0);

ALTER TABLE orders
    ADD CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id);
```

A violation then reports `chk_products_price_nonneg` instead of a random system-generated name —
much easier to debug and to handle in application code.

## 📐 Primary keys, in depth

A primary key is **unique + not null**, and both engines automatically create an **index** on it
(so PK lookups are fast). One per table.

- **Surrogate key** — a meaningless auto-generated number (`IDENTITY`/`GENERATED`). The usual
  default: stable, compact, never needs to change. See
  [Identity & Sequences](../03-Modifying-Data-and-DDL/04.Identity-and-Sequences.md).
- **Natural key** — a real-world unique value (email, ISBN, country code). Meaningful, but risky if
  it can change (people change emails) — a changing PK cascades everywhere.
- **Composite key** — multiple columns together (`order_items(order_id, product_id)`).

> 🟦 In SQL Server, the PK is **clustered by default** (it dictates physical row order). In
> 🐘 PostgreSQL, tables are **heaps** and the PK is just a unique index — no physical ordering. This
> distinction matters a lot for performance; it's covered in
> [Clustered, Nonclustered & Heaps](../06-Indexing-and-Performance/02.Clustered-Nonclustered-Heaps.md).

## 📐 Foreign keys & referential actions

A foreign key guarantees the referenced row exists. You also control what happens when the *parent*
is deleted or updated:

```sql
CREATE TABLE order_items (
    order_id   INT NOT NULL,
    product_id INT NOT NULL,
    quantity   INT NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id)   REFERENCES orders(order_id)     ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(product_id) ON DELETE RESTRICT
);
```

| Referential action | Meaning |
|--------------------|---------|
| `ON DELETE CASCADE` | Delete the parent → delete the children too |
| `ON DELETE RESTRICT` / `NO ACTION` | Block the delete if children exist |
| `ON DELETE SET NULL` | Null the FK in children (requires nullable FK) |
| `ON DELETE SET DEFAULT` | Set the FK to its default |

Both engines support these identically. (🟦 SQL Server additionally rejects *multiple cascade
paths* to the same table — a quirk covered in the EF/relational-design notes.)

## 📐 CHECK constraints & domain rules

`CHECK` enforces any boolean rule on a row's values:

```sql
ALTER TABLE employees ADD CONSTRAINT chk_salary_positive CHECK (salary > 0);
ALTER TABLE orders    ADD CONSTRAINT chk_status_valid
    CHECK (status IN ('Pending','Shipped','Cancelled'));
```

> 🐘 PostgreSQL also has **`DOMAIN`** types — a reusable named type with a built-in check
> (`CREATE DOMAIN positive_int AS INT CHECK (VALUE > 0)`), which 🟦 SQL Server lacks. And both now
> support enumerations differently: 🐘 has a native `ENUM` type; 🟦 uses a `CHECK ... IN (...)` or a
> lookup table.

## ⚖️ Why enforce in the database, not just the app

- **Multiple writers.** Your web app, a background job, a migration, a DBA, and a reporting ETL all
  touch the database. App validation protects only the app's path; a database constraint protects
  *every* path.
- **Race conditions.** A `UNIQUE` constraint atomically prevents two simultaneous inserts of the
  same email; an app-level "check then insert" has a race window.
- **Documentation.** Constraints document the real rules of your data, in the schema, forever.

The trade-off: constraints add a tiny write-time cost and can make bulk loads slower (sometimes
disabled during big imports, then re-validated). Worth it almost always.

## 🚫 Common mistakes

```sql
-- ❌ Relying only on the app to prevent duplicates → races + other writers slip through
-- ✅ enforce it
ALTER TABLE customers ADD CONSTRAINT uq_customers_email UNIQUE (email);

-- ❌ Nullable foreign key you meant to be required → orphan-able / inconsistent
customer_id INT REFERENCES customers(customer_id)         -- nullable!
-- ✅
customer_id INT NOT NULL REFERENCES customers(customer_id)

-- ❌ No CHECK on a domain rule → negative prices, invalid statuses creep in
-- ✅ CHECK (unit_price >= 0), CHECK (status IN (...))

-- ❌ Unnamed constraints → cryptic errors, can't ALTER them by name later
-- ✅ name them: CONSTRAINT chk_... / fk_... / uq_...
```

## 🎯 Practice (with full solutions)

### 1. Lock down a table with constraints — `Medium`
**Task:** Create an `accounts` table where: `account_id` is the PK, `email` is required and unique,
`balance` defaults to 0 and can't be negative, and `status` must be one of `'active'`/`'frozen'`/
`'closed'`.
**Solution (both engines):**
```sql
CREATE TABLE accounts (
    account_id INT PRIMARY KEY,
    email      VARCHAR(255) NOT NULL,
    balance    DECIMAL(12,2) NOT NULL DEFAULT 0,
    status     VARCHAR(10) NOT NULL DEFAULT 'active',
    CONSTRAINT uq_accounts_email   UNIQUE (email),
    CONSTRAINT chk_accounts_balance CHECK (balance >= 0),
    CONSTRAINT chk_accounts_status  CHECK (status IN ('active','frozen','closed'))
);
```
**Why it works:** every rule is enforced by the database for all writers — no app can insert a
duplicate email, a negative balance, or an invalid status.

### 2. Choose a delete behavior — `Easy`
**Task:** Deleting an `order` should also delete its `order_items`, but deleting a `product` that
still appears in orders should be **blocked**. Write the FKs.
**Solution:**
```sql
ALTER TABLE order_items
    ADD CONSTRAINT fk_items_order FOREIGN KEY (order_id)
        REFERENCES orders(order_id) ON DELETE CASCADE,
    ADD CONSTRAINT fk_items_product FOREIGN KEY (product_id)
        REFERENCES products(product_id) ON DELETE RESTRICT;
```
**Why it works:** `CASCADE` cleans up an order's line items automatically (they're owned by the
order); `RESTRICT` protects referential history (you can't erase a product that orders depend on).

## ✅ Key Takeaways

- **Constraints** enforce data rules in the database, for **every** writer — not just your app.
- **PK** (unique + not null, auto-indexed), **FK** (referential integrity + delete behavior),
  **UNIQUE**, **CHECK**, **NOT NULL**, **DEFAULT**.
- Prefer **surrogate keys** for most PKs; **name** your constraints for readable errors and easy
  `ALTER`.
- 🟦 PKs are **clustered by default**; 🐘 tables are **heaps** with a PK index.
- 🐘 extras: `DOMAIN` types and native `ENUM`; 🟦 uses `CHECK ... IN` / lookup tables.
