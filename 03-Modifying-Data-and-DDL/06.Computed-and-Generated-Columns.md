# Computed & Generated Columns

## 🧠 Intuition

A **computed/generated column** is a column whose value is **derived from other columns** by a
formula you define once — `line_total = quantity * unit_price`, `full_name = first_name + ' ' +
last_name`. You never insert or update it directly; the database computes it. This keeps derived
data **consistent** (it can't drift out of sync) and the formula **in one place**.

> 💡 **Analogy — a spreadsheet formula cell.** You don't type the total into the "Total" cell; you
> write `=B2*C2` and it always reflects the inputs. A generated column is that formula cell, living
> in the table.

## 🎯 The Problem

```sql
-- ❌ Storing a derived value and updating it by hand → it drifts out of sync
INSERT INTO order_items (order_id, product_id, quantity, unit_price, line_total)
VALUES (1, 5, 3, 9.99, 29.97);
-- Later someone updates quantity to 4 but FORGETS line_total → now it's wrong (29.97, should be 39.96)
```

A generated column makes `line_total` *always* equal `quantity * unit_price` — impossible to forget.

## 📐 Two flavors: virtual vs stored

- **Virtual (computed on read):** the value is calculated each time you query it. No storage cost;
  always current. Can't be indexed unless persisted (mostly).
- **Stored (persisted):** the value is computed on write and **physically stored**. Costs space, can
  be **indexed** and used in constraints — good for hot filters/sorts on the derived value.

## 💻 🟦 SQL Server — computed columns

```sql
-- Virtual computed column (calculated on read)
ALTER TABLE order_items ADD line_total AS (quantity * unit_price);

-- PERSISTED computed column (stored, can be indexed)
ALTER TABLE order_items ADD line_total AS (quantity * unit_price) PERSISTED;

-- In a table definition
CREATE TABLE order_items (
    order_id   INT,
    product_id INT,
    quantity   INT,
    unit_price DECIMAL(10,2),
    line_total AS (quantity * unit_price) PERSISTED,   -- derived, stored
    PRIMARY KEY (order_id, product_id)
);

-- You can index a PERSISTED computed column
CREATE INDEX ix_items_linetotal ON order_items (line_total);
```

🟦 uses **`AS (expression)`** — add `PERSISTED` to store it (required if you want to index it, in
most cases).

## 💻 🐘 PostgreSQL — generated columns

```sql
-- PostgreSQL only supports STORED generated columns (no virtual yet, as of PG 17)
CREATE TABLE order_items (
    order_id   INT,
    product_id INT,
    quantity   INT,
    unit_price NUMERIC(10,2),
    line_total NUMERIC(10,2) GENERATED ALWAYS AS (quantity * unit_price) STORED,
    PRIMARY KEY (order_id, product_id)
);

-- Add to an existing table
ALTER TABLE order_items
    ADD COLUMN line_total NUMERIC(10,2) GENERATED ALWAYS AS (quantity * unit_price) STORED;

-- Index it like any column
CREATE INDEX ix_items_linetotal ON order_items (line_total);
```

🐘 uses **`GENERATED ALWAYS AS (expression) STORED`** — note 🐘 currently supports **only `STORED`**
(no virtual/computed-on-read columns yet).

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Syntax | `col AS (expr)` | `col type GENERATED ALWAYS AS (expr) STORED` |
| Virtual (compute on read) | ✅ (default) | ❌ (not yet) |
| Stored/persisted | `... PERSISTED` | `... STORED` (the only option) |
| Indexable | Yes (usually needs PERSISTED) | Yes |
| Can reference other tables | ❌ (same row only) | ❌ (same row only) |
| Insert into it directly | ❌ (computed) | ❌ (generated) |

> Both restrict the expression to **the same row's columns** — you can't reference another table or
> use a subquery (that's what views/triggers are for). 🐘 requires the expression be **immutable**
> (deterministic).

## ⚡ Under the Hood / Performance

- **Virtual (🟦)**: no storage, recomputed on every read — cheap to write, costs CPU on read. Fine
  for lightly-read derived values.
- **Stored/persisted (both)**: computed once on write, stored — faster reads, and **indexable**.
  Index a stored generated column when you frequently filter/sort/join on the derived value (e.g.
  `WHERE line_total > 100`).
- A **persisted + indexed** computed column is a classic trick to make a non-SARGable expression
  SARGable: instead of `WHERE quantity * unit_price > 100` (can't use a normal index), filter on the
  indexed `line_total` column. See [SARGability](../06-Indexing-and-Performance/05.SARGability.md).

## 🚫 Common mistakes

```sql
-- ❌ Trying to INSERT/UPDATE a generated column directly
INSERT INTO order_items (..., line_total) VALUES (..., 29.97);   -- ERROR: it's computed
UPDATE order_items SET line_total = 40 WHERE ...;                -- ERROR
-- ✅ change the inputs; the generated column updates itself

-- ❌ Referencing another table in the expression
... GENERATED ALWAYS AS ((SELECT rate FROM fx) * amount) STORED   -- not allowed
-- ✅ use a view or a trigger for cross-table derivation

-- ❌ 🐘: expecting a virtual (non-stored) generated column
... GENERATED ALWAYS AS (expr)   -- ERROR: STORED is required on PostgreSQL
-- ✅ ... GENERATED ALWAYS AS (expr) STORED

-- ❌ Indexing a 🟦 computed column that isn't PERSISTED + deterministic → may be rejected
-- ✅ make it PERSISTED (and deterministic) before indexing
```

## 🌍 Real-World Use

- **Line totals / subtotals:** `quantity * unit_price`, `price * (1 - discount)`.
- **Full names / display strings:** `first_name || ' ' || last_name`.
- **Normalized search keys:** `LOWER(email)` stored + indexed for case-insensitive lookups.
- **Tax/derived amounts:** `amount * tax_rate` (single-row math only).
- **SARGable index targets:** persist+index an expression you filter on a lot.

## 🎯 Practice (with full solutions)

### 1. Always-correct line total — `Easy`
**Task:** Add a `line_total` to `order_items` that always equals `quantity * unit_price`, stored,
in both engines.
**Solution:**
```sql
-- 🟦 SQL Server
ALTER TABLE order_items ADD line_total AS (quantity * unit_price) PERSISTED;
-- 🐘 PostgreSQL
ALTER TABLE order_items
    ADD COLUMN line_total NUMERIC(10,2) GENERATED ALWAYS AS (quantity * unit_price) STORED;
```
**Why it works:** the database recomputes `line_total` whenever `quantity` or `unit_price` changes
— it can never drift, and being stored it's indexable.

### 2. Make an expression SARGable — `Medium`
**Task:** Queries `WHERE quantity * unit_price > 100` are slow (can't use an index on a computed
expression). Fix it.
**Solution:**
```sql
-- Persist + index the derived value, then filter on the column
-- 🟦 SQL Server
ALTER TABLE order_items ADD line_total AS (quantity * unit_price) PERSISTED;
CREATE INDEX ix_items_linetotal ON order_items (line_total);
-- 🐘 PostgreSQL
ALTER TABLE order_items ADD COLUMN line_total NUMERIC(10,2)
    GENERATED ALWAYS AS (quantity * unit_price) STORED;
CREATE INDEX ix_items_linetotal ON order_items (line_total);

-- Now query the indexed column instead of the expression:
SELECT * FROM order_items WHERE line_total > 100;     -- uses the index (SARGable)
```
**Why it works:** the engine can't use an index on the *expression* `quantity * unit_price`, but it
*can* on the stored, indexed `line_total` column — turning a scan into a seek.

## ✅ Key Takeaways

- A **computed/generated column** is derived from other columns by a formula — never set directly,
  always consistent.
- **🟦** supports **virtual** (`AS (expr)`) and **`PERSISTED`** computed columns; **🐘** supports only
  **`GENERATED ALWAYS AS (expr) STORED`**.
- **Stored** columns cost space but are **indexable** — and persisting + indexing an expression
  makes it **SARGable**.
- Expressions can only reference **the same row** (no other tables/subqueries — use views/triggers
  for that).
- You change the **inputs**; the generated column updates itself.
