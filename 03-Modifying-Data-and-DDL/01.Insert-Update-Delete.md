# INSERT, UPDATE, DELETE

## 🧠 Intuition

Reading data is half of SQL; **writing** it is the other half. Three statements cover it:
**`INSERT`** adds rows, **`UPDATE`** changes existing rows, **`DELETE`** removes them. The golden
rule for the destructive two: **`UPDATE` and `DELETE` without a `WHERE` clause hit *every* row** —
the single most dangerous mistake in SQL.

> 💡 **Analogy — editing a filing cabinet.** `INSERT` files a new folder, `UPDATE` edits an existing
> one, `DELETE` shreds one. Forgetting the `WHERE` is like saying "shred the folder" but pointing at
> the whole cabinet. Always know *which rows* you're touching before you run it.

The core syntax is **standardized**; the engines differ mainly in how they **return what changed**
(`OUTPUT` vs `RETURNING`).

## 💻 INSERT

```sql
-- Single row, named columns (always name your columns — order-independent, survives schema changes)
INSERT INTO categories (name) VALUES ('Office Supplies');

-- Multiple rows in one statement (one round-trip, atomic)
INSERT INTO products (name, category_id, unit_price, units_in_stock) VALUES
    ('Stapler', 4, 6.50, 100),
    ('Notebook', 4, 3.25, 250);

-- INSERT ... SELECT: copy/derive rows from a query
INSERT INTO archived_orders (order_id, customer_id, order_date)
SELECT order_id, customer_id, order_date FROM orders WHERE status = 'Cancelled';
```

> ⚠️ **Don't `INSERT INTO products VALUES (...)`** without column names — it breaks the moment
> someone adds or reorders a column. Always list the columns.

## 💻 UPDATE

```sql
-- Update specific rows (WHERE is mandatory in practice!)
UPDATE products SET unit_price = unit_price * 1.10 WHERE category_id = 1;   -- 10% raise on beverages

-- Update multiple columns
UPDATE orders SET status = 'Shipped', employee_id = 3 WHERE order_id = 2;

-- UPDATE with a join (set values from another table)
-- 🟦 SQL Server
UPDATE oi
SET oi.unit_price = p.unit_price
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
WHERE oi.order_id = 2;
-- 🐘 PostgreSQL (UPDATE ... FROM)
UPDATE order_items oi
SET unit_price = p.unit_price
FROM products p
WHERE p.product_id = oi.product_id AND oi.order_id = 2;
```

> The **UPDATE-with-join** syntax is one of the bigger dialect differences: 🟦 uses
> `UPDATE alias SET ... FROM ... JOIN ...`; 🐘 uses `UPDATE table SET ... FROM other WHERE ...`.

## 💻 DELETE

```sql
-- Delete specific rows
DELETE FROM order_items WHERE order_id = 4;

-- DELETE with a join condition
-- 🟦 SQL Server
DELETE oi FROM order_items oi JOIN orders o ON o.order_id = oi.order_id WHERE o.status = 'Cancelled';
-- 🐘 PostgreSQL (DELETE ... USING)
DELETE FROM order_items oi USING orders o WHERE o.order_id = oi.order_id AND o.status = 'Cancelled';

-- Remove ALL rows fast (resets/empties the table) — see note below
TRUNCATE TABLE staging_table;
```

### DELETE vs TRUNCATE

| | `DELETE` | `TRUNCATE` |
|--|----------|------------|
| Removes | Rows matching `WHERE` (or all) | **All** rows, always |
| Logging | Row-by-row (slower, fully logged) | Minimal (fast) |
| Triggers | Fires `DELETE` triggers | Usually does **not** fire triggers |
| Identity/sequence | Keeps the counter | 🟦 resets identity; 🐘 `TRUNCATE ... RESTART IDENTITY` to reset |
| FK-referenced table | Allowed | Blocked if referenced (unless `CASCADE`) |

Use `TRUNCATE` for "empty this whole staging table fast"; use `DELETE` when you need a `WHERE`,
triggers, or it's referenced by FKs.

## 💻 Returning what changed — OUTPUT vs RETURNING

A frequent need: insert a row and immediately get its generated ID, or capture exactly which rows
an update/delete touched.

```sql
-- 🟦 SQL Server: OUTPUT
INSERT INTO categories (name) OUTPUT INSERTED.category_id VALUES ('Garden');
UPDATE products SET unit_price = unit_price * 1.1
OUTPUT INSERTED.product_id, DELETED.unit_price AS old_price, INSERTED.unit_price AS new_price
WHERE category_id = 1;
DELETE FROM orders OUTPUT DELETED.order_id WHERE status = 'Cancelled';
```
```sql
-- 🐘 PostgreSQL: RETURNING
INSERT INTO categories (name) VALUES ('Garden') RETURNING category_id;
UPDATE products SET unit_price = unit_price * 1.1 WHERE category_id = 1
RETURNING product_id, unit_price;
DELETE FROM orders WHERE status = 'Cancelled' RETURNING order_id;
```

> 🟦's `OUTPUT` exposes both `INSERTED` (new values) and `DELETED` (old values) — great for audit
> trails. 🐘's `RETURNING` returns the resulting row values. Both save a round-trip vs "write then
> SELECT."

## ⚡ Under the Hood / Performance

- **Multi-row `INSERT`** (one statement, many `VALUES`) is far faster than many single-row inserts —
  fewer round-trips, one transaction. For bulk loads, use `COPY` (🐘) / `bcp`/`BULK INSERT` (🟦).
- **`UPDATE`/`DELETE` use the same `WHERE` planning as `SELECT`** — an index on the filter column
  makes them fast and lock fewer rows. An unindexed `WHERE` can scan and lock the whole table.
- Big `DELETE`s generate lots of log and locks — consider **batching** (`DELETE TOP (10000)` 🟦 /
  `DELETE ... WHERE ctid IN (... LIMIT)` 🐘) for very large purges.

## 🚫 Common mistakes

```sql
-- ❌ The career-ending classic: no WHERE
UPDATE products SET unit_price = 0;     -- every product is now free
DELETE FROM orders;                     -- all orders gone
-- ✅ ALWAYS include a WHERE (or be certain you mean every row).
--    Tip: write the WHERE first, run it as a SELECT, THEN turn it into UPDATE/DELETE.

-- ❌ INSERT without column names
INSERT INTO products VALUES ('X', 1, 5.0, 10);   -- breaks if columns change
-- ✅ INSERT INTO products (name, category_id, unit_price, units_in_stock) VALUES (...)

-- ❌ Running a destructive statement outside a transaction with no way back
-- ✅ for risky changes: BEGIN; UPDATE ...; -- check rowcount -- COMMIT/ROLLBACK (see Transactions)
```

> 💡 **Safety habit:** before an `UPDATE`/`DELETE`, run the **same `WHERE` as a `SELECT`** to see
> exactly which rows you'll affect. Many SQL editors also have a "safe mode" that rejects
> WHERE-less updates.

## 🌍 Real-World Use

Every form submission, status change, soft delete, data import, and cleanup job is `INSERT`/
`UPDATE`/`DELETE`. `OUTPUT`/`RETURNING` powers "create and show the new ID" flows and audit logging.
Batched deletes purge old data without locking the table for minutes.

## 🎯 Practice (with full solutions)

### 1. Insert and get the new ID — `Easy`
**Task:** Insert a new category `'Garden'` and return its generated `category_id`, in both dialects.
**Solution:**
```sql
-- 🟦 SQL Server
INSERT INTO categories (name) OUTPUT INSERTED.category_id VALUES ('Garden');
-- 🐘 PostgreSQL
INSERT INTO categories (name) VALUES ('Garden') RETURNING category_id;
```
**Why it works:** `OUTPUT`/`RETURNING` hand back the auto-generated key in the same statement — no
second query needed.

### 2. Targeted price update — `Easy`
**Task:** Raise the price of every product in category 1 by 10%.
**Solution:**
```sql
UPDATE products SET unit_price = unit_price * 1.10 WHERE category_id = 1;
```
**Why it works:** the `WHERE` limits the change to category 1; the expression updates each matching
row relative to its current value. (Run `SELECT * FROM products WHERE category_id = 1;` first to
confirm the target rows.)

### 3. Clean up cancelled orders — `Medium`
**Task:** Delete the line items belonging to cancelled orders.
**Solution:**
```sql
-- 🟦 SQL Server
DELETE oi FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
WHERE o.status = 'Cancelled';
-- 🐘 PostgreSQL
DELETE FROM order_items oi
USING orders o
WHERE o.order_id = oi.order_id AND o.status = 'Cancelled';
```
**Why it works:** the join condition identifies line items whose parent order is cancelled; each
engine's join-delete syntax differs but the logic is identical.

## ✅ Key Takeaways

- **`INSERT`** (name your columns!), **`UPDATE`**, **`DELETE`** — and **never `UPDATE`/`DELETE`
  without a `WHERE`** unless you truly mean all rows.
- Capture changes inline with **🟦 `OUTPUT`** (`INSERTED`/`DELETED`) or **🐘 `RETURNING`**.
- **UPDATE/DELETE-with-join** syntax differs: 🟦 `... FROM ... JOIN`, 🐘 `... FROM`/`USING`.
- **`TRUNCATE`** empties a table fast (no `WHERE`, minimal logging, may reset identity); `DELETE` for
  targeted/triggered removal.
- Index the `WHERE` column; batch huge deletes; preview with a `SELECT` first.

**Self-check:**
1. What happens if you run `UPDATE`/`DELETE` without a `WHERE`, and how do you guard against it?
2. How do you get a newly-inserted row's generated ID in each engine?
3. When is `TRUNCATE` preferable to `DELETE`, and what are its caveats?
