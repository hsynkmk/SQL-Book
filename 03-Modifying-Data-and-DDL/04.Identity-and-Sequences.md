# Identity & Sequences

## 🧠 Intuition

Most tables need an automatic, unique number for each new row — the surrogate primary key. You
don't want to compute or track "the next ID" yourself; the database does it. **Identity columns**
auto-fill a number on insert; **sequences** are standalone number generators you can share across
tables. The engines name and configure these quite differently.

> 💡 **Analogy — a deli ticket dispenser.** Each customer pulls the next number automatically — no
> two get the same, and you never reuse a number even if someone leaves. An identity column is that
> dispenser built into the table; a sequence is a standalone dispenser you can wheel between
> counters.

## 📐 The map

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Auto-increment column (modern, ANSI) | `INT IDENTITY(1,1)` | `INT GENERATED ALWAYS AS IDENTITY` |
| Allow manual override of the value | `SET IDENTITY_INSERT ON` (temporary) | `INT GENERATED BY DEFAULT AS IDENTITY` |
| Legacy shorthand | — | `SERIAL` / `BIGSERIAL` (older style) |
| Standalone generator | `CREATE SEQUENCE` | `CREATE SEQUENCE` |
| Get last inserted id | `SCOPE_IDENTITY()` / `OUTPUT` | `RETURNING` / `currval()` / `lastval()` |
| Reset the counter | `DBCC CHECKIDENT(...)` | `ALTER SEQUENCE ... RESTART` |

## 💻 Identity columns

```sql
-- 🟦 SQL Server
CREATE TABLE customers (
    customer_id INT IDENTITY(1,1) PRIMARY KEY,   -- start at 1, step 1
    name        NVARCHAR(100) NOT NULL
);
INSERT INTO customers (name) VALUES ('Acme');    -- customer_id auto-assigned

-- 🐘 PostgreSQL (ANSI-standard, preferred over SERIAL)
CREATE TABLE customers (
    customer_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        text NOT NULL
);
INSERT INTO customers (name) VALUES ('Acme');    -- customer_id auto-assigned
```

### ALWAYS vs BY DEFAULT (🐘) / IDENTITY_INSERT (🟦)

- **`GENERATED ALWAYS`** (🐘): you *cannot* insert your own value — the database always generates it.
  Safest; prevents accidental ID collisions.
- **`GENERATED BY DEFAULT`** (🐘): the database generates one *unless* you supply a value — useful
  for data migration where you need to preserve original IDs.
- **🟦 `IDENTITY`** blocks manual inserts by default; temporarily allow them with:

```sql
-- 🟦 SQL Server: insert explicit IDs (e.g. during a migration)
SET IDENTITY_INSERT customers ON;
INSERT INTO customers (customer_id, name) VALUES (1000, 'Imported');
SET IDENTITY_INSERT customers OFF;
```

## 💻 Getting the generated ID back

```sql
-- 🟦 SQL Server
INSERT INTO customers (name) VALUES ('Globex');
SELECT SCOPE_IDENTITY();                        -- the id from THIS scope's last insert
-- or inline:
INSERT INTO customers (name) OUTPUT INSERTED.customer_id VALUES ('Globex');

-- 🐘 PostgreSQL
INSERT INTO customers (name) VALUES ('Globex') RETURNING customer_id;
```

> ⚠️ 🟦: prefer **`SCOPE_IDENTITY()`** over `@@IDENTITY`. `@@IDENTITY` returns the last identity from
> *any* scope — including one created by a trigger on another table — which is a classic
> hard-to-find bug. `SCOPE_IDENTITY()` is scoped to your statement. Better still, use `OUTPUT`.

## 💻 Sequences (standalone generators)

```sql
-- Create a sequence (both engines, nearly identical syntax)
CREATE SEQUENCE order_number_seq START WITH 1000 INCREMENT BY 1;

-- Use it
-- 🟦 SQL Server
INSERT INTO orders (order_number) VALUES (NEXT VALUE FOR order_number_seq);
-- 🐘 PostgreSQL
INSERT INTO orders (order_number) VALUES (nextval('order_number_seq'));

-- Peek / set
SELECT NEXT VALUE FOR order_number_seq;     -- 🟦
SELECT nextval('order_number_seq'), currval('order_number_seq');   -- 🐘
ALTER SEQUENCE order_number_seq RESTART WITH 5000;   -- both (🟦: ALTER SEQUENCE ... RESTART WITH)
```

**Why sequences over identity?** A sequence can be **shared across multiple tables** (e.g. one
global "document number" for invoices *and* credit notes), or generate values *before* the insert
(useful when you need the ID to build related rows first). Identity is simpler for the common
one-table case.

## ⚖️ Gaps are normal — don't fight them

Both identity columns and sequences **will have gaps**: a rolled-back transaction, a failed insert,
or a cached batch of values on restart consumes numbers that never appear in the table.

> ⚠️ **Surrogate keys are not "row counts" and not guaranteed gap-free or strictly sequential.**
> Never assume IDs are contiguous. If you need a gapless, ordered sequence (e.g. legal invoice
> numbers), that's a *business* requirement needing a dedicated, transactionally-controlled counter
> (and the contention that comes with it) — not the identity/sequence mechanism.

## 🚫 Common mistakes

```sql
-- ❌ 🟦: using @@IDENTITY (returns id from triggers/other scopes too)
SELECT @@IDENTITY;
-- ✅ SCOPE_IDENTITY() or OUTPUT INSERTED.id

-- ❌ Assuming no gaps ("we have 100 IDs so 100 rows")
-- ✅ gaps are expected from rollbacks/caching — count rows with COUNT(*), not MAX(id)

-- ❌ 🐘: trying to insert into a GENERATED ALWAYS identity column
INSERT INTO customers (customer_id, name) VALUES (5, 'X');   -- ERROR
-- ✅ use GENERATED BY DEFAULT, or OVERRIDING SYSTEM VALUE: INSERT ... OVERRIDING SYSTEM VALUE VALUES (5,'X')

-- ❌ Using SERIAL on new 🐘 tables (legacy; ownership/permission quirks)
-- ✅ prefer GENERATED ALWAYS/BY DEFAULT AS IDENTITY (the modern standard)
```

## 🌍 Real-World Use

Virtually every table's primary key is an identity/sequence-backed surrogate. Sequences shine for
shared numbering (multi-table document IDs), pre-allocating IDs in the app before insert, and
high-throughput inserts (cached sequence values reduce contention). 🐘's `GENERATED ... AS IDENTITY`
and 🟦's `IDENTITY` are the everyday defaults.

## 🎯 Practice (with full solutions)

### 1. Auto-incrementing PK — `Easy`
**Task:** Create a `tickets` table with an auto-incrementing `ticket_id` PK and a `subject`, in both
engines, using the modern syntax.
**Solution:**
```sql
-- 🟦 SQL Server
CREATE TABLE tickets (
    ticket_id INT IDENTITY(1,1) PRIMARY KEY,
    subject   NVARCHAR(200) NOT NULL
);
-- 🐘 PostgreSQL
CREATE TABLE tickets (
    ticket_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    subject   text NOT NULL
);
```
**Why it works:** both auto-assign the next ID on insert; 🐘's `GENERATED ALWAYS` is the
ANSI-standard modern replacement for `SERIAL`.

### 2. Shared document numbering — `Medium`
**Task:** Invoices and credit notes must draw from one shared, ever-increasing document number.
**Solution:**
```sql
CREATE SEQUENCE doc_number_seq START WITH 1 INCREMENT BY 1;

-- 🟦 SQL Server
INSERT INTO invoices    (doc_number, ...) VALUES (NEXT VALUE FOR doc_number_seq, ...);
INSERT INTO credit_notes(doc_number, ...) VALUES (NEXT VALUE FOR doc_number_seq, ...);
-- 🐘 PostgreSQL
INSERT INTO invoices    (doc_number, ...) VALUES (nextval('doc_number_seq'), ...);
INSERT INTO credit_notes(doc_number, ...) VALUES (nextval('doc_number_seq'), ...);
```
**Why it works:** a **sequence** is independent of any single table, so both tables pull from the
same monotonically-increasing source — something an identity column (tied to one table) can't do.
(Gaps still possible — fine for document *numbers*, not for a legal gapless requirement.)

## ✅ Key Takeaways

- Auto-increment keys: **🟦 `IDENTITY`** vs **🐘 `GENERATED ALWAYS/BY DEFAULT AS IDENTITY`** (prefer
  over legacy `SERIAL`).
- **Sequences** are standalone generators — share across tables, pre-allocate IDs.
- Get the new ID via **🟦 `SCOPE_IDENTITY()`/`OUTPUT`** (not `@@IDENTITY`) or **🐘 `RETURNING`**.
- **Gaps are normal** — surrogate keys aren't row counts and aren't guaranteed contiguous.
- For a true gapless ordered sequence, build a dedicated transactional counter (accepting
  contention) — don't rely on identity/sequences.
