# Temporary Tables & Table Variables

## 🧠 Intuition

Sometimes a query or procedure needs **scratch space** — a place to stash intermediate results,
break a monster query into steps, or hold a working set while you process it. **Temporary tables**
are real tables that live only for your session and vanish automatically. The engines differ in the
flavors they offer (🟦 has both temp tables *and* table variables; 🐘 has temp tables only).

> 💡 **Analogy — scratch paper.** When solving a hard problem you jot intermediate steps on scratch
> paper, then throw it away. A temp table is database scratch paper: create it, fill it, use it,
> and it's discarded when you're done — no cleanup, no clutter in the real schema.

## 📐 The options

| Feature | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Local temp table | `#temp` (session-scoped) | `CREATE TEMP TABLE` (session-scoped) |
| Global temp table | `##global` (all sessions) | *(no direct equivalent)* |
| Table variable | `DECLARE @t TABLE (...)` | *(no equivalent — use a temp table or CTE)* |
| CTE (single-statement scratch) | `WITH ... AS (...)` | `WITH ... AS (...)` |
| Auto-cleanup | On session/scope end | On session/transaction end |

## 💻 🟦 SQL Server — temp tables and table variables

```sql
-- Local temp table (#) — visible only to your session, auto-dropped when it ends
CREATE TABLE #recent_orders (order_id INT, total DECIMAL(10,2));
INSERT INTO #recent_orders
SELECT o.order_id, SUM(oi.quantity * oi.unit_price)
FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.order_date >= DATEADD(day, -30, GETDATE())
GROUP BY o.order_id;

SELECT * FROM #recent_orders WHERE total > 50;   -- use it
DROP TABLE #recent_orders;                        -- optional; auto-dropped anyway

-- Table variable (@) — lives in the batch, lighter, but with caveats
DECLARE @summary TABLE (category_id INT, cnt INT);
INSERT INTO @summary SELECT category_id, COUNT(*) FROM products GROUP BY category_id;
SELECT * FROM @summary;
```

### 🟦 Temp table vs table variable (a classic interview question)

| | `#temp` table | `@table` variable |
|--|---------------|-------------------|
| Statistics | **Yes** (optimizer estimates well) | **No** (assumes 1 row → bad plans on big sets) |
| Indexes | Can add many, after creation | Only PK/unique declared inline |
| Scope | Session (across batches) | Batch/proc only |
| Transactions | Participates / rolls back | **Not** rolled back (survives `ROLLBACK`) |
| Best for | Larger sets, complex processing | Tiny sets, simple passing of rows |
| In tempdb? | Yes | Yes (despite the name) |

> **Rule of thumb (🟦):** use a **`#temp` table** for anything more than a handful of rows or where
> the optimizer needs good estimates; use a **table variable** only for small, simple working sets.
> The "table variables are in memory, temp tables are on disk" claim is a **myth** — both live in
> tempdb.

## 💻 🐘 PostgreSQL — temp tables

```sql
-- Temp table, session-scoped (or transaction-scoped with ON COMMIT)
CREATE TEMP TABLE recent_orders (order_id INT, total NUMERIC(10,2));
INSERT INTO recent_orders
SELECT o.order_id, SUM(oi.quantity * oi.unit_price)
FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.order_date >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY o.order_id;

SELECT * FROM recent_orders WHERE total > 50;

-- Drop the temp table at COMMIT (transaction-scoped scratch)
CREATE TEMP TABLE tmp (...) ON COMMIT DROP;
```

🐘 has **no table variables** — use a temp table for multi-statement scratch, or a CTE for
single-statement scratch. 🐘 temp tables get statistics and can be indexed, like 🟦's `#temp`.

## 💻 The lightweight alternative — CTEs

For scratch that lives only within **one statement**, a [CTE](../02-Advanced-Querying/02.CTEs-and-Recursion.md)
is cleaner than a temp table — no DDL, no cleanup, just a named subquery:

```sql
-- Both engines: no temp table needed if it's all one query
WITH recent_orders AS (
    SELECT o.order_id, SUM(oi.quantity * oi.unit_price) AS total
    FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
    GROUP BY o.order_id
)
SELECT * FROM recent_orders WHERE total > 50;
```

**Decision guide:** single statement → **CTE**. Multi-statement / reused several times / needs
indexing or stats → **temp table**. 🟦 tiny simple set passed around → table variable (optional).

## ⚡ Under the Hood / Performance

- **Temp tables get statistics**, so the optimizer makes good plans — important when you process a
  large intermediate set in several steps. Table variables (🟦) don't, which can produce terrible
  plans on big data.
- Both flavors live in **tempdb (🟦)** / temp space (🐘) — heavy temp-table churn can pressure that
  shared resource; don't create thousands of tiny ones in a loop.
- A CTE is **not** a temp table — it's usually inlined by the optimizer and isn't separately
  materialized/cached unless the engine chooses to (or you force it with 🐘's `MATERIALIZED`).

## 🚫 Common mistakes

```sql
-- ❌ 🟦: using a table variable for a large set → optimizer assumes 1 row → nested-loop disaster
DECLARE @big TABLE (...);  -- then join a million rows against it
-- ✅ use a #temp table (has statistics) for large/complex sets

-- ❌ Assuming a 🐘 temp table persists across sessions
-- ✅ it's session-scoped; for cross-session sharing use a real table (or unlogged table)

-- ❌ Reaching for a temp table when a CTE would do (single statement)
-- ✅ CTE — less ceremony, no cleanup

-- ❌ Forgetting table variables survive ROLLBACK (🟦) — can leave unexpected data
DECLARE @log TABLE (...);  -- inside a transaction that rolls back → @log still has its rows
```

## 🌍 Real-World Use

- **Staging:** load raw import data into a temp table, clean/validate, then `MERGE`/`INSERT` into
  the real tables.
- **Multi-step procedures:** break a complex stored procedure into readable, debuggable steps each
  writing to a temp table.
- **Performance:** materialize an expensive intermediate result once into a `#temp`, index it, then
  join against it multiple times — often faster than recomputing it.
- **Capturing OUTPUT/RETURNING:** stash affected rows for further processing.

## 🎯 Practice (with full solutions)

### 1. Stage and filter — `Easy`
**Task:** Compute each order's total into scratch space, then return the orders over $50. Use the
most appropriate tool if it's a single query.
**Solution:**
```sql
-- Single statement → a CTE is the cleanest scratch (both engines)
WITH order_totals AS (
    SELECT o.order_id, SUM(oi.quantity * oi.unit_price) AS total
    FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
    GROUP BY o.order_id
)
SELECT * FROM order_totals WHERE total > 50 ORDER BY total DESC;
```
**Why it works:** there's no need for a temp table when the whole thing is one statement — a CTE is
lighter and self-cleaning.

### 2. Multi-step processing — `Medium`
**Task:** In a procedure: (1) stage last-30-days orders with totals, (2) index the staged set, (3)
join it twice for two different reports.
**Solution:**
```sql
-- 🟦 SQL Server
CREATE TABLE #recent (order_id INT PRIMARY KEY, total DECIMAL(10,2));
INSERT INTO #recent
SELECT o.order_id, SUM(oi.quantity * oi.unit_price)
FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.order_date >= DATEADD(day, -30, GETDATE())
GROUP BY o.order_id;
CREATE INDEX ix_recent_total ON #recent (total);
-- now join #recent in multiple subsequent queries...
SELECT ... FROM #recent r JOIN ...;   -- report 1
SELECT ... FROM #recent r JOIN ...;   -- report 2
```
**Why it works:** computing the expensive aggregate **once** into an indexed temp table and reusing
it across several queries beats recomputing it each time; the temp table has statistics so joins
plan well. (🐘: replace `#recent` with `CREATE TEMP TABLE recent` and the date math with `INTERVAL`.)

## ✅ Key Takeaways

- **Temp tables** are session-scoped scratch space, auto-cleaned: **🟦 `#temp`** / **🐘 `CREATE TEMP
  TABLE`** — both get **statistics** and can be **indexed**.
- **🟦 also has table variables** (`DECLARE @t TABLE`) — lighter, but **no statistics** (bad for large
  sets) and they **survive `ROLLBACK`**. 🐘 has **no** table variables.
- For **single-statement** scratch, prefer a **CTE** — no DDL, no cleanup.
- Both temp flavors live in **tempdb/temp space** ("in-memory table variable" is a myth).
- Use temp tables to **materialize-once-reuse-many** expensive intermediates.
