# Creating & Altering Schema (DDL)

## 🧠 Intuition

**DDL (Data Definition Language)** is the SQL that defines and changes the *structure* — databases,
schemas, tables, columns. `CREATE` builds, `ALTER` modifies, `DROP` removes. Where DML
(`INSERT`/`UPDATE`/`DELETE`) changes the *data*, DDL changes the *shape that holds the data*.

> 💡 **Analogy — building vs furnishing.** DDL is construction: putting up the rooms (tables) and
> shelves (columns). DML is moving furniture and boxes (rows) in and out. You build the structure
> once and change it occasionally; you move data constantly.

The core DDL is **standardized**, with predictable dialect differences in type names and a few
clauses.

## 💻 CREATE — databases, schemas, tables

```sql
-- Database
CREATE DATABASE shop;          -- both engines (then connect/USE it)

-- Schema (a namespace inside a database)
CREATE SCHEMA sales;           -- both engines

-- Table (the type-name differences from the Data Types chapter show up here)
-- 🟦 SQL Server
CREATE TABLE sales.invoices (
    invoice_id  INT IDENTITY PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(customer_id),
    total       DECIMAL(10,2) NOT NULL DEFAULT 0,
    created_at  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
-- 🐘 PostgreSQL
CREATE TABLE sales.invoices (
    invoice_id  INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(customer_id),
    total       NUMERIC(10,2) NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> Safe-create idioms: 🐘 supports `CREATE TABLE IF NOT EXISTS ...`; 🟦 traditionally guards with
> `IF OBJECT_ID('sales.invoices') IS NULL` (SQL Server 2016+ also has `CREATE ... IF NOT EXISTS`
> for some objects, and `DROP ... IF EXISTS`).

## 💻 ALTER — evolve a table

```sql
-- Add a column (nullable add is cheap and safe; both engines)
ALTER TABLE products ADD discontinued BIT NULL;          -- 🟦
ALTER TABLE products ADD COLUMN discontinued BOOLEAN;    -- 🐘 (note: COLUMN keyword)

-- Add a column with a default
ALTER TABLE products ADD created_at DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME();   -- 🟦
ALTER TABLE products ADD COLUMN created_at TIMESTAMPTZ NOT NULL DEFAULT now();     -- 🐘

-- Change a column's type
ALTER TABLE products ALTER COLUMN name NVARCHAR(200);            -- 🟦
ALTER TABLE products ALTER COLUMN name TYPE VARCHAR(200);        -- 🐘 (TYPE keyword)

-- Add / drop a constraint
ALTER TABLE products ADD CONSTRAINT chk_price CHECK (unit_price >= 0);   -- both
ALTER TABLE products DROP CONSTRAINT chk_price;                          -- both

-- Rename (engines differ)
EXEC sp_rename 'products.old_name', 'new_name', 'COLUMN';        -- 🟦 (stored proc)
ALTER TABLE products RENAME COLUMN old_name TO new_name;          -- 🐘

-- Drop a column
ALTER TABLE products DROP COLUMN discontinued;                    -- both (🟦 omit COLUMN allowed too)
```

| Operation | 🟦 SQL Server | 🐘 PostgreSQL |
|-----------|--------------|---------------|
| Add column | `ADD col TYPE` | `ADD COLUMN col TYPE` |
| Change type | `ALTER COLUMN col TYPE` | `ALTER COLUMN col TYPE newtype` |
| Rename column | `EXEC sp_rename ...` | `RENAME COLUMN ... TO ...` |
| Rename table | `EXEC sp_rename ...` | `ALTER TABLE ... RENAME TO ...` |
| Drop with guard | `DROP TABLE IF EXISTS` (2016+) | `DROP TABLE IF EXISTS` |

## 💻 DROP — remove objects

```sql
DROP TABLE IF EXISTS staging;            -- both engines (guarded — no error if absent)
DROP VIEW  IF EXISTS active_customers;   -- both
DROP SCHEMA sales;                       -- must be empty, or 🐘: DROP SCHEMA sales CASCADE;
DROP DATABASE shop;                      -- careful — irreversible
```

> ⚠️ `DROP` is **immediate and irreversible** (no `WHERE`, no undo without a backup). Double-check
> the object name, and in production, drop behind a migration with a tested rollback.

## ⚖️ DDL and transactions — a crucial difference

| | 🟦 SQL Server | 🐘 PostgreSQL |
|--|--------------|---------------|
| DDL inside a transaction | ✅ mostly transactional (can `ROLLBACK` a `CREATE`/`ALTER`) | ✅ **fully transactional** |
| Effect | Can wrap schema changes in `BEGIN/COMMIT` | Can wrap *and roll back* an entire migration atomically |

> **🐘 PostgreSQL has fully transactional DDL** — you can `BEGIN`, run several `CREATE`/`ALTER`/
> `DROP`, and `ROLLBACK` to undo *all* of them if something fails. This makes migrations safer. 🟦
> SQL Server supports transactional DDL for most statements too, though a few operations
> auto-commit. This is a meaningful advantage for 🐘 migration tooling.

## ⚡ Under the Hood / Performance

- **Adding a nullable column** is usually instant (metadata-only) on both modern engines. Adding a
  `NOT NULL` column **with a default** can rewrite the table on older versions (modern 🟦/🐘 optimize
  the constant-default case to metadata-only).
- **Changing a column type** that requires data conversion **rewrites the whole table** and takes a
  lock — expensive on big tables. Plan it like a migration (see
  [Versioning & Schema Evolution](../11-Operations/README.md)-style expand/contract patterns).
- **`DROP`** is fast (deallocates), but irreversible.

## 🚫 Common mistakes

```sql
-- ❌ 🐘: forgetting the COLUMN keyword
ALTER TABLE products ADD discontinued BOOLEAN;     -- ERROR on 🐘
-- ✅ ALTER TABLE products ADD COLUMN discontinued BOOLEAN;

-- ❌ Dropping without IF EXISTS in a script that may re-run → error if already gone
DROP TABLE staging;
-- ✅ DROP TABLE IF EXISTS staging;

-- ❌ Changing a column type on a huge table during peak hours → long lock, outage
-- ✅ schedule it, use an online/expand-contract approach, test on a copy first

-- ❌ Adding NOT NULL with no default to a populated table → fails (existing rows have no value)
ALTER TABLE products ADD sku VARCHAR(20) NOT NULL;   -- error if rows exist
-- ✅ add nullable → backfill → then SET NOT NULL (the expand-contract pattern)
```

## 🌍 Real-World Use

Every schema migration is DDL: new feature → new table/columns; refactor → rename/retype; cleanup →
drop. Migration tools (Flyway, Liquibase, EF Core migrations, Alembic) generate and version this
DDL. 🐘's transactional DDL lets a failed migration roll back cleanly — a real operational win.

## 🎯 Practice (with full solutions)

### 1. Create a table with constraints — `Easy`
**Task:** Create a `suppliers` table: `supplier_id` PK (auto), `name` required, `email` unique,
`rating` between 1 and 5. Both engines.
**Solution:**
```sql
-- 🟦 SQL Server
CREATE TABLE suppliers (
    supplier_id INT IDENTITY PRIMARY KEY,
    name        NVARCHAR(100) NOT NULL,
    email       NVARCHAR(255) NOT NULL UNIQUE,
    rating      INT CHECK (rating BETWEEN 1 AND 5)
);
-- 🐘 PostgreSQL
CREATE TABLE suppliers (
    supplier_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        text NOT NULL,
    email       text NOT NULL UNIQUE,
    rating      INT CHECK (rating BETWEEN 1 AND 5)
);
```
**Why it works:** auto-identity PK, required/unique/check constraints — same structure, type names
swapped per engine.

### 2. Safely add a required column — `Medium`
**Task:** Add a required `sku` column to the already-populated `products` table.
**Solution (expand-contract):**
```sql
-- Step 1: add nullable
ALTER TABLE products ADD sku VARCHAR(20) NULL;            -- 🟦 (🐘: ADD COLUMN sku VARCHAR(20))
-- Step 2: backfill existing rows
UPDATE products SET sku = CONCAT('SKU-', product_id) WHERE sku IS NULL;
-- Step 3: enforce NOT NULL now that data is clean
ALTER TABLE products ALTER COLUMN sku VARCHAR(20) NOT NULL;   -- 🟦
-- 🐘: ALTER TABLE products ALTER COLUMN sku SET NOT NULL;
```
**Why it works:** you can't add a `NOT NULL` column with no value to existing rows — so add it
nullable, fill it, then enforce the constraint. This three-step "expand-contract" is the safe way to
make any column required.

## ✅ Key Takeaways

- **DDL** (`CREATE`/`ALTER`/`DROP`) defines structure; DML changes data.
- Dialect differences: 🐘 needs **`ADD COLUMN`** / **`TYPE`** keywords; 🟦 uses **`sp_rename`** for
  renames; both support `IF EXISTS`/`IF NOT EXISTS` guards.
- **🐘 has fully transactional DDL** — wrap and roll back whole migrations; 🟦 is mostly transactional.
- **Adding a nullable column is cheap**; **changing a type rewrites the table** (lock — plan it).
- Make columns required with the **expand-contract** pattern (nullable → backfill → `NOT NULL`).
