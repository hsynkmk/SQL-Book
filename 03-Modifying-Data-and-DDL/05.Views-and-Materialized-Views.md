# Views & Materialized Views

## 🧠 Intuition

A **view** is a saved query that behaves like a virtual table — you `SELECT` from it as if it were
a table, but it runs its underlying query each time. It's a way to name a complex query once, hide
complexity, and create a stable interface. A **materialized view** goes further: it *stores* the
query's results physically (like a cached table) and you refresh it on demand — trading freshness
for speed.

> 💡 **Analogy — a saved search vs a printed report.** A view is a *saved search*: every time you
> open it, it re-runs and shows current data. A materialized view is a *printed report*: fast to
> read, but it shows the data as of the last time you printed it — you reprint (refresh) when you
> want it current.

## 🎯 The Problem

```sql
-- ❌ Every report re-types the same gnarly join
SELECT c.name, COUNT(o.order_id) AS order_count, SUM(oi.quantity * oi.unit_price) AS total_spent
FROM customers c
JOIN orders o      ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id  = o.order_id
GROUP BY c.name;
-- ...pasted into 12 different queries, each slightly different, all needing maintenance.
```

Name it once as a view, and every report just does `SELECT * FROM customer_summary`.

## 💻 Views (identical on both engines)

```sql
-- Create a view: a named, reusable query
CREATE VIEW customer_summary AS
SELECT c.customer_id, c.name,
       COUNT(o.order_id) AS order_count,
       COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS total_spent
FROM customers c
LEFT JOIN orders o      ON o.customer_id = c.customer_id
LEFT JOIN order_items oi ON oi.order_id  = o.order_id
GROUP BY c.customer_id, c.name;

-- Use it like a table
SELECT name, total_spent FROM customer_summary WHERE total_spent > 50 ORDER BY total_spent DESC;

-- Replace its definition
CREATE OR REPLACE VIEW customer_summary AS SELECT ...;   -- 🐘 (and 🟦 2016+ supports CREATE OR ALTER VIEW)
```

What views give you:
- **Abstraction:** hide a complex join behind a simple name.
- **Security:** grant access to a view exposing only some columns/rows, without granting access to
  the base tables ([Permissions](../10-Security/03.Permissions.md)). A view can also embed a
  `WHERE` that scopes rows per role.
- **Stability:** apps query the view; you can refactor the underlying tables without breaking them.

> A plain view stores **no data** — it's just the query text. Reading it costs the same as running
> the query.

## 💻 Updatable views

Simple views (one table, no aggregation/`DISTINCT`/`GROUP BY`) are often **updatable** — you can
`INSERT`/`UPDATE`/`DELETE` through them and it affects the base table. Complex views are read-only
unless you add an `INSTEAD OF` trigger (🟦) or a rule/trigger (🐘).

```sql
CREATE VIEW active_products AS SELECT product_id, name, unit_price FROM products WHERE discontinued = 0;
UPDATE active_products SET unit_price = 9.99 WHERE product_id = 5;   -- updates the base table
```

🟦 SQL Server's `WITH CHECK OPTION` prevents updates that would push a row *out* of the view's
filter — both engines support it.

## 💻 Materialized views — the dialect split

This is where 🟦 and 🐘 differ significantly:

### 🐘 PostgreSQL — first-class materialized views

```sql
CREATE MATERIALIZED VIEW customer_summary_mv AS
SELECT c.customer_id, c.name, COUNT(o.order_id) AS order_count
FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name;

-- Read is fast (it's stored). Data is stale until you refresh:
REFRESH MATERIALIZED VIEW customer_summary_mv;
-- Refresh without locking reads (needs a unique index on the MV):
REFRESH MATERIALIZED VIEW CONCURRENTLY customer_summary_mv;

-- You can index a materialized view like a table
CREATE INDEX ix_mv_name ON customer_summary_mv (name);
```

🐘 materialized views are **manually refreshed** (or via a scheduled job / [pg_cron](../11-Operations/04.Automation.md))
— they don't auto-update when base data changes.

### 🟦 SQL Server — indexed views (auto-maintained)

SQL Server has no `MATERIALIZED VIEW` keyword. Instead, an **indexed view** = a view with a unique
clustered index, which physically materializes it **and keeps it in sync automatically** as base
data changes:

```sql
CREATE VIEW dbo.category_totals WITH SCHEMABINDING AS
SELECT category_id, COUNT_BIG(*) AS cnt, SUM(units_in_stock) AS total_stock
FROM dbo.products
GROUP BY category_id;
GO
CREATE UNIQUE CLUSTERED INDEX ix_category_totals ON dbo.category_totals (category_id);
```

| | 🐘 Materialized view | 🟦 Indexed view |
|--|---------------------|-----------------|
| Storage | Physical, stored | Physical (via the clustered index) |
| Freshness | **Manual** `REFRESH` (or scheduled) | **Automatic** (maintained on every base write) |
| Write cost | None until refresh | Every base insert/update updates the indexed view too |
| Restrictions | Few | Many (`SCHEMABINDING`, `COUNT_BIG`, no `LEFT JOIN`/many aggregates, deterministic only) |
| Best for | Expensive reports refreshed periodically | Aggregations that must always be current |

## ⚖️ View vs Materialized View

- **Plain view:** always current, zero storage, but pays the full query cost on every read. Use for
  abstraction/security and queries that aren't expensive.
- **Materialized/indexed view:** fast reads of expensive aggregations. 🐘's is **stale-until-refresh**
  (great when periodic freshness is fine — dashboards, nightly reports). 🟦's indexed view is
  **always fresh but taxes writes** (great for must-be-current aggregates, but slows the OLTP path).

## 🚫 Common mistakes

```sql
-- ❌ Expecting a 🐘 materialized view to auto-update
SELECT * FROM customer_summary_mv;   -- shows data from the last REFRESH, not live!
-- ✅ REFRESH it on a schedule, or use a plain view if you need live data

-- ❌ Stacking views on views on views → the optimizer expands them all; can produce monstrous plans
-- ✅ keep view nesting shallow; flatten hot paths

-- ❌ 🐘: REFRESH MATERIALIZED VIEW CONCURRENTLY without a unique index → error
-- ✅ create a UNIQUE index on the MV first

-- ❌ 🟦: indexed view without SCHEMABINDING / using non-deterministic functions → creation fails
-- ✅ follow the strict indexed-view rules (SCHEMABINDING, COUNT_BIG, two-part names, deterministic)
```

## 🌍 Real-World Use

- **Views:** a `v_active_users` exposing only non-deleted rows; a reporting view hiding a 6-table
  join; a security view exposing customers without their `credit_card` column.
- **🐘 materialized views:** pre-computed dashboard metrics refreshed every 5 minutes via pg_cron;
  expensive geospatial/analytics rollups.
- **🟦 indexed views:** always-current per-category totals on a busy e-commerce catalog (accepting
  the write overhead for instant reads).

## 🎯 Practice (with full solutions)

### 1. Abstract a complex query — `Easy`
**Task:** Create a view `order_totals` giving each order's id, date, and total value (from its
items). Then query orders over $50.
**Solution:**
```sql
CREATE VIEW order_totals AS
SELECT o.order_id, o.order_date,
       SUM(oi.quantity * oi.unit_price) AS total
FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
GROUP BY o.order_id, o.order_date;

SELECT * FROM order_totals WHERE total > 50 ORDER BY total DESC;
```
**Why it works:** the view names the aggregation once; queries read from it like a table and stay
current (it re-runs each time).

### 2. Speed up an expensive dashboard — `Medium`
**Task:** A dashboard reads per-customer order counts thousands of times an hour; base data changes
nightly. Make reads fast.
**Solution:**
```sql
-- 🐘 PostgreSQL: materialized view refreshed nightly
CREATE MATERIALIZED VIEW customer_order_counts AS
SELECT customer_id, COUNT(*) AS order_count FROM orders GROUP BY customer_id;
CREATE UNIQUE INDEX ux_coc ON customer_order_counts (customer_id);
-- nightly job (e.g. pg_cron):
REFRESH MATERIALIZED VIEW CONCURRENTLY customer_order_counts;
```
```sql
-- 🟦 SQL Server: indexed view (always fresh, auto-maintained)
CREATE VIEW dbo.customer_order_counts WITH SCHEMABINDING AS
SELECT customer_id, COUNT_BIG(*) AS order_count FROM dbo.orders GROUP BY customer_id;
GO
CREATE UNIQUE CLUSTERED INDEX ux_coc ON dbo.customer_order_counts (customer_id);
```
**Why it works:** because the data only changes nightly, 🐘's stale-until-refresh materialized view
is ideal (fast reads, trivial refresh cost). 🟦's indexed view stays auto-current — also fine here,
at the cost of a little write overhead.

## ✅ Key Takeaways

- A **view** is a named, reusable query (no stored data) — for abstraction, security, and stability.
- Simple views are **updatable**; complex ones are read-only without `INSTEAD OF` triggers.
- **🐘 materialized views**: stored, **manually refreshed** (stale until `REFRESH`), indexable.
- **🟦 indexed views**: stored via a unique clustered index, **auto-maintained** (always fresh) but
  with strict rules and write overhead.
- Choose plain views for live/cheap queries; materialized/indexed for expensive aggregations.
