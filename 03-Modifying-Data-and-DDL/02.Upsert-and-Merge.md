# Upsert & MERGE

> One of the **biggest dialect divergences** in everyday SQL: 🐘 has the clean `INSERT ... ON
> CONFLICT`; 🟦 has the powerful-but-thorny `MERGE`.

## 🧠 Intuition

**Upsert** = "**up**date if it exists, in**sert** if it doesn't." You have a row of data and you
want it in the table regardless of whether it's already there — without first checking, then
branching in application code (which has a race condition). Both engines give you an atomic way to
do it; the syntax is completely different.

> 💡 **Analogy — saving a contact.** "Save this phone number for Alice." If Alice is already in your
> contacts, update her number; if not, add her. You don't want to manually check first — you want
> one "save" action that does the right thing atomically.

## 🎯 The Problem

```sql
-- ❌ The racy application pattern: check-then-act
-- if (SELECT COUNT(*) FROM stock WHERE product_id = 5) = 0
--     INSERT ...
-- else
--     UPDATE ...
-- Between the SELECT and the INSERT, another connection can insert the same row → duplicate key error / lost update.
```

You need the database to do "insert-or-update" **atomically**, in one statement.

## 💻 🐘 PostgreSQL — `INSERT ... ON CONFLICT` (the clean way)

```sql
-- Upsert a stock level; if product_id already exists, update the quantity instead
INSERT INTO stock (product_id, quantity)
VALUES (5, 100)
ON CONFLICT (product_id)                 -- the unique/PK column that defines "already exists"
DO UPDATE SET quantity = EXCLUDED.quantity;   -- EXCLUDED = the row you tried to insert
```

- **`ON CONFLICT (col)`** names the unique constraint/column that detects the duplicate.
- **`EXCLUDED`** refers to the values from the attempted insert (so you can use them in the update).
- **`DO NOTHING`** is the other option — insert if new, silently skip if it exists:

```sql
INSERT INTO categories (name) VALUES ('Beverages') ON CONFLICT (name) DO NOTHING;
```

You can even reference the existing row to merge values:
```sql
INSERT INTO stock (product_id, quantity) VALUES (5, 100)
ON CONFLICT (product_id) DO UPDATE SET quantity = stock.quantity + EXCLUDED.quantity;  -- add to existing
```

This is concise, race-free, and the idiomatic 🐘 upsert.

## 💻 🟦 SQL Server — `MERGE`

SQL Server's upsert is the ANSI `MERGE` statement (also in 🐘 15+, but 🐘 devs prefer `ON CONFLICT`):

```sql
MERGE INTO stock AS target
USING (VALUES (5, 100)) AS source (product_id, quantity)
    ON target.product_id = source.product_id
WHEN MATCHED THEN
    UPDATE SET target.quantity = source.quantity
WHEN NOT MATCHED THEN
    INSERT (product_id, quantity) VALUES (source.product_id, source.quantity);
```

`MERGE` is more general than upsert — it can `INSERT`, `UPDATE`, **and** `DELETE` in one statement
against a source set (great for syncing a staging table into a target):

```sql
MERGE INTO products AS t
USING staging_products AS s ON t.product_id = s.product_id
WHEN MATCHED THEN UPDATE SET t.unit_price = s.unit_price, t.name = s.name
WHEN NOT MATCHED BY TARGET THEN INSERT (product_id, name, unit_price) VALUES (s.product_id, s.name, s.unit_price)
WHEN NOT MATCHED BY SOURCE THEN DELETE;   -- rows in target not in source → remove
```

> ⚠️ **`MERGE` has a notorious history of bugs and concurrency pitfalls in SQL Server** (race
> conditions, deadlocks, and several CVE-like correctness issues over the years). Microsoft's own
> guidance is to be cautious. For a **simple upsert**, many SQL Server experts prefer an explicit
> `UPDATE` then `INSERT` (guarded by a transaction + the unique constraint) over `MERGE`. Use
> `MERGE` for genuine multi-action set syncs, with proper locking hints, not for trivial upserts.

## 💻 🟦 The "safe simple upsert" pattern (no MERGE)

```sql
-- SQL Server: explicit upsert, relying on the unique constraint to stay correct under concurrency
BEGIN TRANSACTION;
    UPDATE stock WITH (UPDLOCK, SERIALIZABLE) SET quantity = @qty WHERE product_id = @id;
    IF @@ROWCOUNT = 0
        INSERT INTO stock (product_id, quantity) VALUES (@id, @qty);
COMMIT;
```

The `UPDLOCK, SERIALIZABLE` hints + the unique constraint close the race window. Verbose, but
battle-tested.

## ⚖️ Comparison

| | 🐘 `INSERT ... ON CONFLICT` | 🟦 `MERGE` | 🟦 UPDATE-then-INSERT |
|--|----------------------------|-----------|----------------------|
| Best for | Simple, race-free upsert | Multi-action set sync (insert/update/delete) | Simple upsert without MERGE's risks |
| Concurrency safety | Excellent (built-in) | Needs care (history of bugs) | Good with locking hints + unique constraint |
| Readability | Very clean | Verbose | Moderate |
| Detects "exists" by | A unique/PK constraint | The `ON` join condition | The unique constraint |

## 🚫 Common mistakes

```sql
-- ❌ Check-then-insert in app code → race condition → duplicate key crash
-- ✅ ON CONFLICT (🐘) or a guarded MERGE/UPDATE-INSERT (🟦)

-- ❌ ON CONFLICT without a matching unique constraint → ERROR (it needs a constraint to "conflict" on)
INSERT INTO stock (...) VALUES (...) ON CONFLICT (product_id) ...;   -- product_id must be UNIQUE/PK
-- ✅ ensure the conflict target has a unique index/PK

-- ❌ Using MERGE for a trivial upsert in SQL Server without understanding its concurrency caveats
-- ✅ for simple upserts, prefer ON CONFLICT (🐘) or the guarded UPDATE/INSERT pattern (🟦)

-- ❌ Forgetting EXCLUDED in 🐘 (referencing the table's OLD value when you meant the new one)
ON CONFLICT (id) DO UPDATE SET qty = qty   -- sets it to the existing value (no-op)
-- ✅ ON CONFLICT (id) DO UPDATE SET qty = EXCLUDED.qty
```

## 🌍 Real-World Use

- **Idempotent imports:** re-running an ETL load shouldn't create duplicates — upsert each row.
- **Counters/inventory:** "add 5 to stock, creating the row if absent."
- **Sync from external source:** a nightly `MERGE` of a partner feed into your products table.
- **"Save settings":** insert-or-update a user's preference row.

## 🎯 Practice (with full solutions)

### 1. Idempotent stock upsert — `Medium`
**Task:** Set product 5's stock to 100, creating the row if it doesn't exist, in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL
INSERT INTO stock (product_id, quantity) VALUES (5, 100)
ON CONFLICT (product_id) DO UPDATE SET quantity = EXCLUDED.quantity;

-- 🟦 SQL Server (guarded simple upsert — preferred over MERGE for this)
BEGIN TRANSACTION;
    UPDATE stock WITH (UPDLOCK, SERIALIZABLE) SET quantity = 100 WHERE product_id = 5;
    IF @@ROWCOUNT = 0 INSERT INTO stock (product_id, quantity) VALUES (5, 100);
COMMIT;
```
**Why it works:** 🐘 does it atomically in one statement via `ON CONFLICT`; 🟦's transaction +
locking hints + unique constraint make the update-or-insert race-safe.

### 2. Insert-if-new only — `Easy`
**Task:** Add category `'Beverages'` only if it isn't already present (do nothing if it is).
**Solution:**
```sql
-- 🐘 PostgreSQL
INSERT INTO categories (name) VALUES ('Beverages') ON CONFLICT (name) DO NOTHING;
-- 🟦 SQL Server
IF NOT EXISTS (SELECT 1 FROM categories WHERE name = 'Beverages')
    INSERT INTO categories (name) VALUES ('Beverages');
```
**Why it works:** `DO NOTHING` (🐘) silently skips the duplicate; 🟦's `IF NOT EXISTS` guard does the
same (relying on the `UNIQUE(name)` constraint as the backstop against races).

## ✅ Key Takeaways

- **Upsert** = insert-or-update atomically — never check-then-act in app code (race condition).
- **🐘: `INSERT ... ON CONFLICT (col) DO UPDATE/NOTHING`** with **`EXCLUDED`** — clean and idiomatic;
  requires a unique constraint on the conflict target.
- **🟦: `MERGE`** is powerful for multi-action set syncs but has **real concurrency/bug caveats** —
  for simple upserts, prefer a guarded **UPDATE-then-INSERT**.
- The conflict/match is detected by a **unique constraint/PK** (🐘) or the `ON` condition (🟦).
- Upsert makes imports **idempotent** — re-running won't duplicate.
