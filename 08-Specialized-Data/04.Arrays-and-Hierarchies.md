# Arrays & Hierarchies

> Two areas where the engines diverge sharply: 🐘 has **native arrays** and the **`ltree`** hierarchy
> type; 🟦 has the **`HierarchyId`** type (and no native arrays).

## 🧠 Intuition

Two specialized shapes:
- **Arrays** — a column holding a *list* of values (`text[]`, `int[]`). PostgreSQL supports these
  natively; SQL Server does not (you use JSON or a related table).
- **Hierarchies** — tree-structured data (org charts, category trees, file paths). Beyond
  [recursive CTEs](../02-Advanced-Querying/02.CTEs-and-Recursion.md), each engine has a dedicated type
  that encodes the *path* to a node for fast ancestor/descendant queries: 🟦's **`HierarchyId`** and
  🐘's **`ltree`**.

> 💡 **Analogy — a labeled position in a family tree.** Instead of repeatedly asking "who's your
> parent? and theirs?" (recursive CTE), each person carries a label like `/1/3/2/` encoding their
> exact position. Comparing labels instantly answers "is X an ancestor of Y?" That label is what
> `HierarchyId`/`ltree` store.

## 💻 🐘 PostgreSQL — native arrays

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name       text,
    tags       text[]            -- a native array of text
);

INSERT INTO products VALUES (1, 'Coffee', ARRAY['hot','beverage','sale']);
INSERT INTO products VALUES (2, 'Tea',    '{hot,beverage}');           -- array literal syntax

-- Query arrays
SELECT * FROM products WHERE 'sale' = ANY(tags);            -- contains 'sale'
SELECT * FROM products WHERE tags @> ARRAY['hot','sale'];   -- contains all of these (@>)
SELECT * FROM products WHERE tags && ARRAY['sale','clearance'];  -- overlaps (any in common)
SELECT array_length(tags, 1) AS num_tags FROM products;

-- Expand an array into rows
SELECT product_id, unnest(tags) AS tag FROM products;

-- Index for containment queries (GIN)
CREATE INDEX ix_products_tags ON products USING GIN (tags);
```

Native arrays are convenient for genuinely list-like attributes (tags, multi-select options). But
**don't over-use them** — if you need to join, constrain, or heavily query the elements
relationally, a proper related table is better (and portable). Arrays shine for small, read-mostly
lists.

> **🟦 SQL Server has no native array type.** Use a **JSON array** ([JSON](01.JSON.md)), a
> comma-separated string + `STRING_SPLIT`, or — usually best — a **related table** (the normalized
> approach).

## 💻 🟦 SQL Server — `HierarchyId`

`HierarchyId` is a built-in type encoding a node's position in a tree as a compact path:

```sql
CREATE TABLE org (
    employee_id INT PRIMARY KEY,
    name        NVARCHAR(100),
    node        HIERARCHYID
);

-- Insert a root and children
INSERT INTO org VALUES (1, 'CEO', hierarchyid::GetRoot());                 -- '/'
DECLARE @ceo HIERARCHYID = (SELECT node FROM org WHERE employee_id = 1);
INSERT INTO org VALUES (2, 'VP',   @ceo.GetDescendant(NULL, NULL));        -- '/1/'

-- Query the tree
SELECT name, node.ToString() AS path, node.GetLevel() AS depth FROM org;

-- All descendants of the CEO (ancestor query)
SELECT name FROM org WHERE node.IsDescendantOf(@ceo) = 1;

-- Index it (depth-first or breadth-first)
CREATE INDEX ix_org_node ON org (node);
```

Methods: `GetRoot`, `GetDescendant`, `GetAncestor`, `IsDescendantOf`, `GetLevel`, `ToString`.

## 💻 🐘 PostgreSQL — `ltree`

PostgreSQL's **`ltree`** extension stores hierarchical paths as dot-separated labels with powerful
matching:

```sql
CREATE EXTENSION IF NOT EXISTS ltree;

CREATE TABLE categories (
    category_id INT PRIMARY KEY,
    name        text,
    path        ltree            -- e.g. 'electronics.computers.laptops'
);

INSERT INTO categories VALUES
    (1, 'Electronics', 'electronics'),
    (2, 'Computers',   'electronics.computers'),
    (3, 'Laptops',     'electronics.computers.laptops');

-- Descendants of 'electronics.computers' (<@ = is descendant of)
SELECT name FROM categories WHERE path <@ 'electronics.computers';

-- Ancestors of laptops (@> = is ancestor of)
SELECT name FROM categories WHERE path @> 'electronics.computers.laptops';

-- Pattern matching with lquery
SELECT name FROM categories WHERE path ~ 'electronics.*.laptops';

-- Index for fast tree queries (GiST)
CREATE INDEX ix_categories_path ON categories USING GiST (path);
```

## 🟦 SQL Server vs 🐘 PostgreSQL

| Feature | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Native arrays | ❌ (use JSON / related table) | ✅ `text[]`, `int[]`, ... with `@>`, `&&`, `ANY`, `unnest`, GIN |
| Hierarchy type | **`HierarchyId`** (built-in) | **`ltree`** (extension) |
| Hierarchy queries | `IsDescendantOf`, `GetAncestor`, `GetLevel` | `<@`, `@>`, `~` (lquery), GiST index |
| Recursive alternative | recursive CTE (both engines) | recursive CTE (both engines) |

> Both hierarchy types are alternatives to **recursive CTEs**: the CTE computes the tree at query
> time (flexible, no extra column); `HierarchyId`/`ltree` **materialize the path** for fast,
> index-backed ancestor/descendant queries (better for read-heavy, deep, frequently-queried trees).

## ⚖️ Choosing an approach for hierarchies

| Approach | Best for |
|----------|----------|
| **Adjacency list** (`parent_id` column) + **recursive CTE** | Simple, portable, write-friendly trees |
| **Materialized path** (`HierarchyId` / `ltree`) | Read-heavy, deep trees, frequent ancestor/descendant queries; harder to re-parent |
| **Closure table** (a row per ancestor-descendant pair) | Complex queries, portable, fast — at storage cost |

Start with `parent_id` + recursive CTE (portable, simple). Move to `HierarchyId`/`ltree`/closure
table when tree queries are hot and the depth/volume justify it.

## 🚫 Common mistakes

```sql
-- ❌ Overusing arrays for data you'll join/constrain on → use a related table instead
tags text[]   -- fine for display tags; bad if you need FK integrity / heavy querying
-- ✅ a junction table (product_tags) for relational tag data

-- ❌ Expecting native arrays on SQL Server (there aren't any)
-- ✅ JSON array, STRING_SPLIT, or a related table on 🟦

-- ❌ Querying a deep hierarchy with recursive CTEs on every request when it's read-heavy
-- ✅ materialize the path (HierarchyId/ltree) and index it

-- ❌ Re-parenting nodes with materialized paths → must update all descendants' paths (expensive)
-- ✅ adjacency list is easier to re-parent; choose based on read vs write patterns
```

## 🌍 Real-World Use

- **Arrays (🐘):** tags, multi-select preferences, small embedded lists — avoiding a junction table for
  simple cases.
- **Hierarchies:** org charts, product category trees, threaded comments, file/folder structures,
  bill-of-materials, geographic regions. `HierarchyId`/`ltree` for read-heavy trees; recursive CTEs
  for everything else.

## 🎯 Practice (with full solutions)

### 1. Tag containment with arrays — `Easy` (🐘)
**Task:** Find products tagged both `hot` and `sale`, using a native array + index.
**Solution:**
```sql
-- 🐘 PostgreSQL
CREATE INDEX ix_products_tags ON products USING GIN (tags);
SELECT name FROM products WHERE tags @> ARRAY['hot','sale'];   -- contains BOTH
```
**Why it works:** `@>` tests array containment ("has all of these"), and the GIN index accelerates
it. (On 🟦 you'd model tags as a related table or JSON array.)

### 2. Descendants in a category tree — `Medium`
**Task:** List all categories under `electronics.computers`, in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL: ltree
SELECT name FROM categories WHERE path <@ 'electronics.computers';

-- 🟦 SQL Server: HierarchyId
DECLARE @root HIERARCHYID = (SELECT node FROM categories WHERE name = 'Computers');
SELECT name FROM categories WHERE node.IsDescendantOf(@root) = 1;

-- Portable alternative (both): recursive CTE on a parent_id column
WITH RECURSIVE sub AS (
    SELECT category_id, name FROM categories WHERE name = 'Computers'
    UNION ALL
    SELECT c.category_id, c.name FROM categories c JOIN sub ON c.parent_id = sub.category_id
)
SELECT name FROM sub;
```
**Why it works:** the materialized-path types (`ltree` `<@` / `HierarchyId.IsDescendantOf`) answer
"all descendants" with an indexed comparison; the recursive CTE is the portable, no-extra-column
alternative.

## ✅ Key Takeaways

- **🐘 has native arrays** (`text[]`, `@>`, `&&`, `ANY`, `unnest`, GIN-indexable) — great for small
  list-like attributes; **🟦 has none** (use JSON / a related table).
- Don't over-use arrays for relational data you join/constrain on — a **related table** is often
  better (and portable).
- **Hierarchies:** **🟦 `HierarchyId`** and **🐘 `ltree`** materialize the path for fast, indexed
  ancestor/descendant queries — alternatives to **recursive CTEs**.
- Choose by read/write pattern: **adjacency list + recursive CTE** (simple, re-parent-friendly) vs
  **materialized path** (read-heavy, deep) vs **closure table**.
