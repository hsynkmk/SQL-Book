# Temporal & Vector Data

> Two "time and AI" features. **Temporal tables** auto-track history (🟦 first-class; 🐘 via
> extensions/patterns). **Vector data** powers AI semantic search (🟦 in SQL Server 2025 / Azure SQL;
> 🐘 via the popular **pgvector** extension).

## 🧠 Intuition — Part 1: Temporal tables

A **system-versioned temporal table** automatically keeps a full history of every change. Each
update/delete moves the previous row into a hidden history table with the time window it was valid.
You can then query the table **as of any past moment** — "what did this order look like last
Tuesday?" — without writing any audit code.

> 💡 **Analogy — a self-updating photo album.** Every time the data changes, the database snaps a
> photo first and files it by timestamp. You can flip back to any moment in the past. No manual audit
> trail to build or forget.

## 💻 🟦 SQL Server — built-in temporal tables

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name       NVARCHAR(100),
    unit_price DECIMAL(10,2),
    valid_from DATETIME2 GENERATED ALWAYS AS ROW START HIDDEN,
    valid_to   DATETIME2 GENERATED ALWAYS AS ROW END   HIDDEN,
    PERIOD FOR SYSTEM_TIME (valid_from, valid_to)
)
WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.products_history));

-- Every UPDATE/DELETE now auto-archives the old row. Query history:
SELECT * FROM products FOR SYSTEM_TIME AS OF '2025-05-01';                    -- state at a moment
SELECT * FROM products FOR SYSTEM_TIME BETWEEN '2025-05-01' AND '2025-05-31'; -- changes in a range
SELECT * FROM products FOR SYSTEM_TIME ALL WHERE product_id = 5;              -- full history of a row
```

## 💻 🐘 PostgreSQL — temporal via patterns/extensions

PostgreSQL has **no built-in system-versioning** (as of PG 17). You implement it with:
- A **history table + trigger** that copies the old row on update/delete (the classic DIY approach).
- Extensions like **`temporal_tables`** or **`periods`** that automate it.
- Or application-level / event-sourcing audit.

```sql
-- 🐘: a trigger-based pattern (sketch)
CREATE TABLE products_history (LIKE products, valid_from timestamptz, valid_to timestamptz);
CREATE OR REPLACE FUNCTION archive_product() RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO products_history SELECT OLD.*, OLD.updated_at, now();
    RETURN NEW;
END $$;
CREATE TRIGGER trg_archive_product BEFORE UPDATE OR DELETE ON products
    FOR EACH ROW EXECUTE FUNCTION archive_product();
```

> The dialect gap: **🟦 SQL Server has first-class temporal tables** (auto history, `FOR SYSTEM_TIME`
> queries); **🐘 requires a trigger pattern or an extension**. (See the EF Core notes' temporal chapter
> for the SQL Server feature in depth.)

## 🧠 Intuition — Part 2: Vector data (AI)

AI models turn text/images into **vectors** (embeddings — arrays of floats capturing meaning).
Similar content → nearby vectors. **Vector search** finds the *nearest* vectors to a query vector,
powering **semantic search** and **RAG** (retrieval-augmented generation): "find documents that
*mean* the same as this question," not just keyword matches.

> 💡 **Analogy — coordinates of meaning.** Keyword search finds the exact word. Vector search finds
> the *nearest landmark* in a high-dimensional "meaning space" — so a query about "automobiles"
> retrieves documents about "cars" even with no shared words.

## 💻 🐘 PostgreSQL — pgvector

The **pgvector** extension is the de facto standard for vectors in PostgreSQL:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
    doc_id    INT PRIMARY KEY,
    content   text,
    embedding vector(1536)          -- e.g. 1536-dim embedding from an LLM
);

-- Nearest neighbors by cosine distance (<=>), L2 (<->), or inner product (<#>)
SELECT content
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector     -- query embedding
LIMIT 5;

-- Approximate-nearest-neighbor index for scale (HNSW or IVFFlat)
CREATE INDEX ix_docs_embedding ON documents USING hnsw (embedding vector_cosine_ops);
```

Distance operators: **`<->`** (L2/Euclidean), **`<=>`** (cosine), **`<#>`** (negative inner product).
Index with **HNSW** (high recall, fast) or **IVFFlat** for approximate nearest-neighbor at scale.

## 💻 🟦 SQL Server 2025 / Azure SQL — native `VECTOR`

SQL Server 2025 (and Azure SQL) added a native **`VECTOR`** type and **`VECTOR_DISTANCE()`** function:

```sql
CREATE TABLE documents (
    doc_id    INT PRIMARY KEY,
    content   NVARCHAR(MAX),
    embedding VECTOR(1536)
);

-- Nearest neighbors
SELECT TOP 5 content
FROM documents
ORDER BY VECTOR_DISTANCE('cosine', embedding, @queryVector);   -- 'cosine' | 'euclidean' | 'dot'
```

`VECTOR_DISTANCE('cosine' | 'euclidean' | 'dot', a, b)` computes the distance; `cosine` is typical
for text embeddings. (Covered in depth in the EF Core notes' vector chapter — EF Core 10 exposes this
via `EF.Functions.VectorDistance`.)

## 🟦 SQL Server vs 🐘 PostgreSQL

| Feature | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Temporal tables | **Built-in** (`SYSTEM_VERSIONING`, `FOR SYSTEM_TIME`) | trigger pattern / `temporal_tables` extension |
| Vector type | **`VECTOR`** (SQL Server 2025 / Azure SQL) | **pgvector** extension `vector(n)` |
| Vector distance | `VECTOR_DISTANCE('cosine'/'euclidean'/'dot', ...)` | `<=>` cosine, `<->` L2, `<#>` inner product |
| ANN index | (evolving in 2025/Azure SQL) | **HNSW** / **IVFFlat** (mature) |
| Maturity | New (2025) | pgvector is widely adopted & battle-tested |

> **Temporal:** 🟦 wins on built-in support. **Vector:** both are now first-class — 🐘's **pgvector** is
> the more mature/widely-used ecosystem; 🟦's native `VECTOR` (2025) integrates cleanly with the
> Microsoft stack (and EF Core 10).

## ⚖️ When to use these

- **Temporal tables:** auditing, compliance, point-in-time analysis, "as of" reporting, slowly-
  changing-dimension history. Mind **storage growth** (history accumulates — set retention) and PII
  (history makes deletion harder).
- **Vector data:** semantic search, RAG for LLM apps, recommendations, image/audio similarity,
  deduplication. Persist the **embedding model version**; cap **Top-K**; combine with filters
  (tenant, category) for hybrid search.

## 🚫 Common mistakes

```sql
-- Temporal
-- ❌ Temporal-izing a huge high-churn table with no retention → history explodes
-- ✅ set HISTORY_RETENTION_PERIOD (🟦) or prune the history table
-- ❌ PII in temporal history with a "right to erasure" requirement → hard to delete
-- ✅ avoid temporal for PII, or build a redaction process

-- Vector
-- ❌ Mixing embeddings from different models → distances are meaningless
-- ✅ store/track the embedding model version; re-embed on model change
-- ❌ No ANN index → every search scans all vectors (O(n) distance computations)
-- ✅ HNSW/IVFFlat (🐘); appropriate vector index (🟦 2025/Azure SQL)
-- ❌ Returning thousands of neighbors → defeats the index; cap Top-K (5–50)
```

## 🌍 Real-World Use

- **Temporal:** financial/audit trails, regulatory compliance ("show the record as of the audit
  date"), versioned configuration, historical analytics.
- **Vector:** the retrieval layer of LLM apps (RAG) — embed your docs, vector-search the most relevant
  chunks for a question, feed them to the model. Also semantic product search, "more like this"
  recommendations, and near-duplicate detection.

## 🎯 Practice (with full solutions)

### 1. Point-in-time query — `Medium` (🟦)
**Task:** Show a product's state as it was on 2025-05-01 using temporal tables.
**Solution:**
```sql
-- 🟦 SQL Server (table is system-versioned)
SELECT * FROM products FOR SYSTEM_TIME AS OF '2025-05-01' WHERE product_id = 5;
-- 🐘 PostgreSQL: query the history table by valid_from/valid_to window (trigger-maintained)
SELECT * FROM products_history WHERE product_id = 5 AND '2025-05-01' BETWEEN valid_from AND valid_to;
```
**Why it works:** 🟦's `FOR SYSTEM_TIME AS OF` reconstructs the row's state at that instant from the
auto-maintained history; 🐘 achieves the same by querying the trigger-built history table's validity
window.

### 2. Semantic search — `Medium`
**Task:** Return the 5 documents most semantically similar to a query embedding, in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL (pgvector, cosine distance, HNSW index)
SELECT content FROM documents ORDER BY embedding <=> $1::vector LIMIT 5;

-- 🟦 SQL Server 2025 / Azure SQL
SELECT TOP 5 content FROM documents ORDER BY VECTOR_DISTANCE('cosine', embedding, @queryVector);
```
**Why it works:** both rank documents by vector distance to the query embedding (cosine for text) and
take the nearest 5 — the core of semantic search / RAG retrieval. With an ANN index it stays fast at
scale.

## ✅ Key Takeaways

- **Temporal tables** auto-track row history with point-in-time (`AS OF`) queries — **🟦 built-in**
  (`SYSTEM_VERSIONING`); **🐘 via triggers/extensions**. Mind storage retention and PII.
- **Vector data** powers AI semantic search / RAG: **🐘 pgvector** (`vector(n)`, `<=>`/`<->`/`<#>`,
  HNSW/IVFFlat) — mature; **🟦 native `VECTOR` + `VECTOR_DISTANCE`** (SQL Server 2025 / Azure SQL).
- Vectors: track the **embedding model version**, use an **ANN index**, cap **Top-K**, combine with
  filters.
- These bring "time travel" and "AI search" into the relational database — no separate system needed
  for many use cases.
