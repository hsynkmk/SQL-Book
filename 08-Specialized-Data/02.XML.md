# XML

## 🧠 Intuition

Before JSON took over, **XML** was *the* semi-structured format, and both databases still support it
richly. XML is more verbose than JSON but supports schemas (validation), namespaces, attributes, and
a powerful query language (**XQuery/XPath**). You'll meet it in enterprise integrations, legacy
systems, SOAP services, document standards (invoices, healthcare HL7), and config.

> 💡 **Analogy — JSON's older, more formal sibling.** If JSON is a quick handwritten note, XML is a
> formal typed letter with letterhead, signatures, and a notary (schema validation). More ceremony,
> but stronger guarantees and a richer query language — which is why regulated industries still use
> it.

## 📐 When you'll use XML today

- **Legacy & enterprise integration** — SOAP, EDI, B2B document exchange.
- **Industry standards** — HL7 (healthcare), FpML (finance), UBL (invoicing), Office Open XML.
- **Documents needing validation** against an **XSD schema**.
- For *new* semi-structured storage, **JSON is usually the better choice** (lighter, native `jsonb`
  on 🐘). Reach for XML when the data *is* XML or a standard mandates it.

## 💻 🟦 SQL Server — the richer XML support

SQL Server has a first-class **`XML`** data type with typed/untyped columns, XML schema collections,
XQuery methods, and XML indexes:

```sql
CREATE TABLE invoices (
    invoice_id INT PRIMARY KEY,
    doc        XML                       -- untyped; or XML(my_schema_collection) for typed/validated
);

INSERT INTO invoices VALUES (1,
    '<invoice><customer>Acme</customer><lines><line sku="A1" qty="3"/><line sku="B2" qty="5"/></lines></invoice>');

-- XQuery methods on the XML column:
SELECT doc.value('(/invoice/customer)[1]', 'NVARCHAR(100)') AS customer FROM invoices;   -- .value()
SELECT invoice_id FROM invoices WHERE doc.exist('/invoice/lines/line[@sku="A1"]') = 1;   -- .exist()

-- Shred XML into rows with .nodes()
SELECT i.invoice_id,
       l.value('@sku', 'NVARCHAR(20)') AS sku,
       l.value('@qty', 'INT') AS qty
FROM invoices i
CROSS APPLY i.doc.nodes('/invoice/lines/line') AS t(l);

-- Produce XML from relational data
SELECT name, unit_price FROM products FOR XML PATH('product'), ROOT('products');

-- Index the XML column (primary + secondary XML indexes) for query performance
CREATE PRIMARY XML INDEX px_invoices_doc ON invoices (doc);
```

| 🟦 XML method | Does |
|--------------|------|
| `.value()` | Extract a scalar |
| `.exist()` | Test if a node exists (returns 0/1) |
| `.query()` | Return an XML fragment |
| `.nodes()` | Shred into rows |
| `.modify()` | Update the XML (XML DML) |
| `FOR XML` | Serialize results as XML |

## 💻 🐘 PostgreSQL — XML type + XPath

PostgreSQL has an **`xml`** type and **XPath**-based functions (XQuery support is more limited than
🟦's):

```sql
CREATE TABLE invoices (invoice_id INT PRIMARY KEY, doc xml);

INSERT INTO invoices VALUES (1, '<invoice><customer>Acme</customer></invoice>');

-- Extract with xpath() (returns an array of xml nodes)
SELECT (xpath('/invoice/customer/text()', doc))[1]::text AS customer FROM invoices;

-- Test existence
SELECT * FROM invoices WHERE xpath_exists('/invoice/customer', doc);

-- Shred with xmltable() — the clean, SQL/XML-standard way (PG 10+)
SELECT x.sku, x.qty
FROM invoices i,
     XMLTABLE('/invoice/lines/line' PASSING i.doc
              COLUMNS sku text PATH '@sku', qty int PATH '@qty') AS x;

-- Produce XML
SELECT xmlelement(name product, xmlforest(name, unit_price)) FROM products;
```

🐘's **`XMLTABLE`** is the idiomatic, standard way to turn XML into relational rows — comparable to
🟦's `.nodes()`.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Type | `XML` (typed/untyped) | `xml` |
| Query language | **XQuery** (`.value`/`.exist`/`.query`/`.nodes`/`.modify`) | **XPath** (`xpath`, `xpath_exists`) + `XMLTABLE` |
| Schema validation | **XML schema collections** (XSD) | basic; relies on `IS DOCUMENT`/well-formedness |
| XML indexes | **Yes** (primary + secondary) | **No** (no XML-specific index) |
| Modify in place | `.modify()` (XML DML) | rebuild the value |
| Maturity | **Richer** (full XQuery, indexes, XSD) | Adequate (XPath + XMLTABLE) |

> SQL Server's XML support is notably **richer** (full XQuery, XML indexes, XSD validation) — a legacy
> of XML's enterprise heyday on the Microsoft stack. PostgreSQL covers the essentials (XPath +
> XMLTABLE) but has no XML indexes and weaker schema validation.

## ⚖️ XML vs JSON today

| | XML | JSON |
|--|-----|------|
| Verbosity | High (tags, closing tags) | Low |
| Schema/validation | Strong (XSD) | Weaker (JSON Schema, app-side) |
| Attributes/namespaces | Yes | No |
| Query language | XQuery/XPath (powerful) | path operators (simpler) |
| Native binary type | no | **🐘 jsonb** |
| Best for | Standards, legacy, validated docs | Modern semi-structured storage |

**For new work, prefer JSON** unless the data is inherently XML or a standard requires it.

## 🚫 Common mistakes

```sql
-- ❌ Choosing XML for new semi-structured storage out of habit
-- ✅ use JSON (jsonb on 🐘) unless the format is mandated XML

-- ❌ 🟦: querying a huge untyped XML column without an XML index → slow
-- ✅ add a PRIMARY XML INDEX (and secondary) for frequent XQuery

-- ❌ Treating XML as a string and parsing it in the app
-- ✅ use the database's XQuery/XPath to query/shred it server-side

-- ❌ Expecting PostgreSQL to validate against XSD like SQL Server
-- ✅ 🐘 only checks well-formedness; validate in the app if you need XSD
```

## 🌍 Real-World Use

- **Healthcare (HL7), finance (FpML/FIX), government/EDI** document exchange where XML is the standard.
- **SOAP web service** payloads stored/queried in the database.
- **Legacy enterprise systems** built before JSON.
- Migrating XML feeds: shred incoming XML into relational tables with `.nodes()`/`XMLTABLE`.

## 🎯 Practice (with full solutions)

### 1. Extract a value from XML — `Easy`
**Task:** Get the `<customer>` from each invoice's XML, in both engines.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT invoice_id, doc.value('(/invoice/customer)[1]', 'NVARCHAR(100)') AS customer FROM invoices;
-- 🐘 PostgreSQL
SELECT invoice_id, (xpath('/invoice/customer/text()', doc))[1]::text AS customer FROM invoices;
```
**Why it works:** each engine navigates the XML path to the `customer` node and extracts its text —
🟦's `.value()` with XQuery, 🐘's `xpath()`.

### 2. Shred XML lines into rows — `Medium`
**Task:** Turn each invoice's `<line sku qty>` elements into relational rows (`sku`, `qty`).
**Solution:**
```sql
-- 🟦 SQL Server: .nodes() + CROSS APPLY
SELECT i.invoice_id, l.value('@sku','NVARCHAR(20)') AS sku, l.value('@qty','INT') AS qty
FROM invoices i CROSS APPLY i.doc.nodes('/invoice/lines/line') AS t(l);

-- 🐘 PostgreSQL: XMLTABLE
SELECT i.invoice_id, x.sku, x.qty
FROM invoices i,
     XMLTABLE('/invoice/lines/line' PASSING i.doc COLUMNS sku text PATH '@sku', qty int PATH '@qty') AS x;
```
**Why it works:** both produce one relational row per `line` element, projecting the `sku`/`qty`
attributes into columns — 🟦's `.nodes()`/`CROSS APPLY` and 🐘's standard `XMLTABLE` are the
idiomatic shredding tools.

## ✅ Key Takeaways

- **XML** is the older semi-structured format — verbose but supports **schemas (XSD)**, namespaces,
  attributes, and **XQuery/XPath**.
- **🟦 SQL Server** has **richer** XML support: full XQuery (`.value/.exist/.query/.nodes/.modify`),
  **XML indexes**, and XSD validation.
- **🐘 PostgreSQL** has the `xml` type with **XPath** + **`XMLTABLE`** (shredding), but **no XML
  indexes** and weaker validation.
- For **new** semi-structured storage, **prefer JSON** (🐘 `jsonb`); use XML for **standards/legacy**.
- Query/shred XML **server-side**, don't string-parse it in the app.
