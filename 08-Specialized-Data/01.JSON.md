# JSON

> A major dialect split: 🐘 has a **native binary `jsonb`** type (mature, indexable); 🟦 stores JSON
> as text and provides **JSON functions** (with a native `json` type arriving in SQL Server 2025).

## 🧠 Intuition

Sometimes data is **semi-structured** — a flexible bag of attributes that varies per row, or a nested
document you don't want to shred into many tables. JSON columns let a relational database store and
query documents *inside* a row, blending relational and document-store models. You keep the
structured, queryable parts as columns and stash the flexible payload as JSON.

> 💡 **Analogy — a labeled box inside a filing cabinet.** Most of your filing is neat folders
> (columns). But some items don't fit a fixed form, so you put them in a labeled box (a JSON column)
> in the drawer. You can still reach in and pull out specific items by name — just less rigidly than
> a dedicated folder.

## 📐 Where JSON fits (and where it doesn't)

- ✅ **Flexible/variable attributes** (product specs that differ by category, feature flags, settings).
- ✅ **Nested documents** you read/write as a unit (an order's shipping info, an event payload).
- ✅ **Sparse data** (hundreds of rarely-used optional fields).
- 🚫 **Core relational data** you join/filter/constrain on heavily — keep that as **columns**. JSON
  queries are slower and weaker on constraints than real columns.

**Rule:** structured, queried-on keys → columns; flexible payload → JSON. Don't model your whole
schema as one JSON blob.

## 💻 🐘 PostgreSQL — native `jsonb`

PostgreSQL's **`jsonb`** is binary, indexable, and feature-rich (the idiomatic choice over `json`,
which is plain text):

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name       text NOT NULL,
    attributes jsonb           -- e.g. {"color": "red", "tags": ["sale","new"], "specs": {"weight": 5}}
);

-- Access fields: -> returns jsonb, ->> returns text, #> for deep paths
SELECT name, attributes->>'color' AS color, attributes#>>'{specs,weight}' AS weight FROM products;

-- Filter by a key
SELECT * FROM products WHERE attributes->>'color' = 'red';

-- Containment (@>) — "has this structure" — and key existence (?)
SELECT * FROM products WHERE attributes @> '{"color":"red"}';
SELECT * FROM products WHERE attributes ? 'discount';        -- has a 'discount' key

-- Index for containment/existence queries (GIN — see Specialized Indexes)
CREATE INDEX ix_products_attrs ON products USING GIN (attributes);

-- Modify
UPDATE products SET attributes = attributes || '{"on_sale": true}' WHERE product_id = 1;   -- merge
UPDATE products SET attributes = attributes - 'discount' WHERE product_id = 1;              -- remove key

-- Expand JSON into rows
SELECT jsonb_array_elements_text(attributes->'tags') AS tag FROM products WHERE product_id = 1;
```

🐘's `jsonb` operators (`->`, `->>`, `#>>`, `@>`, `?`, `||`) plus **GIN indexes** make it a genuinely
capable document store inside PostgreSQL.

## 💻 🟦 SQL Server — JSON functions

SQL Server (pre-2025) stores JSON in an `NVARCHAR` column and provides functions to query it.
**SQL Server 2025** adds a native **`json`** type (more efficient, validated):

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    name       NVARCHAR(100) NOT NULL,
    attributes NVARCHAR(MAX)        -- (SQL Server 2025: attributes JSON)
    -- optional validation pre-2025:
    CONSTRAINT chk_attrs_json CHECK (ISJSON(attributes) = 1)
);

-- Extract a scalar value
SELECT name, JSON_VALUE(attributes, '$.color') AS color FROM products;

-- Extract an object/array (JSON_QUERY)
SELECT JSON_QUERY(attributes, '$.specs') AS specs FROM products;

-- Filter by a JSON value
SELECT * FROM products WHERE JSON_VALUE(attributes, '$.color') = 'red';

-- Modify
UPDATE products SET attributes = JSON_MODIFY(attributes, '$.on_sale', CAST(1 AS BIT)) WHERE product_id = 1;

-- Shred JSON into rows/columns with OPENJSON
SELECT p.name, t.value AS tag
FROM products p
CROSS APPLY OPENJSON(p.attributes, '$.tags') AS t;

-- Produce JSON from relational data
SELECT name, unit_price FROM products FOR JSON PATH;
```

| Function | Does |
|----------|------|
| `JSON_VALUE` | Extract a **scalar** |
| `JSON_QUERY` | Extract an **object/array** |
| `JSON_MODIFY` | Update a value |
| `OPENJSON` | Shred JSON into rows |
| `FOR JSON` | Serialize query results as JSON |
| `ISJSON` | Validate |

> Indexing JSON in 🟦 (pre-2025) is done via a **computed column** on `JSON_VALUE(...)` + an index on
> that column — there's no GIN equivalent. SQL Server 2025's native `json` type improves storage and
> adds better indexing.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Storage | `NVARCHAR` + functions; native `json` in 2025 | native **`jsonb`** (binary) / `json` (text) |
| Extract scalar | `JSON_VALUE(col, '$.path')` | `col->>'key'`, `col#>>'{a,b}'` |
| Containment / existence | (manual via `JSON_VALUE`) | `@>`, `?`, `?|`, `?&` |
| Modify | `JSON_MODIFY` | `\|\|` merge, `-` remove, `jsonb_set` |
| Index | computed column + index | **GIN** index (powerful) |
| Shred to rows | `OPENJSON` | `jsonb_array_elements`, `jsonb_each` |
| Maturity | Good; better in 2025 | Excellent (jsonb is best-in-class) |

> The headline: **PostgreSQL's `jsonb` is one of the best JSON implementations in any relational
> database** — binary storage, rich operators, GIN indexing. SQL Server's JSON is capable via
> functions and is significantly upgraded in 2025 with a native type.

## ⚡ Performance

- **🐘:** index `jsonb` with **GIN** for `@>`/`?` queries; or index a specific extracted value with a
  B-tree expression index (`((attributes->>'color'))`). Without an index, JSON predicates scan.
- **🟦:** create a **persisted computed column** from `JSON_VALUE(...)` and index it to make JSON
  filters [SARGable](../06-Indexing-and-Performance/05.SARGability.md).
- **Always keep frequently-queried keys as real columns** — JSON access is slower than a column read.

## 🚫 Common mistakes

```sql
-- ❌ Modeling everything as one big JSON blob → lose constraints, joins, and query performance
-- ✅ structured keys as columns; only flexible payload in JSON

-- ❌ 🐘: using `json` (text) when you want querying/indexing → use `jsonb`
-- ✅ jsonb for anything you'll query

-- ❌ Filtering JSON without an index on a big table → full scan
-- ✅ GIN (🐘) / persisted-computed-column index (🟦)

-- ❌ 🟦: forgetting ISJSON validation → garbage text in the column
-- ✅ CHECK (ISJSON(col) = 1), or the native json type in 2025
```

## 🌍 Real-World Use

- **Flexible product catalogs** (specs vary by category), **user settings/preferences**, **feature
  flags**, **event/audit payloads**, **API response caching**, **EAV replacement** (entity-attribute-
  value done sanely).
- PostgreSQL `jsonb` is frequently used as a lightweight document store, avoiding a separate MongoDB
  for semi-structured data.

## 🎯 Practice (with full solutions)

### 1. Query a JSON attribute — `Easy`
**Task:** Find products whose `attributes` JSON has `"color": "red"`, in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL (jsonb)
SELECT name FROM products WHERE attributes->>'color' = 'red';
-- or containment: WHERE attributes @> '{"color":"red"}';
-- 🟦 SQL Server
SELECT name FROM products WHERE JSON_VALUE(attributes, '$.color') = 'red';
```
**Why it works:** each engine extracts the `color` value from the document and compares it — `->>`/
`@>` on 🐘, `JSON_VALUE` on 🟦.

### 2. Make a JSON filter fast — `Medium`
**Task:** The color query above scans a 5M-row table. Index it in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL: GIN for containment, or a B-tree expression index for the specific key
CREATE INDEX ix_products_attrs ON products USING GIN (attributes);          -- supports @>
-- or: CREATE INDEX ix_products_color ON products (((attributes->>'color')));
SELECT name FROM products WHERE attributes @> '{"color":"red"}';

-- 🟦 SQL Server: persisted computed column + index
ALTER TABLE products ADD color AS JSON_VALUE(attributes, '$.color') PERSISTED;
CREATE INDEX ix_products_color ON products (color);
SELECT name FROM products WHERE color = 'red';
```
**Why it works:** 🐘's GIN indexes the document for containment; 🟦 materializes the extracted value
into an indexed column so the filter becomes a seek instead of scanning + parsing JSON per row.

## ✅ Key Takeaways

- JSON columns store **semi-structured/nested** data inside a relational row — keys you query stay
  **columns**, flexible payload goes in JSON.
- **🐘 `jsonb`** is native, binary, richly-operatored (`->`, `->>`, `@>`, `?`, `||`) and **GIN-
  indexable** — best-in-class.
- **🟦** uses **JSON functions** (`JSON_VALUE`, `JSON_QUERY`, `JSON_MODIFY`, `OPENJSON`, `FOR JSON`) on
  `NVARCHAR`; **SQL Server 2025** adds a native `json` type. Index via computed column.
- Index JSON predicates (**GIN** 🐘 / **computed-column index** 🟦) — unindexed JSON filters scan.
- Don't model your whole schema as one JSON blob.
