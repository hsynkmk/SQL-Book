# Full-Text Search

## 🧠 Intuition

`LIKE '%word%'` is a terrible way to search text: it can't use an index (leading wildcard →
[non-SARGable](../06-Indexing-and-Performance/05.SARGability.md), full scan), it doesn't understand
word boundaries, stemming ("run" vs "running"), relevance ranking, or stop words. **Full-text
search** builds a specialized index of the *words* in your text so you can search documents fast,
with linguistic awareness and relevance ranking — like a mini search engine inside your database.

> 💡 **Analogy — the index of a book vs reading every page.** `LIKE '%transactions%'` reads all 500
> pages looking for the word. Full-text search uses the book's word index: "transactions → pp. 142,
> 305," instantly, and it knows "transaction" and "transactions" are the same word, and ranks pages
> by how relevant they are.

## 🎯 The Problem

```sql
-- ❌ LIKE '%error%' — scans every row, no stemming, no ranking, no relevance
SELECT * FROM articles WHERE body LIKE '%error%';
-- misses "errors"? no. matches "terrorist"? yes (substring). ranks results? no. fast? no.
```

For real text search — articles, product descriptions, comments — you want word-aware, ranked,
indexed search. That's full-text search.

## 💻 🐘 PostgreSQL — `tsvector` / `tsquery`

PostgreSQL's full-text search converts text to a **`tsvector`** (a sorted list of normalized words +
positions) and matches it against a **`tsquery`** (search terms), with the **`@@`** match operator:

```sql
-- Search on the fly (small data): to_tsvector parses + normalizes; to_tsquery parses the query
SELECT title FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'error & connection');   -- both words

-- For performance: store a generated tsvector column and GIN-index it
ALTER TABLE articles ADD COLUMN search tsvector
    GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || body)) STORED;
CREATE INDEX ix_articles_search ON articles USING GIN (search);

-- Now the search uses the index
SELECT title FROM articles WHERE search @@ to_tsquery('english', 'database & performance');

-- Relevance ranking
SELECT title, ts_rank(search, to_tsquery('english', 'database')) AS rank
FROM articles WHERE search @@ to_tsquery('english', 'database')
ORDER BY rank DESC;

-- Friendlier query parsing: plainto_tsquery / websearch_to_tsquery (handles "quoted phrases", -negation)
SELECT title FROM articles WHERE search @@ websearch_to_tsquery('english', 'database "query plan" -mysql');
```

Features: **stemming** (`run`/`running`/`ran` match), **stop words** (ignore "the", "a"), **language
configs**, **ranking** (`ts_rank`), **highlighting** (`ts_headline`), and boolean/phrase queries.

## 💻 🟦 SQL Server — Full-Text Search

SQL Server has a Full-Text Search engine: create a **full-text catalog** and a **full-text index** on
a column, then query with **`CONTAINS`** / **`FREETEXT`**:

```sql
-- 1. Create a full-text catalog and index (requires the Full-Text feature installed)
CREATE FULLTEXT CATALOG ftCatalog AS DEFAULT;
CREATE FULLTEXT INDEX ON articles (title, body)
    KEY INDEX PK_articles ON ftCatalog;

-- 2. Query
-- CONTAINS: precise — boolean, prefix, proximity, inflectional
SELECT title FROM articles WHERE CONTAINS(body, 'error AND connection');
SELECT title FROM articles WHERE CONTAINS(body, 'FORMSOF(INFLECTIONAL, run)');   -- run/running/ran
SELECT title FROM articles WHERE CONTAINS(body, '"query plan"');                 -- phrase

-- FREETEXT: natural-language, fuzzy — matches meaning, not exact terms
SELECT title FROM articles WHERE FREETEXT(body, 'slow database queries');

-- Ranked results with CONTAINSTABLE / FREETEXTTABLE
SELECT a.title, kt.RANK
FROM articles a
JOIN CONTAINSTABLE(articles, body, 'database') kt ON kt.[KEY] = a.article_id
ORDER BY kt.RANK DESC;
```

| 🟦 Predicate | Style |
|-------------|-------|
| `CONTAINS` | Precise: boolean, prefix (`"data*"`), proximity (`NEAR`), inflectional |
| `FREETEXT` | Natural language, fuzzy meaning |
| `CONTAINSTABLE`/`FREETEXTTABLE` | Same but return a **`RANK`** for relevance ordering |

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Mechanism | Full-text **catalog + index** | **`tsvector`** column + **GIN** index |
| Search | `CONTAINS` / `FREETEXT` | `@@` with `to_tsquery`/`plainto_tsquery`/`websearch_to_tsquery` |
| Ranking | `CONTAINSTABLE`/`FREETEXTTABLE` `RANK` | `ts_rank` / `ts_rank_cd` |
| Stemming/stop words | Language-specific word breakers | Language configs (`'english'`, ...) |
| Highlighting | (limited) | `ts_headline` |
| Setup | Feature install + catalog | Built-in; GIN index |

> Both are capable. **🐘's full-text is built-in and very flexible** (generated `tsvector` columns,
> `websearch_to_tsquery` for Google-style queries, `ts_headline` highlighting). **🟦's is a separate
> feature** that must be installed/enabled but offers strong natural-language (`FREETEXT`) and
> proximity search. For *very* advanced search (typo tolerance, faceting, huge scale), many teams use
> a dedicated engine (**Elasticsearch**, **OpenSearch**, 🐘's **pg_trgm** for fuzzy/typo matching).

## ⚡ Performance & extras

- The **index is essential** — full-text without its index is just a scan. 🐘: GIN on the `tsvector`;
  🟦: the full-text index.
- **🐘 `pg_trgm`** (trigram extension) complements full-text with **fuzzy/typo-tolerant** matching and
  makes even `LIKE '%word%'` indexable via a trigram GIN/GiST index.
- For relevance-critical or web-scale search, a dedicated search engine (Elasticsearch) often
  outperforms in-database full-text — but in-database FTS is perfect for "good search without another
  system."

## 🚫 Common mistakes

```sql
-- ❌ Using LIKE '%term%' for real text search → scan, no ranking, no stemming
-- ✅ full-text search (tsvector/@@ 🐘 or CONTAINS/FREETEXT 🟦)

-- ❌ 🐘: computing to_tsvector() on every query for a big table → slow
-- ✅ a STORED generated tsvector column + GIN index

-- ❌ Forgetting the language config → wrong stemming/stop words
-- ✅ specify 'english' (or your language) consistently

-- ❌ Expecting full-text to do typo tolerance out of the box
-- ✅ 🐘 pg_trgm for fuzzy matching, or a dedicated engine
```

## 🌍 Real-World Use

Article/blog/document search, product description search, comment/forum search, knowledge bases,
e-commerce site search (often combined with filters). In-database full-text covers most needs;
fuzzy/typo-tolerant or web-scale faceted search graduates to `pg_trgm` or Elasticsearch.

## 🎯 Practice (with full solutions)

### 1. Replace LIKE with full-text — `Medium`
**Task:** Search `articles.body` for documents about "database performance," with stemming and
ranking, in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL
ALTER TABLE articles ADD COLUMN search tsvector
    GENERATED ALWAYS AS (to_tsvector('english', body)) STORED;
CREATE INDEX ix_articles_search ON articles USING GIN (search);
SELECT title, ts_rank(search, q) AS rank
FROM articles, to_tsquery('english','database & performance') q
WHERE search @@ q ORDER BY rank DESC;

-- 🟦 SQL Server
CREATE FULLTEXT INDEX ON articles (body) KEY INDEX PK_articles ON ftCatalog;
SELECT a.title, kt.RANK
FROM articles a JOIN CONTAINSTABLE(articles, body, 'database AND performance') kt ON kt.[KEY] = a.article_id
ORDER BY kt.RANK DESC;
```
**Why it works:** the full-text index supports word-aware matching with stemming; `ts_rank`/`RANK`
order results by relevance — none of which `LIKE` can do, and it's index-fast.

### 2. Google-style query (🐘) — `Easy`
**Task:** Let users type `database "query plan" -mysql` and search naturally.
**Solution:**
```sql
-- 🐘 PostgreSQL: websearch_to_tsquery parses quoted phrases and -negation like a search box
SELECT title FROM articles WHERE search @@ websearch_to_tsquery('english', 'database "query plan" -mysql');
```
**Why it works:** `websearch_to_tsquery` understands web-search syntax (phrases in quotes, `-` to
exclude), giving users a familiar search experience over the GIN-indexed `tsvector`.

## ✅ Key Takeaways

- **Full-text search** indexes *words* for fast, word-aware, ranked text search — far better than
  `LIKE '%x%'` (which scans, can't stem, can't rank).
- **🐘:** **`tsvector`** + **`@@`** + **GIN** index; use a **STORED generated tsvector** column;
  `ts_rank` for relevance, `websearch_to_tsquery` for Google-style queries, `ts_headline` to
  highlight.
- **🟦:** **full-text catalog + index**, queried with **`CONTAINS`** (precise) / **`FREETEXT`**
  (natural language); `CONTAINSTABLE`/`FREETEXTTABLE` for ranking.
- The **index is essential**; both support stemming/stop words via language configs.
- For typo tolerance use **`pg_trgm`** (🐘); for web-scale faceted search, a dedicated engine
  (Elasticsearch).
