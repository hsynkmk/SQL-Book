# Spatial Data

## 🧠 Intuition

**Spatial data** is locations and shapes — points (a store), lines (a road), polygons (a delivery
zone) — and the queries you run on them: "stores within 5 km of me," "does this delivery area
overlap that one," "the nearest 3 hospitals." A regular database treats coordinates as just numbers;
**spatial types and indexes** understand geometry, so these queries are correct *and* fast.

> 💡 **Analogy — a map vs a list of coordinates.** A list of lat/long pairs is just numbers — to find
> "within 5km" you'd compute distance to every point (a scan). A spatial database is a *map*: it
> understands shapes and distances natively, and its spatial index lets it ignore everything far away
> and jump to the nearby points.

## 📐 Geometry vs Geography

A crucial distinction in both engines:

| | **Geometry** (planar) | **Geography** (geodetic) |
|--|----------------------|--------------------------|
| Model | Flat plane (Euclidean) | Round earth (lat/long, ellipsoid) |
| Coordinates | x, y on a plane | longitude, latitude |
| Distance | Straight-line on a plane | Great-circle (accounts for earth's curvature) |
| Use for | CAD, local/projected maps, games | GPS, global distances, "near me" |

For real-world "find places near a GPS location," use **geography**; for projected/local planar work,
use **geometry**.

## 💻 🟦 SQL Server — built-in `GEOGRAPHY` / `GEOMETRY`

SQL Server has native spatial types and methods (OGC-standard):

```sql
CREATE TABLE stores (
    store_id INT PRIMARY KEY,
    name     NVARCHAR(100),
    location GEOGRAPHY            -- a point on the earth
);

-- Insert a point (longitude, latitude) — note: lon first, SRID 4326 = WGS84/GPS
INSERT INTO stores VALUES (1, 'Berlin Shop', geography::Point(52.52, 13.405, 4326));

-- Distance (returns meters for geography)
SELECT name, location.STDistance(geography::Point(52.50, 13.40, 4326)) AS meters
FROM stores ORDER BY meters;

-- Within a radius (5 km)
SELECT name FROM stores
WHERE location.STDistance(geography::Point(52.50, 13.40, 4326)) <= 5000;

-- Spatial index (essential for performance)
CREATE SPATIAL INDEX six_stores_location ON stores (location);
```

Common methods: `STDistance`, `STIntersects`, `STContains`, `STWithin`, `STBuffer`, `STArea`,
`STLength`.

## 💻 🐘 PostgreSQL — PostGIS (the gold standard)

PostgreSQL itself has minimal geometry; the **PostGIS extension** turns it into arguably the **best
spatial database in the world** — used by governments, mapping companies, and OpenStreetMap:

```sql
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE stores (
    store_id INT PRIMARY KEY,
    name     text,
    location geography(Point, 4326)        -- geography type from PostGIS, SRID 4326 (GPS)
);

-- Insert (longitude, latitude order in PostGIS)
INSERT INTO stores VALUES (1, 'Berlin Shop', ST_SetSRID(ST_MakePoint(13.405, 52.52), 4326));

-- Distance in meters (geography)
SELECT name, ST_Distance(location, ST_SetSRID(ST_MakePoint(13.40, 52.50), 4326)) AS meters
FROM stores ORDER BY meters;

-- Within a radius (ST_DWithin is index-accelerated — preferred over ST_Distance < x)
SELECT name FROM stores
WHERE ST_DWithin(location, ST_SetSRID(ST_MakePoint(13.40, 52.50), 4326), 5000);

-- Spatial index (GiST)
CREATE INDEX six_stores_location ON stores USING GiST (location);

-- Nearest-neighbor (KNN) — the <-> operator with the GiST index
SELECT name FROM stores
ORDER BY location <-> ST_SetSRID(ST_MakePoint(13.40, 52.50), 4326)
LIMIT 3;
```

PostGIS has **hundreds** of functions (`ST_Intersects`, `ST_Contains`, `ST_Buffer`, `ST_Area`,
`ST_Union`, raster support, projections, ...) and the GiST index powers fast nearest-neighbor and
overlap queries.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL (PostGIS) |
|---------|--------------|--------------------------|
| Availability | Built-in (`GEOGRAPHY`/`GEOMETRY`) | Extension (`CREATE EXTENSION postgis`) |
| Function naming | `ST*` methods on the column (`location.STDistance(...)`) | `ST_*` functions (`ST_Distance(location, ...)`) |
| Point order | `Point(lat, lon, srid)` | `ST_MakePoint(lon, lat)` *(lon first!)* |
| Index | Spatial index (grid-based) | **GiST** (also SP-GiST/BRIN) |
| Nearest-neighbor | order by `STDistance` | `<->` KNN operator (very efficient) |
| Radius query | `STDistance(...) <= r` | **`ST_DWithin(..., r)`** (index-friendly) |
| Depth/ecosystem | Solid | **PostGIS = industry leader** (raster, topology, projections) |

> The headline: **PostGIS is the gold standard for spatial** — more functions, raster support, and
> mapping-industry adoption. SQL Server's built-in spatial is solid and convenient (no extension), but
> PostGIS is far more powerful for serious GIS work. **Watch the coordinate order** — both use
> (longitude, latitude) for points, which trips people who think "lat, long."

## ⚡ Performance

- **Always create a spatial index** (🟦 spatial index / 🐘 **GiST**) — without it, every spatial query
  scans and computes geometry for all rows.
- **🐘:** use **`ST_DWithin`** (not `ST_Distance(...) < r`) for radius queries — it can use the GiST
  index; and the **`<->` KNN operator** for nearest-neighbor with index support.
- Spatial computations are CPU-heavy; the index's job is to prune the candidate set to the small set
  actually near the query geometry.

## 🚫 Common mistakes

```sql
-- ❌ Coordinate order: passing (lat, lon) where the function wants (lon, lat)
ST_MakePoint(52.52, 13.405)   -- WRONG: that's (lat, lon) → point in the wrong place / ocean
-- ✅ ST_MakePoint(13.405, 52.52)  -- (longitude, latitude)

-- ❌ Geometry vs geography mismatch → distances in degrees instead of meters, or wrong math
-- ✅ use geography for earth/GPS distances; geometry for planar/projected

-- ❌ No spatial index → every "near me" query scans the whole table
-- ✅ CREATE SPATIAL INDEX (🟦) / USING GiST (🐘)

-- ❌ 🐘: ST_Distance(loc, p) < 5000 in WHERE → not index-accelerated
-- ✅ ST_DWithin(loc, p, 5000) → uses the GiST index
```

## 🌍 Real-World Use

- **"Stores/ATMs/restaurants near me"**, ride-hailing driver matching, delivery radius checks.
- **Geofencing** — is this location inside a zone? (`ST_Contains`/`STContains`).
- **Logistics & routing**, territory management, real-estate search by area.
- **GIS / mapping** — PostGIS underpins OpenStreetMap, QGIS, and countless government/mapping systems.

## 🎯 Practice (with full solutions)

### 1. Stores within 5 km — `Medium`
**Task:** Find stores within 5 km of a GPS point (lon 13.40, lat 52.50), in both engines, using the
spatial index.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT name FROM stores
WHERE location.STDistance(geography::Point(52.50, 13.40, 4326)) <= 5000;   -- meters
-- (with a SPATIAL INDEX on location)

-- 🐘 PostgreSQL (PostGIS) — ST_DWithin is index-accelerated
SELECT name FROM stores
WHERE ST_DWithin(location, ST_SetSRID(ST_MakePoint(13.40, 52.50), 4326), 5000);
-- (with a GiST index on location)
```
**Why it works:** geography distances are in meters, so `<= 5000` is 5 km; 🐘's `ST_DWithin` uses the
GiST index to prune far-away rows. Mind the (lon, lat) order in `ST_MakePoint`.

### 2. Nearest 3 stores — `Medium`
**Task (🐘):** Return the 3 closest stores to a point, efficiently.
**Solution:**
```sql
-- 🐘 PostGIS: KNN with the <-> operator + GiST index
SELECT name FROM stores
ORDER BY location <-> ST_SetSRID(ST_MakePoint(13.40, 52.50), 4326)
LIMIT 3;
```
**Why it works:** the `<->` (distance) operator combined with the GiST index does an
**index-assisted nearest-neighbor** search — it walks the index toward the query point instead of
computing distance to every store, so it stays fast even on millions of rows.

## ✅ Key Takeaways

- Spatial types model **points/lines/polygons** and answer distance/overlap/nearest queries
  correctly and (with an index) fast.
- **Geometry** = planar; **Geography** = round-earth (use geography for GPS/global distances in
  meters).
- **🟦 has built-in `GEOGRAPHY`/`GEOMETRY`** (`ST*` methods); **🐘 uses PostGIS** — the industry-leading
  spatial extension (`ST_*` functions, GiST index, KNN `<->`).
- **Always create a spatial index**; prefer **`ST_DWithin`** (🐘) over `ST_Distance < r` for radius;
  watch the **(lon, lat)** coordinate order.
