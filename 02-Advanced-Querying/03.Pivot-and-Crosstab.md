# Pivot & Crosstab

> One of the bigger dialect splits: 🟦 has a dedicated `PIVOT` operator; 🐘 uses conditional
> aggregation or the `crosstab` extension function.

## 🧠 Intuition

**Pivoting** rotates rows into columns: instead of one row per (category, month) with a value, you
get one row per category and a *column* per month. It turns tall, normalized data into a wide,
spreadsheet-style report — the shape humans love to read.

> 💡 **Analogy — a spreadsheet pivot table.** You have a flat list of sales (date, region, amount).
> A pivot table turns regions into columns and months into rows, with totals in the grid. SQL
> pivoting does the same transformation in a query.

## 🎯 The Problem

```sql
-- Tall data: one row per (status), hard to compare side by side in a report
SELECT status, COUNT(*) FROM orders GROUP BY status;
-- status     | count
-- Shipped    | 3
-- Pending    | 1
-- Cancelled  | 1
```

A report often wants this **wide**: one row, with `Shipped`, `Pending`, `Cancelled` as columns.
That's a pivot.

## 💻 The portable way — conditional aggregation (works on BOTH engines)

The most portable and flexible technique is `CASE` inside aggregates — it works everywhere and you
control exactly which columns appear:

```sql
-- One row, a column per status (portable: SQL Server AND PostgreSQL)
SELECT
    COUNT(CASE WHEN status = 'Shipped'   THEN 1 END) AS shipped,
    COUNT(CASE WHEN status = 'Pending'   THEN 1 END) AS pending,
    COUNT(CASE WHEN status = 'Cancelled' THEN 1 END) AS cancelled
FROM orders;

-- Pivot with a grouping key: order count per status, per employee
SELECT employee_id,
    COUNT(CASE WHEN status = 'Shipped'   THEN 1 END) AS shipped,
    COUNT(CASE WHEN status = 'Pending'   THEN 1 END) AS pending,
    COUNT(CASE WHEN status = 'Cancelled' THEN 1 END) AS cancelled
FROM orders
GROUP BY employee_id;
```

🐘 PostgreSQL can use its cleaner **`FILTER`** syntax for the same thing:

```sql
-- 🐘 PostgreSQL
SELECT employee_id,
    COUNT(*) FILTER (WHERE status = 'Shipped')   AS shipped,
    COUNT(*) FILTER (WHERE status = 'Pending')   AS pending,
    COUNT(*) FILTER (WHERE status = 'Cancelled') AS cancelled
FROM orders
GROUP BY employee_id;
```

> **Recommendation:** learn the **conditional-aggregation** form first — it's portable, readable,
> and handles any pivot. The dedicated operators below are nice but engine-specific.

## 💻 The dedicated operators

### 🟦 SQL Server — the `PIVOT` operator

```sql
SELECT employee_id, [Shipped], [Pending], [Cancelled]
FROM (
    SELECT employee_id, status FROM orders
) src
PIVOT (
    COUNT(status) FOR status IN ([Shipped], [Pending], [Cancelled])
) pvt;
```

`PIVOT` is compact but **requires you to hard-code the column values** (`[Shipped]`, etc.). For a
*dynamic* set of columns (unknown at write time), you must build the SQL string dynamically with
[dynamic SQL](../04-Programmable-SQL/05.Dynamic-SQL-and-Control-Flow.md) — a common pain point.

### 🐘 PostgreSQL — the `crosstab` function

```sql
-- Requires the tablefunc extension
CREATE EXTENSION IF NOT EXISTS tablefunc;

SELECT * FROM crosstab(
    'SELECT employee_id, status, COUNT(*)::int
     FROM orders GROUP BY employee_id, status ORDER BY 1,2',
    'SELECT DISTINCT status FROM orders ORDER BY 1'
) AS ct(employee_id INT, cancelled INT, pending INT, shipped INT);
```

`crosstab` is powerful but fiddly — you must declare the output columns and their order. Most
PostgreSQL developers just use **`FILTER`/`CASE`** unless they need `crosstab`'s specific shape.

### Unpivot (wide → tall)

```sql
-- 🟦 SQL Server: UNPIVOT operator
-- 🐘 PostgreSQL: use a LATERAL/VALUES unnest or a UNION ALL
-- Portable approach (both): UNION ALL each column into rows
SELECT employee_id, 'Shipped' AS status, shipped AS cnt FROM wide_table
UNION ALL SELECT employee_id, 'Pending', pending FROM wide_table
UNION ALL SELECT employee_id, 'Cancelled', cancelled FROM wide_table;
```

## ⚖️ When to pivot in SQL vs the app

Pivoting in SQL is great for fixed, known categories. But for **dynamic** pivots (columns unknown
ahead of time) it gets ugly in both engines (dynamic SQL on 🟦, declared columns on 🐘). Often the
cleaner answer is: **return the tall data from SQL and pivot in the application or BI tool**
(Power BI, Excel, a chart library) which do dynamic pivoting natively. Reserve SQL pivoting for
reports with a stable, small set of output columns.

## 🚫 Common mistakes

```sql
-- ❌ Assuming PIVOT works on PostgreSQL (it doesn't)
SELECT ... PIVOT (...)   -- 🟦 only
-- ✅ use FILTER/CASE on 🐘

-- ❌ Hard-coding pivot columns that change over time → report breaks when a new status appears
-- ✅ for dynamic categories, pivot in the app/BI layer, or generate SQL dynamically

-- ❌ COUNT(CASE WHEN ... THEN 1 ELSE 0 END) for counting → counts the 0s too!
COUNT(CASE WHEN status='Shipped' THEN 1 ELSE 0 END)   -- counts ALL rows (0 is not null)
-- ✅ omit ELSE so non-matches are NULL (and COUNT skips NULL); or use SUM(CASE ... THEN 1 ELSE 0 END)
COUNT(CASE WHEN status='Shipped' THEN 1 END)
```

> Subtle but important: `COUNT(CASE WHEN x THEN 1 ELSE 0 END)` counts **every** row (because `0`
> isn't NULL). Either drop the `ELSE` (so non-matches become NULL and `COUNT` skips them) or use
> `SUM(CASE WHEN x THEN 1 ELSE 0 END)`.

## 🌍 Real-World Use

Monthly/quarterly cross-tab reports (region × month sales), status dashboards (counts per status
per team), survey results (question × response), attendance grids. In practice, fixed small pivots
live in SQL; large or dynamic ones get pivoted in the reporting tool.

## 🎯 Practice (with full solutions)

### 1. Status counts per employee — `Easy`
**Task:** One row per employee with columns `shipped`, `pending`, `cancelled` (order counts).
Portable solution.
**Solution:**
```sql
SELECT employee_id,
    COUNT(CASE WHEN status = 'Shipped'   THEN 1 END) AS shipped,
    COUNT(CASE WHEN status = 'Pending'   THEN 1 END) AS pending,
    COUNT(CASE WHEN status = 'Cancelled' THEN 1 END) AS cancelled
FROM orders
GROUP BY employee_id;
```
**Why it works:** conditional aggregation counts only the matching rows per column (no `ELSE`, so
non-matches are NULL and skipped by `COUNT`). Works on both engines.

### 2. Same, the engine-native way — `Medium`
**Task:** Rewrite using each engine's dedicated feature.
**Solution:**
```sql
-- 🐘 PostgreSQL: FILTER
SELECT employee_id,
    COUNT(*) FILTER (WHERE status='Shipped')   AS shipped,
    COUNT(*) FILTER (WHERE status='Pending')   AS pending,
    COUNT(*) FILTER (WHERE status='Cancelled') AS cancelled
FROM orders GROUP BY employee_id;
```
```sql
-- 🟦 SQL Server: PIVOT
SELECT employee_id, [Shipped], [Pending], [Cancelled]
FROM (SELECT employee_id, status FROM orders) s
PIVOT (COUNT(status) FOR status IN ([Shipped],[Pending],[Cancelled])) p;
```
**Why it works:** `FILTER` is 🐘's clean conditional aggregate; `PIVOT` is 🟦's dedicated operator
with hard-coded column values.

## ✅ Key Takeaways

- **Pivoting** rotates rows into columns for wide, report-friendly output.
- The **portable, flexible** technique is **conditional aggregation** (`CASE`/`FILTER` inside
  aggregates) — learn this first.
- Engine-specific: **🟦 `PIVOT`** (hard-coded columns) and **🐘 `crosstab`** (extension, declared
  columns).
- **`COUNT(CASE WHEN x THEN 1 ELSE 0 END)` is a bug** — drop the `ELSE` or use `SUM`.
- For **dynamic** pivots, pivot in the **app/BI tool** rather than fighting SQL.
