# Covering, Filtered & Included Indexes

## 🧠 Intuition

Three index refinements that turn a "good" index into a "great" one:

- **Covering index** — contains *every column the query needs*, so the database answers the query
  **entirely from the index** without touching the table (no key lookup / heap fetch).
- **Included columns (`INCLUDE`)** — add non-key columns to an index's leaf level just to cover
  queries, without bloating the searchable key.
- **Filtered / partial index** — indexes only a *subset* of rows (`WHERE active = 1`), making it
  smaller, faster, and cheaper to maintain.

> 💡 **Analogy — a complete catalog entry.** A plain index entry says "Acme → see the file cabinet."
> A *covering* entry says "Acme → Berlin, Germany, joined 2025" — everything you wanted is right
> there on the card, no trip to the cabinet. `INCLUDE` is adding those extra details to the card; a
> *filtered* index is keeping cards only for active customers.

## 🎯 The Problem — the key lookup tax

```sql
-- Index on (customer_id) only
SELECT customer_id, name, city FROM customers WHERE customer_id = 5;
```

The index finds the row by `customer_id`, but `name` and `city` aren't in it — so the engine does a
**key lookup** (🟦) / **heap fetch** (🐘) back to the table for each match. On many rows, those random
lookups dominate the cost. A **covering index** removes them.

## 💻 Covering indexes via INCLUDE

```sql
-- Add the SELECTed columns as INCLUDE so the index covers the query
-- 🟦 SQL Server
CREATE NONCLUSTERED INDEX ix_customers_cover
ON customers (customer_id)        -- key: what you search by
INCLUDE (name, city);             -- payload: extra columns to cover the SELECT

-- 🐘 PostgreSQL (INCLUDE supported since PG 11)
CREATE INDEX ix_customers_cover
ON customers (customer_id)
INCLUDE (name, city);
```

Now `SELECT customer_id, name, city FROM customers WHERE customer_id = 5` is satisfied **entirely
from the index** — an **index-only scan** (🐘) / **covered seek** (🟦), no table access.

### Key columns vs INCLUDE columns

| | Key columns `(...)` | INCLUDE columns |
|--|---------------------|-----------------|
| Used for | Searching, sorting, range (the `WHERE`/`ORDER BY`) | Only covering the `SELECT` |
| In the B-tree | At every level (searchable) | Only at the **leaf** |
| Order matters? | Yes | No |
| Bloat | Larger keys slow the whole tree | Cheaper — leaf only |

**Rule:** put columns you **filter/sort by** in the key; put columns you only **return** in
`INCLUDE`. Don't stuff everything into the key — it bloats the tree and slows searches.

## 💻 Filtered (🟦) / Partial (🐘) indexes

Index only the rows that matter:

```sql
-- 🟦 SQL Server: filtered index
CREATE NONCLUSTERED INDEX ix_orders_open
ON orders (customer_id)
INCLUDE (order_date)
WHERE status = 'Pending';          -- only index pending orders

-- 🐘 PostgreSQL: partial index
CREATE INDEX ix_orders_open
ON orders (customer_id)
WHERE status = 'Pending';
```

If 95% of orders are shipped/cancelled and you constantly query *pending* ones, a filtered/partial
index on just the pending rows is **a fraction of the size**, faster to scan, and cheaper to
maintain (writes to non-pending rows don't touch it). It's the perfect partner for **soft delete**
(`WHERE is_deleted = 0`) and **multi-tenant active rows**.

## ⚡ Under the Hood / Performance

- A covering index turns a "seek + N lookups" plan into a single **index-only** operation — often a
  10×+ improvement on selective-but-multi-row queries. Confirm via the
  [execution plan](04.Reading-Execution-Plans.md): the key-lookup/heap-fetch operator disappears.
- 🐘 index-only scans also require the page to be **all-visible** (visibility map up to date) — heavy
  write churn can force occasional heap visits until `VACUUM` updates the map.
- **Don't over-cover:** adding many `INCLUDE` columns enlarges the index (more storage, more write
  cost). Cover the *hot* queries, not every query.

## 🚫 Common mistakes

```sql
-- ❌ Putting return-only columns in the KEY (bloats the searchable tree)
CREATE INDEX ix ON customers (customer_id, name, city);   -- name/city aren't searched
-- ✅ key on what you search; INCLUDE the rest
CREATE INDEX ix ON customers (customer_id) INCLUDE (name, city);

-- ❌ A giant covering index that duplicates half the table
-- ✅ cover specific hot queries; measure storage/write impact

-- ❌ Filtered index whose WHERE doesn't match the query's predicate → not used
CREATE INDEX ix ON orders (customer_id) WHERE status = 'Pending';
SELECT ... WHERE status = 'Shipped';   -- won't use the filtered index
-- ✅ the query predicate must be compatible with the index filter

-- ❌ 🟦: filtered index gotchas (parameterized queries may not use them without the literal predicate)
```

## 🌍 Real-World Use

- **Covering indexes** for hot read endpoints: a dashboard query selecting 4 columns filtered by 1 —
  cover it and it flies.
- **Filtered/partial indexes** for soft delete (`WHERE is_deleted = 0`), active records, recent data,
  or any "small hot subset of a big table."
- **Index-only scans (🐘)** as the heap-world equivalent of covering — a key tuning technique.

## 🎯 Practice (with full solutions)

### 1. Eliminate the key lookup — `Medium`
**Task:** `SELECT customer_id, name, city FROM customers WHERE customer_id = ?` does a seek plus a
lookup for each row. Make it index-only.
**Solution:**
```sql
-- both engines
CREATE INDEX ix_customers_cover ON customers (customer_id) INCLUDE (name, city);
```
**Why it works:** with `name` and `city` in the index leaf, the engine returns everything from the
index — no key lookup / heap fetch. The query becomes a single covered/index-only operation.

### 2. Small index for a hot subset — `Medium`
**Task:** `orders` has 10M rows; 99% are closed. Queries constantly fetch *pending* orders by
customer. Build a small, fast index.
**Solution:**
```sql
-- 🟦 SQL Server
CREATE NONCLUSTERED INDEX ix_orders_pending ON orders (customer_id)
INCLUDE (order_date) WHERE status = 'Pending';
-- 🐘 PostgreSQL
CREATE INDEX ix_orders_pending ON orders (customer_id) WHERE status = 'Pending';
```
**Why it works:** the filtered/partial index covers only the ~1% pending rows — tiny, fast to scan,
and untouched by writes to closed orders. The query `WHERE status = 'Pending' AND customer_id = ?`
matches the filter and uses it.

## ✅ Key Takeaways

- A **covering index** answers a query entirely from the index — no key lookup / heap fetch.
- Use **`INCLUDE`** to add return-only columns to the leaf without bloating the searchable **key**:
  key = what you **filter/sort** by, INCLUDE = what you **return**.
- **Filtered (🟦) / partial (🐘)** indexes index only a subset of rows — smaller, faster, cheaper;
  ideal for soft delete and hot subsets. The query predicate must match the index filter.
- 🐘's **index-only scan** is the equivalent of covering (also needs the page all-visible).
- Don't over-cover or over-filter — target the **hot** queries.
