# SARGability

## 🧠 Intuition

**SARGable** = "**S**earch **ARG**ument **able**" — a `WHERE` predicate the database can satisfy with
an **index seek** instead of scanning every row. The killer rule: **don't wrap an indexed column in a
function or expression.** `WHERE YEAR(order_date) = 2025` forces the engine to compute `YEAR(...)` for
*every* row (a scan); `WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'` lets it
**seek** the index. Same result, wildly different speed.

> 💡 **Analogy — looking up a name in a phone book.** The book is sorted by last name. "Find SMITH"
> is instant — you seek. But "find everyone whose name *reversed* is HTIMS" forces you to read every
> entry and reverse it. Putting a function on the column is asking the database to do the reversed
> lookup: the sorted index becomes useless.

## 🎯 The Problem

```sql
-- ❌ Non-SARGable: function on the indexed column → full scan, even with an index on order_date
SELECT * FROM orders WHERE YEAR(order_date) = 2025;

-- ❌ Non-SARGable: column inside an expression
SELECT * FROM products WHERE unit_price * 1.2 > 12;

-- ❌ Non-SARGable: leading wildcard
SELECT * FROM customers WHERE name LIKE '%acme%';

-- ❌ Non-SARGable: implicit type conversion on the column (sneaky!)
SELECT * FROM customers WHERE phone = 5551234;   -- phone is VARCHAR → engine converts the column
```

Each forces the engine to evaluate something **per row**, defeating the index.

## 💻 Making predicates SARGable

The fix is always: **isolate the bare column on one side**, apply the transformation to the
*constant* instead.

```sql
-- ✅ Date range instead of YEAR() on the column
SELECT * FROM orders WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01';

-- ✅ Move the math to the constant side
SELECT * FROM products WHERE unit_price > 12 / 1.2;          -- = 10

-- ✅ Prefix search (uses the index); leading wildcard cannot
SELECT * FROM customers WHERE name LIKE 'Acme%';

-- ✅ Match the literal's type to the column (no implicit conversion on the column)
SELECT * FROM customers WHERE phone = '5551234';            -- string literal for a VARCHAR column
```

| ❌ Non-SARGable | ✅ SARGable rewrite |
|----------------|--------------------|
| `WHERE YEAR(d) = 2025` | `WHERE d >= '2025-01-01' AND d < '2026-01-01'` |
| `WHERE UPPER(name) = 'ACME'` | store/compare consistently, or index `UPPER(name)` (expression index) |
| `WHERE price * 1.2 > 12` | `WHERE price > 12/1.2` |
| `WHERE col + 1 = 10` | `WHERE col = 9` |
| `WHERE name LIKE '%x%'` | `LIKE 'x%'`, or full-text search |
| `WHERE CAST(id AS VARCHAR) = '5'` | `WHERE id = 5` |
| implicit conversion (`varchar = int`) | match the literal's type |

## 💻 When you *can't* rewrite — index the expression

If a transformation is genuinely required (case-insensitive search, a computed value), index the
**expression itself**:

```sql
-- 🐘 PostgreSQL: expression (functional) index
CREATE INDEX ix_customers_lower_name ON customers (LOWER(name));
SELECT * FROM customers WHERE LOWER(name) = 'acme';        -- now SARGable against the expression index

-- 🟦 SQL Server: persisted computed column + index (it has no direct expression index)
ALTER TABLE customers ADD name_lower AS LOWER(name) PERSISTED;
CREATE INDEX ix_customers_name_lower ON customers (name_lower);
SELECT * FROM customers WHERE name_lower = 'acme';
```

> A nice dialect difference: **🐘 supports expression indexes directly** (`CREATE INDEX ... ON t
> (LOWER(name))`); **🟦 doesn't** — you create a **persisted computed column** and index that (see
> [Computed Columns](../03-Modifying-Data-and-DDL/06.Computed-and-Generated-Columns.md)).

## ⚡ Under the Hood / Performance

- A SARGable predicate produces an **Index Seek**; a non-SARGable one produces a **Scan** + per-row
  function evaluation — you'll see the difference plainly in the
  [execution plan](04.Reading-Execution-Plans.md).
- **Implicit conversions are the sneakiest culprit:** comparing a `VARCHAR` column to a number (or an
  `NVARCHAR` parameter to a `VARCHAR` column) makes the engine convert the *column*, killing the
  index. The plan shows a `CONVERT_IMPLICIT` warning. Always match literal/parameter types to the
  column.
- `OR` across different columns and `NOT`/`<>` predicates are often non-SARGable too — sometimes
  rewritten as `UNION` of two SARGable queries.

## 🚫 Common mistakes

```sql
-- ❌ Function on the column (the #1 SARGability killer)
WHERE YEAR(order_date) = 2025
WHERE LOWER(email) = 'a@b.com'
WHERE LEFT(code, 3) = 'ABC'
-- ✅ range / expression index / prefix

-- ❌ Implicit conversion from a type mismatch
WHERE varchar_col = 123          -- converts the column
-- ✅ WHERE varchar_col = '123'

-- ❌ Leading wildcard for "contains" search → always a scan
WHERE description LIKE '%error%'
-- ✅ full-text search (see Specialized Data) for real "contains" queries

-- ❌ Math/concatenation on the column
WHERE salary / 12 > 500
-- ✅ WHERE salary > 6000
```

## 🌍 Real-World Use

SARGability is one of the highest-leverage everyday tuning skills. A report filtering `WHERE
YEAR(date) = ...` that scans 50M rows becomes instant when rewritten as a date range hitting an
index. Case-insensitive searches get expression indexes (🐘) or persisted-computed-column indexes
(🟦). And spotting an `CONVERT_IMPLICIT` in a plan — a hidden type mismatch silently scanning a
huge table — is a classic senior catch.

## 🎯 Practice (with full solutions)

### 1. Rewrite a date filter — `Easy`
**Task:** Make `WHERE YEAR(order_date) = 2025` use an index on `order_date`.
**Solution:**
```sql
SELECT * FROM orders WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01';
```
**Why it works:** the bare `order_date` column is compared to constants, so the engine can **seek**
the index for the range — no per-row `YEAR()` evaluation, no scan.

### 2. Case-insensitive search, SARGably — `Medium`
**Task:** Users search customers by name case-insensitively. `WHERE LOWER(name) = 'acme'` scans the
table. Fix it in both engines.
**Solution:**
```sql
-- 🐘 PostgreSQL: expression index
CREATE INDEX ix_customers_lower_name ON customers (LOWER(name));
SELECT * FROM customers WHERE LOWER(name) = 'acme';      -- now a seek on the expression index

-- 🟦 SQL Server: persisted computed column + index (no direct expression index)
ALTER TABLE customers ADD name_lower AS LOWER(name) PERSISTED;
CREATE INDEX ix_customers_name_lower ON customers (name_lower);
SELECT * FROM customers WHERE name_lower = 'acme';
```
**Why it works:** you can't avoid the `LOWER()` transformation, so you **index the transformed
value** — 🐘 directly via an expression index, 🟦 via a persisted computed column. The predicate now
matches the index and seeks.

## ✅ Key Takeaways

- **SARGable** predicates can use an **index seek**; non-SARGable ones force a **scan** + per-row
  evaluation.
- **Never wrap an indexed column in a function/expression** — apply the transformation to the
  **constant** instead (`YEAR(d)=2025` → date range).
- **Implicit type conversions** silently kill SARGability — match literal/parameter types to the
  column.
- **Leading-wildcard `LIKE '%x%'`** can't seek — use full-text search for "contains."
- When a transformation is unavoidable, **index the expression**: 🐘 expression index / 🟦 persisted
  computed column + index.
