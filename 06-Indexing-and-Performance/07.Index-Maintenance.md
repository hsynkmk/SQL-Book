# Index Maintenance

## 🧠 Intuition

Indexes degrade over time. As rows are inserted, updated, and deleted, index pages **fragment** —
the logical order drifts from the physical order, pages get half-empty, and reads do more I/O. On
PostgreSQL, MVCC's dead row versions cause **bloat**. Index maintenance — rebuilding/reorganizing
(🟦), `REINDEX`/`VACUUM` (🐘) — reclaims that efficiency. The flip side: **unused indexes** silently
tax every write and should be dropped.

> 💡 **Analogy — a library shelf over time.** As books are added, removed, and reshelved, gaps form
> and the order gets messy — finding things slows down. Periodically you tidy the shelves (rebuild)
> and remove books nobody borrows (drop unused indexes). A neglected shelf still works, just slowly.

## 📐 Fragmentation & bloat

- **Fragmentation (🟦):** logical page order ≠ physical order; pages partially full. Range scans read
  more pages than necessary.
- **Bloat (🐘):** MVCC leaves dead tuples in tables *and indexes*; until `VACUUM` reclaims them, the
  index is larger than its live data (see [MVCC vs Lock-Based](../05-Transactions-and-Concurrency/04.MVCC-vs-Lock-Based.md)).
- Both worsen with high `UPDATE`/`DELETE` churn and random-key inserts.

## 💻 🟦 SQL Server — rebuild vs reorganize

```sql
-- Check fragmentation
SELECT OBJECT_NAME(object_id), index_id, avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED')
WHERE avg_fragmentation_in_percent > 10;

-- Reorganize: light, online, for moderate fragmentation (~10–30%)
ALTER INDEX ix_orders_customer ON orders REORGANIZE;

-- Rebuild: heavy, rebuilds the whole index, for high fragmentation (>30%)
ALTER INDEX ix_orders_customer ON orders REBUILD;
ALTER INDEX ALL ON orders REBUILD WITH (ONLINE = ON);   -- online rebuild (Enterprise) = minimal blocking
```

| | REORGANIZE | REBUILD |
|--|------------|---------|
| Effort | Light (defrags leaf pages) | Heavy (recreates the index) |
| Blocking | Always online | Online only on Enterprise (else locks) |
| Updates stats? | No | **Yes** (full-scan stats as a bonus) |
| Use when | 10–30% fragmented | >30% fragmented |

## 💻 🐘 PostgreSQL — VACUUM, REINDEX, and bloat

```sql
-- VACUUM reclaims dead tuples (autovacuum usually does this automatically)
VACUUM orders;                    -- reclaim space for reuse (non-blocking)
VACUUM (ANALYZE) orders;          -- vacuum + refresh statistics
VACUUM FULL orders;               -- rewrites the table compactly — but takes an EXCLUSIVE LOCK!

-- REINDEX rebuilds bloated indexes
REINDEX INDEX ix_orders_customer;
REINDEX TABLE orders;
REINDEX INDEX CONCURRENTLY ix_orders_customer;   -- PG 12+: rebuild without blocking writes

-- Check bloat / dead tuples
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;
```

> ⚠️ **`VACUUM FULL` and plain `REINDEX` take heavy locks** — don't run them on a busy table during
> peak hours. Use **`REINDEX ... CONCURRENTLY`** (PG 12+) or the community **`pg_repack`** tool for
> online compaction. Regular (non-FULL) `VACUUM` is non-blocking and is what autovacuum runs.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Task | 🟦 SQL Server | 🐘 PostgreSQL |
|------|--------------|---------------|
| Light defrag | `ALTER INDEX ... REORGANIZE` | (autovacuum reclaims; no direct "reorganize") |
| Full rebuild | `ALTER INDEX ... REBUILD` | `REINDEX` (use `CONCURRENTLY`) |
| Reclaim dead space | n/a (no MVCC bloat) | **`VACUUM`** (autovacuum) |
| Compact table | rebuild clustered index | `VACUUM FULL` / `pg_repack` |
| Update stats | `UPDATE STATISTICS` (rebuild does it) | `ANALYZE` (autovacuum does it) |
| Automate | Maintenance Plans / Agent jobs / Ola Hallengren scripts | autovacuum + `pg_cron` |

> The key difference: **🐘's main maintenance is VACUUM** (because MVCC creates dead tuples), which is
> mostly automatic via **autovacuum** — your job is to ensure it keeps up. **🟦's main maintenance is
> defrag + stats**, scheduled via jobs. Neither needs the other's primary concern.

## 💻 Finding & dropping unused indexes

Every index slows writes. Periodically find ones nobody reads:

```sql
-- 🟦 SQL Server: indexes with writes but ~no reads
SELECT OBJECT_NAME(s.object_id) AS tbl, i.name, s.user_seeks, s.user_scans, s.user_updates
FROM sys.dm_db_index_usage_stats s
JOIN sys.indexes i ON i.object_id = s.object_id AND i.index_id = s.index_id
WHERE s.user_seeks + s.user_scans + s.user_lookups = 0 AND s.user_updates > 0;

-- 🐘 PostgreSQL: indexes never scanned
SELECT relname, indexrelname, idx_scan FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY relname;
```

An index with thousands of `updates` but zero `seeks/scans` is pure write overhead — a candidate to
drop (after confirming it's not for a rare-but-critical query or a constraint).

## ⚖️ How often to maintain

- **Autovacuum (🐘):** keep it **on and tuned** — it's the default and handles most bloat. Increase
  aggressiveness on high-churn tables; watch `n_dead_tup`.
- **🟦 rebuilds:** schedule based on **fragmentation %**, not blindly nightly — only reorganize/rebuild
  what's actually fragmented (the Ola Hallengren scripts are the community standard).
- **Don't over-maintain:** rebuilding lightly-fragmented indexes wastes I/O and (🟦) can bloat the
  transaction log. Maintain by threshold.

## 🚫 Common mistakes

```sql
-- ❌ 🐘: running VACUUM FULL on a busy table mid-day → exclusive lock → outage
-- ✅ rely on autovacuum; use REINDEX CONCURRENTLY / pg_repack for online compaction

-- ❌ 🟦: rebuilding ALL indexes nightly regardless of fragmentation → wasted I/O, log bloat
-- ✅ maintain by fragmentation threshold (reorganize 10–30%, rebuild >30%)

-- ❌ Letting unused indexes pile up → every INSERT/UPDATE pays for indexes nobody reads
-- ✅ review usage stats; drop truly-unused indexes

-- ❌ 🐘: ignoring autovacuum falling behind on a high-churn table → runaway bloat
-- ✅ tune autovacuum_vacuum_scale_factor/cost limits; monitor dead tuples
```

## 🌍 Real-World Use

Index maintenance is core DBA work. On PostgreSQL it's mostly **"keep autovacuum healthy"** plus the
occasional `REINDEX CONCURRENTLY`/`pg_repack` for badly bloated objects. On SQL Server it's
**scheduled, threshold-based reorganize/rebuild + statistics updates** (usually via Ola Hallengren's
scripts) plus periodic **unused-index cleanup**. Both pay back in steady, predictable query
performance.

## 🎯 Practice (with full solutions)

### 1. Maintain by threshold (🟦) — `Medium`
**Task:** Reorganize moderately fragmented indexes and rebuild heavily fragmented ones — not
everything.
**Solution:**
```sql
-- Inspect, then act by threshold:
-- avg_fragmentation_in_percent BETWEEN 10 AND 30  → REORGANIZE
-- avg_fragmentation_in_percent > 30               → REBUILD (ONLINE on Enterprise)
ALTER INDEX ix_orders_customer ON orders REORGANIZE;     -- moderate
ALTER INDEX ix_orders_date ON orders REBUILD WITH (ONLINE = ON);   -- heavy
```
**Why it works:** matching the operation to the fragmentation level avoids wasting I/O on
lightly-fragmented indexes, and REBUILD also refreshes statistics for free.

### 2. Address PostgreSQL bloat safely — `Medium`
**Task:** A high-churn 🐘 table's indexes are heavily bloated and queries slowed. Fix it without an
outage.
**Solution:**
```sql
-- Confirm autovacuum is keeping up; for already-bloated indexes, rebuild online:
REINDEX INDEX CONCURRENTLY ix_orders_customer;    -- PG 12+, no write blocking
-- For severe table+index bloat, use pg_repack (online) rather than VACUUM FULL (locks).
-- And tune autovacuum so it doesn't fall behind again:
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02);
```
**Why it works:** `REINDEX CONCURRENTLY`/`pg_repack` rebuild without the exclusive lock of `VACUUM
FULL`, so the busy table stays available; tuning autovacuum prevents the bloat from recurring.

## ✅ Key Takeaways

- Indexes **fragment** (🟦) and **bloat** (🐘) over time, slowing reads — maintenance reclaims
  efficiency.
- **🟦:** `REORGANIZE` (light, 10–30%) vs `REBUILD` (heavy, >30%; refreshes stats); maintain **by
  fragmentation threshold**, scheduled.
- **🐘:** **VACUUM** (mostly automatic via **autovacuum**) reclaims MVCC dead tuples; `REINDEX
  CONCURRENTLY`/`pg_repack` for bloated indexes — avoid the locking `VACUUM FULL` on busy tables.
- **Drop unused indexes** — they tax every write for no read benefit.
- Don't over-maintain; keep autovacuum tuned (🐘) and maintain by threshold (🟦).
