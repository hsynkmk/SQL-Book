# Reading Execution Plans

## 🧠 Intuition

When you submit a query, the **optimizer** decides *how* to run it — which indexes to use, which
join algorithm, what order — and produces an **execution plan**. Reading that plan is how you move
from guessing about performance to *knowing*. It tells you exactly why a query is slow: a scan that
should be a seek, a missing index, a bad row estimate, an expensive sort.

> 💡 **Analogy — GPS route details.** You asked to "get to the airport" (your query). The GPS (the
> optimizer) picks a route (the plan). The turn-by-turn directions with time estimates are the
> execution plan — and reading them shows you *why* it's taking 40 minutes (it routed you through
> downtown / a table scan) and where to fix it.

## 📐 Estimated vs actual plans

- **Estimated plan:** what the optimizer *thinks* it'll do, based on statistics — without running the
  query. Fast to get.
- **Actual plan:** the real plan *with real row counts and timings* — gathered by executing the
  query. **More valuable** for diagnosis, because the gap between *estimated* and *actual* rows is
  often the root cause of a bad plan.

## 💻 Getting the plan

```sql
-- 🟦 SQL Server
-- In SSMS / Azure Data Studio: "Include Actual Execution Plan" (Ctrl+M), then run.
SET STATISTICS IO, TIME ON;     -- also see logical reads + CPU/elapsed time
SELECT ... ;
SET STATISTICS IO, TIME OFF;
-- Text/XML plan:
SET SHOWPLAN_ALL ON;            -- estimated, no execution
```
```sql
-- 🐘 PostgreSQL
EXPLAIN SELECT ...;                              -- estimated plan
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;           -- ACTUAL plan: real rows, timing, buffer reads
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;
```

> **`EXPLAIN (ANALYZE, BUFFERS)`** is the 🐘 workhorse — it runs the query and shows actual rows vs
> estimated, timing per node, and how many pages were read from cache vs disk. The 🟦 equivalent is
> the **actual execution plan** + `SET STATISTICS IO, TIME ON`.

## 📐 Reading a plan — what to look for

Plans are trees of **operators**; data flows from the leaves up to the root. Key operators:

| Operator | Good or bad? | Meaning |
|----------|--------------|---------|
| **Index Seek** | 👍 | Jumped straight to matching rows via a B-tree |
| **Index Scan** | 🤔 | Read the whole index (fine if you need most rows) |
| **Table/Heap Scan** / **Seq Scan** (🐘) | ⚠️ on big tables | Read every row — often a missing-index sign |
| **Key Lookup** (🟦) / **Heap Fetch** | ⚠️ if frequent | Index didn't cover; fetching the rest of the row |
| **Nested Loops** join | 👍 small/indexed | Good for few rows with an index on the inner side |
| **Hash Match / Hash Join** | 👍 large unindexed | Builds a hash table; good for big equality joins |
| **Merge Join** | 👍 pre-sorted | Both inputs already sorted |
| **Sort** | ⚠️ expensive | Sorting a big set (often avoidable with an index) |

**The three biggest red flags:**
1. A **scan** where a **seek** was expected on a large table → missing or unusable (non-SARGable)
   index.
2. A large gap between **estimated and actual rows** → stale [statistics](06.Statistics-and-Cardinality.md)
   or a non-sargable predicate confusing the optimizer.
3. An expensive **Sort** or **Hash** spilling to disk → memory pressure or a missing supporting index.

## 💻 A worked example

```sql
-- 🐘 PostgreSQL
EXPLAIN (ANALYZE, BUFFERS)
SELECT name FROM customers WHERE city = 'Berlin';
```
Before an index:
```
Seq Scan on customers  (cost=0.00..18.50 rows=2 width=10) (actual time=0.02..0.31 rows=2 loops=1)
  Filter: (city = 'Berlin')
  Rows Removed by Filter: 998      ← read 1000 rows to return 2 (a scan)
```
After `CREATE INDEX ix_customers_city ON customers (city);`:
```
Index Scan using ix_customers_city on customers  (actual time=0.01..0.02 rows=2 loops=1)
  Index Cond: (city = 'Berlin')    ← jumped straight to the 2 matching rows (a seek)
```
The "Rows Removed by Filter: 998" is the smoking gun — the index turns a 1000-row scan into a
2-row seek.

## 📐 Cost, rows, and width

Each operator shows an estimated **cost** (the optimizer's relative effort unit — not milliseconds),
estimated **rows**, and **width** (bytes per row). Focus on:
- **Actual rows vs estimated rows** — big mismatches mean the optimizer was misled (bad stats /
  non-sargable predicate) and likely chose a poor plan.
- **The most expensive operator** (highest cost / time) — that's where to focus tuning.
- **Reads** (`STATISTICS IO` logical reads / 🐘 `BUFFERS` shared hits & reads) — high reads on a small
  result = inefficient access.

## 🚫 Common mistakes

```sql
-- ❌ Tuning by guesswork instead of reading the plan
-- ✅ always EXPLAIN ANALYZE (🐘) / actual plan (🟦) first — let the plan tell you what's slow

-- ❌ Trusting the estimated plan when estimates are wildly off
-- ✅ get the ACTUAL plan; compare estimated vs actual rows

-- ❌ Panicking at any "Scan" — a scan on a tiny table (or when you need most rows) is fine
-- ✅ scans matter on BIG tables when you wanted few rows

-- ❌ Ignoring "Rows Removed by Filter" (🐘) / huge logical reads (🟦) — the clearest waste signals
```

## 🌍 Real-World Use

Reading plans is the core diagnostic loop of SQL performance: a query is slow → capture its **actual
plan** → find the expensive operator (scan, lookup, sort, estimate gap) → fix it (add/cover an index,
make the predicate [SARGable](05.SARGability.md), update [statistics](06.Statistics-and-Cardinality.md))
→ re-check the plan to prove the improvement. Every senior SQL developer lives in the execution plan.

## 🎯 Practice (with full solutions)

### 1. Diagnose a slow filter — `Easy`
**Task:** `SELECT name FROM customers WHERE city = 'Berlin'` is slow on a big table. Use the plan to
find and fix the cause.
**Solution:**
```sql
-- 🐘: EXPLAIN (ANALYZE, BUFFERS) SELECT name FROM customers WHERE city = 'Berlin';
-- See "Seq Scan ... Rows Removed by Filter: <many>" → missing index. Fix:
CREATE INDEX ix_customers_city ON customers (city);
-- Re-run EXPLAIN → now "Index Scan ... Index Cond: (city = 'Berlin')" (a seek).
-- 🟦: enable Actual Execution Plan → Table/Clustered Index Scan → add the index → becomes a Seek.
```
**Why it works:** the plan reveals the scan and the "rows removed" waste; the index converts it into
a seek, which the re-run plan confirms.

### 2. Spot the estimate gap — `Medium`
**Task:** A query's actual plan shows an operator estimated at 1 row but actually producing 2
million, after which an expensive nested-loop join runs. What's happening and what do you check?
**Solution:** the optimizer **under-estimated rows** (estimated 1, actual 2M) and therefore chose a
**nested loops** join that's catastrophic at that scale. Likely causes: stale
[statistics](06.Statistics-and-Cardinality.md), or a **non-sargable** predicate (a function on a
column) the optimizer couldn't estimate. Fix by **updating statistics** and **making the predicate
sargable**; the optimizer should then estimate correctly and pick a hash join.
**Why it works:** estimate-vs-actual gaps drive bad join/operator choices — fixing the estimate (the
root cause) fixes the plan, rather than band-aiding the symptom.

## ✅ Key Takeaways

- The **execution plan** shows *how* the optimizer runs your query — the key to diagnosing slowness.
- Prefer the **actual plan**: **🐘 `EXPLAIN (ANALYZE, BUFFERS)`** / **🟦 actual plan + `SET STATISTICS
  IO, TIME ON`**.
- Red flags: a **scan where a seek belongs** (big table), frequent **key lookups**, expensive
  **sorts/hashes**, and **estimated-vs-actual row gaps**.
- Focus on the **most expensive operator** and the **estimate gap** — they point to the fix
  (index, SARGability, statistics).
- Always **re-check the plan** after a change to prove it helped.
