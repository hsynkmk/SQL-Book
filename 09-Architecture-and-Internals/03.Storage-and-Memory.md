# Storage & Memory

## 🧠 Intuition

Databases live on **slow disk** but work in **fast memory**. The whole performance game is: keep the
data you need in memory (the cache), write changes durably without waiting for slow random disk I/O
(the write-ahead log), and periodically reconcile the two (checkpoints). Understanding **pages**,
**caching**, **WAL**, and **checkpoints** explains both why databases are fast *and* how they never
lose committed data.

> 💡 **Analogy — a desk and a filing cabinet.** Working on paper at your desk (memory) is fast; the
> filing cabinet (disk) is slow. You keep frequently-used files on the desk (cache), jot every change
> in a running notebook first (the log) so nothing's lost if you're interrupted, and periodically
> file the desk's papers back into the cabinet (checkpoint).

## 📐 Pages — the unit of I/O

Both engines store data in fixed-size **pages** (the smallest unit read/written): **8 KB** in both
SQL Server and PostgreSQL. A row lives in a page; reading "one row" actually reads its whole page.
This is why **narrow rows** (fewer/smaller columns) are faster — more rows fit per page, so the same
query reads fewer pages.

- **🟦:** 8 KB pages, grouped into 64 KB **extents**; stored in `.mdf`/`.ndf` data files.
- **🐘:** 8 KB pages in **heap** files (split into 1 GB segments); oversized values go to **TOAST**.

## 📐 Caching — keeping hot data in memory

Reads check memory first; a **cache hit** avoids disk entirely.

| | 🟦 SQL Server | 🐘 PostgreSQL |
|--|--------------|---------------|
| DB cache | **Buffer pool** (most of RAM) | **`shared_buffers`** (~25% of RAM) |
| Also uses OS cache? | Minimal (manages its own) | **Yes — heavily** (effective cache = shared_buffers + OS page cache) |
| "Is it working?" metric | Page Life Expectancy, buffer cache hit ratio | `pg_stat_database` hit ratio; `pg_buffercache` |
| Per-op work memory | (workspace memory) | **`work_mem`** (per sort/hash, per query step) |

A high cache hit ratio means most reads are served from RAM. Cache **misses** cause **physical
reads** (slow disk I/O) — the thing you minimize via memory sizing, good indexes, and narrow
projections.

## 📐 Write-Ahead Logging (WAL) — durability without slow writes

Here's the clever part. When you `COMMIT`, the database does **not** immediately write the changed
data pages to their final (random) locations on disk — that would be slow. Instead:

1. It writes a **log record** describing the change to the **sequential** transaction log (🟦 `.ldf` /
   🐘 WAL), and **flushes that log to disk** before `COMMIT` returns.
2. The actual data pages stay modified ("dirty") in memory for now.
3. A background **checkpoint** later writes the dirty data pages to the data files.

```mermaid
graph LR
    A[COMMIT] --> B[Write log record to sequential log + flush]
    B --> C[Return success to client]
    C --> D[Dirty data pages stay in memory]
    D --> E[Checkpoint: flush dirty pages to data files later]
```

**Why this is brilliant:** sequential log writes are fast (no random seeks), so commits are quick.
And durability holds — if the server crashes, **crash recovery** replays the log from the last
checkpoint to redo committed changes and undo uncommitted ones. **You never lose a committed
transaction**, even though its data pages hadn't been written to their final spots yet.

| Term | 🟦 SQL Server | 🐘 PostgreSQL |
|------|--------------|---------------|
| The log | Transaction log (`.ldf`) | **WAL** (`pg_wal`) |
| Principle | Write-ahead logging | Write-ahead logging |
| Reconcile to data files | **Checkpoint** | **Checkpoint** |
| Recovery | Redo/undo from log | Replay WAL from last checkpoint |
| Powers replication/PITR | Log shipping / Always On | WAL streaming / PITR |

## 📐 Checkpoints — reconciling memory and disk

A **checkpoint** flushes dirty pages from memory to the data files and records a recovery point.
Benefits: bounds crash-recovery time (recovery only replays log since the last checkpoint) and frees
the log for reuse/archival. Checkpoints cause an I/O spike; both engines spread them out (🐘
`checkpoint_completion_target`, 🟦 indirect checkpoints) to avoid stalls.

## ⚖️ Practical implications

- **Narrow rows = fewer pages = less I/O.** Avoid `SELECT *`; right-size types; this is *physical*
  performance, not just style.
- **Cache is king.** Enough RAM to hold the working set turns physical reads into memory reads.
  Monitor the hit ratio.
- **Log on fast storage.** The transaction log/WAL is written on every commit — put it on fast,
  low-latency storage; a slow log = slow commits.
- **Sequential vs random I/O.** The log is sequential (fast); data-file reads/writes are often random
  (slow) — which is why caching and the WAL design matter so much.

## 🚫 Common mistakes

```text
❌ Putting the transaction log/WAL on slow storage → every commit waits on it → slow writes.
✅ fast, dedicated, low-latency storage for the log.

❌ Under-provisioning RAM → constant cache misses → physical reads dominate → slow everything.
✅ size memory to hold the working set; watch the cache hit ratio.

❌ SELECT * pulling wide rows → more pages read per query → more I/O.
✅ project only needed columns (also enables covering indexes).

❌ Ignoring checkpoint I/O spikes → periodic stalls.
✅ spread checkpoints (completion target / indirect checkpoints).
```

## 🌍 Real-World Use

This model underlies every performance and reliability decision: why adding RAM often fixes "slow
database" (more cache), why the log disk's latency caps your write throughput, why `SELECT *` is
slow at scale (more pages), and why you never lose committed data on a crash (WAL + recovery). It's
also the foundation for **replication** and **point-in-time recovery**, which ship/replay the log.

## 🎯 Practice (with full solutions)

### 1. Explain durability without slow writes — `Medium`
**Task:** How can a database commit quickly yet guarantee the change survives a crash, if it doesn't
immediately write the data pages to disk?
**Solution:** It uses **write-ahead logging**: on `COMMIT`, it writes a **log record** to the
**sequential** transaction log/WAL and flushes *that* to disk (fast — no random seeks), while the
modified data pages stay dirty in memory. If the server crashes, **recovery replays the log** from
the last checkpoint to redo committed changes. So the commit is fast (sequential log write) and
durable (the log can reconstruct the change), even before the data pages reach their final spots.
**Why it works:** decoupling durability (sequential log) from data placement (random writes, done
lazily at checkpoint) gives both speed and safety.

### 2. Tune for I/O — `Easy`
**Task:** A write-heavy database has slow commits. The data files are on fast SSD but the transaction
log is on a slow shared HDD. What's the fix?
**Solution:** Move the **transaction log/WAL to fast, low-latency storage**. Commits flush the log
synchronously, so the log disk's latency directly limits commit speed — fast data files don't help if
the log is slow.
**Why it works:** every commit waits on the log write; the log is the throughput bottleneck for
writes, so its storage latency matters most.

## ✅ Key Takeaways

- Data is stored/read in **8 KB pages** — **narrow rows = fewer pages = less I/O**.
- **Caching** (🟦 buffer pool / 🐘 shared_buffers + OS cache) keeps hot data in RAM; maximize the **hit
  ratio**.
- **Write-ahead logging** makes commits **fast and durable**: write the change to the **sequential
  log** first, flush on commit; data pages are written later by a **checkpoint**.
- A crash replays the log from the last checkpoint — **committed data is never lost**.
- Put the **log on fast storage**; provision enough **RAM** for the working set.
