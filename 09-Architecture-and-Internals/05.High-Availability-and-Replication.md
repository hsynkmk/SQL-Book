# High Availability & Replication

## 🧠 Intuition

A single database server *will* fail eventually — hardware dies, disks fill, datacenters lose power.
**High Availability (HA)** keeps the database running through failures (automatic failover to a
standby). **Disaster Recovery (DR)** recovers after a catastrophe (a copy in another region).
**Replication** is the mechanism underneath both: continuously copying data to one or more standby
servers, usually by **shipping the transaction log/WAL**.

> 💡 **Analogy — a co-pilot and a backup flight plan.** HA is the co-pilot ready to take the controls
> instantly if the pilot is incapacitated (automatic failover). DR is the backup aircraft waiting at
> another airport in case the whole plane is lost (regional recovery). Replication is the constant
> radio link keeping the co-pilot and backup up to date.

## 📐 Key concepts

- **Primary** — the active server handling writes.
- **Standby / replica / secondary** — a copy kept in sync; can be promoted to primary on failover.
- **Synchronous vs asynchronous replication:**
  - **Synchronous** — commit waits until the standby has the change → **zero data loss** (RPO=0) but
    slower writes (and stalls if the standby is down).
  - **Asynchronous** — commit returns immediately; standby catches up → fast writes but possible
    **small data loss** on failover (the lag window).
- **RPO** (Recovery Point Objective) = how much data you can afford to lose; **RTO** (Recovery Time
  Objective) = how fast you must be back up. These drive your HA/DR design.
- **Failover** — promoting a standby to primary. **Automatic** (fast, needs a quorum/witness) or
  **manual**.

## 💻 🟦 SQL Server — Always On & friends

| Option | What it does |
|--------|--------------|
| **Always On Availability Groups (AGs)** | The flagship: a group of databases replicated to several replicas, with **automatic failover** and **readable secondaries** (offload reads). Sync or async replicas. |
| **Failover Cluster Instances (FCI)** | Instance-level failover over **shared storage** (the whole instance moves to another node). |
| **Log Shipping** | Periodically ships + restores transaction-log backups to a warm standby (simple DR, larger RPO). |
| **Replication** (transactional/merge/snapshot) | Object-level data distribution (e.g. push some tables to other servers) — more for data distribution than HA. |

```sql
-- Conceptual: an AG with a sync replica (auto-failover) + an async DR replica in another region
-- Configured via SSMS wizard or T-SQL; readable secondary serves reporting:
-- ApplicationIntent=ReadOnly routes read-only connections to a readable secondary.
```

Readable secondaries are a big win — route reporting/read traffic there (see
[Scaling Out](../07-Partitioning-and-Scale/03.Scaling-Out.md)).

## 💻 🐘 PostgreSQL — streaming & logical replication

| Option | What it does |
|--------|--------------|
| **Streaming (physical) replication** | Ships **WAL** to standbys byte-for-byte → **hot standbys** that serve read-only queries. Sync or async. The standard HA mechanism. |
| **Logical replication** | Replicates **selected tables** via logical decoding (publish/subscribe). Works **across versions** and for partial replication, zero-downtime upgrades, and selective data distribution. |
| **Patroni / repmgr / pg_auto_failover** | External tools that add **automatic failover** + cluster management on top of streaming replication (PostgreSQL core gives the replication; these add the orchestration). |
| **Point-in-time recovery (PITR)** | Base backup + archived WAL → restore to any moment (see [Backup & Restore](../11-Operations/01.Backup-and-Restore.md)). |

```sql
-- 🐘 logical replication (publish/subscribe) — replicate specific tables
-- On primary:
CREATE PUBLICATION my_pub FOR TABLE orders, customers;
-- On replica:
CREATE SUBSCRIPTION my_sub CONNECTION 'host=primary dbname=shop' PUBLICATION my_pub;
```

> Important nuance: **PostgreSQL core doesn't include automatic failover** — streaming replication
> gives you the replicas, but you add **Patroni** (or repmgr / pg_auto_failover / a cloud provider's
> managed service) for automatic promotion and quorum. SQL Server's Always On has automatic failover
> built in.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Aspect | 🟦 SQL Server | 🐘 PostgreSQL |
|--------|--------------|---------------|
| Primary HA | **Always On AGs** (auto-failover, readable secondaries) | **Streaming replication** + **Patroni** (for auto-failover) |
| Physical replication | AG / FCI | streaming (WAL) |
| Logical/partial | Transactional replication | **Logical replication** (cross-version, selective) |
| Auto-failover | **Built-in** (AG with quorum/witness) | **External tool** (Patroni/repmgr/cloud) |
| Readable standby | Readable secondaries | Hot standbys (read-only) |
| DR | Async AG replica / Log Shipping | Async streaming / WAL archiving + PITR |
| Cloud managed | Azure SQL (HA built in) | RDS/Aurora/Cloud SQL (HA built in) |

> Both achieve the same goals; the **packaging differs**. 🟦 bundles auto-failover into Always On; 🐘
> provides robust replication and relies on external orchestration (Patroni) or managed cloud
> services for automatic failover.

## ⚖️ Designing HA/DR

1. **Define RPO/RTO** from the business. Zero data loss? → synchronous replication. Minutes of loss
   OK? → asynchronous (faster, simpler).
2. **HA within a region** — a synchronous standby with automatic failover (AG / Patroni) for local
   resilience.
3. **DR across regions** — an asynchronous replica far away for disaster recovery (regional outage).
4. **Test failover regularly** — an untested failover is a hope, not a plan. Practice promoting the
   standby.
5. **Often: just use managed cloud** (Azure SQL, Aurora, Cloud SQL) — they build HA/DR in, sparing you
   the machinery.

## 🚫 Common mistakes

```text
❌ Synchronous replication to a distant region → every commit waits on cross-region latency → slow.
✅ sync standby nearby (HA); async replica far away (DR).

❌ Assuming PostgreSQL streaming replication = automatic failover → it doesn't (needs Patroni/etc.).
✅ add an orchestration tool or use managed cloud for auto-failover.

❌ Never testing failover → discovering it's broken during a real outage.
✅ rehearse failover regularly.

❌ Treating a read replica as a backup → replication faithfully copies a DROP TABLE too!
✅ replicas are for HA/reads, NOT backups — keep real backups (next module).
```

> ⚠️ A replica is **not a backup.** Replication copies *everything*, including a mistaken
> `DELETE`/`DROP`. You still need point-in-time backups to recover from human/application errors.

## 🌍 Real-World Use

Production databases run with a **synchronous standby for HA** (automatic failover within the region)
and often an **asynchronous replica in another region for DR**, plus **readable secondaries** for
reporting. Most teams now get this via **managed cloud** (Azure SQL / Aurora / Cloud SQL) rather than
operating Always On or Patroni themselves. The constant: define RPO/RTO, replicate accordingly, keep
real backups, and **test failover**.

## 🎯 Practice (with full solutions)

### 1. Design for RPO=0 + regional DR — `Medium`
**Task:** A bank needs zero data loss for HA and recovery from a full-region outage. Sketch the
topology for each engine.
**Solution:**
- **🟦:** an **Always On AG** with a **synchronous** replica in the same region (automatic failover,
  RPO=0) **plus** an **asynchronous** replica in another region for DR. Readable secondary for reports.
- **🐘:** **synchronous streaming replication** to a same-region standby (RPO=0) orchestrated by
  **Patroni** for automatic failover, **plus** an **asynchronous** streaming replica in another
  region for DR; WAL archiving for PITR.
**Why it works:** synchronous-nearby gives zero-loss HA without crippling latency; async-far gives DR
without slowing commits; Patroni (🐘) supplies the auto-failover that Always On (🟦) has built in.

### 2. Why a replica isn't a backup — `Easy`
**Task:** "We have a hot standby, so we don't need backups." What's wrong?
**Solution:** Replication copies **every** change, including a destructive `DROP TABLE customers` or a
buggy mass `UPDATE` — the standby will faithfully apply it too, instantly corrupting both copies. A
replica protects against **hardware/server failure**, not **human/application error**. You still need
**point-in-time backups** to roll back to before the mistake.
**Why it matters:** HA and backups solve *different* problems; you need both.

## ✅ Key Takeaways

- **HA** = survive failures (auto-failover to a standby); **DR** = recover from disasters (remote
  copy); **replication** (log/WAL shipping) underpins both.
- **Sync** replication = zero loss (RPO=0) but slower; **async** = fast but small loss on failover.
- **🟦 Always On AGs** include **built-in auto-failover** + readable secondaries; **🐘 streaming
  replication** needs **Patroni**/managed cloud for auto-failover; **logical replication** does
  selective/cross-version copies.
- Design from **RPO/RTO**: sync-nearby for HA, async-far for DR, **test failover**.
- **A replica is not a backup** — keep real point-in-time backups too.
