# Maintenance

## 🧠 Intuition

A database that's never maintained slowly degrades: indexes fragment, statistics go stale, PostgreSQL
accumulates dead-tuple bloat, and old data piles up. **Maintenance** is the routine housekeeping that
keeps performance steady — and the two engines have *different primary chores* because of their
different architectures: 🟦's main jobs are **index defrag + statistics**; 🐘's main job is **VACUUM**
(because of MVCC).

> 💡 **Analogy — car servicing.** You don't drive a car for 200,000 km without oil changes, tire
> rotations, and tune-ups. A database needs the same: keep the indexes tidy, the statistics current,
> reclaim wasted space, and prune old junk. Skip it and performance degrades until something breaks.

## 📐 The maintenance chores

| Chore | 🟦 SQL Server | 🐘 PostgreSQL |
|-------|--------------|---------------|
| Reclaim dead space (MVCC) | n/a | **VACUUM** (mostly **autovacuum**) |
| Defragment indexes | REORGANIZE / REBUILD | (autovacuum + `REINDEX` for bloat) |
| Update statistics | `UPDATE STATISTICS` (or rebuild does it) | **ANALYZE** (autovacuum's auto-analyze) |
| Prevent ID wraparound | n/a | autovacuum **freeze** (anti-wraparound) |
| Integrity check | `DBCC CHECKDB` | `amcheck` / `pg_amcheck` |
| Purge/archive old data | partition drop / delete | partition drop / delete |

## 💻 🐘 PostgreSQL — VACUUM is the headline

Because [MVCC](../05-Transactions-and-Concurrency/04.MVCC-vs-Lock-Based.md) leaves dead row versions on
every `UPDATE`/`DELETE`, **VACUUM** is essential — it reclaims that space and updates the visibility
map. **Autovacuum** runs it automatically; your job is to ensure it **keeps up**.

```sql
VACUUM;                          -- reclaim dead tuples (non-blocking)
VACUUM (ANALYZE) orders;         -- vacuum + refresh statistics in one go
ANALYZE orders;                  -- just refresh statistics

-- Check whether autovacuum is keeping up
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

-- Tune autovacuum to be more aggressive on a high-churn table
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_analyze_scale_factor = 0.01);
```

> ⚠️ Two VACUUM-specific dangers:
> - **Bloat:** if autovacuum can't keep up (or a long-running transaction blocks it), dead tuples
>   accumulate → tables/indexes bloat → queries slow → disk grows. **Keep transactions short** and
>   tune autovacuum.
> - **Transaction ID wraparound:** PostgreSQL must periodically "freeze" old rows to avoid XID
>   wraparound (which would cause data loss). Autovacuum handles this — but if it's disabled or far
>   behind, you get scary "must be vacuumed within N transactions" warnings. **Never disable
>   autovacuum.**

`VACUUM FULL` reclaims space to the OS but takes an **exclusive lock** — use `pg_repack` or
`REINDEX CONCURRENTLY` for online compaction instead (see
[Index Maintenance](../06-Indexing-and-Performance/07.Index-Maintenance.md)).

## 💻 🟦 SQL Server — index defrag + statistics + integrity

SQL Server has no MVCC bloat, so its chores are **fragmentation**, **statistics**, and **integrity
checks**, typically scheduled via SQL Server Agent / **Ola Hallengren's maintenance scripts** (the
community standard):

```sql
-- Defrag by fragmentation threshold (reorganize 10–30%, rebuild >30%)
ALTER INDEX ix_orders_customer ON orders REORGANIZE;
ALTER INDEX ALL ON orders REBUILD WITH (ONLINE = ON);

-- Update statistics
UPDATE STATISTICS orders WITH FULLSCAN;

-- Integrity check — detects corruption EARLY
DBCC CHECKDB('shop') WITH NO_INFOMSGS;
```

> **Run `DBCC CHECKDB` regularly** — it detects page corruption (from disk/hardware issues) before it
> spreads or gets backed up. Finding corruption early, while you still have a clean backup, is the
> difference between a quick restore and a catastrophe.

## ⚖️ Building a maintenance plan

A healthy routine (automate via [Automation](04.Automation.md)):
- **Daily:** statistics updates / ANALYZE (where auto isn't enough); log/backup checks.
- **Weekly:** index reorganize/rebuild by threshold (🟦); confirm autovacuum is keeping up (🐘);
  `DBCC CHECKDB` / `amcheck`.
- **Ongoing:** autovacuum tuned (🐘); monitor bloat, fragmentation, dead tuples.
- **Periodically:** purge/archive old data (partition drop is instant — see
  [Partitioning](../07-Partitioning-and-Scale/01.Table-Partitioning.md)).
- **Don't over-maintain:** rebuilding lightly-fragmented indexes or aggressive VACUUM FULL wastes I/O
  and causes locks/log growth. Maintain **by threshold/need**, not blindly nightly.

## 🚫 Common mistakes

```text
❌ 🐘: disabling autovacuum or letting it fall behind → bloat + XID wraparound risk. ✅ keep it on, tune it.
❌ 🐘: long-running transactions blocking vacuum → bloat. ✅ keep transactions short; watch idle-in-transaction.
❌ 🟦: never running DBCC CHECKDB → corruption discovered too late (already in backups). ✅ schedule it.
❌ Rebuilding ALL indexes nightly regardless of fragmentation → wasted I/O, huge log. ✅ by threshold.
❌ Never purging old data → tables grow unbounded → everything slows. ✅ archive/partition-drop on retention.
❌ 🐘: VACUUM FULL on a busy table mid-day → exclusive lock → outage. ✅ pg_repack / REINDEX CONCURRENTLY.
```

## 🌍 Real-World Use

DBAs run **Ola Hallengren's scripts** (🟦) for threshold-based index/stats maintenance + integrity
checks on a schedule, and **monitor autovacuum** (🐘) to ensure it keeps pace with churn (tuning
scale factors on hot tables, watching `n_dead_tup`). Both purge/archive old data on a retention
policy (partition drops where possible). Cloud-managed databases automate much of this, but you still
watch bloat/fragmentation and verify the housekeeping is happening.

## 🎯 Practice (with full solutions)

### 1. Diagnose & fix bloat — `Medium` (🐘)
**Task:** A high-update PostgreSQL table is bloated and slow. Diagnose and remediate without an
outage.
**Solution:**
```sql
-- Diagnose: lots of dead tuples, autovacuum behind?
SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;
-- Check for transactions blocking vacuum:
SELECT pid, state, xact_start FROM pg_stat_activity WHERE state = 'idle in transaction';
-- Remediate: make autovacuum aggressive on this table; rebuild bloated indexes online
ALTER TABLE hot SET (autovacuum_vacuum_scale_factor = 0.02);
REINDEX INDEX CONCURRENTLY ix_hot_key;   -- or pg_repack for table+index bloat
```
**Why it works:** the dead-tuple count + autovacuum timing reveal the cause; tuning autovacuum and
ending blocking transactions stops new bloat, while `REINDEX CONCURRENTLY`/`pg_repack` reclaim
existing bloat **without** the exclusive lock of `VACUUM FULL`.

### 2. Catch corruption early — `Easy` (🟦)
**Task:** How do you make sure disk/hardware corruption is caught before it's backed up and spreads?
**Solution:**
```sql
-- Schedule a regular integrity check (e.g. weekly), alert on any errors:
DBCC CHECKDB('shop') WITH NO_INFOMSGS, ALL_ERRORMSGS;
```
**Why it works:** `DBCC CHECKDB` scans for page/structure corruption; running it regularly means you
detect problems while you still have **clean backups** to restore from — before the corruption is
silently captured in every backup. (🐘: `amcheck`/`pg_amcheck` for similar index/heap verification.)

## ✅ Key Takeaways

- Maintenance keeps performance steady; the **primary chore differs by engine**.
- **🐘: VACUUM** (via **autovacuum**) reclaims MVCC dead tuples and prevents **bloat** + **XID
  wraparound** — never disable it; keep transactions short; tune scale factors. Compact online with
  `pg_repack`/`REINDEX CONCURRENTLY`, not `VACUUM FULL`.
- **🟦: index defrag (by threshold) + `UPDATE STATISTICS` + `DBCC CHECKDB`** — automate via Agent / Ola
  Hallengren scripts.
- **Purge/archive old data** on a retention policy (partition drop = instant).
- **Maintain by threshold/need**, not blindly; run **integrity checks** to catch corruption early.
