# Backup & Restore

## 🧠 Intuition

The single most important job in operating a database: **be able to get the data back**. Disks fail,
people run `DELETE` without a `WHERE`, ransomware strikes, a deploy corrupts data. Backups are your
safety net — but only if they're **tested** (an untested backup is a hope, not a backup) and support
**point-in-time recovery (PITR)** so you can restore to *just before* the disaster, not just to last
night.

> 💡 **Analogy — a save game.** Backups are save points. A nightly full backup is "saved last night."
> But if you make a fatal mistake at 2 PM, you don't want to lose the whole day — point-in-time
> recovery lets you reload to **1:59 PM**, right before the mistake. That's the difference between
> losing minutes and losing a day.

## 📐 Backup types

| Type | Contains | Restore role |
|------|----------|--------------|
| **Full** | The entire database | The baseline to restore from |
| **Differential** (🟦) | Changes since the last full | Faster than replaying all logs |
| **Transaction log / WAL** | Every change since the last log backup | Enables **point-in-time recovery** |

A typical strategy: weekly full + daily differential + frequent (e.g. 15-min) log backups → you can
restore to **any moment** with minimal data loss.

## 💻 🟦 SQL Server

```sql
-- Full backup
BACKUP DATABASE shop TO DISK = 'D:\backups\shop_full.bak' WITH COMPRESSION, CHECKSUM;

-- Differential (changes since last full)
BACKUP DATABASE shop TO DISK = 'D:\backups\shop_diff.bak' WITH DIFFERENTIAL;

-- Transaction log backup (requires FULL recovery model — enables PITR)
BACKUP LOG shop TO DISK = 'D:\backups\shop_log.trn';

-- Restore to a point in time
RESTORE DATABASE shop FROM DISK = 'D:\backups\shop_full.bak' WITH NORECOVERY;
RESTORE DATABASE shop FROM DISK = 'D:\backups\shop_diff.bak' WITH NORECOVERY;
RESTORE LOG shop FROM DISK = 'D:\backups\shop_log.trn'
    WITH STOPAT = '2025-05-10 13:59:00', RECOVERY;     -- restore to just before the mistake
```

> ⚠️ PITR requires the **FULL recovery model** (so the log is retained until backed up). In **SIMPLE**
> recovery, the log is truncated automatically and you **cannot** do log backups or PITR — only full/
> differential. Choose the recovery model deliberately.

## 💻 🐘 PostgreSQL

PostgreSQL has two backup styles:

```bash
# Logical backup: pg_dump (a portable script/archive of the database — great for one DB / migrations)
pg_dump -Fc shop > shop.dump            # custom-format archive
pg_restore -d shop_restored shop.dump   # restore

pg_dumpall > all.sql                    # all databases + roles (cluster-wide)
```

```bash
# Physical backup + PITR: base backup + archived WAL
# 1. Continuous archiving (postgresql.conf): archive_mode = on; archive_command = 'cp %p /archive/%f'
# 2. Take a base backup:
pg_basebackup -D /backups/base -Fp -Xs -P
# 3. Recover to a point in time (recovery.signal + postgresql.conf):
#    restore_command = 'cp /archive/%f %p'
#    recovery_target_time = '2025-05-10 13:59:00'
```

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Logical (portable) | (script via SSMS/`bcp`) | **`pg_dump`** / `pg_dumpall` |
| Physical full | `BACKUP DATABASE` | **`pg_basebackup`** |
| Incremental | **Differential** backup | (WAL since base backup) |
| Log/WAL backup | `BACKUP LOG` | **WAL archiving** (`archive_command`) |
| PITR | `STOPAT` + FULL recovery model | base backup + archived WAL + `recovery_target_time` |
| Cloud-managed | automatic (Azure SQL) | automatic (RDS/Aurora/Cloud SQL) |

> **`pg_dump` vs `pg_basebackup`:** `pg_dump` is **logical** (a portable script — good for copying one
> database, migrating, or cross-version) but slow to restore large DBs and **doesn't do PITR**.
> `pg_basebackup` + WAL archiving is **physical** (fast restore, whole cluster, **enables PITR**) —
> the production HA/DR choice. Use both for different purposes.

## ⚖️ A real backup strategy

1. **Define RPO/RTO** ([HA & Replication](../09-Architecture-and-Internals/05.High-Availability-and-Replication.md))
   — how much data can you lose, how fast must you recover?
2. **Full + differential/WAL + frequent log/WAL backups** to hit that RPO.
3. **Store backups off the database server** (and off-site / another region) — a backup on the same
   disk that failed is useless. Follow **3-2-1**: 3 copies, 2 media, 1 off-site.
4. **Encrypt backups** (they contain all your data) and protect them from ransomware (immutable/
   offline copies).
5. **TEST RESTORES regularly** — restore to a scratch server and verify. Most "we have backups"
   stories end badly because nobody tested them.
6. **Monitor backup success** and retention; automate it ([Automation](04.Automation.md)).

## 🚫 Common mistakes

```text
❌ Never testing a restore → discovering the backups are corrupt/incomplete during a real disaster.
✅ scheduled test restores + verification (CHECKSUM/pg_verifybackup).

❌ Backups on the same disk/server as the database → both lost together. ✅ off-server + off-site (3-2-1).

❌ 🟦: SIMPLE recovery model when you need PITR → no log backups, can only restore to the last full/diff.
   ✅ FULL recovery model + regular log backups for PITR.

❌ Treating a replica/HA standby as a backup → it copies a DROP TABLE too. ✅ replicas ≠ backups.

❌ Unencrypted, unprotected backup files → a stolen backup = a full data breach. ✅ encrypt + protect.
```

## 🌍 Real-World Use

Production runs automated **full + differential/WAL + frequent log** backups, copies them off-site
(another region / cold storage), encrypts them, and **periodically restores to a test server** to
prove recoverability. PITR is the lifeline for human error ("someone deleted the customers table at 2
PM" → restore to 1:59 PM). Managed cloud databases automate most of this — but you still verify
retention and test restores.

## 🎯 Practice (with full solutions)

### 1. Recover from a 2 PM mistake — `Medium`
**Task:** Someone ran `DELETE FROM customers` at 2:00 PM. You have a nightly full backup and 15-minute
log/WAL backups. Recover with minimal loss.
**Solution:**
```sql
-- 🟦 SQL Server: restore full, then logs up to 1:59 PM
RESTORE DATABASE shop FROM DISK='...full.bak' WITH NORECOVERY;
-- (apply differentials/logs...) then:
RESTORE LOG shop FROM DISK='...log.trn' WITH STOPAT='2025-05-10 13:59:00', RECOVERY;
```
```bash
# 🐘 PostgreSQL: restore base backup, set recovery_target_time = '2025-05-10 13:59:00', replay WAL
```
**Why it works:** point-in-time recovery replays the log/WAL up to **just before** the destructive
statement, recovering everything except the last minute — far better than reverting to last night's
full backup. (A replica wouldn't help — it deleted the rows there too.)

### 2. Choose pg_dump vs pg_basebackup — `Easy`
**Task (🐘):** You need (a) to copy one database to a developer's laptop, and (b) production
disaster-recovery with PITR. Which tool for each?
**Solution:** (a) **`pg_dump`** — a portable logical backup of a single database, easy to restore
anywhere (even a different PG version). (b) **`pg_basebackup` + WAL archiving** — a physical backup of
the whole cluster that supports **point-in-time recovery**, the production DR choice.
**Why it matters:** logical dumps are for portability/migration; physical base backups + WAL are for
production recovery and PITR — different tools for different jobs.

## ✅ Key Takeaways

- Backups are only real if **tested** and support **point-in-time recovery** (restore to just before a
  disaster).
- Types: **full** + **differential (🟦) / WAL (🐘)** + frequent **log/WAL** backups → minimal data loss.
- **🟦:** `BACKUP DATABASE/LOG`, `STOPAT` for PITR — requires the **FULL recovery model**.
- **🐘:** **`pg_dump`** (logical, portable, no PITR) vs **`pg_basebackup` + WAL archiving** (physical,
  PITR) — use the right one.
- Store backups **off-server + off-site (3-2-1)**, **encrypt** them, and **test restores regularly**.
  Replicas are **not** backups.
