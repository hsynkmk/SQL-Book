# Capacity & Performance Counters

## 🧠 Intuition

Beyond per-query tuning, you need to watch the database's **overall resource health** — CPU, memory,
disk I/O, storage space, and connections — and **plan capacity** so you scale *before* you hit a
wall. Performance counters are the vital signs; capacity planning is reading the trend and acting
ahead of the curve.

> 💡 **Analogy — a body's vital signs + a growth chart.** Performance counters are the vitals (heart
> rate, blood pressure) telling you how the system is *right now*. Capacity planning is the growth
> chart: project the trend so you provision more resources before the patient runs out — not during
> the emergency.

## 📐 The vital signs to watch

| Resource | What to watch | Trouble sign |
|----------|---------------|--------------|
| **CPU** | % utilization, signal waits | Sustained high CPU; lots of `SOS_SCHEDULER_YIELD` (🟦) |
| **Memory** | Cache hit ratio, Page Life Expectancy (🟦) | Low PLE / low hit ratio → memory pressure → disk I/O |
| **Disk I/O** | Reads/writes, latency, queue | High latency on data or log disk |
| **Storage space** | Data + log + tempdb/WAL free space | Running out (the classic 3 AM outage) |
| **Connections** | Active/idle, pool usage | Near `max_connections`; idle-in-transaction (🐘) |
| **Throughput** | Transactions/sec, batch requests/sec | Plateau under load |
| **Replication lag** | Standby delay | Growing lag |

## 💻 🟦 SQL Server — counters & DMVs

- **Windows Performance Monitor (PerfMon)** exposes SQL Server counters:
  - **Buffer Cache Hit Ratio** (want high), **Page Life Expectancy** (low = memory pressure),
  - **Batch Requests/sec** (throughput), **% Processor Time**, **Avg Disk sec/Read|Write** (I/O
    latency).
- **DMVs** for in-engine views:

```sql
-- Wait stats: what the server spends time waiting on (the best compass)
SELECT TOP 10 wait_type, wait_time_ms, signal_wait_time_ms FROM sys.dm_os_wait_stats
ORDER BY wait_time_ms DESC;

-- File I/O latency per database file
SELECT DB_NAME(database_id), file_id, io_stall_read_ms, io_stall_write_ms, num_of_reads, num_of_writes
FROM sys.dm_io_virtual_file_stats(NULL, NULL);

-- Memory / cache health
SELECT cntr_value FROM sys.dm_os_performance_counters WHERE counter_name = 'Page life expectancy';
```

## 💻 🐘 PostgreSQL — pg_stat_* & OS tools

```sql
-- Cache hit ratio (want > ~99% for OLTP working sets)
SELECT datname, blks_hit::float / NULLIF(blks_hit + blks_read, 0) AS hit_ratio FROM pg_stat_database;

-- Transaction throughput and rollbacks
SELECT datname, xact_commit, xact_rollback FROM pg_stat_database;

-- Connections and states (watch idle-in-transaction!)
SELECT state, count(*) FROM pg_stat_activity GROUP BY state;

-- Database / table sizes (storage planning)
SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database ORDER BY pg_database_size(datname) DESC;
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) FROM pg_catalog.pg_statio_user_tables ORDER BY pg_total_relation_size(relid) DESC;
```

Plus OS-level tools (CPU/memory/disk via `top`, `iostat`, Prometheus `node_exporter` +
`postgres_exporter`), and `pg_stat_io` (PG 16+) for detailed I/O.

## 📐 The danger signs (and what they mean)

- **Low cache hit ratio / low Page Life Expectancy** → not enough RAM for the working set; reads go to
  disk. **Add memory**, or reduce data read (better indexes/projections).
- **High disk latency on the log/WAL** → commits are slow; **move the log to faster storage** (see
  [Storage & Memory](../09-Architecture-and-Internals/03.Storage-and-Memory.md)).
- **Sustained high CPU** → expensive queries (missing indexes, bad plans), or genuine load → tune
  queries first, then scale.
- **Connections near the limit / many idle-in-transaction (🐘)** → connection leak or missing pooler;
  idle-in-transaction also **blocks vacuum** → bloat.
- **Storage filling up** → the most preventable outage. **Alert on free space** well before it's
  critical; watch log/WAL/tempdb growth especially.

## 📐 Capacity planning

1. **Trend the vitals over time** (dashboards) — don't just look at "now," look at the slope.
2. **Project growth** — data volume, transaction rate, connection count. When will you hit a limit?
3. **Provision ahead** — add storage/RAM/CPU, or [scale out](../07-Partitioning-and-Scale/03.Scaling-Out.md)
   (replicas/sharding) *before* saturation, not during the incident.
4. **Right-size, don't over-provision** — capacity costs money; match it to projected need + headroom.
5. **Set alerts on leading indicators** (disk %, connection %, replication lag, cache ratio) so you
   act on the trend, not the outage.

## 🚫 Common mistakes

```text
❌ No disk-space alert → the database fills its volume and stops (a classic, preventable outage).
✅ alert on free space (data, log/WAL, tempdb) well ahead of full.

❌ Watching only "right now," never the trend → surprised by predictable growth. ✅ trend + project.

❌ Adding hardware to mask a missing index → wastes money; the query is the problem. ✅ tune first, then scale.

❌ 🐘: ignoring idle-in-transaction sessions → connection exhaustion + vacuum-blocking bloat.
   ✅ alert on long idle-in-transaction; use a pooler.

❌ Reacting to saturation instead of provisioning ahead → emergency scaling under fire.
```

## 🌍 Real-World Use

Production databases feed counters into dashboards (Grafana + exporters, Azure Monitor, CloudWatch /
RDS Performance Insights, SolarWinds DPA, pganalyze) with **alerts on leading indicators**. Capacity
reviews trend storage/CPU/connections and provision ahead of need. The most common preventable
incident — **running out of disk** — is solved by a simple free-space alert. The second — masking a
missing index with a bigger server — is solved by **tuning before scaling**.

## 🎯 Practice (with full solutions)

### 1. Spot memory pressure — `Medium`
**Task:** Queries that were fast are now doing lots of disk I/O. Which counters confirm memory
pressure, and what's the fix?
**Solution:** Check the **cache hit ratio** (low = reads going to disk) and, on 🟦, **Page Life
Expectancy** (low = pages evicted too fast). On 🐘:
```sql
SELECT blks_hit::float/NULLIF(blks_hit+blks_read,0) AS hit_ratio FROM pg_stat_database WHERE datname='shop';
```
If the hit ratio dropped (e.g. data outgrew RAM), the working set no longer fits in memory. Fix:
**add RAM** (raise buffer pool / `shared_buffers` appropriately), and/or **reduce data read** (better
indexes, projections, archiving old data) so the working set fits.
**Why it works:** a falling cache hit ratio / PLE directly signals the working set exceeding memory;
more RAM or less data-per-query restores in-memory serving.

### 2. Prevent the disk-full outage — `Easy`
**Task:** Make sure the database never silently runs out of storage.
**Solution:** Add an **alert on free disk space** for the data, log/WAL, and tempdb/temp volumes,
triggering well before full (e.g. at 80%). Trend storage growth to forecast when to expand. On 🐘,
also alert on **WAL accumulation** (a stuck `archive_command` or an orphaned replication slot can fill
the disk); on 🟦, watch **log file growth** (a long-running transaction or missing log backups bloats
it).
**Why it works:** running out of storage is the most common *preventable* outage; a leading-indicator
free-space alert turns a 3 AM emergency into a routine "expand the volume" ticket.

## ✅ Key Takeaways

- Watch the **vital signs**: CPU, memory (**cache hit ratio** / 🟦 **Page Life Expectancy**), **disk
  I/O latency**, **storage free space**, **connections**, throughput, replication lag.
- **🟦:** PerfMon counters + DMVs (`dm_os_wait_stats`, `dm_io_virtual_file_stats`); **🐘:** `pg_stat_*`
  views + OS tools/exporters.
- **Leading indicators + alerts**: disk space, connection %, replication lag, cache ratio — act on the
  **trend**, provision **ahead** of saturation.
- **Tune before you scale** (a missing index, not a small server, is often the real problem).
- The classic preventable outage — **disk full** — is solved by a simple free-space alert.
