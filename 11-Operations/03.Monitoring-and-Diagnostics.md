# Monitoring & Diagnostics

## 🧠 Intuition

You can't fix what you can't see. **Monitoring** is the continuous visibility into a database's
health — which queries are slow, what's blocking what, how full the cache is, where the I/O and CPU
go. Both engines expose rich internal **system views** that turn "the database feels slow" into
"*this* query is doing 2 million reads because of a missing index."

> 💡 **Analogy — a car's dashboard.** You don't drive blind hoping nothing's wrong — you watch the
> speedometer, fuel, temperature, warning lights. A database's monitoring views are its dashboard:
> CPU, cache hit ratio, slow-query list, blocking chains, disk I/O. Watch them and you catch problems
> before they become outages.

## 📐 What to monitor

| Signal | Why |
|--------|-----|
| **Slow / expensive queries** | The usual culprit; find the top resource consumers |
| **Blocking & deadlocks** | One session stuck behind another ([Locking](../05-Transactions-and-Concurrency/03.Locking-Blocking-Deadlocks.md)) |
| **Cache hit ratio** | Low = memory pressure / too much disk I/O |
| **Wait statistics** | *What* queries wait on (CPU, I/O, locks, latches) — the best tuning compass |
| **Connections** | Counts, idle-in-transaction (🐘 bloat risk), pool exhaustion |
| **Disk / CPU / memory** | Resource saturation |
| **Replication lag** | Standbys falling behind |

## 💻 🟦 SQL Server — DMVs, Query Store, Extended Events

```sql
-- Top expensive queries (Dynamic Management Views)
SELECT TOP 10 qs.total_logical_reads, qs.execution_count,
       SUBSTRING(st.text, 1, 200) AS query_text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_logical_reads DESC;

-- Who is blocking whom right now
SELECT session_id, blocking_session_id, wait_type, wait_time, wait_resource
FROM sys.dm_exec_requests WHERE blocking_session_id <> 0;

-- Missing index suggestions
SELECT * FROM sys.dm_db_missing_index_details;

-- Wait stats (what the server spends time waiting on)
SELECT TOP 10 wait_type, wait_time_ms FROM sys.dm_os_wait_stats ORDER BY wait_time_ms DESC;
```

- **DMVs** (`sys.dm_*`) — live diagnostics: query stats, requests, waits, index usage, sessions.
- **Query Store** (the killer feature) — automatically **records query history and plans over time**,
  so you can see *when* a query regressed and force a known-good plan. Turn it on.
- **Extended Events** — lightweight tracing for deep diagnostics (deadlock graphs, slow events),
  replacing the old Profiler/SQL Trace.

## 💻 🐘 PostgreSQL — pg_stat_* views & pg_stat_statements

```sql
-- Top queries by total time (requires the pg_stat_statements extension — install it!)
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- Current activity: running queries, blocked sessions, idle-in-transaction
SELECT pid, state, wait_event_type, wait_event, query, xact_start
FROM pg_stat_activity WHERE state <> 'idle';

-- Blocking: which PID blocks which
SELECT blocked.pid AS blocked_pid, blocking.pid AS blocking_pid, blocked.query AS blocked_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));

-- Cache hit ratio per database
SELECT datname, blks_hit::float / NULLIF(blks_hit + blks_read, 0) AS cache_hit_ratio FROM pg_stat_database;

-- Table-level stats: scans, dead tuples, vacuum timing
SELECT relname, seq_scan, idx_scan, n_dead_tup, last_autovacuum FROM pg_stat_user_tables;
```

> **`pg_stat_statements`** is PostgreSQL's most important monitoring extension — it aggregates query
> performance (calls, total/mean time, rows) so you can find the worst offenders. **Install and enable
> it** on every production database (it's the 🐘 equivalent of SQL Server's Query Store / query-stats
> DMVs).

## 🟦 SQL Server vs 🐘 PostgreSQL

| Need | 🟦 SQL Server | 🐘 PostgreSQL |
|------|--------------|---------------|
| Live diagnostics | **DMVs** (`sys.dm_*`) | **`pg_stat_*`** views |
| Query history/regression | **Query Store** | **pg_stat_statements** (+ external history) |
| Current activity | `sys.dm_exec_requests`/`sessions` | `pg_stat_activity` |
| Blocking | `blocking_session_id` | `pg_blocking_pids()` |
| Slow-query log | Extended Events / Query Store | `log_min_duration_statement` |
| Deep tracing | **Extended Events** | `auto_explain`, log analysis (pgBadger) |
| Single-query plan | actual execution plan | `EXPLAIN (ANALYZE, BUFFERS)` |

## 📐 From monitoring to fixing — the loop

1. **Monitor** flags a problem (a query in the top-10 by reads, a blocking chain, a low cache ratio).
2. **Drill in:** get the query's [execution plan](../06-Indexing-and-Performance/04.Reading-Execution-Plans.md)
   (`EXPLAIN ANALYZE` / actual plan).
3. **Diagnose:** scan vs seek, key lookups, estimate gaps, missing index, non-SARGable predicate.
4. **Fix:** add/cover an index, make it [SARGable](../06-Indexing-and-Performance/05.SARGability.md),
   update [statistics](../06-Indexing-and-Performance/06.Statistics-and-Cardinality.md), rewrite.
5. **Verify:** re-check the plan and the monitoring metric. Prove the fix.

**Wait statistics** are the best starting compass: they tell you *what the server is waiting on*
(CPU? I/O? locks? latches? network?), pointing you at the right class of problem instead of guessing.

## 💻 Production observability

Beyond ad-hoc queries, production uses dashboards and alerting: **Prometheus + Grafana** (with the SQL
exporter / `postgres_exporter`), **Application Insights / Azure Monitor** (🟦), cloud-native
monitoring (CloudWatch/RDS Performance Insights), and tools like **SolarWinds DPA**, **Redgate**,
**pgBadger**, **pganalyze**. Alert on: slow-query thresholds, blocking duration, replication lag, low
cache hit ratio, high connections, disk space.

## 🚫 Common mistakes

```text
❌ Tuning by guesswork instead of reading the stats/plan. ✅ measure first (DMVs / pg_stat_statements / plan).
❌ 🐘: not installing pg_stat_statements → flying blind on query performance. ✅ enable it everywhere.
❌ 🟦: leaving Query Store off → can't see when/why a query regressed. ✅ turn it on.
❌ Ignoring wait stats → chasing the wrong bottleneck. ✅ let waits point you at the real issue.
❌ No alerting → you find out about problems from angry users, not the dashboard. ✅ alert on key signals.
```

## 🌍 Real-World Use

The daily reality of running databases: a dashboard shows the top queries by resource use, alerts fire
on blocking/slow queries/replication lag, and when something's slow you pull the query from
`pg_stat_statements`/Query Store, get its plan, and fix the root cause. **Query Store** (🟦) and
**pg_stat_statements** (🐘) are the two most valuable monitoring features — enable them on every
production database.

## 🎯 Practice (with full solutions)

### 1. Find the worst query — `Easy`
**Task:** A database is slow. Find the most resource-intensive queries in each engine.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT TOP 10 total_logical_reads, execution_count, SUBSTRING(st.text,1,200) AS q
FROM sys.dm_exec_query_stats qs CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY total_logical_reads DESC;
-- 🐘 PostgreSQL (pg_stat_statements enabled)
SELECT query, calls, mean_exec_time, total_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
```
**Why it works:** these views aggregate per-query resource usage, surfacing the few queries
responsible for most of the load — where tuning effort pays off most.

### 2. Find what's blocking — `Medium`
**Task:** Users report hangs. Identify the blocking session(s) in each engine.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT session_id, blocking_session_id, wait_type, wait_resource
FROM sys.dm_exec_requests WHERE blocking_session_id <> 0;
-- 🐘 PostgreSQL
SELECT blocked.pid AS blocked, blocking.pid AS blocking, blocked.query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));
```
**Why it works:** both reveal the blocking chain (who waits on whom) so you can find the lead blocker
(often a long transaction) and address it — kill it, or fix the code holding the lock too long.

## ✅ Key Takeaways

- **Monitoring = visibility:** slow queries, blocking, cache hit ratio, **wait stats**, connections,
  resources, replication lag.
- **🟦:** **DMVs** (live), **Query Store** (history/regression — *turn it on*), **Extended Events**
  (tracing).
- **🐘:** **`pg_stat_*`** views, **`pg_stat_statements`** (worst queries — *install it everywhere*),
  `pg_stat_activity` + `pg_blocking_pids()`, `EXPLAIN ANALYZE`.
- **Wait statistics** point you at the real bottleneck class — start there.
- Follow the loop: **monitor → drill into the plan → diagnose → fix → verify**; add dashboards +
  alerting for production.
