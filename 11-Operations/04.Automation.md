# Automation

## 🧠 Intuition

The routine work of running a database — backups, index maintenance, statistics updates, data purges,
report generation, integrity checks — should happen **automatically on a schedule**, not because a
human remembered to run it at 2 AM. Automation makes operations reliable and repeatable. SQL Server
has a built-in scheduler (**SQL Server Agent**); PostgreSQL relies on **`pg_cron`** or external
schedulers.

> 💡 **Analogy — a dishwasher on a timer.** You don't wash every dish by hand the moment it's dirty —
> you load the dishwasher and set it to run overnight. Database automation is that timer: load up the
> recurring jobs (backup, reindex, purge), schedule them, and they run reliably without you.

## 💻 🟦 SQL Server — SQL Server Agent

SQL Server Agent is a built-in service that runs **jobs** (one or more steps) on **schedules**, with
**alerts** and **operator notifications** on failure:

```sql
-- Conceptual: a nightly backup job (usually created via SSMS GUI or sp_add_job procedures)
EXEC msdb.dbo.sp_add_job @job_name = N'Nightly Full Backup';
EXEC msdb.dbo.sp_add_jobstep @job_name = N'Nightly Full Backup', @step_name = N'Backup',
     @subsystem = N'TSQL',
     @command = N'BACKUP DATABASE shop TO DISK = ''D:\backups\shop_full.bak'' WITH COMPRESSION;';
EXEC msdb.dbo.sp_add_schedule @schedule_name = N'Daily 2AM',
     @freq_type = 4, @freq_interval = 1, @active_start_time = 020000;   -- daily at 02:00
EXEC msdb.dbo.sp_attach_schedule @job_name = N'Nightly Full Backup', @schedule_name = N'Daily 2AM';
EXEC msdb.dbo.sp_add_jobserver @job_name = N'Nightly Full Backup';
```

- **Jobs** have **steps** (T-SQL, PowerShell, SSIS packages, OS commands) that run in sequence.
- **Schedules** (daily/weekly/on startup/on idle).
- **Alerts & Operators** — notify on failure or on performance-counter/error conditions (email, etc.).
- Steps can branch on success/failure; jobs log history.

SQL Server Agent is the backbone of SQL Server operations — backups, Ola Hallengren maintenance,
ETL (SSIS), report delivery, and custom jobs all run through it.

## 💻 🐘 PostgreSQL — pg_cron & external schedulers

PostgreSQL has **no built-in job scheduler**. The options:

```sql
-- pg_cron extension: cron-style scheduling INSIDE the database
CREATE EXTENSION IF NOT EXISTS pg_cron;

-- Schedule a nightly VACUUM ANALYZE at 03:00
SELECT cron.schedule('nightly-vacuum', '0 3 * * *', 'VACUUM ANALYZE');

-- Refresh a materialized view every 15 minutes
SELECT cron.schedule('refresh-mv', '*/15 * * * *',
                     'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue');

-- List / remove jobs
SELECT * FROM cron.job;
SELECT cron.unschedule('nightly-vacuum');
```

| Option | What it is |
|--------|-----------|
| **pg_cron** | A popular extension adding cron scheduling inside PostgreSQL (great for VACUUM, MV refresh, purges) |
| **OS cron / Task Scheduler** | Run `psql`/`pg_dump` scripts via the operating system's scheduler |
| **External orchestrators** | **Airflow**, **dbt Cloud**, CI schedulers, k8s CronJobs for ETL/workflows |
| **Cloud-managed** | RDS/Aurora/Cloud SQL provide managed backups, maintenance windows, and event scheduling |

> The dialect gap: **🟦 has a full built-in scheduler (Agent) with jobs/alerts/operators**; **🐘 relies
> on `pg_cron` or external tools.** Many PostgreSQL shops use OS cron + scripts, pg_cron for in-DB
> tasks, and a workflow engine (Airflow) for complex ETL.

## ⚖️ What to automate

| Task | Typical schedule |
|------|------------------|
| Backups (full / diff / log-WAL) | full nightly/weekly; logs every 15 min |
| Index maintenance (🟦) / confirm autovacuum (🐘) | weekly, by threshold |
| Statistics / `ANALYZE` | daily (where auto isn't enough) |
| Integrity checks (`DBCC CHECKDB` / `amcheck`) | weekly |
| Data purge / archival (partition drop) | daily/weekly on retention |
| Materialized view refresh | per freshness need |
| Monitoring/alerting | continuous |

**Always include failure notification** — an automated job that fails silently is worse than no job
(you *think* you have backups). Alert on every failure.

## 🚫 Common mistakes

```text
❌ Manual operations ("I'll run the backup tonight") → eventually forgotten → no backup when needed.
✅ scheduled jobs (Agent / pg_cron / cron).

❌ Automated jobs with no failure alerting → silent failures (the backup quietly stops working).
✅ notify operators on every failure; monitor job history.

❌ 🐘: assuming a built-in scheduler exists → there isn't one. ✅ pg_cron or external scheduler.

❌ Scheduling heavy maintenance during peak hours → user impact. ✅ off-peak windows; online operations.

❌ Hard-coding credentials in job scripts. ✅ use service accounts / managed identity / secrets.
```

## 🌍 Real-World Use

Every production database has automated, alerted jobs for backups, maintenance, and purges.
**🟦 SQL Server Agent** runs the whole operational schedule (backups, Ola Hallengren maintenance, SSIS
ETL, report delivery). **🐘 PostgreSQL** uses **pg_cron** for in-database tasks (VACUUM, MV refresh,
purges) plus OS cron / Airflow for scripts and ETL. **Cloud-managed** databases automate backups and
maintenance windows for you — you configure and monitor rather than build.

## 🎯 Practice (with full solutions)

### 1. Schedule nightly maintenance — `Medium`
**Task:** Automate a nightly backup (🟦) and a nightly `VACUUM ANALYZE` + materialized-view refresh
(🐘).
**Solution:**
```sql
-- 🟦 SQL Server Agent: a job with a BACKUP step on a daily 2 AM schedule (sp_add_job/step/schedule,
--   or the SSMS New Job wizard), with an operator notified on failure.

-- 🐘 PostgreSQL: pg_cron
SELECT cron.schedule('nightly-vacuum', '0 2 * * *', 'VACUUM ANALYZE');
SELECT cron.schedule('refresh-revenue', '15 2 * * *',
                     'REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue');
```
**Why it works:** the recurring chores now run unattended at off-peak times. (Add failure alerting:
Agent operators on 🟦; monitor `cron.job_run_details` / external alerting on 🐘.)

### 2. Avoid the silent-failure trap — `Easy`
**Task:** Your nightly backup job has been "running" for months. How do you ensure you'd know if it
started failing?
**Solution:** Configure **failure notification** — 🟦: an Agent **operator** emailed on job failure; 🐘:
check `cron.job_run_details` (or wrap the script to alert on non-zero exit) and pipe to your alerting.
Additionally, **monitor backup age** (alert if the newest backup is older than expected) and **test
restores** periodically.
**Why it works:** automation without alerting can fail invisibly; explicit failure notification +
backup-age monitoring + test restores ensure you discover a broken job *before* you need the backup.

## ✅ Key Takeaways

- **Automate** the recurring operational work — backups, maintenance, stats, purges, refreshes,
  integrity checks — on schedules; don't rely on humans.
- **🟦: SQL Server Agent** — built-in **jobs** (multi-step), **schedules**, **alerts/operators**; the
  backbone of SQL Server ops.
- **🐘: no built-in scheduler** — use **`pg_cron`** (in-DB), **OS cron** (scripts), or **Airflow/k8s**
  (ETL/workflows); cloud-managed automates backups/maintenance.
- **Always alert on failure** and **monitor backup age** — silent failures are the dangerous ones.
- Schedule heavy work **off-peak**; use **online** operations to avoid user impact.
