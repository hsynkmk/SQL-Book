# Table Partitioning

## 🧠 Intuition

When a table grows to hundreds of millions of rows, a single table becomes unwieldy — queries scan
too much, maintenance windows balloon, deleting old data locks everything. **Partitioning** splits
one logical table into multiple physical pieces (**partitions**) by a key (usually a date range), so
the engine can read/maintain just the relevant pieces. To your queries it still looks like one
table.

> 💡 **Analogy — a filing system with yearly drawers.** Instead of one giant drawer with every
> document, you have a drawer per year. Need 2025 invoices? Open just the 2025 drawer (partition
> elimination). Done with 2019? Pull the whole drawer out and toss it (drop a partition) — instant,
> no rummaging through everything.

## 🎯 The Problem

```sql
-- ❌ A 500M-row events table, all in one
SELECT * FROM events WHERE event_time >= '2025-05-01';   -- may scan a huge index
DELETE FROM events WHERE event_time < '2024-01-01';      -- deletes millions of rows: slow, huge log, locks
```

Range queries touch a giant structure, and purging old data is a painful mass `DELETE`. Partitioning
makes both fast.

## 📐 Benefits

- **Partition elimination:** a query filtered on the partition key reads only matching partitions —
  `WHERE event_time >= '2025-05-01'` skips every earlier partition.
- **Fast data lifecycle:** drop/truncate a whole partition to purge old data **instantly** (metadata
  operation) instead of a row-by-row `DELETE`. Switch/attach partitions for fast bulk load.
- **Targeted maintenance:** rebuild/vacuum one partition at a time.
- **Parallelism:** the engine can process partitions in parallel.

## 💻 🐘 PostgreSQL — declarative partitioning (clean, modern)

```sql
-- Parent table partitioned BY RANGE on event_time
CREATE TABLE events (
    event_id   BIGINT,
    event_time TIMESTAMPTZ NOT NULL,
    payload    JSONB
) PARTITION BY RANGE (event_time);

-- Child partitions (one per period)
CREATE TABLE events_2025_05 PARTITION OF events
    FOR VALUES FROM ('2025-05-01') TO ('2025-06-01');
CREATE TABLE events_2025_06 PARTITION OF events
    FOR VALUES FROM ('2025-06-01') TO ('2025-07-01');

-- Insert routes to the right partition automatically; queries eliminate irrelevant partitions
SELECT * FROM events WHERE event_time >= '2025-05-15';   -- reads only events_2025_05 (+ later)

-- Purge instantly: drop a whole partition
DROP TABLE events_2024_01;          -- or DETACH PARTITION to archive it
```

🐘 also supports `PARTITION BY LIST` (e.g. by region) and `PARTITION BY HASH` (even distribution).
Each partition can have its own indexes; create a matching index on the parent and 🐘 propagates it.

## 💻 🟦 SQL Server — partition function + scheme

SQL Server partitioning is more ceremonious — you define a **partition function** (the boundaries)
and a **partition scheme** (mapping partitions to filegroups), then build the table/index on the
scheme:

```sql
-- 1. Partition FUNCTION: the boundary values
CREATE PARTITION FUNCTION pf_event_month (DATETIME2)
AS RANGE RIGHT FOR VALUES ('2025-05-01', '2025-06-01', '2025-07-01');

-- 2. Partition SCHEME: map partitions to filegroup(s)
CREATE PARTITION SCHEME ps_event_month
AS PARTITION pf_event_month ALL TO ([PRIMARY]);

-- 3. Create the table ON the scheme, partitioned by event_time
CREATE TABLE events (
    event_id   BIGINT,
    event_time DATETIME2 NOT NULL,
    payload    NVARCHAR(MAX)
) ON ps_event_month (event_time);

-- Fast purge/load: SWITCH a partition in/out (metadata-only)
ALTER TABLE events SWITCH PARTITION 1 TO events_archive;
```

🟦's **`SWITCH`** is the fast-load/fast-purge mechanism: swap a fully-built table in as a partition,
or swap an old partition out to an archive table — instant, no data movement.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Style | Partition **function** + **scheme** (then build on scheme) | **Declarative** `PARTITION BY RANGE/LIST/HASH` |
| Create partitions | Implicit via boundaries; manage with SPLIT/MERGE | Explicit child tables (`PARTITION OF`) |
| Add/remove data fast | `SWITCH` partition in/out | `ATTACH`/`DETACH PARTITION`, `DROP` child |
| Partition-local indexes | Aligned indexes on the scheme | Index per partition (parent index propagates) |
| Ease | More setup | Cleaner, more intuitive |

## ⚖️ When to partition (and when not to)

- ✅ **Very large tables** (typically 100M+ rows / tens of GB) with a natural range key (time).
- ✅ **Rolling data lifecycle** — keep N months, drop the oldest (partition drop is the killer feature).
- ✅ **Range-scoped queries** that benefit from elimination.
- 🚫 **Small/medium tables** — partitioning adds complexity for no gain; a good index is enough.
- 🚫 **Queries that don't filter on the partition key** — they scan *all* partitions (no elimination),
  sometimes slower than an unpartitioned table.

> ⚠️ Partitioning is **not** a general performance fix — it's a **data-management and
> elimination** tool for huge tables. Partition on the key your queries actually filter by, or you
> lose the main benefit.

## 🚫 Common mistakes

```sql
-- ❌ Partitioning by a key queries don't filter on → no elimination, all partitions scanned
-- ✅ partition by the column in your range predicates (usually a date/time)

-- ❌ Partitioning a small table "for performance" → complexity, no benefit
-- ✅ index it instead; partition only very large tables

-- ❌ Using DELETE to purge old data on a partitioned table → defeats the purpose
DELETE FROM events WHERE event_time < '2024-01-01';   -- slow
-- ✅ DROP/DETACH (🐘) or SWITCH out (🟦) the old partition — instant

-- ❌ Forgetting per-partition indexes / unaligned indexes → poor plans
-- ✅ ensure indexes are partition-aligned
```

## 🌍 Real-World Use

Time-series and log/event tables (IoT, audit, analytics) are the canonical case: partition by month,
query recent ranges (elimination), and drop months past retention (instant purge). Data warehouses
partition fact tables by date for fast loads (switch/attach) and pruning. It's a standard pattern for
any table that grows without bound and is queried/maintained by time.

## 🎯 Practice (with full solutions)

### 1. Partition a time-series table — `Medium`
**Task (🐘):** Create a monthly-partitioned `events` table and show how a recent-range query and an
old-data purge both benefit.
**Solution:**
```sql
CREATE TABLE events (event_id BIGINT, event_time TIMESTAMPTZ NOT NULL, payload JSONB)
PARTITION BY RANGE (event_time);
CREATE TABLE events_2025_05 PARTITION OF events FOR VALUES FROM ('2025-05-01') TO ('2025-06-01');
CREATE TABLE events_2025_06 PARTITION OF events FOR VALUES FROM ('2025-06-01') TO ('2025-07-01');

-- Recent-range query → partition elimination (reads only May+):
SELECT count(*) FROM events WHERE event_time >= '2025-05-20';
-- Purge old data instantly:
DROP TABLE events_2025_05;     -- (once it's past retention) — metadata operation, no row-by-row delete
```
**Why it works:** the range predicate lets the planner skip non-matching partitions; dropping a whole
partition removes a month of data instantly instead of a massive `DELETE`.

### 2. Fast purge on SQL Server — `Medium`
**Task (🟦):** Purge the oldest month from a partitioned `events` table without a slow `DELETE`.
**Solution:**
```sql
-- Switch the oldest partition out to a staging table (metadata-only), then drop staging
ALTER TABLE events SWITCH PARTITION 1 TO events_old_month;
DROP TABLE events_old_month;
-- (then MERGE the now-empty boundary out of the partition function if desired)
```
**Why it works:** `SWITCH` reassigns the partition's data to another table instantly (no data
movement, minimal logging), turning a multi-million-row delete into a metadata operation.

## ✅ Key Takeaways

- **Partitioning** splits one big table into pieces by a key (usually time) — still one logical table.
- Wins: **partition elimination** (queries read only relevant pieces) and **instant data lifecycle**
  (drop/detach/switch a whole partition vs slow `DELETE`).
- **🐘:** clean **declarative** `PARTITION BY RANGE/LIST/HASH` with child tables. **🟦:** **partition
  function + scheme**, with **`SWITCH`** for fast load/purge.
- Partition by the key your queries **filter on**, and only for **very large** tables — it's a data-
  management tool, not a general speed-up.
