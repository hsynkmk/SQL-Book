# Triggers

## 🧠 Intuition

A **trigger** is code that fires **automatically** in response to a data change (`INSERT`, `UPDATE`,
`DELETE`) on a table. You don't call it — the database does, every time the event happens. Triggers
enforce rules, maintain audit trails, keep derived data in sync, or block invalid changes — all
transparently to whoever wrote the `INSERT`.

> 💡 **Analogy — a motion sensor light.** You don't flip a switch; walking into the room *triggers*
> the light automatically. A database trigger is that sensor: any change to the table automatically
> runs your code, no matter which app or person caused it.

Triggers are powerful but **double-edged** — they hide logic, run inside the triggering transaction
(so they affect performance and locking), and can cascade in surprising ways.

## 📐 Timing & scope

| Dimension | Options |
|-----------|---------|
| **Timing** | `BEFORE` (validate/modify before the write) · `AFTER` (react after) · `INSTEAD OF` (replace the operation) |
| **Event** | `INSERT` · `UPDATE` · `DELETE` (or combinations) |
| **Granularity** | per **row** (fires once per affected row) · per **statement** (fires once per statement) |

🟦 and 🐘 support overlapping but differently-named subsets of these.

## 💻 🟦 SQL Server — AFTER / INSTEAD OF, statement-level

SQL Server triggers are **statement-level** and expose the affected rows via two pseudo-tables:
**`inserted`** (new rows) and **`deleted`** (old rows).

```sql
-- Audit every salary change
CREATE OR ALTER TRIGGER trg_audit_salary
ON employees
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    INSERT INTO salary_audit (employee_id, old_salary, new_salary, changed_at)
    SELECT i.employee_id, d.salary, i.salary, SYSUTCDATETIME()
    FROM inserted i
    JOIN deleted  d ON d.employee_id = i.employee_id
    WHERE i.salary <> d.salary;       -- only when it actually changed
END;
```

- `inserted` / `deleted` are **sets** (multiple rows if the UPDATE hit many) — write set-based
  trigger code, never assume one row.
- **`INSTEAD OF`** triggers replace the operation — used to make a complex view updatable.

## 💻 🐘 PostgreSQL — BEFORE / AFTER, row or statement, via a trigger function

PostgreSQL triggers call a **trigger function** (a special function returning `TRIGGER`), and expose
the rows as **`NEW`** and **`OLD`** records:

```sql
-- 1. Define the trigger function
CREATE OR REPLACE FUNCTION audit_salary()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit (employee_id, old_salary, new_salary, changed_at)
        VALUES (NEW.employee_id, OLD.salary, NEW.salary, now());
    END IF;
    RETURN NEW;        -- BEFORE triggers can modify NEW; AFTER triggers ignore the return
END;
$$;

-- 2. Attach it to the table
CREATE TRIGGER trg_audit_salary
AFTER UPDATE ON employees
FOR EACH ROW
EXECUTE FUNCTION audit_salary();
```

- **`NEW`** / **`OLD`** are single-row records (because it's `FOR EACH ROW`).
- A **`BEFORE`** trigger can **modify `NEW`** (e.g. normalize/validate a value before it's written)
  or `RETURN NULL` to **cancel** the operation.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Timing | `AFTER`, `INSTEAD OF` (no `BEFORE`) | `BEFORE`, `AFTER`, `INSTEAD OF` (on views) |
| Granularity | **statement-level** (always) | `FOR EACH ROW` **or** `FOR EACH STATEMENT` |
| Affected rows | `inserted` / `deleted` pseudo-**tables** (sets) | `NEW` / `OLD` **records** (per row) |
| Structure | trigger body inline | separate trigger **function** + `CREATE TRIGGER` |
| Modify the row pre-write | via `INSTEAD OF` | natural with a `BEFORE` trigger modifying `NEW` |
| Cancel the operation | `ROLLBACK` / raise error | `BEFORE` trigger `RETURN NULL` |

> The biggest practical differences: **🟦 has no `BEFORE` trigger** (use `INSTEAD OF` or do
> validation in the AFTER trigger and roll back), and **🟦 triggers are set-based** (write code that
> handles multiple `inserted`/`deleted` rows) while **🐘 `FOR EACH ROW` triggers see one row at a
> time** via `NEW`/`OLD`.

## ⚖️ The case against overusing triggers

**Pros:** enforce invariants no matter who writes; centralized auditing; keep derived/denormalized
data in sync automatically.
**Cons:**
- **Hidden logic** — an `INSERT` mysteriously does five other things; debugging is hard.
- **Performance** — they run *inside* the triggering transaction, extending it and its locks.
- **Cascades** — triggers can fire other triggers; loops and surprises lurk.
- **Hard to test/version** alongside application code.

Many teams prefer to handle auditing/derivation in the application or a [stored procedure](01.Stored-Procedures.md)
they call explicitly, reserving triggers for cross-cutting integrity that *must* hold regardless of
the write path.

## 🚫 Common mistakes

```sql
-- ❌ 🟦: writing a trigger as if `inserted` has one row
SELECT @id = employee_id FROM inserted;   -- WRONG if the UPDATE hit many rows (gets an arbitrary one)
-- ✅ set-based: INSERT INTO audit SELECT ... FROM inserted JOIN deleted ...

-- ❌ Heavy work inside a trigger (calling external services, big aggregations)
-- → slows every write, extends locks. ✅ keep triggers tiny; offload heavy work (queue/outbox)

-- ❌ 🐘: forgetting to RETURN NEW (BEFORE/row trigger) → the row may not be written as expected
-- ✅ RETURN NEW (or OLD for DELETE, or NULL to cancel)

-- ❌ Recursive/cascading triggers causing loops
-- ✅ guard against re-entrancy; understand the cascade; sometimes disable nested triggers
```

## 🌍 Real-World Use

- **Audit trails:** record who changed what and when (the canonical use).
- **Enforce complex rules** that constraints can't express (cross-row/cross-table invariants).
- **Maintain denormalized/derived data:** update a cached `order_total` when line items change.
- **Soft delete:** an `INSTEAD OF DELETE` trigger sets `is_deleted = 1` instead of removing the row.
- **`BEFORE` normalization (🐘):** lowercase an email, trim whitespace, set a timestamp before insert.

## 🎯 Practice (with full solutions)

### 1. Audit salary changes — `Medium`
**Task:** Whenever an employee's salary changes, record the old and new value with a timestamp.
**Solution:** the `trg_audit_salary` trigger shown above for each engine. Test by running
`UPDATE employees SET salary = salary * 1.1 WHERE employee_id = 3;` and checking `salary_audit`.
**Why it works:** the trigger fires automatically on every UPDATE, compares old (`deleted`/`OLD`) vs
new (`inserted`/`NEW`), and logs only genuine changes — no matter which app issued the update.

### 2. Auto-timestamp on update (🐘 BEFORE trigger) — `Medium`
**Task:** Keep an `updated_at` column current on every row update, without the app having to set it.
**Solution:**
```sql
-- 🐘 PostgreSQL — a BEFORE trigger modifies NEW before the write
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN NEW.updated_at := now(); RETURN NEW; END;
$$;
CREATE TRIGGER trg_set_updated_at BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```
For 🟦 (no `BEFORE`), use an `AFTER UPDATE` trigger that writes `updated_at`, or set it in the app/
proc — a good example of the engines' different timing models.
**Why it works:** 🐘's `BEFORE` trigger can mutate `NEW.updated_at` *before* the row is stored, so the
column is always current with zero app involvement — something 🟦 must approximate differently
because it lacks `BEFORE` triggers.

## ✅ Key Takeaways

- A **trigger** runs **automatically** on `INSERT`/`UPDATE`/`DELETE` — for auditing, integrity, and
  keeping derived data in sync.
- **🟦:** `AFTER`/`INSTEAD OF`, **statement-level**, rows via **`inserted`/`deleted`** (sets — write
  set-based code). **No `BEFORE`.**
- **🐘:** `BEFORE`/`AFTER`, **row or statement** level, via a **trigger function** with **`NEW`/`OLD`**;
  `BEFORE` can modify/cancel the write.
- Triggers **hide logic, extend transactions, and can cascade** — keep them tiny and use them only
  for cross-cutting integrity.
