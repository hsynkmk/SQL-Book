# Stored Procedures

> Here the engines diverge the most: 🟦 uses **T-SQL**; 🐘 uses **PL/pgSQL**. Same idea, different
> language.

## 🧠 Intuition

A **stored procedure** is a named block of SQL + procedural logic stored *in* the database. You call
it by name, optionally pass parameters, and it runs server-side. Procedures encapsulate business
logic, reduce round-trips (do multiple steps in one call), enable plan reuse, and provide a security
boundary (grant `EXECUTE` without granting table access).

> 💡 **Analogy — a saved macro.** Instead of repeating the same ten-step process by hand each time,
> you record it once as a macro and run it with one click. A stored procedure is that macro, living
> on the database server, callable by any app.

## 🎯 The Problem

```sql
-- ❌ The same multi-step "place an order" logic, re-implemented in every app, each slightly different:
--   1. insert the order
--   2. insert the line items
--   3. decrement stock
--   4. return the new order id
-- Five apps × subtle differences = bugs, drift, and N network round-trips per order.
```

Encapsulate it once as a procedure: every caller runs the *same* correct logic in *one* round-trip.

## 💻 🟦 SQL Server — T-SQL procedures

```sql
CREATE OR ALTER PROCEDURE dbo.PlaceOrder
    @customer_id INT,
    @product_id  INT,
    @quantity    INT,
    @order_id    INT OUTPUT          -- output parameter
AS
BEGIN
    SET NOCOUNT ON;                  -- suppress "n rows affected" noise

    BEGIN TRANSACTION;
        INSERT INTO orders (customer_id, order_date, status)
        VALUES (@customer_id, CAST(GETDATE() AS DATE), 'Pending');

        SET @order_id = SCOPE_IDENTITY();

        INSERT INTO order_items (order_id, product_id, quantity, unit_price)
        SELECT @order_id, @product_id, @quantity, unit_price
        FROM products WHERE product_id = @product_id;

        UPDATE products SET units_in_stock = units_in_stock - @quantity
        WHERE product_id = @product_id;
    COMMIT;
END;
GO

-- Call it
DECLARE @newId INT;
EXEC dbo.PlaceOrder @customer_id = 1, @product_id = 5, @quantity = 2, @order_id = @newId OUTPUT;
SELECT @newId AS new_order_id;
```

## 💻 🐘 PostgreSQL — PL/pgSQL procedures

```sql
CREATE OR REPLACE PROCEDURE place_order(
    p_customer_id INT,
    p_product_id  INT,
    p_quantity    INT,
    INOUT p_order_id INT DEFAULT NULL    -- INOUT for "return" values
)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO orders (customer_id, order_date, status)
    VALUES (p_customer_id, CURRENT_DATE, 'Pending')
    RETURNING order_id INTO p_order_id;          -- capture the generated id

    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    SELECT p_order_id, p_product_id, p_quantity, unit_price
    FROM products WHERE product_id = p_product_id;

    UPDATE products SET units_in_stock = units_in_stock - p_quantity
    WHERE product_id = p_product_id;
END;
$$;

-- Call it
CALL place_order(1, 5, 2, NULL);   -- INOUT param returns the new id to the caller
```

> Note the **`$$ ... $$`** "dollar quoting" — PostgreSQL's way to delimit the procedure body (so you
> don't have to escape single quotes). 🟦 doesn't need it; the body is just between `AS BEGIN ...
> END`.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server (T-SQL) | 🐘 PostgreSQL (PL/pgSQL) |
|---------|----------------------|--------------------------|
| Define | `CREATE PROCEDURE ... AS BEGIN ... END` | `CREATE PROCEDURE ... LANGUAGE plpgsql AS $$ ... $$` |
| Call | `EXEC proc @p = ...` | `CALL proc(...)` |
| Parameters | `@p TYPE`, `OUTPUT` | `p TYPE`, `INOUT`/`OUT` |
| Variables | `DECLARE @x INT; SET @x = 1;` | `DECLARE x INT; BEGIN x := 1;` |
| Body delimiter | `BEGIN ... END` | `$$ ... $$` (dollar quoting) |
| Transactions inside | implicit/explicit `BEGIN TRAN` | `COMMIT`/`ROLLBACK` allowed in procedures (PG 11+) |
| "Procedure vs function" | procs can't be in a `SELECT` | same — procedures use `CALL`, not `SELECT` |

> 🟦 historically only had functions + procedures; 🐘 added true `PROCEDURE`s (with `CALL` and
> transaction control) in PG 11 — before that everything was a `FUNCTION`. Procedures differ from
> [functions](02.Functions.md): procedures are invoked with `CALL`/`EXEC` and can manage
> transactions; functions return a value and are used inside queries.

## ⚖️ Pros & cons of stored procedures

**Pros:** encapsulate logic in one place; fewer round-trips (batch steps); a security boundary
(grant `EXECUTE` only); plan reuse/caching; can enforce complex invariants atomically.
**Cons:** business logic split between app and DB (harder to test/version with app code); database-
specific language (T-SQL ≠ PL/pgSQL — not portable); can become a dumping ground for logic that
belongs in the application. Modern app teams often keep logic in the app and use procedures
selectively for performance-critical or data-integrity-critical operations.

## 🚫 Common mistakes

```sql
-- ❌ 🟦: forgetting SET NOCOUNT ON → extra "rows affected" messages confuse some clients/ORMs
-- ✅ SET NOCOUNT ON; at the top

-- ❌ No transaction around multi-step writes → partial failure leaves inconsistent data
-- ✅ wrap the steps in BEGIN TRAN/COMMIT (🟦) — and handle errors (see Error Handling)

-- ❌ 🐘: forgetting dollar quoting or LANGUAGE → syntax errors
-- ✅ CREATE PROCEDURE ... LANGUAGE plpgsql AS $$ BEGIN ... END $$;

-- ❌ Naming SQL Server procs with the sp_ prefix → reserved for system procs, causes a lookup penalty
CREATE PROCEDURE sp_PlaceOrder ...   -- avoid sp_
-- ✅ use a different prefix (usp_, or schema-qualified dbo.PlaceOrder)
```

## 🌍 Real-World Use

- **Transactional operations:** place order, transfer funds, post a journal entry — multi-step,
  must-be-atomic logic.
- **Batch/ETL steps:** nightly aggregation, data cleanup, archival.
- **Security gateway:** apps get `EXECUTE` on a proc that touches sensitive tables, without direct
  table access.
- **Performance:** push a chatty multi-round-trip operation into a single server-side call.

## 🎯 Practice (with full solutions)

### 1. A simple parameterized proc — `Easy`
**Task:** Write a procedure `GetCustomerOrders(customer_id)` returning that customer's orders, in
both engines.
**Solution:**
```sql
-- 🟦 SQL Server
CREATE OR ALTER PROCEDURE dbo.GetCustomerOrders @customer_id INT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT order_id, order_date, status FROM orders WHERE customer_id = @customer_id;
END;
GO
EXEC dbo.GetCustomerOrders @customer_id = 1;
```
```sql
-- 🐘 PostgreSQL (a function is more natural for returning a result set; see Functions chapter)
CREATE OR REPLACE FUNCTION get_customer_orders(p_customer_id INT)
RETURNS TABLE (order_id INT, order_date DATE, status TEXT)
LANGUAGE sql AS $$
    SELECT order_id, order_date, status FROM orders WHERE customer_id = p_customer_id;
$$;
SELECT * FROM get_customer_orders(1);
```
**Why it works:** 🟦 procs can directly return a result set via a `SELECT`; in 🐘, returning a *set*
is idiomatically a **function** (`RETURNS TABLE`) you `SELECT` from — a key cross-engine nuance.

### 2. Atomic multi-step proc — `Medium`
**Task:** `PlaceOrder` that inserts an order + one line item + decrements stock atomically, returning
the new order id.
**Solution:** the `PlaceOrder` / `place_order` procedures shown above. The key is wrapping the three
writes so they all succeed or all roll back.
**Why it works:** encapsulating the steps means every caller runs identical, atomic logic in one
round-trip; the transaction guarantees no partial orders. (Add error handling per the next-but-one
chapter for production-grade robustness.)

## ✅ Key Takeaways

- A **stored procedure** is named, server-side logic — encapsulation, fewer round-trips, plan reuse,
  a security boundary.
- **🟦 T-SQL** (`CREATE PROCEDURE ... AS BEGIN/END`, `EXEC`, `@params`, `OUTPUT`) vs **🐘 PL/pgSQL**
  (`LANGUAGE plpgsql AS $$...$$`, `CALL`, `INOUT`).
- Returning a **result set**: natural in 🟦 procs; in 🐘 use a **function** (`RETURNS TABLE`).
- **Procedures vs functions:** procedures use `CALL`/`EXEC` and can manage transactions; functions
  return values and are used in queries.
- They're not portable (T-SQL ≠ PL/pgSQL) and can over-centralize logic — use them deliberately.
