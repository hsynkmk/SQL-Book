# Cursors & Why to Avoid Them

## 🧠 Intuition

A **cursor** lets you process a result set **one row at a time** — fetch a row, do something, fetch
the next, loop until done. It feels natural to programmers used to loops. But SQL is **set-based**:
it's designed to operate on *all* matching rows at once. A cursor throws that away, processing
row-by-row — what DBAs call **RBAR** ("Row By Agonizing Row") — and is often **orders of magnitude
slower** than the equivalent set-based statement.

> 💡 **Analogy — a checkout line.** A set-based query is a self-checkout where 50 people scan
> simultaneously. A cursor is one cashier ringing up 50 customers one at a time. For the same work,
> the parallel approach finishes vastly faster. Cursors make the database stand in a slow line.

## 🎯 The Problem — the cursor people reach for

```sql
-- ❌ 🟦 SQL Server: cursor to give every beverage a 10% price increase
DECLARE @id INT, @price DECIMAL(10,2);
DECLARE c CURSOR FOR SELECT product_id, unit_price FROM products WHERE category_id = 1;
OPEN c;
FETCH NEXT FROM c INTO @id, @price;
WHILE @@FETCH_STATUS = 0
BEGIN
    UPDATE products SET unit_price = @price * 1.10 WHERE product_id = @id;   -- one update PER ROW
    FETCH NEXT FROM c INTO @id, @price;
END;
CLOSE c; DEALLOCATE c;
```

This issues **one UPDATE per row** plus cursor overhead. The set-based version does it in **one
statement**:

```sql
-- ✅ Set-based: one statement, the engine optimizes it
UPDATE products SET unit_price = unit_price * 1.10 WHERE category_id = 1;
```

The set-based form is shorter, clearer, and typically **10×–1000× faster**.

## 📐 Why set-based wins

- **One statement, one plan, one pass** — the optimizer batches the work, uses indexes, and can
  parallelize. A cursor forces serial, row-at-a-time execution.
- **Less locking churn** — a cursor holds resources across many small operations; a set statement
  does it in one transaction-friendly unit.
- **Less network/engine overhead** — no per-row fetch round-trips inside the engine.

Almost anything you'd loop over can be expressed as `UPDATE ... WHERE`, `INSERT ... SELECT`,
`DELETE ... WHERE`, a [window function](../02-Advanced-Querying/01.Window-Functions.md), a
[recursive CTE](../02-Advanced-Querying/02.CTEs-and-Recursion.md), or [`MERGE`](../03-Modifying-Data-and-DDL/02.Upsert-and-Merge.md).

## 💻 Replacing common cursor patterns with set-based SQL

| Cursor does... | Set-based replacement |
|----------------|-----------------------|
| Update each row by a formula | `UPDATE t SET col = expr WHERE ...` |
| Insert derived rows one by one | `INSERT INTO t2 SELECT ... FROM t1 WHERE ...` |
| Running total / row numbering | window functions (`SUM() OVER`, `ROW_NUMBER()`) |
| "Previous row" comparison | `LAG()` / `LEAD()` |
| Walk a hierarchy | recursive CTE |
| Upsert each row | `MERGE` / `INSERT ... ON CONFLICT` |
| Concatenate rows into a string | `STRING_AGG` / `string_agg` |

```sql
-- Cursor computing a running total → window function
SELECT order_date, total,
       SUM(total) OVER (ORDER BY order_date ROWS UNBOUNDED PRECEDING) AS running_total
FROM daily_sales;

-- Cursor building a CSV → STRING_AGG
SELECT category_id, STRING_AGG(name, ', ') AS products    -- 🟦 STRING_AGG / 🐘 string_agg
FROM products GROUP BY category_id;
```

## ⚖️ When a cursor is *actually* acceptable

Cursors aren't *always* evil — there are narrow legitimate cases:

- **Row-by-row side effects that can't be set-based:** calling a per-row stored procedure that does
  something external (sending an email, calling a service) for each row — though even then, a queue/
  outbox is usually better.
- **Administrative iteration over objects:** looping over each database/table to run maintenance
  (rebuild indexes per table) — operating on *metadata*, not data rows.
- **Truly sequential algorithms** where each step depends on the previous in a way windows/recursion
  can't express (rare).

Even here, prefer set-based or batch approaches first; reach for a cursor only when you've confirmed
there's no set-based path.

## 💻 If you must use one — both dialects

```sql
-- 🟦 SQL Server cursor (see structure above): DECLARE/OPEN/FETCH/WHILE @@FETCH_STATUS=0/CLOSE/DEALLOCATE

-- 🐘 PostgreSQL: cursors exist too (in PL/pgSQL), but FOR loops over a query are the idiomatic form
DO $$
DECLARE rec RECORD;
BEGIN
    FOR rec IN SELECT product_id, unit_price FROM products WHERE category_id = 1 LOOP
        -- per-row work (only if genuinely necessary)
        RAISE NOTICE 'Product % at %', rec.product_id, rec.unit_price;
    END LOOP;
END $$;
```

> 🐘's `FOR rec IN SELECT ... LOOP` is a lightweight implicit cursor — still row-by-row, so the same
> "avoid unless necessary" advice applies.

## 🚫 Common mistakes

```sql
-- ❌ Using a cursor for bulk data transformation
-- (the price-increase example) → slow, verbose
-- ✅ a single UPDATE/INSERT...SELECT/MERGE

-- ❌ 🟦: forgetting CLOSE + DEALLOCATE → leaked cursor resources
-- ✅ always CLOSE and DEALLOCATE (or use a TRY/CATCH/FINALLY-style cleanup)

-- ❌ Reaching for a WHILE loop to fake a cursor → same RBAR problem
-- ✅ think "how do I express this as ONE statement over the whole set?"
```

## 🌍 Real-World Use

In practice, well-written database code has **very few cursors**. You'll mostly encounter them in
legacy systems or in genuine per-object maintenance scripts. The senior skill is **recognizing a
cursor (or a `WHILE` loop) and rewriting it as a set-based statement** — it's one of the most
impactful performance fixes you can make.

## 🎯 Practice (with full solutions)

### 1. Kill the cursor — `Easy`
**Task:** Rewrite the beverage price-increase cursor (from The Problem) as set-based SQL.
**Solution:**
```sql
UPDATE products SET unit_price = unit_price * 1.10 WHERE category_id = 1;
```
**Why it works:** the engine applies the formula to every matching row in one optimized,
index-using, potentially-parallel statement — eliminating per-row overhead and cursor management
entirely.

### 2. Replace a "previous row" cursor — `Medium`
**Task:** A cursor walks daily sales in date order computing each day's change from the previous day.
Rewrite it.
**Solution:**
```sql
SELECT order_date, total,
       total - LAG(total) OVER (ORDER BY order_date) AS change_from_prev
FROM daily_sales
ORDER BY order_date;
```
**Why it works:** `LAG()` gives each row direct access to the previous row's value in one pass — the
exact thing the cursor was looping to compute, but set-based and fast.

## ✅ Key Takeaways

- A **cursor** processes rows **one at a time** (RBAR) — usually **far slower** than the equivalent
  set-based statement.
- **SQL is set-based:** prefer `UPDATE/INSERT...SELECT/DELETE`, **window functions**, **recursive
  CTEs**, **`MERGE`**, and **`STRING_AGG`** over loops.
- Cursors/`WHILE` loops are justified only for genuine per-row side effects or metadata iteration —
  and even then, consider alternatives.
- The senior reflex: **see a cursor/loop → rewrite it set-based.** It's a top performance win.
- 🐘's `FOR ... IN SELECT LOOP` is an implicit cursor — same caution applies.
