# Functions

## 🧠 Intuition

A **user-defined function (UDF)** is reusable logic that **returns a value** (or a table) and can be
used **inside a query** — in `SELECT`, `WHERE`, `JOIN`, etc. Unlike a [procedure](01.Stored-Procedures.md)
(invoked with `CALL`/`EXEC` for side effects), a function is meant to *compute and return*. Two
flavors: **scalar** (returns one value) and **table-valued** (returns a result set).

> 💡 **Analogy — a calculator button.** A scalar function is like the `√` button: give it a number,
> get a number back, usable anywhere a number fits. A table-valued function is a mini-query you can
> call by name and join to.

## 📐 The two flavors

| Flavor | Returns | Used in |
|--------|---------|---------|
| **Scalar** | A single value | `SELECT col, fn(col) ...`, `WHERE fn(col) = x` |
| **Table-valued (TVF)** | A result set (rows) | `FROM fn(args)`, joined like a table |

## 💻 Scalar functions

```sql
-- 🟦 SQL Server
CREATE OR ALTER FUNCTION dbo.LineTotal(@qty INT, @price DECIMAL(10,2))
RETURNS DECIMAL(12,2)
AS
BEGIN
    RETURN @qty * @price;
END;
GO
SELECT order_id, dbo.LineTotal(quantity, unit_price) AS total FROM order_items;
```
```sql
-- 🐘 PostgreSQL
CREATE OR REPLACE FUNCTION line_total(qty INT, price NUMERIC)
RETURNS NUMERIC
LANGUAGE sql IMMUTABLE        -- IMMUTABLE: same inputs → same output (lets the planner optimize)
AS $$ SELECT qty * price; $$;

SELECT order_id, line_total(quantity, unit_price) AS total FROM order_items;
```

> ⚠️ **🟦 scalar UDFs have a notorious performance problem:** historically they execute **row by row**
> and block parallelism, making queries that call them per-row very slow. **SQL Server 2019+
> *inlines* many scalar UDFs** (Scalar UDF Inlining) to fix this — but if you're on older versions
> or your function isn't inlineable, prefer an inline expression, a computed column, or an inline
> TVF. This is a top 🟦 gotcha.

## 💻 Table-valued functions (TVFs)

### Inline TVF (🟦) / SQL function (🐘) — fast, optimizer-friendly

```sql
-- 🟦 SQL Server: inline TVF (a parameterized view — the GOOD kind, optimizes well)
CREATE OR ALTER FUNCTION dbo.OrdersForCustomer(@customer_id INT)
RETURNS TABLE
AS
RETURN (
    SELECT order_id, order_date, status FROM orders WHERE customer_id = @customer_id
);
GO
SELECT * FROM dbo.OrdersForCustomer(1);                 -- use it like a table
SELECT * FROM dbo.OrdersForCustomer(1) WHERE status = 'Shipped';   -- composes with WHERE!
```
```sql
-- 🐘 PostgreSQL: a set-returning function with RETURNS TABLE
CREATE OR REPLACE FUNCTION orders_for_customer(p_customer_id INT)
RETURNS TABLE (order_id INT, order_date DATE, status TEXT)
LANGUAGE sql STABLE
AS $$
    SELECT order_id, order_date, status FROM orders WHERE customer_id = p_customer_id;
$$;
SELECT * FROM orders_for_customer(1);
```

### Multi-statement TVF (🟦) — flexible but slower

```sql
-- 🟦: multi-statement TVF builds a table variable step by step (more flexible, but worse estimates)
CREATE OR ALTER FUNCTION dbo.TopProducts(@n INT)
RETURNS @result TABLE (name NVARCHAR(100), units INT)
AS
BEGIN
    INSERT INTO @result
    SELECT TOP (@n) p.name, SUM(oi.quantity)
    FROM products p JOIN order_items oi ON oi.product_id = p.product_id
    GROUP BY p.name ORDER BY SUM(oi.quantity) DESC;
    RETURN;
END;
```

> **Prefer inline TVFs (🟦)** over multi-statement TVFs — inline ones the optimizer can "see through"
> and integrate into the plan; multi-statement ones get poor cardinality estimates (assumed 1 row).

## 🟦 SQL Server vs 🐘 PostgreSQL — function determinism labels

🐘 makes you label a function's **volatility**, which lets the planner optimize:

| 🐘 Label | Meaning | Example |
|---------|---------|---------|
| `IMMUTABLE` | Same args → same result, always | `line_total(qty, price)` |
| `STABLE` | Constant within one statement (can read DB) | `now()`, a lookup by id |
| `VOLATILE` (default) | Can change anytime / has side effects | `random()`, `nextval()` |

🟦 has a related concept (deterministic vs nondeterministic functions) that affects whether you can
index a computed column using the function. Labeling correctly (🐘) or keeping functions
deterministic (🟦) unlocks optimizations like inlining and index usage.

## ⚖️ Function vs Procedure vs View

- **Scalar function:** compute one value, use in queries — but beware 🟦 per-row performance.
- **Inline TVF / set-returning function:** a *parameterized view* — composes with `WHERE`/`JOIN`,
  optimizes well. Often the best tool.
- **Procedure:** side effects, multiple steps, transactions — invoked with `CALL`/`EXEC`, not in a
  query.
- **View:** a non-parameterized saved query.

## 🚫 Common mistakes

```sql
-- ❌ 🟦: scalar UDF called per row in a big query (pre-2019 or non-inlineable) → severe slowdown
SELECT order_id, dbo.LineTotal(quantity, unit_price) FROM order_items;   -- millions of rows = slow
-- ✅ inline the expression, use a computed column, or an inline TVF; upgrade to 2019+ for inlining

-- ❌ 🟦: multi-statement TVF where an inline TVF would do → bad estimates, bad plans
-- ✅ RETURNS TABLE AS RETURN (...) — the inline form

-- ❌ 🐘: mislabeling volatility (e.g. marking a DB-reading function IMMUTABLE) → wrong results when cached
-- ✅ use STABLE for DB reads, IMMUTABLE only for pure math, VOLATILE for side effects

-- ❌ Putting heavy business logic in functions that the app should own → hard to test/version
```

## 🌍 Real-World Use

- **Scalar:** formatting, unit conversion, derived calculations (carefully, given 🟦's caveat).
- **Inline TVF / set-returning function:** reusable, parameterized query building blocks — "orders
  for customer X," "active items in category Y" — that compose into larger queries.
- **Determinism labels (🐘):** enabling the planner to cache/inline pure functions, and to build
  indexes on expressions.

## 🎯 Practice (with full solutions)

### 1. Reusable parameterized query — `Medium`
**Task:** A function returning all orders for a given customer, usable in a `FROM` clause and
further filterable.
**Solution:**
```sql
-- 🟦 SQL Server: inline TVF (composes with WHERE)
CREATE OR ALTER FUNCTION dbo.OrdersForCustomer(@cid INT)
RETURNS TABLE AS RETURN (
    SELECT order_id, order_date, status FROM orders WHERE customer_id = @cid
);
GO
SELECT * FROM dbo.OrdersForCustomer(1) WHERE status = 'Shipped';
```
```sql
-- 🐘 PostgreSQL
CREATE OR REPLACE FUNCTION orders_for_customer(cid INT)
RETURNS TABLE (order_id INT, order_date DATE, status TEXT)
LANGUAGE sql STABLE AS $$
    SELECT order_id, order_date, status FROM orders WHERE customer_id = cid;
$$;
SELECT * FROM orders_for_customer(1) WHERE status = 'Shipped';
```
**Why it works:** an inline TVF / set-returning function behaves like a parameterized view — the
optimizer folds it into the outer query, so the `WHERE status = 'Shipped'` is applied efficiently.

### 2. Avoid the scalar-UDF trap — `Medium`
**Task:** You need `quantity * unit_price` available everywhere. Instead of a scalar UDF called per
row, what's better?
**Solution:** a **persisted computed/generated column** (see
[Computed Columns](../03-Modifying-Data-and-DDL/06.Computed-and-Generated-Columns.md)):
```sql
-- 🟦: ALTER TABLE order_items ADD line_total AS (quantity * unit_price) PERSISTED;
-- 🐘: ALTER TABLE order_items ADD COLUMN line_total NUMERIC(10,2)
--        GENERATED ALWAYS AS (quantity * unit_price) STORED;
SELECT order_id, line_total FROM order_items;   -- no function call per row
```
**Why it works:** the value is computed once on write and stored (and indexable) — far cheaper than
invoking a scalar function for every row at query time, sidestepping 🟦's UDF performance problem
entirely.

## ✅ Key Takeaways

- Functions **return a value/table** and are used **inside queries**; procedures are for side
  effects via `CALL`/`EXEC`.
- **Scalar** (one value) vs **table-valued** (a set). Prefer **inline TVFs (🟦) / set-returning
  functions (🐘)** — they compose and optimize like parameterized views.
- **🟦 scalar UDFs can be slow** (per-row) — use inlining (2019+), inline expressions, or computed
  columns instead.
- **🐘 volatility labels** (`IMMUTABLE`/`STABLE`/`VOLATILE`) let the planner optimize — label
  correctly.
- Don't overload functions with logic the application should own.
