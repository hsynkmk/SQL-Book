# Error Handling

## 🧠 Intuition

When something goes wrong mid-procedure — a constraint violation, a divide-by-zero, a deadlock —
you need to **catch the error, undo partial work, and report it cleanly** instead of leaving the
data half-changed. SQL Server uses **`TRY...CATCH`** + `THROW`; PostgreSQL uses **`BEGIN...EXCEPTION`**
blocks in PL/pgSQL. Both pair tightly with [transactions](../05-Transactions-and-Concurrency/01.Transactions-and-ACID.md)
— catch the error, roll back, surface it.

> 💡 **Analogy — a safety net under a tightrope.** If the performer (your multi-step operation)
> falls (errors), the net (the CATCH/EXCEPTION block) catches them, the show stops cleanly (rollback),
> and the audience is told what happened (a clear error) — instead of a silent, broken state.

## 🎯 The Problem

```sql
-- ❌ No error handling: step 2 fails, step 1 already committed → inconsistent data
INSERT INTO orders (...) VALUES (...);          -- succeeds
INSERT INTO order_items (...) VALUES (...);      -- fails (e.g. FK violation)
-- Now there's an order with no items, and nobody was told. The data is broken.
```

You need: if *any* step fails, undo *all* of them, and report the error.

## 💻 🟦 SQL Server — TRY...CATCH

```sql
CREATE OR ALTER PROCEDURE dbo.PlaceOrder @customer_id INT, @product_id INT, @qty INT
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        BEGIN TRANSACTION;
            INSERT INTO orders (customer_id, order_date, status)
            VALUES (@customer_id, CAST(GETDATE() AS DATE), 'Pending');

            DECLARE @order_id INT = SCOPE_IDENTITY();

            INSERT INTO order_items (order_id, product_id, quantity, unit_price)
            SELECT @order_id, @product_id, @qty, unit_price FROM products WHERE product_id = @product_id;

            IF @qty <= 0 THROW 50001, 'Quantity must be positive', 1;   -- custom error
        COMMIT;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;     -- undo partial work

        -- inspect the error
        DECLARE @msg NVARCHAR(2048) = ERROR_MESSAGE(),
                @num INT = ERROR_NUMBER();
        -- log it, then re-raise to the caller
        INSERT INTO error_log (number, message, occurred_at) VALUES (@num, @msg, SYSUTCDATETIME());
        THROW;                            -- re-throw the original error to the caller
    END CATCH
END;
```

Key T-SQL error functions (valid inside `CATCH`): `ERROR_NUMBER()`, `ERROR_MESSAGE()`,
`ERROR_SEVERITY()`, `ERROR_LINE()`, `ERROR_PROCEDURE()`.

> **Use `THROW`, not the old `RAISERROR`**, for raising/re-raising errors in modern SQL Server —
> `THROW` is simpler and preserves the original error when called with no arguments inside `CATCH`.

## 💻 🐘 PostgreSQL — BEGIN...EXCEPTION

In PL/pgSQL, a `BEGIN ... EXCEPTION ... END` block catches errors. Crucially, **an exception
automatically rolls back to the start of the block** (a savepoint), so you don't manually roll back
the block's work:

```sql
CREATE OR REPLACE PROCEDURE place_order(p_customer_id INT, p_product_id INT, p_qty INT)
LANGUAGE plpgsql
AS $$
DECLARE
    v_order_id INT;
BEGIN
    IF p_qty <= 0 THEN
        RAISE EXCEPTION 'Quantity must be positive' USING ERRCODE = 'check_violation';
    END IF;

    INSERT INTO orders (customer_id, order_date, status)
    VALUES (p_customer_id, CURRENT_DATE, 'Pending')
    RETURNING order_id INTO v_order_id;

    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    SELECT v_order_id, p_product_id, p_qty, unit_price FROM products WHERE product_id = p_product_id;

EXCEPTION
    WHEN foreign_key_violation THEN
        RAISE NOTICE 'Bad product reference: %', SQLERRM;
        RAISE;                                    -- re-raise to the caller
    WHEN OTHERS THEN
        INSERT INTO error_log (message, occurred_at) VALUES (SQLERRM, now());
        RAISE;                                    -- re-raise
END;
$$;
```

Key PL/pgSQL error tools: `RAISE EXCEPTION/NOTICE/WARNING`, the `SQLSTATE`/`SQLERRM` variables,
named condition handlers (`WHEN unique_violation THEN ...`), and `WHEN OTHERS` as the catch-all.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Try/catch construct | `BEGIN TRY ... END TRY BEGIN CATCH ... END CATCH` | `BEGIN ... EXCEPTION WHEN ... THEN ... END` |
| Rollback on error | **manual** (`IF @@TRANCOUNT>0 ROLLBACK`) | **automatic** to the block's savepoint |
| Raise an error | `THROW num, msg, state` | `RAISE EXCEPTION 'msg' USING ERRCODE = ...` |
| Re-raise original | `THROW;` (no args, in CATCH) | `RAISE;` (no args, in EXCEPTION) |
| Error details | `ERROR_MESSAGE()`, `ERROR_NUMBER()`, ... | `SQLERRM`, `SQLSTATE`, `GET STACKED DIAGNOSTICS` |
| Catch specific errors | inspect `ERROR_NUMBER()` in CATCH | `WHEN unique_violation THEN ...` (named) |

> The conceptual difference: **🐘's `EXCEPTION` block auto-rolls-back** its work to a savepoint, so
> the block is transactional-by-default; **🟦 requires you to explicitly `ROLLBACK`** in the `CATCH`.

## ⚖️ Patterns

- **Always pair error handling with a transaction** for multi-step writes — catch → rollback →
  re-raise.
- **Log then re-raise:** record the error for diagnostics, then let it propagate so the caller knows
  it failed (don't swallow errors silently).
- **Catch specific errors** when you can recover (e.g. retry on deadlock — see
  [Optimistic vs Pessimistic](../05-Transactions-and-Concurrency/05.Optimistic-vs-Pessimistic.md));
  use the catch-all only to log + re-raise.

## 🚫 Common mistakes

```sql
-- ❌ Catching an error and swallowing it (no re-raise) → caller thinks it succeeded
BEGIN CATCH /* log */ END CATCH;   -- silently continues with broken data!
-- ✅ THROW; / RAISE; after logging

-- ❌ 🟦: forgetting to ROLLBACK in CATCH → the transaction stays open / partial data committed later
-- ✅ IF @@TRANCOUNT > 0 ROLLBACK;

-- ❌ 🟦: using RAISERROR for everything (legacy, fiddly severity/state)
-- ✅ THROW for modern code

-- ❌ Assuming 🐘 needs a manual rollback inside EXCEPTION (it doesn't — it auto-rolls-back the block)
-- but DO re-raise if the caller should know
```

## 🌍 Real-World Use

Any multi-step transactional procedure (order placement, fund transfer, batch posting) needs error
handling so a mid-operation failure doesn't corrupt data. Error logging tables capture failures for
ops teams. Deadlock-retry loops catch the specific deadlock error and retry the transaction.

## 🎯 Practice (with full solutions)

### 1. Atomic, error-safe insert pair — `Medium`
**Task:** Insert an order and its line item; if either fails, undo both and report the error.
**Solution:** the `PlaceOrder` (🟦 `TRY...CATCH`) and `place_order` (🐘 `EXCEPTION`) procedures above.
The transaction + catch/exception guarantees all-or-nothing; the re-raise tells the caller.
**Why it works:** 🟦 explicitly rolls back in `CATCH` and re-`THROW`s; 🐘's `EXCEPTION` block
auto-rolls-back its work and `RAISE`s — both leave the data consistent and the caller informed.

### 2. Catch a specific, recoverable error — `Medium`
**Task:** On a duplicate-key violation when inserting a tag, ignore it (the tag already exists);
re-raise anything else.
**Solution:**
```sql
-- 🐘 PostgreSQL — named condition
BEGIN
    INSERT INTO tags (name) VALUES ('sql');
EXCEPTION
    WHEN unique_violation THEN
        NULL;          -- tag already exists; ignore
    WHEN OTHERS THEN
        RAISE;         -- anything else propagates
END;
```
```sql
-- 🟦 SQL Server — inspect the error number
BEGIN TRY
    INSERT INTO tags (name) VALUES ('sql');
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() NOT IN (2627, 2601)  -- unique/PK violation numbers
        THROW;                              -- re-raise everything except duplicate-key
END CATCH;
```
**Why it works:** catching the *specific* recoverable error (duplicate key) lets you handle it
gracefully, while the catch-all re-raise ensures genuine problems still surface. (Often `ON
CONFLICT`/`IF NOT EXISTS` is even cleaner — but this shows targeted error handling.)

## ✅ Key Takeaways

- Wrap multi-step writes in a **transaction + error handler**: catch → roll back → log → **re-raise**.
- **🟦 `TRY...CATCH`** with **`THROW`** (use `THROW;` to re-raise); manual `ROLLBACK` required;
  details via `ERROR_*()` functions.
- **🐘 `BEGIN...EXCEPTION`**: **auto-rolls-back** to the block savepoint; **`RAISE`** to throw/
  re-raise; details via `SQLSTATE`/`SQLERRM`; catch by **named condition**.
- **Never swallow errors** — always re-raise after logging, or the caller proceeds on broken data.
- Catch *specific* errors when you can recover; use the catch-all only to log + re-raise.
