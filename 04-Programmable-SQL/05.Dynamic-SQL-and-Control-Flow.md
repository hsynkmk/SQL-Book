# Dynamic SQL & Control Flow

## 🧠 Intuition

Two procedural tools live here. **Control flow** — `IF`, `WHILE`, variables — lets a procedure make
decisions and loop. **Dynamic SQL** builds a SQL statement as a *string* at runtime and executes it,
for cases where the query shape isn't known until then (a variable table name, a dynamic column
list, an optional set of filters). Dynamic SQL is powerful and occasionally necessary — and the #1
source of **SQL injection** if you build it wrong.

> 💡 **Analogy — a fill-in-the-blanks form vs writing a letter from scratch.** Normal SQL is a fixed
> form with blanks for *values* (parameters) — safe, the structure is fixed. Dynamic SQL is writing
> the whole letter at runtime, structure and all — flexible, but if you paste in user text
> carelessly, they can rewrite your letter (injection).

## 💻 Variables & control flow

```sql
-- 🟦 SQL Server
DECLARE @threshold DECIMAL(10,2) = 5.00;
DECLARE @count INT;
SELECT @count = COUNT(*) FROM products WHERE unit_price > @threshold;

IF @count > 3
    PRINT 'Many expensive products';
ELSE
    PRINT 'Few expensive products';

-- WHILE loop (use sparingly — set-based is usually better!)
DECLARE @i INT = 1;
WHILE @i <= 3
BEGIN
    PRINT CONCAT('Iteration ', @i);
    SET @i = @i + 1;
END;
```
```sql
-- 🐘 PostgreSQL (inside a DO block or function/procedure)
DO $$
DECLARE
    threshold NUMERIC := 5.00;
    cnt INT;
BEGIN
    SELECT COUNT(*) INTO cnt FROM products WHERE unit_price > threshold;

    IF cnt > 3 THEN
        RAISE NOTICE 'Many expensive products';
    ELSE
        RAISE NOTICE 'Few expensive products';
    END IF;

    FOR i IN 1..3 LOOP
        RAISE NOTICE 'Iteration %', i;
    END LOOP;
END $$;
```

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Declare variable | `DECLARE @x INT;` | `DECLARE x INT;` (in a block) |
| Assign | `SET @x = 1;` / `SELECT @x = ...` | `x := 1;` / `SELECT ... INTO x` |
| If/else | `IF ... BEGIN ... END ELSE ...` | `IF ... THEN ... ELSE ... END IF;` |
| Loop | `WHILE ... BEGIN ... END` | `LOOP` / `WHILE` / `FOR ... IN ... LOOP` |
| Anonymous block | a batch | `DO $$ ... $$;` |

> ⚠️ **Loops are usually the wrong tool in SQL.** A `WHILE` that processes rows one at a time
> (RBAR — "row by agonizing row") is far slower than a single set-based statement. Reach for loops
> only when there's truly no set-based way (rare). See
> [Anti-Patterns](../13-Best-Practices-and-Interview/02.Anti-Patterns.md).

## 💻 Dynamic SQL — the safe way

When you must build SQL at runtime (dynamic filters, variable identifiers), **never concatenate user
input**. Use **parameterized** dynamic SQL.

### 🟦 SQL Server — `sp_executesql` (parameterized)

```sql
-- ✅ Safe: values passed as PARAMETERS, not concatenated
DECLARE @sql NVARCHAR(MAX), @city NVARCHAR(50) = N'Berlin';
SET @sql = N'SELECT customer_id, name FROM customers WHERE city = @city';
EXEC sp_executesql @sql, N'@city NVARCHAR(50)', @city = @city;

-- ❌ DANGEROUS: string concatenation → SQL injection
SET @sql = N'SELECT * FROM customers WHERE city = ''' + @city + '''';   -- never do this with user input
EXEC(@sql);
```

For dynamic **identifiers** (table/column names — which can't be parameters), validate them against a
whitelist or use `QUOTENAME()` to safely quote them:
```sql
SET @sql = N'SELECT * FROM ' + QUOTENAME(@table_name);   -- QUOTENAME guards the identifier
```

### 🐘 PostgreSQL — `EXECUTE` with `USING` and `format()`

```sql
-- ✅ Safe: values via USING (parameters); identifiers via format() %I
DO $$
DECLARE
    v_city TEXT := 'Berlin';
    v_table TEXT := 'customers';
BEGIN
    EXECUTE format('SELECT customer_id, name FROM %I WHERE city = $1', v_table)
    USING v_city;            -- $1 bound to v_city as a PARAMETER (injection-safe)
END $$;
```

`format()` placeholders: **`%I`** safely quotes an **identifier** (table/column), **`%L`** safely
quotes a **literal**, **`%s`** is a raw string (dangerous with user input — avoid). Combine `%I` for
identifiers with `USING` for values.

## ⚖️ When dynamic SQL is justified

- **Optional filters:** a search screen where any subset of 10 filters may be active (building only
  the `WHERE` clauses that apply). Often better solved with `(@p IS NULL OR col = @p)` patterns first
  — try that before dynamic SQL.
- **Dynamic identifiers:** operating on a table/column whose name is a parameter (admin tools,
  generic audit routines).
- **Dynamic pivots:** unknown pivot columns (see [Pivot](../02-Advanced-Querying/03.Pivot-and-Crosstab.md)).

If you don't need runtime structure, **don't use dynamic SQL** — static parameterized queries are
safer, cache better, and are easier to read.

## 🚫 Common mistakes

```sql
-- ❌ THE classic: concatenating user input into a SQL string → injection
'... WHERE name = ''' + @userInput + ''''     -- @userInput = "'; DROP TABLE customers; --"
-- ✅ parameterize: sp_executesql (🟦) / EXECUTE ... USING (🐘)

-- ❌ Treating a value placeholder as an identifier (or vice versa)
EXECUTE format('SELECT %L FROM customers', col_name)   -- %L quotes it as a string literal, not a column!
-- ✅ %I for identifiers, %L/USING for values

-- ❌ RBAR WHILE loop where a single UPDATE/INSERT...SELECT would do
-- ✅ set-based statement

-- ❌ Building a huge dynamic SQL string and losing readability/plan reuse
-- ✅ prefer static parameterized SQL unless the structure truly must be dynamic
```

## 🌍 Real-World Use

- **Generic admin/maintenance routines** that operate on a table name passed in.
- **Advanced search** with many optional filters (carefully — or use the `IS NULL OR` pattern).
- **Dynamic reporting/pivots** with runtime column sets.
- **Control flow** in procedures: branch on a status, validate inputs, orchestrate steps.

## 🎯 Practice (with full solutions)

### 1. Safe dynamic filter — `Medium`
**Task:** A procedure searches customers by an optional city; build it with parameterized dynamic
SQL (or better).
**Solution:**
```sql
-- 🟦: parameterized dynamic SQL (or, simpler, a static query with IS NULL OR)
-- Static, preferred when possible:
SELECT customer_id, name FROM customers WHERE (@city IS NULL OR city = @city);
-- Dynamic, when the shape truly varies:
DECLARE @sql NVARCHAR(MAX) = N'SELECT customer_id, name FROM customers WHERE city = @city';
EXEC sp_executesql @sql, N'@city NVARCHAR(50)', @city = @city;
```
```sql
-- 🐘
EXECUTE 'SELECT customer_id, name FROM customers WHERE city = $1' USING p_city;
```
**Why it works:** the city is always passed as a **parameter** (`@city` / `$1`), never concatenated —
injection-proof, and the plan can be reused. The static `IS NULL OR` form avoids dynamic SQL
entirely when the only variability is "filter present or not."

### 2. Dynamic table name, safely — `Medium`
**Task:** Count rows in a table whose name is supplied at runtime.
**Solution:**
```sql
-- 🐘 PostgreSQL: %I safely quotes the identifier
DO $$
DECLARE v_table TEXT := 'orders'; n BIGINT;
BEGIN
    EXECUTE format('SELECT COUNT(*) FROM %I', v_table) INTO n;
    RAISE NOTICE 'Rows: %', n;
END $$;
```
```sql
-- 🟦 SQL Server: QUOTENAME guards the identifier
DECLARE @table SYSNAME = N'orders', @sql NVARCHAR(MAX), @n INT;
SET @sql = N'SELECT @n = COUNT(*) FROM ' + QUOTENAME(@table);
EXEC sp_executesql @sql, N'@n INT OUTPUT', @n = @n OUTPUT;
```
**Why it works:** table/column names **can't** be parameters, so you must quote them safely —
`%I` (🐘) / `QUOTENAME` (🟦) prevent an attacker-supplied "name" from injecting SQL.

## ✅ Key Takeaways

- **Control flow** (`IF`/`WHILE`/`FOR`, variables) adds decisions and loops — but **prefer set-based
  SQL over loops** (RBAR is slow).
- **Dynamic SQL** builds statements at runtime — necessary for runtime structure (dynamic
  identifiers, optional filters, dynamic pivots).
- **Always parameterize values**: **🟦 `sp_executesql` with `@params`** / **🐘 `EXECUTE ... USING`** —
  never concatenate user input (SQL injection).
- **Quote dynamic identifiers**: **🟦 `QUOTENAME`** / **🐘 `format('%I', ...)`** (`%I` = identifier,
  `%L` = literal).
- Use static parameterized SQL whenever the structure is fixed — it's safer and caches better.
