# Power BI Integration (with both engines)

## 🧠 Intuition

**Power BI** is Microsoft's self-service BI and visualization tool — drag-and-drop dashboards, KPIs,
and interactive reports built on top of your data. Unlike SSRS (paginated documents), Power BI is for
**exploration**: filters, drill-down, cross-highlighting. It connects to **both SQL Server and
PostgreSQL** (and dozens of other sources), so it's a BI front-end for either engine.

> 💡 **Analogy — a dashboard vs a printout.** [SSRS](04.Reporting-with-SSRS.md) is the printed monthly
> statement. Power BI is the car dashboard — live gauges you watch and interact with, drilling from
> "total sales" into "which region, which month, which product" with a click.

## 📐 The two connectivity modes

The single most important Power BI decision is **how** it gets the data:

| Mode | How it works | Data freshness | Best for |
|------|--------------|----------------|----------|
| **Import** | Data is **loaded into** Power BI's in-memory **VertiPaq** engine | As of last refresh (scheduled) | Most reports — fast, snappy |
| **DirectQuery** | Queries are **sent live** to the source on each interaction | Real-time (live source) | Huge data, real-time needs, no data copy |
| **Composite** | Mix: some tables imported, some DirectQuery | Mixed | Large fact + small dims |

- **Import** is the default and fastest — Power BI caches a compressed copy in memory and queries that.
  Refreshed on a schedule (e.g. nightly). Both 🟦 and 🐘 support it.
- **DirectQuery** sends a SQL query to the source for every visual interaction — always live, no data
  copy, but performance depends on the **source database and its indexes**. Both engines support it
  (SQL Server natively; PostgreSQL via the connector).

## 💻 Connecting to each engine

```text
🟦 SQL Server / Azure SQL:
   - Native connector ("SQL Server database"). Import or DirectQuery.
   - Tabular semantic model = same VertiPaq engine as SSAS Tabular.
   - Can connect live to an SSAS model ("Analysis Services" / "live connection").

🐘 PostgreSQL:
   - Built-in "PostgreSQL database" connector (uses Npgsql).
   - Import or DirectQuery both supported.
   - Same DAX measures, visuals, refresh — the front-end is identical regardless of source.
```

The modeling/measures (**DAX**), visuals, and refresh experience are **the same** whether the source
is SQL Server or PostgreSQL — only the connector and the SQL generated underneath differ.

## 📐 The Power BI model (DAX)

Inside Power BI you build a **tabular semantic model**: relationships between tables (star schema),
calculated columns, and **measures** written in **DAX** (Data Analysis Expressions):

```text
Total Sales   = SUM(order_items[quantity] * order_items[unit_price])
Sales LY      = CALCULATE([Total Sales], SAMEPERIODLASTYEAR(dim_date[date]))
YoY Growth %  = DIVIDE([Total Sales] - [Sales LY], [Sales LY])
```

This is the **same semantic-model concept as SSAS Tabular** — in fact Power BI *is* the VertiPaq/
tabular engine. Define metrics once in the model; every visual reuses them consistently. Push heavy
shaping **down to SQL** (a view or the warehouse) and keep DAX for analytics.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Aspect | 🟦 SQL Server | 🐘 PostgreSQL |
|--------|--------------|---------------|
| Connector | Native ("SQL Server database") | Built-in ("PostgreSQL database", Npgsql) |
| Import mode | ✅ | ✅ |
| DirectQuery | ✅ (mature) | ✅ |
| Live connection to OLAP | ✅ SSAS Tabular/Multidimensional | (via imported model / external semantic layer) |
| Gateway for on-prem | On-premises data gateway | On-premises data gateway |
| Modeling language | DAX (same) | DAX (same) |

> Power BI is **engine-agnostic for the front-end**: the visuals, DAX, and refresh are identical. The
> difference is only the connector and (for DirectQuery) the SQL each engine receives — so source-side
> indexing/tuning matters for DirectQuery performance on **both**.

## ⚖️ Import vs DirectQuery — choosing

- **Import** when: data fits in memory after compression, near-real-time isn't required, you want the
  fastest interaction. (Most reports.) Schedule refresh (needs an **on-premises data gateway** for
  on-prem sources).
- **DirectQuery** when: data is too large to import, you need **live** data, or policy forbids copying
  data into Power BI. Cost: each interaction hits the source — so **index the source** and keep the
  model simple; some DAX is limited.
- **Composite** when: a huge fact table (DirectQuery) with small dimensions (Import) — best of both.

## 🚫 Common mistakes

```text
❌ DirectQuery against an un-indexed source → every click runs a slow query → sluggish dashboard.
✅ index the source for the queries Power BI generates; or use Import.

❌ Importing a billion-row fact table that won't fit in memory → refresh fails/huge.
✅ DirectQuery or composite; pre-aggregate in the warehouse.

❌ Doing heavy data shaping in Power Query/DAX that belongs in SQL → slow, hard to maintain.
✅ push transformations down to a SQL view / the warehouse; keep DAX for measures.

❌ Defining the same metric differently in many reports → inconsistent numbers.
✅ one semantic model (shared dataset) reused across reports.

❌ Forgetting the on-premises data gateway for scheduled refresh of on-prem SQL Server/PostgreSQL.
```

## 🌍 Real-World Use

- **Both engines:** Power BI is the dashboard layer over a SQL Server or PostgreSQL warehouse — sales
  KPIs, operational monitoring, executive scorecards, with scheduled refresh.
- **Enterprise:** a shared **Power BI dataset** (governed semantic model, often on SSAS Tabular)
  feeds many reports for consistent metrics; row-level security in the model restricts data per user.
- **Real-time:** DirectQuery against the live database for operational dashboards that must reflect
  current state.

## 🎯 Practice (with full solutions)

### 1. Import vs DirectQuery — `Medium`
**Task:** (a) An executive sales dashboard over a 20M-row warehouse, refreshed nightly. (b) A live
operations board that must show orders as they arrive this minute. Pick the mode for each, for either
engine.
**Solution:** (a) **Import** — 20M rows compress well into VertiPaq; nightly freshness is fine; Import
gives the fastest interaction. Schedule a nightly refresh (via the data gateway if on-prem). (b)
**DirectQuery** — "this minute" needs live data, so query the source directly; ensure the source
(🟦 or 🐘) is **indexed** for the generated queries to keep it responsive.
**Why it works:** Import trades freshness for speed (great when nightly is enough); DirectQuery trades
speed for liveness (required for real-time) — and shifts the performance burden to source indexing.

### 2. Same model, two sources — `Easy`
**Task:** Your company has one product line on SQL Server and another on PostgreSQL. Can the same Power
BI report logic serve both?
**Solution:** Yes — Power BI's **visuals, DAX measures, and modeling are identical** regardless of
source. Use the **SQL Server connector** for one and the **PostgreSQL connector** for the other; build
the same star-schema model and DAX measures (e.g. `Total Sales`, `YoY Growth`). Only the connector and
the underlying generated SQL differ.
**Why it works:** Power BI is a front-end on top of a source-agnostic semantic model; the DAX/visual
layer doesn't care whether VertiPaq was fed by 🟦 or 🐘.

## ✅ Key Takeaways

- **Power BI** = self-service interactive BI/visualization; connects to **both SQL Server and
  PostgreSQL** (and more) with an **identical** modeling/DAX/visual experience.
- **Import** (data cached in in-memory VertiPaq, scheduled refresh — fast, default) vs **DirectQuery**
  (live queries to the source — real-time, but source indexing matters) vs **Composite**.
- The **semantic model uses DAX** — same engine as **SSAS Tabular**; define metrics once, reuse
  everywhere; push heavy shaping down to **SQL**.
- For DirectQuery, **index the source** on both engines; use the **on-premises data gateway** for
  scheduled refresh of on-prem sources.
