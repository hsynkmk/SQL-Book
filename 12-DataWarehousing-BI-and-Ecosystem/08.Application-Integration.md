# Application Integration (connecting apps to SQL)

## 🧠 Intuition

Most SQL runs not in a query tool but from **application code** — a web API, a background worker, a
mobile backend. Each language has a **driver** that opens a connection, sends SQL, and reads results.
The patterns that keep this **safe, fast, and reliable** — parameterized queries, connection pooling,
ORMs, and migrations — are the same across languages and **both engines**; only the driver name
changes.

> 💡 **Analogy — power plugs and adapters.** The appliance (your app) is the same; you just need the
> right plug adapter (driver) for the socket (SQL Server vs PostgreSQL). The electrical safety rules
> (don't stick a fork in it = don't concatenate user input into SQL) are universal.

## 📐 The drivers per language

| Language | 🟦 SQL Server driver | 🐘 PostgreSQL driver |
|----------|---------------------|----------------------|
| **.NET / C#** | **Microsoft.Data.SqlClient** (ADO.NET); **EF Core** (SqlServer provider) | **Npgsql**; **EF Core** (Npgsql provider) |
| **Python** | **pyodbc** / pymssql | **psycopg** (psycopg3/2), asyncpg |
| **Java** | **Microsoft JDBC Driver** | **PostgreSQL JDBC** (pgjdbc) |
| **Node.js** | **mssql** (tedious) | **pg** (node-postgres) |
| **Go** | go-mssqldb | **pgx** / lib/pq |
| **ORMs (cross-engine)** | EF Core, Hibernate, SQLAlchemy, Prisma, TypeORM, Sequelize — swap the provider/dialect |

The application code is largely the same; you configure a **connection string** and pick the matching
driver/provider.

## 📐 The non-negotiable patterns

### 1. Parameterized queries (always)

Never concatenate user input into SQL — it causes **SQL injection** and defeats plan caching. Use
**parameters**:

```csharp
// ✅ .NET (works the same shape for SqlClient 🟦 and Npgsql 🐘)
using var cmd = new SqlCommand("SELECT * FROM customers WHERE email = @email", conn);
cmd.Parameters.AddWithValue("@email", userInput);   // driver safely binds the value
```
```python
# ✅ Python — psycopg (🐘)  /  pyodbc (🟦) — parameter placeholders, never f-strings
cur.execute("SELECT * FROM customers WHERE email = %s", (user_input,))   # psycopg
cur.execute("SELECT * FROM customers WHERE email = ?",  (user_input,))   # pyodbc
```

> ❌ `"... WHERE email = '" + userInput + "'"` is the classic injection hole. ✅ parameters — the
> driver sends the value separately from the SQL text. (See
> [Dynamic SQL](../04-Programmable-SQL/05.Dynamic-SQL-and-Control-Flow.md) for the server-side angle.)

### 2. Connection pooling

Opening a database connection is expensive. **Pools** reuse a set of live connections. .NET's
SqlClient/Npgsql pool **automatically** (just open/close per operation — it returns to the pool).
PostgreSQL servers often add an external pooler (**PgBouncer**) because each PG connection is a
process; SQL Server handles many connections more cheaply but pooling still matters.

```text
✅ Open late, close early (using/with) → the pool reuses connections; don't hold one open across a request.
✅ 🐘 high-concurrency: front the DB with PgBouncer (transaction pooling) to cap backend connections.
```

### 3. ORMs vs raw SQL

- **ORM** (EF Core, Hibernate, SQLAlchemy, Prisma) maps tables↔objects, generates SQL, tracks changes
  — great productivity; **swap the provider** to target 🟦 or 🐘. Watch for **N+1 queries** and leaky
  abstractions.
- **Raw SQL / micro-ORM** (Dapper, direct ADO.NET/psycopg) — full control, best for hot paths and
  complex queries. Most real apps **mix**: ORM for CRUD, raw SQL for performance-critical/reporting.

### 4. Schema migrations (DB-as-code)

Evolve the schema in version control, applied automatically on deploy:

| | 🟦 / .NET | Cross-engine |
|--|-----------|--------------|
| Tooling | **EF Core Migrations**, **DACPAC** (state-based) | **Flyway**, **Liquibase**, **sqitch** (migration-based) |

Both engines are supported by EF Core Migrations and Flyway/Liquibase — pick state-based (DACPAC) or
migration-based per your workflow (see [Dev Tools](07.Dev-Tools.md)).

## 🟦 SQL Server vs 🐘 PostgreSQL — integration notes

| Aspect | 🟦 SQL Server | 🐘 PostgreSQL |
|--------|--------------|---------------|
| .NET provider | Microsoft.Data.SqlClient / EF Core SqlServer | Npgsql / EF Core Npgsql |
| Connection cost | cheaper (thread-based) | each connection = a **process** → use PgBouncer at scale |
| Pooling | built into SqlClient | built into Npgsql; external **PgBouncer** common |
| Returning inserted id | `OUTPUT INSERTED.id` / `SCOPE_IDENTITY()` | `INSERT ... RETURNING id` |
| Bulk insert from app | `SqlBulkCopy` | Npgsql **binary `COPY`** / `COPY` |
| Async | async ADO.NET | Npgsql async / **asyncpg** (Python) |

> Two handy app-level idioms: **`SCOPE_IDENTITY()`/`OUTPUT`** (🟦) vs **`RETURNING`** (🐘) to get a
> generated key back, and **`SqlBulkCopy`** (🟦) vs **binary `COPY`** (🐘) for fast app-side bulk inserts.

## 📐 DevOps / CI-CD for databases

- **Source-control the schema** (migrations or DACPAC) — never hand-edit production.
- **Apply migrations in the deploy pipeline** (EF Core `database update`, Flyway/Liquibase migrate).
- **Backward-compatible changes** for zero-downtime: expand → migrate data → contract (add column,
  backfill, switch code, later drop old).
- **Test against the real engine** in CI (a containerized SQL Server / PostgreSQL) so dialect
  differences surface before production.

## 🚫 Common mistakes

```text
❌ String-concatenating user input into SQL → SQL injection + no plan reuse. ✅ parameters, always.

❌ Opening a connection and holding it for the whole request/app lifetime → pool starvation.
✅ open late/close early; let the pool reuse connections.

❌ 🐘: thousands of direct app connections (each a process) → memory exhaustion. ✅ PgBouncer.

❌ N+1 queries from an ORM (a query per row in a loop) → death by round-trips.
✅ eager-load/join, or batch; watch the generated SQL.

❌ Manual schema changes on production, no source control → drift, failed deploys.
✅ migrations/DACPAC in version control, applied by CI.

❌ Developing on SQLite/one engine but deploying on another → dialect surprises. ✅ test on the real engine.
```

## 🌍 Real-World Use

- **.NET + SQL Server:** EF Core (SqlServer provider) for CRUD, Dapper for hot queries,
  Microsoft.Data.SqlClient underneath, EF Core Migrations or DACPAC in CI/CD.
- **.NET/Python/Node + PostgreSQL:** Npgsql / psycopg / node-`pg`, EF Core (Npgsql) or SQLAlchemy/
  Prisma, **PgBouncer** for connection pooling at scale, Flyway/Liquibase or EF migrations.
- **Both:** parameterized queries everywhere, pooled connections, schema-as-code applied by the deploy
  pipeline, integration tests against a containerized instance of the real engine.

## 🎯 Practice (with full solutions)

### 1. Fix an injection-prone query — `Easy`
**Task:** `var sql = "SELECT * FROM customers WHERE name = '" + name + "'";` — make it safe on both
engines.
**Solution:**
```csharp
// 🟦 SqlClient                                   // 🐘 Npgsql — same shape, @param works for both
using var cmd = new SqlCommand(                    // (Npgsql also accepts @name)
    "SELECT * FROM customers WHERE name = @name", conn);
cmd.Parameters.AddWithValue("@name", name);        // value sent separately from SQL text
```
```python
cur.execute("SELECT * FROM customers WHERE name = %s", (name,))  # psycopg (🐘)
cur.execute("SELECT * FROM customers WHERE name = ?",  (name,))  # pyodbc  (🟦)
```
**Why it works:** parameters send the user value to the server **separately** from the SQL text, so it
can never be parsed as SQL — closing the injection hole — and the parameterized text is reused from
the plan cache.

### 2. Return the new id — `Medium`
**Task:** Insert a customer and get the generated `customer_id` back in one round-trip, each engine.
**Solution:**
```sql
-- 🟦 SQL Server
INSERT INTO customers (name, email) OUTPUT INSERTED.customer_id VALUES (@name, @email);
-- (or SELECT SCOPE_IDENTITY(); after the insert)

-- 🐘 PostgreSQL
INSERT INTO customers (name, email) VALUES ($1, $2) RETURNING customer_id;
```
**Why it works:** 🟦's `OUTPUT INSERTED.*` and 🐘's `RETURNING` both return generated values from the
same statement — one round-trip, no race from a separate "get last id" call. ORMs use exactly these
under the hood.

## ✅ Key Takeaways

- Each language has a 🟦 and 🐘 **driver** (e.g. **Microsoft.Data.SqlClient/Npgsql**, **pyodbc/psycopg**,
  JDBC, **mssql/pg**); app code is largely the same, swap the driver/connection string.
- **Always parameterize** (anti-injection + plan reuse); **pool connections** (open late/close early;
  **PgBouncer** for 🐘 at scale); use **ORMs** for CRUD + **raw SQL** for hot paths (mind **N+1**).
- Get generated keys via **`OUTPUT`/`SCOPE_IDENTITY()`** (🟦) vs **`RETURNING`** (🐘); bulk-insert via
  **`SqlBulkCopy`** (🟦) vs **binary `COPY`** (🐘).
- **Schema as code**: EF Core Migrations / DACPAC (🟦-leaning) or Flyway/Liquibase (cross-engine),
  applied by **CI/CD**; test against the **real engine** to catch dialect differences.
