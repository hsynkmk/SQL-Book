# Data Warehouse Design

## 🧠 Intuition

Your transactional database (OLTP) is **normalized** for fast, correct writes — but that shape is
awful for analytics ("total sales by region by quarter" needs ten joins). A **data warehouse** is a
*separate*, **denormalized**, read-optimized database designed for analytics (OLAP). Its signature
shape is the **star schema**: a central **fact** table of measurements surrounded by **dimension**
tables of descriptive attributes.

> 💡 **Analogy — a kitchen vs a buffet.** OLTP is the kitchen: organized for *preparing* food
> efficiently (writes), everything in its labeled place (normalized). The warehouse is the buffet:
> arranged for *serving* — everything laid out for easy grabbing (reads), even if the same ingredient
> appears in several dishes (denormalized). You cook in one, you eat from the other.

## 📐 OLTP vs OLAP

| | OLTP (transactional) | OLAP (analytical / warehouse) |
|--|----------------------|-------------------------------|
| Optimized for | Many small reads/writes | Few huge aggregate reads |
| Schema | Normalized (3NF) | Denormalized (star/snowflake) |
| Queries | "Get/update this order" | "Sum sales by region by month" |
| Data | Current, operational | Historical, integrated, often huge |
| Storage | Rowstore | Often **columnstore** ([Columnstore](../07-Partitioning-and-Scale/02.Columnstore-and-Analytics-Indexing.md)) |

## 📐 The star schema

```mermaid
erDiagram
    DIM_DATE ||--o{ FACT_SALES : when
    DIM_PRODUCT ||--o{ FACT_SALES : what
    DIM_CUSTOMER ||--o{ FACT_SALES : who
    DIM_STORE ||--o{ FACT_SALES : where
    FACT_SALES { int date_key FK; int product_key FK; int customer_key FK; int store_key FK; decimal amount; int quantity }
```

- **Fact table** — the center. Holds **measures** (numeric facts: `amount`, `quantity`) and **foreign
  keys** to dimensions. Long and narrow; millions/billions of rows. One row per event (a sale).
- **Dimension tables** — the points of the star. Descriptive attributes you **group/filter by**:
  `dim_product` (name, category, brand), `dim_date` (day, month, quarter, year), `dim_customer`,
  `dim_store`. Wide but short.
- A query joins the fact to a few dimensions and aggregates: `SUM(amount) GROUP BY product.category,
  date.quarter`.

### Star vs snowflake

- **Star** — dimensions are flat/denormalized (a `dim_product` row has category *and* brand columns).
  Simpler, faster (fewer joins). The usual choice.
- **Snowflake** — dimensions are normalized into sub-dimensions (`dim_product` → `dim_category` →
  `dim_brand`). Saves space, more joins, slower. Use when dimensions are large/shared.

## 📐 Surrogate keys & the date dimension

- **Surrogate keys:** dimensions use meaningless integer keys (`product_key`), not the OLTP natural
  key — so the warehouse is insulated from source-system key changes and can track history (below).
- **Date dimension:** a dedicated `dim_date` table (one row per day, with columns for day/week/month/
  quarter/year/holiday/fiscal-period) is a warehouse staple — it makes time-based grouping trivial and
  consistent (`GROUP BY dim_date.quarter`) instead of computing date parts everywhere.

## 📐 Slowly Changing Dimensions (SCD)

Dimension attributes change over time (a customer moves city, a product is recategorized). How you
handle history is the **SCD type**:

| SCD Type | Behavior | Example |
|----------|----------|---------|
| **Type 0** | Never changes | Date of birth |
| **Type 1** | Overwrite (no history) | Fix a typo in a name |
| **Type 2** | **Add a new row** with validity dates (full history) | Customer moves → new row, old row retained |
| **Type 3** | Keep a "previous" column | Track only the prior value |

**Type 2 is the classic** — it preserves history so "sales by the customer's city *at the time of the
sale*" is answerable. It uses a surrogate key + `valid_from`/`valid_to`/`is_current` columns; the fact
references the surrogate key that was current when the event happened.

## 📐 Conformed dimensions

When multiple fact tables (sales, returns, inventory) **share the same dimension** (the same
`dim_product`, `dim_date`), those are **conformed dimensions** — they let you compare/combine facts
consistently across the business ("sales vs returns by product category"). Conforming dimensions is
the backbone of an enterprise warehouse.

## 🟦 SQL Server vs 🐘 PostgreSQL for warehousing

| Aspect | 🟦 SQL Server | 🐘 PostgreSQL |
|--------|--------------|---------------|
| Columnar storage | **Columnstore indexes** (built-in) | Citus/Hydra columnar, or external engine |
| Dedicated DW product | **Azure Synapse Analytics** (MPP) | Citus (distributed), or cloud warehouses |
| Partitioning fact tables | partition function/scheme | declarative partitioning |
| ETL | **SSIS** ([ETL](02.ETL-with-SSIS.md)) | external (Airflow, dbt, COPY/FDW) |

Both can host a star schema; SQL Server's **columnstore** gives it a strong built-in analytics story.
For large-scale warehousing, teams often use dedicated platforms (Synapse, Snowflake, BigQuery,
Redshift, Databricks) rather than an OLTP engine.

## 🚫 Common mistakes

```text
❌ Running heavy analytics directly on the OLTP database → slows the write path; wrong schema shape.
✅ a separate warehouse with a star schema (and/or columnstore).

❌ Over-normalizing the warehouse (full 3NF) → ten-join analytic queries. ✅ denormalize (star).

❌ Type 1 (overwrite) dimensions when you need history → can't answer "as of the sale" questions.
✅ Type 2 SCD for attributes whose history matters.

❌ No date dimension → recomputing date parts everywhere, inconsistent fiscal logic. ✅ dim_date.

❌ Non-conformed dimensions → can't compare facts across the business. ✅ conform shared dimensions.
```

## 🌍 Real-World Use

Reporting and BI run off a warehouse, not the OLTP database: nightly (or streaming) ETL loads sales/
inventory/web events into fact tables keyed to conformed dimensions; analysts query star schemas
(often columnstore) for dashboards. Type 2 SCDs preserve history for "point-in-time" analysis. At
scale, this lives in Synapse/Snowflake/BigQuery/Redshift; smaller shops run it in SQL Server
(columnstore) or PostgreSQL.

## 🎯 Practice (with full solutions)

### 1. Design a star schema — `Medium`
**Task:** Design a simple star schema for retail sales analytics (sales amount/quantity, by product,
customer, store, and date).
**Solution:**
```sql
-- Dimensions (surrogate keys, denormalized attributes)
CREATE TABLE dim_date     (date_key INT PRIMARY KEY, full_date DATE, month INT, quarter INT, year INT);
CREATE TABLE dim_product  (product_key INT PRIMARY KEY, name ..., category ..., brand ...);
CREATE TABLE dim_customer (customer_key INT PRIMARY KEY, name ..., city ..., segment ...);
CREATE TABLE dim_store    (store_key INT PRIMARY KEY, name ..., region ...);
-- Fact (measures + FKs to dimensions)
CREATE TABLE fact_sales (
    sale_id      BIGINT PRIMARY KEY,
    date_key     INT REFERENCES dim_date(date_key),
    product_key  INT REFERENCES dim_product(product_key),
    customer_key INT REFERENCES dim_customer(customer_key),
    store_key    INT REFERENCES dim_store(store_key),
    quantity     INT,
    amount       DECIMAL(12,2)
);
-- Analytic query: revenue by category by quarter
SELECT p.category, d.quarter, SUM(f.amount) AS revenue
FROM fact_sales f JOIN dim_product p ON p.product_key=f.product_key
                  JOIN dim_date d ON d.date_key=f.date_key
GROUP BY p.category, d.quarter;
```
**Why it works:** the central fact holds the numbers + dimension keys; flat dimensions make grouping
trivial; the query joins a few dimensions and aggregates — the natural analytics shape (add a
columnstore on `fact_sales` for speed on 🟦).

### 2. Choose the SCD type — `Easy`
**Task:** A customer's `city` changes when they move. You need "sales by the city the customer lived
in *at the time of each sale*." Which SCD type?
**Solution:** **Type 2** — add a new `dim_customer` row (new surrogate key) with `valid_from`/`valid_to`
when the city changes, keeping the old row. Each `fact_sales` row references the surrogate key current
at sale time, so historical sales stay attributed to the old city.
**Why it works:** Type 2 preserves dimension history, which is exactly what "as of the time of the
event" analysis requires; Type 1 (overwrite) would retroactively move all past sales to the new city.

## ✅ Key Takeaways

- A **data warehouse** is a separate, **denormalized**, read-optimized analytics database (OLAP) vs
  the normalized OLTP database.
- The **star schema**: a central **fact** table (measures + dimension FKs) surrounded by **dimension**
  tables (descriptive attributes). **Snowflake** normalizes dimensions (more joins).
- Use **surrogate keys**, a dedicated **date dimension**, and **conformed dimensions** (shared across
  facts).
- **Slowly Changing Dimensions** handle attribute history — **Type 2** (new row + validity dates) is
  the classic for preserving history.
- **🟦 columnstore** gives a strong built-in analytics story; large-scale warehousing often uses
  dedicated platforms (Synapse/Snowflake/BigQuery).
