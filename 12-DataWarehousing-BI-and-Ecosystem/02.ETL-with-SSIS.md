# ETL with SSIS (and PostgreSQL analogs)

## 🧠 Intuition

A warehouse doesn't fill itself — data must be **moved** from operational sources (databases, files,
APIs) into the warehouse, usually transformed along the way. That process is **ETL — Extract,
Transform, Load**. **SQL Server Integration Services (SSIS)** is Microsoft's flagship ETL platform.
PostgreSQL has no first-party SSIS equivalent — you use `COPY`, foreign data wrappers, or external
tools (Airflow, dbt, Talend).

> 💡 **Analogy — a factory assembly line for data.** Extract = receive raw materials (pull from
> sources). Transform = process them on the line (clean, reshape, combine, aggregate). Load = box up
> the finished product (insert into the warehouse). ETL is that assembly line, run on a schedule.

## 📐 ETL vs ELT

| | **ETL** | **ELT** |
|--|---------|---------|
| Order | Extract → **Transform** → Load | Extract → Load → **Transform** (in the warehouse) |
| Transform happens | In a separate engine (SSIS) before loading | Inside the powerful warehouse (SQL) |
| Best for | Traditional warehouses, complex transforms | Modern cloud warehouses (Snowflake/BigQuery) + **dbt** |

The industry has shifted toward **ELT** for cloud warehouses (load raw, transform with SQL/dbt
leveraging the warehouse's compute) — but ETL (SSIS) remains widespread in Microsoft enterprises.

## 💻 🟦 SQL Server — SSIS

SSIS is a visual ETL tool (designed in Visual Studio / SSDT) where you build **packages**:

- **Control Flow** — the orchestration: tasks run in sequence/parallel with precedence (Execute SQL,
  File System, Data Flow, Send Mail, loops).
- **Data Flow** — the row-by-row pipeline: a **source** (DB/file/API) → **transformations** (lookup,
  derived column, conditional split, aggregate, merge, slowly-changing-dimension wizard, data
  cleansing) → a **destination** (the warehouse).
- **Connection managers** for sources/targets; **parameters/variables** for configuration;
  deployment to the **SSIS Catalog**; scheduled via **SQL Server Agent** ([Automation](../11-Operations/04.Automation.md)).

```text
Control Flow:  [Truncate Staging] → [Data Flow: Load Sales] → [Execute SQL: Merge into Fact] → [Send Mail on done]
Data Flow:     [OLE DB Source: orders] → [Lookup: dim_product] → [Derived Column: amount] → [SCD wizard] → [OLE DB Destination: fact_sales]
```

SSIS handles bulk loading, restartability, logging, error rows (redirect bad rows), and complex
multi-source merges — the workhorse of Microsoft-stack data integration.

## 💻 🐘 PostgreSQL — the ETL/ELT toolbox

PostgreSQL has **no SSIS**. The analogs:

```sql
-- COPY: blazing-fast bulk load from/to a file (the bulk-load workhorse)
COPY staging_sales FROM '/data/sales.csv' WITH (FORMAT csv, HEADER true);
COPY (SELECT * FROM fact_sales WHERE year = 2025) TO '/export/sales2025.csv' WITH (FORMAT csv, HEADER true);

-- Foreign Data Wrappers (FDW): query external sources AS IF they were local tables
CREATE EXTENSION postgres_fdw;
-- (set up a foreign server + user mapping) then:
CREATE FOREIGN TABLE src_orders (...) SERVER source_db OPTIONS (table_name 'orders');
INSERT INTO staging_orders SELECT * FROM src_orders;   -- pull from another database
```

| Need | PostgreSQL approach |
|------|---------------------|
| Bulk load files | **`COPY`** (extremely fast) / `\copy` in psql |
| Pull from other databases | **`postgres_fdw`** / `mysql_fdw` / `file_fdw` (foreign data wrappers) |
| Orchestration/scheduling | **Apache Airflow**, **dbt** (ELT transforms), cron, k8s |
| Visual ETL | external tools: **Talend**, **Pentaho**, **Apache NiFi**, Fivetran/Airbyte (ingestion) |
| In-DB transforms (ELT) | plain SQL / `INSERT ... SELECT` / `MERGE` / materialized views, orchestrated by dbt |

> The modern PostgreSQL data stack is typically **EL** (Fivetran/Airbyte or `COPY`/FDW to load) **+ T**
> (dbt running SQL transforms in the warehouse) **+ orchestration** (Airflow) — an ELT pipeline rather
> than a monolithic ETL tool.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| First-party ETL | **SSIS** (visual, full-featured) | **None** (use external tools) |
| Bulk load | `BULK INSERT` / `bcp` / SSIS | **`COPY`** |
| Cross-source | SSIS connection managers / linked servers | **FDWs** (postgres_fdw, etc.) |
| Orchestration | **SQL Server Agent** | Airflow / pg_cron / cron |
| Transform style | ETL (in SSIS) | usually **ELT** (dbt + SQL) |
| Cloud | Azure Data Factory (cloud ETL) | cloud ETL/ELT services |

> Microsoft's **cloud** ETL successor to SSIS is **Azure Data Factory** (and SSIS can run in ADF). The
> PostgreSQL world leans on best-of-breed open tools.

## 🚫 Common mistakes

```text
❌ Hand-rolling fragile custom ETL scripts when a tool/framework fits → unmaintainable. ✅ SSIS / dbt / Airflow.
❌ Row-by-row loading into the warehouse → slow. ✅ bulk load (COPY / bcp / SSIS fast-load).
❌ No restartability/logging → a failed 3-hour load restarts from zero. ✅ stage + idempotent loads + checkpoints.
❌ Transforming huge data outside the warehouse when ELT-in-warehouse would be faster. ✅ ELT with dbt for cloud DWs.
❌ Loading directly into fact tables without staging → hard to validate/clean. ✅ stage → validate → merge.
```

## 🌍 Real-World Use

- **Microsoft shops:** SSIS packages (or Azure Data Factory) extract from ERP/OLTP/files, transform
  (lookups, SCD, cleansing), and bulk-load star-schema warehouses, scheduled via SQL Server Agent.
- **PostgreSQL/cloud shops:** Fivetran/Airbyte or `COPY`/FDW load raw data; **dbt** runs SQL transforms
  in the warehouse (ELT); **Airflow** orchestrates; everything version-controlled.
- Both stage data first, validate, then merge into facts/dimensions with idempotent, restartable
  loads.

## 🎯 Practice (with full solutions)

### 1. Bulk-load a CSV into staging — `Easy`
**Task:** Load `sales.csv` into a `staging_sales` table as fast as possible, in each engine.
**Solution:**
```sql
-- 🐘 PostgreSQL: COPY (server-side) or \copy (client-side in psql)
COPY staging_sales FROM '/data/sales.csv' WITH (FORMAT csv, HEADER true);
```
```sql
-- 🟦 SQL Server: BULK INSERT (or bcp / SSIS fast-load)
BULK INSERT staging_sales FROM 'D:\data\sales.csv'
WITH (FORMAT='CSV', FIRSTROW=2, FIELDTERMINATOR=',', ROWTERMINATOR='\n');
```
**Why it works:** bulk-load paths (`COPY` / `BULK INSERT`) load thousands of rows per second by
bypassing per-row overhead — far faster than `INSERT` statements, the right way to land data in
staging.

### 2. Pull from another database (🐘) — `Medium`
**Task:** Extract `orders` from a separate PostgreSQL source database into your warehouse staging,
without an external tool.
**Solution:**
```sql
-- 🐘 postgres_fdw: query the remote table as if it were local
CREATE EXTENSION IF NOT EXISTS postgres_fdw;
CREATE SERVER source_db FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host 'src', dbname 'shop');
CREATE USER MAPPING FOR current_user SERVER source_db OPTIONS (user 'etl', password '...');
IMPORT FOREIGN SCHEMA public LIMIT TO (orders) FROM SERVER source_db INTO staging;
INSERT INTO staging_orders SELECT * FROM staging.orders WHERE order_date >= CURRENT_DATE - 1;  -- incremental
```
**Why it works:** the foreign data wrapper exposes the remote `orders` table locally, so a normal
`INSERT ... SELECT` extracts it (here incrementally) — PostgreSQL's built-in answer to SSIS's
cross-source extraction.

## ✅ Key Takeaways

- **ETL = Extract, Transform, Load** fills the warehouse; modern cloud stacks favor **ELT** (load raw,
  transform in-warehouse with **dbt**).
- **🟦: SSIS** — visual, full-featured ETL (control flow + data flow, SCD wizard, error handling),
  scheduled by **SQL Server Agent**; **Azure Data Factory** is the cloud successor.
- **🐘: no SSIS** — use **`COPY`** (bulk load), **FDWs** (cross-source), and external tools
  (**Airflow**, **dbt**, Fivetran/Airbyte) for an ELT pipeline.
- Always **bulk-load** (not row-by-row), **stage → validate → merge**, and make loads **idempotent and
  restartable**.
