# PolyBase, Foreign Data Wrappers & Big Data

## 🧠 Intuition

Sometimes the data you need lives **outside** your database — in another SQL Server, a PostgreSQL
instance, a CSV/Parquet file in cloud storage, Hadoop, or a different vendor's database. Instead of
copying it in first, **data virtualization** lets you query that external data **as if it were a local
table**. SQL Server calls this **PolyBase**; PostgreSQL calls it **Foreign Data Wrappers (FDW)**.

> 💡 **Analogy — a library inter-loan.** You don't physically move every book into your branch. A
> catalog entry lets you request and read a book from another branch as if it were on your shelf.
> PolyBase/FDW are catalog entries pointing at external data — you query through them, the engine
> fetches on demand.

## 📐 Data virtualization

- **Query external data in place** — no (or minimal) copying; you `SELECT ... JOIN` an external source
  alongside local tables.
- **Push-down** — both engines try to push filters/aggregations to the remote source so less data
  crosses the wire.
- Trade-off: convenient and copy-free, but performance depends on the **remote source and network**;
  for heavy repeated analytics, ETL into a local/warehouse table is often faster.

## 💻 🟦 SQL Server — PolyBase

PolyBase (enable the feature, then create an **external data source** + **external table**) lets
T-SQL query external data — other databases, files in Azure Blob/ADLS/S3, Hadoop, etc.:

```sql
-- 1. External data source (e.g. another SQL Server / blob storage / generic ODBC)
CREATE EXTERNAL DATA SOURCE ext_sales
WITH (LOCATION = 'sqlserver://reporting-srv', CREDENTIAL = sql_cred);

-- 2. External table maps a remote table into the local catalog
CREATE EXTERNAL TABLE ext_orders (
    order_id INT, customer_id INT, order_date DATE, total DECIMAL(12,2)
) WITH (LOCATION = 'sales.dbo.orders', DATA_SOURCE = ext_sales);

-- 3. Query it like a local table — even JOIN to local tables
SELECT c.name, SUM(o.total)
FROM ext_orders o JOIN dbo.customers c ON c.customer_id = o.customer_id
GROUP BY c.name;
```

PolyBase supports SQL Server, Oracle, Teradata, MongoDB, generic ODBC, and files (CSV/Parquet) in
object storage. (In Azure Synapse, PolyBase/`COPY` is the bulk-load path from the data lake.)

## 💻 🐘 PostgreSQL — Foreign Data Wrappers (FDW)

FDW is PostgreSQL's SQL-standard data-virtualization mechanism. **`postgres_fdw`** connects to another
PostgreSQL; many other wrappers exist for other sources:

```sql
CREATE EXTENSION IF NOT EXISTS postgres_fdw;

-- 1. Foreign server + user mapping
CREATE SERVER reporting_srv FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'reporting-host', dbname 'sales', port '5432');
CREATE USER MAPPING FOR current_user SERVER reporting_srv
    OPTIONS (user 'reader', password '***');

-- 2. Foreign table (or IMPORT FOREIGN SCHEMA to bring many at once)
CREATE FOREIGN TABLE ext_orders (
    order_id int, customer_id int, order_date date, total numeric(12,2)
) SERVER reporting_srv OPTIONS (schema_name 'public', table_name 'orders');

-- 3. Query like a local table, JOIN to local tables
SELECT c.name, SUM(o.total)
FROM ext_orders o JOIN customers c ON c.customer_id = o.customer_id
GROUP BY c.name;
```

The FDW ecosystem is broad: **`postgres_fdw`**, **`file_fdw`** (CSV), **`oracle_fdw`**, **`mysql_fdw`**,
**`tds_fdw`** (→ SQL Server!), **`mongo_fdw`**, **`parquet_fdw`**, plus cloud/lake wrappers. `IMPORT
FOREIGN SCHEMA` maps many foreign tables at once.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Mechanism | **PolyBase** (external data source + external table) | **Foreign Data Wrappers** (`postgres_fdw`, etc.) |
| Cross-engine reach | SQL Server, Oracle, Teradata, MongoDB, ODBC, files | many FDWs (incl. `tds_fdw` → SQL Server) |
| Files in object storage | Azure Blob/ADLS/S3 (CSV/Parquet) | `file_fdw`, `parquet_fdw`, lake extensions |
| Bring many tables | per external table | **`IMPORT FOREIGN SCHEMA`** |
| Bulk-load cousin | `COPY` / `BULK INSERT` / Synapse `COPY` | `COPY` |
| Older linked alternative | **Linked Servers** (`OPENQUERY`) | dblink extension |

> Both engines can even reach **each other**: PolyBase (or a linked server) from SQL Server to
> PostgreSQL, and `tds_fdw` from PostgreSQL to SQL Server.

## 📐 Big-data landscape (where this fits)

Data virtualization is one option among several for "data bigger than one database":

- **Cloud data warehouses** — Azure Synapse, Snowflake, BigQuery, Redshift: massively parallel,
  columnar, separate storage/compute; PolyBase/`COPY` (🟦) load from the lake.
- **Lakehouse / data lake** — Parquet/Delta files in object storage queried by Spark/Databricks/
  Synapse; both engines can read lake files (PolyBase / `parquet_fdw`).
- **Distributed PostgreSQL** — **Citus** shards PostgreSQL across nodes for scale-out (see
  [Scaling Out](../07-Partitioning-and-Scale/03.Scaling-Out.md)).
- **Streaming** — Kafka/Debezium for change-data-capture feeding warehouses in near-real-time.

## ⚖️ Virtualize vs ingest

- **Virtualize (PolyBase/FDW)** when: data is occasional/ad-hoc, must stay at the source, or you're
  doing a one-off join. No copy, always current, minimal storage.
- **Ingest (ETL/ELT into a local/warehouse table)** when: the data is queried heavily/repeatedly,
  needs indexing, or the remote source is slow/unreliable. A local copy you can index and optimize
  beats repeatedly pulling across the wire.

## 🚫 Common mistakes

```text
❌ Running heavy repeated analytics through FDW/PolyBase against a slow remote → every query pays the network cost.
✅ for hot, repeated queries, ETL the data local and index it; virtualize for ad-hoc/occasional.

❌ Expecting full push-down always → some predicates/functions can't push down, dragging all rows over the wire.
✅ check the plan; keep remote-side filters simple and SARGable so they push down.

❌ Forgetting credentials/security on the foreign source → exposing or failing the connection.
✅ use proper CREDENTIAL (🟦) / USER MAPPING (🐘) with least privilege.

❌ Treating virtualization as a substitute for a warehouse at scale → use a real DW (Synapse/Snowflake/Citus).
```

## 🌍 Real-World Use

- **🟦:** PolyBase to query a CSV/Parquet data lake or another database without ETL; Synapse uses
  PolyBase/`COPY` to bulk-load from the lake; linked servers for legacy cross-database queries.
- **🐘:** `postgres_fdw` to query/join another PostgreSQL (sharding, multi-tenant, cross-service
  reporting); `file_fdw`/`parquet_fdw` over lake files; `tds_fdw`/`oracle_fdw` to integrate other
  vendors. Citus for true scale-out.
- **Both:** a "logical data warehouse" pattern — virtualize sources for ad-hoc joins, ingest the hot
  paths into a real warehouse.

## 🎯 Practice (with full solutions)

### 1. Join across two databases — `Medium`
**Task:** Customers are in your local DB; orders live in a separate reporting database. Produce
revenue-per-customer **without copying** the orders table, on each engine.
**Solution:**
```sql
-- 🟦 SQL Server: PolyBase external table over the remote orders, then JOIN local customers
SELECT c.name, SUM(o.total) AS revenue
FROM ext_orders o JOIN dbo.customers c ON c.customer_id = o.customer_id
GROUP BY c.name;

-- 🐘 PostgreSQL: postgres_fdw foreign table over remote orders, JOIN local customers
SELECT c.name, SUM(o.total) AS revenue
FROM ext_orders o JOIN customers c ON c.customer_id = o.customer_id
GROUP BY c.name;
```
**Why it works:** the external/foreign table makes the remote `orders` queryable in place; the engine
fetches (ideally with the `SUM`/filter pushed down) and joins to local `customers` — no ETL copy
needed. For a one-off or occasional report this is ideal.

### 2. Virtualize or ingest? — `Easy`
**Task:** A dashboard runs the cross-database revenue query above **every few seconds** and it's slow.
Keep virtualizing or change approach?
**Solution:** **Ingest** — for a hot, repeated query, replace live virtualization with **ETL/ELT**:
load `orders` into a local (or warehouse) table on a schedule (or via CDC), index it, and query
locally. Reserve PolyBase/FDW for ad-hoc/occasional access.
**Why it works:** virtualization pays the remote+network cost on every call; a local indexed copy
amortizes one load across many fast queries — the right trade-off for high-frequency analytics.

## ✅ Key Takeaways

- **Data virtualization** queries **external** data as if local: **🟦 PolyBase** (external data source +
  external table) vs **🐘 Foreign Data Wrappers** (`postgres_fdw`, `file_fdw`, `tds_fdw`, …;
  `IMPORT FOREIGN SCHEMA`).
- Both reach other databases and **files (CSV/Parquet) in object storage**; both can even reach **each
  other**; older 🟦 alternative is **linked servers**, 🐘's is **dblink**.
- **Push-down** filters/aggregations to minimize data over the wire; check the plan.
- **Virtualize** for ad-hoc/occasional/copy-free access; **ingest (ETL/ELT)** for hot, repeated,
  index-needing analytics. At scale, use a **cloud warehouse / Citus / lakehouse**.
