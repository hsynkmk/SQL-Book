# Reporting with SSRS (and PostgreSQL analogs)

## 🧠 Intuition

Sometimes you don't need an interactive dashboard — you need a **paginated report**: a precisely
formatted, printable document (an invoice, a monthly financial statement, a regulatory filing) that
looks the same every time, paginates cleanly, and can be scheduled and emailed. **SQL Server
Reporting Services (SSRS)** is Microsoft's paginated-reporting platform. PostgreSQL has no first-party
equivalent — you use external reporting tools.

> 💡 **Analogy — a printed report vs a live dashboard.** A dashboard ([Power BI](05.Power-BI-Integration.md))
> is an interactive screen you explore. A paginated report is a *printed document* — pixel-perfect,
> page-numbered, header/footer on every page, designed to be printed or PDF'd and filed. Invoices,
> payslips, and statements are paginated reports.

## 📐 Paginated vs interactive

| | Paginated report (SSRS) | Interactive dashboard (Power BI) |
|--|-------------------------|----------------------------------|
| Format | Pixel-perfect, printable, multi-page | Interactive, exploratory, on-screen |
| Best for | Invoices, statements, regulatory docs, operational lists | Trend analysis, KPIs, drill-down |
| Output | PDF, Word, Excel, print | Live tiles, filters |
| Delivery | Scheduled email/file (subscriptions) | Self-service exploration |

## 💻 🟦 SQL Server — SSRS

SSRS reports are designed in **Report Builder** or Visual Studio (SSDT), defined in **RDL** (Report
Definition Language, an XML format), and hosted on the **Report Server / web portal**:

- **Datasets** — SQL queries (or stored procedures) against the database/warehouse.
- **Parameters** — user inputs that filter the report (date range, region) — often driven by
  parameterized SQL.
- **Layout** — tables, matrices (cross-tabs/pivots), charts, lists, with precise formatting, grouping,
  page headers/footers, and page breaks.
- **Subscriptions** — schedule the report to render and **deliver** (email, file share) automatically.
- **Power BI Report Server** — an on-prem option that hosts both SSRS paginated reports *and* Power BI
  reports together.

```text
SSRS report:  Dataset (SELECT ... FROM fact_sales WHERE region = @Region AND year = @Year)
              + Parameters (@Region, @Year)
              + Matrix (rows: product category, columns: month, values: SUM(amount))
              + Chart + page header/footer
              → rendered to PDF, emailed monthly via a subscription.
```

## 💻 🐘 PostgreSQL — reporting analogs

PostgreSQL has **no SSRS**. Paginated/operational reporting options (all database-agnostic — they
connect to PostgreSQL via standard drivers):

| Need | Tool |
|------|------|
| Open-source paginated reports | **JasperReports** (+ JasperReports Server), **BIRT**, **Pentaho Reporting** |
| Commercial | **Crystal Reports**, **Power BI paginated reports** (connects to PG), **Telerik Reporting** |
| Pixel-perfect docs from data | Jasper/BIRT (RDL-like designers), or app-side PDF generation |
| Scheduled delivery | JasperReports Server, Pentaho, or a cron job rendering + emailing |
| Modern operational dashboards | **Metabase**, **Apache Superset**, **Grafana** (also do some reporting) |

> The key point: **paginated reporting tools are mostly database-agnostic** — JasperReports, Crystal,
> and even Power BI paginated reports happily connect to PostgreSQL via JDBC/ODBC/Npgsql. So a
> PostgreSQL shop uses these instead of SSRS; the report *engine* is just not bundled with the
> database.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| First-party reporting | **SSRS** (RDL, Report Server, subscriptions) | None |
| Open-source analog | (Power BI Report Server) | **JasperReports**, **BIRT**, **Pentaho** |
| Modern/dashboards | Power BI | **Metabase**, **Superset**, Grafana |
| Connectivity | native | via ODBC/JDBC/Npgsql (tools connect fine) |

## ⚖️ When you actually need paginated reporting

Most "reporting" today is interactive dashboards (Power BI/Metabase/Superset). Paginated reporting is
specifically for **documents** — things that must print or PDF identically every time: invoices,
account statements, payslips, regulatory/compliance filings, picking lists, certificates. If you need
pixel-perfect, multi-page, scheduled documents, that's SSRS (🟦) or JasperReports/BIRT/Crystal (any
DB). If you need exploration and KPIs, that's a BI tool.

## 🚫 Common mistakes

```text
❌ Forcing pixel-perfect invoices out of an interactive dashboard tool → fights its layout model.
✅ paginated reporting (SSRS / Jasper / BIRT) for document-style output.

❌ Building a custom PDF-from-SQL engine when JasperReports/SSRS exists → reinventing the wheel.
✅ use a reporting tool with a designer, parameters, and scheduled delivery.

❌ Assuming PostgreSQL can't do paginated reports → it can, via DB-agnostic tools (Jasper/BIRT/Crystal/Power BI).

❌ Running heavy report queries against the OLTP database → use a warehouse/replica for reporting load.
```

## 🌍 Real-World Use

- **Microsoft enterprises:** SSRS for operational/regulatory paginated reports (invoices, statements,
  audit docs), with scheduled email subscriptions; Power BI for dashboards.
- **PostgreSQL/open shops:** **JasperReports**/BIRT for paginated documents, **Metabase**/**Superset**
  for self-service dashboards — all connecting to PostgreSQL.
- Report queries typically run against a **warehouse or read replica**, not the OLTP primary, to avoid
  loading the transactional path.

## 🎯 Practice (with full solutions)

### 1. Choose the right tool — `Easy`
**Task:** For each, pick paginated reporting or an interactive dashboard: (a) a monthly customer
invoice PDF, (b) a sales-trends KPI screen analysts explore, (c) a regulatory compliance filing.
**Solution:** (a) **paginated** (SSRS / Jasper) — a precise, printable document. (b) **interactive
dashboard** (Power BI / Metabase / Superset) — exploration and KPIs. (c) **paginated** — pixel-perfect,
fixed-format document for submission.
**Why it matters:** matching the output type (document vs exploration) to the tool avoids fighting the
tool's design — paginated for documents, dashboards for analysis.

### 2. Paginated reporting on PostgreSQL — `Easy`
**Task:** Your data is in PostgreSQL and you need scheduled, pixel-perfect monthly statements. You
don't have SSRS. What do you use?
**Solution:** Use a **database-agnostic paginated reporting tool** — **JasperReports** (with
JasperReports Server for scheduling/delivery), **BIRT**, or **Crystal Reports** — connecting to
PostgreSQL via **JDBC/ODBC**. Design the statement layout with parameters (account, period), and
schedule rendering + email delivery. (Power BI paginated reports also connect to PostgreSQL.)
**Why it works:** the reporting engine is independent of the database; these tools connect to
PostgreSQL just like to SQL Server, providing SSRS-equivalent paginated output and scheduling.

## ✅ Key Takeaways

- **Paginated reports** are pixel-perfect, printable, multi-page **documents** (invoices, statements,
  filings) — distinct from interactive dashboards.
- **🟦: SSRS** — RDL reports, datasets/parameters, Report Server portal, **scheduled subscriptions**;
  Power BI Report Server hosts both.
- **🐘: no SSRS** — use **database-agnostic** tools (**JasperReports**, **BIRT**, **Crystal**, Power BI
  paginated) that connect via JDBC/ODBC/Npgsql.
- Use **paginated** for documents, **dashboards** (Power BI/Metabase/Superset) for exploration; run
  report queries against a **warehouse/replica**, not the OLTP primary.
