# OLAP with SSAS (and PostgreSQL analogs)

## 🧠 Intuition

A star-schema warehouse is great, but analysts running ad-hoc "slice and dice" — revenue by product
by region by month, drill down to week, pivot by channel — want **instant** answers over huge data.
**OLAP (Online Analytical Processing)** pre-aggregates data into a **semantic model** ("cube" or
tabular model) so those multidimensional queries return in milliseconds. **SQL Server Analysis
Services (SSAS)** is Microsoft's OLAP engine. PostgreSQL has no first-party OLAP server — you use
external tools or pre-aggregation.

> 💡 **Analogy — pre-cooked meal components.** Instead of cooking every dish from raw ingredients on
> demand (re-aggregating the warehouse each query), a buffet pre-prepares components so any plate
> assembles instantly. An OLAP cube pre-computes aggregations across every dimension combination, so
> "slice by these, drill into that" is instant.

## 📐 The OLAP concepts

- **Cube / model** — a multidimensional structure with **measures** (the numbers: sales, quantity)
  and **dimensions** (the axes: product, time, geography), built from the warehouse star schema.
- **Slicing & dicing** — filter to a subset (slice: "just 2025") and view across dimensions (dice:
  "by product *and* region").
- **Drill down / roll up** — navigate the hierarchy (year → quarter → month → day; country → region →
  store).
- **Pre-aggregation** — the cube stores rolled-up totals so queries don't re-scan the fact table.

## 💻 🟦 SQL Server — SSAS (two flavors)

SSAS comes in two modes (built in Visual Studio / SSDT, deployed to an SSAS server):

| Mode | Storage | Query language | Best for |
|------|---------|----------------|----------|
| **Multidimensional** (classic cubes) | MOLAP (pre-aggregated) | **MDX** | Complex hierarchies, traditional OLAP |
| **Tabular** (modern, in-memory) | VertiPaq columnar in-memory | **DAX** | Most new projects; powers Power BI |

```text
-- Conceptual tabular model:
Measures:    Total Sales = SUM(fact_sales[amount])     -- DAX measure
             YoY Growth  = ([Total Sales] - [Total Sales LY]) / [Total Sales LY]
Dimensions:  Date (Year→Quarter→Month), Product (Category→Brand→Product), Geography (Region→Store)
-- Clients (Excel, Power BI) connect and pivot/slice instantly against the model.
```

- **Tabular** is the modern default — it's the **same VertiPaq engine that powers Power BI**, uses
  **DAX** for measures, is in-memory columnar (fast), and is easier than multidimensional.
- **Multidimensional** cubes (MDX) handle very complex hierarchies and are still used in legacy/
  enterprise BI.

The **semantic model** centralizes business logic (a single definition of "Net Revenue," "Active
Customer") so every report uses consistent numbers — a key benefit beyond speed.

## 💻 🐘 PostgreSQL — OLAP analogs

PostgreSQL has **no OLAP server** like SSAS. The approaches:

| Need | PostgreSQL / open approach |
|------|----------------------------|
| Pre-aggregation | **Materialized views** ([Views](../03-Modifying-Data-and-DDL/05.Views-and-Materialized-Views.md)) refreshed on a schedule; rollup tables |
| Fast multidimensional queries | **Columnar** (Citus/Hydra), `ROLLUP`/`CUBE`/`GROUPING SETS`, parallel query |
| Semantic layer | external BI tools' models (**Power BI**, **Looker/LookML**, **dbt metrics/Cube.dev**) |
| Dedicated OLAP engine | external: **ClickHouse**, **Apache Druid**, **Apache Pinot**, cloud warehouses |
| Cube-like tools | **Mondrian** (open-source OLAP), **Apache Kylin** |

> The modern pattern: PostgreSQL (or a cloud warehouse) holds the star schema; the **semantic layer
> lives in the BI tool** (Power BI's tabular model, Looker's LookML, **Cube.dev**, dbt metrics) rather
> than a separate OLAP server. For sub-second analytics at huge scale, a dedicated columnar OLAP
> engine (ClickHouse/Druid) is used.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| OLAP server | **SSAS** (multidimensional + tabular) | None (external/materialized views) |
| Query languages | **MDX** (cubes), **DAX** (tabular) | SQL (+ tool-specific: DAX in Power BI) |
| Pre-aggregation | cube processing | materialized views / rollup tables |
| Semantic model | SSAS model (centralized) | BI-tool model / dbt metrics / Cube.dev |
| In-memory columnar | VertiPaq (tabular) | columnstore extensions / external |

## ⚖️ Do you even need OLAP?

Modern fast columnar warehouses (Synapse, Snowflake, BigQuery, columnstore SQL Server) can often
aggregate huge data fast enough that a **separate OLAP cube is unnecessary** — the BI tool queries the
warehouse directly with its own semantic model. SSAS (especially tabular) still shines for: a
**centralized, governed semantic layer** shared across many reports, very **complex calculations**
(DAX time-intelligence), and **enterprise BI** consistency. Evaluate need vs the simpler "BI tool on a
fast warehouse" approach.

## 🚫 Common mistakes

```text
❌ Building an SSAS cube when a fast columnstore warehouse + Power BI model would suffice → needless complexity.
✅ start with BI-tool-on-warehouse; add SSAS for governed semantic layers / complex DAX at scale.

❌ Choosing multidimensional (MDX) for a new project → harder, legacy. ✅ tabular (DAX) for most new work.

❌ Defining "Revenue" differently in every report → inconsistent numbers. ✅ a single semantic model.

❌ 🐘: expecting a built-in cube engine → there isn't one. ✅ materialized views / BI semantic layer / ClickHouse.
```

## 🌍 Real-World Use

- **Microsoft BI:** SSAS **Tabular** models centralize metrics and feed Power BI; Excel users pivot
  against cubes; complex DAX time-intelligence (YoY, YTD, rolling averages) lives in one model.
- **PostgreSQL/modern:** the semantic layer lives in **Power BI / Looker / dbt metrics / Cube.dev** on
  top of the warehouse; **materialized views** pre-aggregate; **ClickHouse/Druid** for sub-second
  analytics at scale.
- Increasingly, fast cloud warehouses make a separate cube optional — the BI tool models directly.

## 🎯 Practice (with full solutions)

### 1. Pre-aggregate without an OLAP server (🐘) — `Medium`
**Task:** Analysts re-run "revenue by category by month" constantly and it scans the fact table each
time. Speed it up on PostgreSQL (no SSAS).
**Solution:**
```sql
-- Materialized view pre-aggregates the rollup; refresh on a schedule (pg_cron)
CREATE MATERIALIZED VIEW mv_revenue_cat_month AS
SELECT p.category, date_trunc('month', d.full_date) AS month, SUM(f.amount) AS revenue
FROM fact_sales f JOIN dim_product p ON p.product_key=f.product_key
                  JOIN dim_date d ON d.date_key=f.date_key
GROUP BY p.category, date_trunc('month', d.full_date);
CREATE UNIQUE INDEX ON mv_revenue_cat_month (category, month);
-- pg_cron: REFRESH MATERIALIZED VIEW CONCURRENTLY mv_revenue_cat_month nightly.
```
**Why it works:** the materialized view stores the pre-computed rollup (the "cube" of this query), so
analysts read tiny, indexed summary rows instantly instead of re-aggregating the fact table — the
poor-man's OLAP for PostgreSQL.

### 2. Pick the SSAS mode — `Easy`
**Task (🟦):** A new BI project needs a semantic model feeding Power BI with custom measures. SSAS
multidimensional or tabular?
**Solution:** **Tabular** — it's the modern default, uses the same VertiPaq engine as Power BI, models
with **DAX** (matching Power BI), is in-memory/fast, and is simpler than multidimensional. Choose
multidimensional only for legacy cubes or very complex hierarchies requiring MDX.
**Why it works:** tabular aligns with the Power BI stack and modern practice; multidimensional/MDX is
the older, more complex path reserved for specific legacy needs.

## ✅ Key Takeaways

- **OLAP** pre-aggregates the warehouse into a **semantic model (cube/tabular)** for instant
  slice/dice/drill-down and a **centralized definition of metrics**.
- **🟦: SSAS** — **Tabular** (modern, in-memory VertiPaq, **DAX**, powers Power BI) vs
  **Multidimensional** (classic cubes, **MDX**). Prefer tabular for new work.
- **🐘: no OLAP server** — use **materialized views**/rollup tables, the **BI tool's semantic layer**
  (Power BI/Looker/dbt metrics/**Cube.dev**), or dedicated engines (**ClickHouse/Druid**).
- Fast columnar warehouses often make a **separate cube optional** — BI-tool-on-warehouse may suffice;
  SSAS earns its place for governed semantics and complex DAX at scale.
