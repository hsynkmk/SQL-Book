# Optimistic vs Pessimistic Concurrency

## 🧠 Intuition

When two users might edit the same row, you have two strategies. **Pessimistic**: assume conflict is
likely — **lock the row** the moment you read it, so no one else can touch it until you're done.
**Optimistic**: assume conflict is rare — don't lock; just **check at save time** whether the row
changed since you read it, and if so, reject the update. The right choice depends on how much
contention you actually have.

> 💡 **Analogy — a library book.** Pessimistic: you check the book out the moment you glance at it,
> so nobody else can read it while you decide. Optimistic: you read it on the shelf and only at
> checkout does the librarian verify nobody else changed it meanwhile — if they did, you start over.
> Optimistic wins when conflicts are rare (most reads don't lead to edits); pessimistic wins when
> they're frequent.

## 📐 The two strategies

| | Pessimistic | Optimistic |
|--|-------------|------------|
| Assumption | Conflicts are **likely** | Conflicts are **rare** |
| Mechanism | **Lock** the row on read (`FOR UPDATE`) | **Version/timestamp check** at write |
| Cost | Holds locks → blocking, less concurrency | No locks → must handle the occasional conflict (retry) |
| Best for | Hot rows, short critical sections, high contention | Web apps, long "think time," low contention |
| Failure mode | Others wait/timeout | Update rejected → app retries or asks user |

## 💻 Pessimistic — lock the row

`SELECT ... FOR UPDATE` (🐘) / `WITH (UPDLOCK)` (🟦) locks the selected rows until the transaction
ends, so a concurrent transaction can't modify them:

```sql
-- 🐘 PostgreSQL
BEGIN;
    SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- lock row 1
    -- ... compute new balance based on the locked value ...
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```
```sql
-- 🟦 SQL Server
BEGIN TRANSACTION;
    SELECT balance FROM accounts WITH (UPDLOCK, ROWLOCK) WHERE id = 1;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

The lock guarantees the value you read can't change before you write — no lost updates — but other
transactions block on that row. Keep the locked section **short**. 🐘 also offers `FOR UPDATE SKIP
LOCKED` (skip already-locked rows) and `FOR UPDATE NOWAIT` (fail instead of wait) — great for **job
queues**.

## 💻 Optimistic — version/timestamp check

Add a version column; on update, assert it hasn't changed since you read it. If the `WHERE` matches
0 rows, someone else won the race.

```sql
-- A 'version' (or rowversion/xmin) column tracks each change
-- Read: get the current version
SELECT id, balance, version FROM accounts WHERE id = 1;   -- say version = 7

-- Write: only succeeds if version is STILL 7, and bump it
UPDATE accounts
SET balance = @newBalance, version = version + 1
WHERE id = 1 AND version = 7;
-- if @@ROWCOUNT (🟦) / affected rows (🐘) = 0 → someone else updated it → conflict → retry
```

### Built-in version tokens

| | 🟦 SQL Server | 🐘 PostgreSQL |
|--|--------------|---------------|
| Auto version column | **`ROWVERSION`** (`rowversion`/`timestamp`) — auto-increments on every update | system **`xmin`** column (transaction id of last write) |
| Manual version | an `INT`/`bigint` you increment yourself | same |

```sql
-- 🟦 SQL Server: rowversion auto-changes on any update; check it on save
-- (column rv ROWVERSION)
UPDATE accounts SET balance = @newBalance WHERE id = 1 AND rv = @rvReadEarlier;

-- 🐘 PostgreSQL: use the hidden xmin
SELECT id, balance, xmin FROM accounts WHERE id = 1;          -- read xmin
UPDATE accounts SET balance = @newBalance WHERE id = 1 AND xmin = @xminReadEarlier::text::xid;
```

This is exactly how ORMs (EF Core, Hibernate) implement optimistic concurrency — they add a version
column and put it in the `WHERE`, throwing a "concurrency conflict" when 0 rows update.

## 💻 Deadlock & conflict retry

Both strategies need **retry logic**: pessimistic can deadlock; optimistic rejects conflicting
saves. Wrap the operation and retry a bounded number of times:

```sql
-- Pseudocode pattern (in app or a proc):
-- for attempt in 1..3:
--     try: run the transaction; break on success
--     catch deadlock (🟦 1205 / 🐘 40P01) or serialization_failure (40001) or 0-rows-updated:
--         wait a tiny random backoff; retry
-- else: surface the conflict to the user
```

## ⚖️ Choosing

- **Web / API apps** (read a row, user thinks for minutes, then saves) → **optimistic**. You can't
  hold a database lock across a user's coffee break, and conflicts are rare. Reject-and-retry on the
  rare clash.
- **Hot counters / inventory / queues** (many transactions hitting the same rows in milliseconds) →
  **pessimistic** (`FOR UPDATE`) or **atomic server-side updates** (`UPDATE ... SET stock = stock -
  1 WHERE stock > 0`), which sidestep the read-modify-write entirely.
- **High-throughput job queues** → `FOR UPDATE SKIP LOCKED` (🐘) so workers grab different rows without
  blocking each other.

## 🚫 Common mistakes

```sql
-- ❌ Read-modify-write without protection → lost update
SELECT balance FROM accounts WHERE id = 1;   -- read 500 (in two sessions)
-- both compute 500 - 100 = 400 and write 400 → one decrement is LOST (should be 300)
-- ✅ pessimistic (FOR UPDATE) OR optimistic (version check) OR atomic (SET balance = balance - 100)

-- ❌ Holding a pessimistic lock across user "think time" (a web form)
-- ✅ optimistic versioning for anything involving a human pause

-- ❌ Optimistic update with no conflict handling → silent overwrite or ignored failure
-- ✅ check affected-rows = 0 and retry / inform the user

-- ❌ Forgetting that an atomic UPDATE often beats both for simple counters
UPDATE inventory SET stock = stock - 1 WHERE product_id = 5 AND stock > 0;  -- no read needed, no lost update
```

## 🌍 Real-World Use

- **Optimistic:** the default for ORMs and web apps — edit a record, save, get a "this was changed by
  someone else" message on conflict.
- **Pessimistic:** banking/inventory critical sections, "claim this task" in a worker queue
  (`FOR UPDATE SKIP LOCKED`), seat/ticket reservation.
- **Atomic updates:** counters, stock decrements, like-counts — the simplest and often best answer,
  no read needed.

## 🎯 Practice (with full solutions)

### 1. Prevent a lost update (optimistic) — `Medium`
**Task:** Two users edit the same product. Ensure the second save fails if the row changed since they
loaded it.
**Solution:**
```sql
-- 🟦 SQL Server with rowversion column rv:
UPDATE products SET unit_price = @newPrice WHERE product_id = @id AND rv = @rvLoaded;
IF @@ROWCOUNT = 0 THROW 51000, 'Row was modified by another user', 1;
-- 🐘 PostgreSQL with a version INT column:
UPDATE products SET unit_price = @newPrice, version = version + 1
WHERE product_id = @id AND version = @versionLoaded;
-- check affected rows; 0 → conflict
```
**Why it works:** the version/`rv` in the `WHERE` makes the update succeed only if nobody else
changed the row since it was read; 0 affected rows signals the conflict so the app can retry or
prompt — no silent lost update.

### 2. Safe stock decrement (atomic / pessimistic) — `Medium`
**Task:** Decrement stock by 1 only if stock is available, with no lost updates under heavy
concurrency.
**Solution:**
```sql
-- Best: a single atomic conditional UPDATE (no read-modify-write, no explicit lock needed)
UPDATE inventory SET stock = stock - 1 WHERE product_id = 5 AND stock > 0;
-- affected rows = 1 → success; = 0 → out of stock

-- Pessimistic alternative when you must read-then-decide:
-- 🐘: SELECT stock FROM inventory WHERE product_id = 5 FOR UPDATE;  then UPDATE.
```
**Why it works:** the atomic `UPDATE ... WHERE stock > 0` does the read-check-write in one
statement the engine serializes per row — no lost updates, no separate lock, no version column.
It's usually the simplest correct answer for counters/inventory.

## ✅ Key Takeaways

- **Pessimistic** = lock on read (`FOR UPDATE` 🐘 / `WITH (UPDLOCK)` 🟦) — for **high-contention** hot
  rows and short critical sections.
- **Optimistic** = no lock; **version/timestamp check** at write (`WHERE version = @loaded`) — for
  **low-contention** web apps and long think-time; reject-and-retry on conflict. This is how ORMs do
  it.
- Built-in version tokens: **🟦 `ROWVERSION`**, **🐘 `xmin`**.
- For simple counters, an **atomic `UPDATE ... WHERE`** beats both — no read, no lost update.
- Both strategies need **retry** logic (deadlocks / conflicts).
