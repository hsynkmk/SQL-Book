# Isolation Levels

## 🧠 Intuition

The **I** in [ACID](01.Transactions-and-ACID.md) is *Isolation* — how much one transaction is
protected from the effects of others running at the same time. There's a fundamental trade-off:
**more isolation = more correctness but less concurrency** (more blocking/overhead); **less
isolation = more concurrency but more anomalies**. The **isolation level** is the dial you set to
choose your spot on that trade-off.

> 💡 **Analogy — a shared whiteboard.** If everyone can read it while someone's mid-edit (low
> isolation), you might read a half-finished, soon-to-be-erased note (an anomaly). If only one person
> can touch it at a time (high isolation), nobody sees garbage — but everyone waits in line. Isolation
> levels decide how much in-progress mess readers can see.

## 📐 The read phenomena (the anomalies)

Higher isolation prevents more of these:

| Phenomenon | What happens |
|------------|--------------|
| **Dirty read** | You read another transaction's **uncommitted** change (which may be rolled back) |
| **Non-repeatable read** | You read a row twice in your transaction and get **different values** (another txn updated it between) |
| **Phantom read** | You run the same query twice and get **different rows** (another txn inserted/deleted matching rows) |

## 📐 The four standard levels

| Level | Dirty read | Non-repeatable read | Phantom read |
|-------|:----------:|:-------------------:|:------------:|
| **READ UNCOMMITTED** | ✅ possible | ✅ possible | ✅ possible |
| **READ COMMITTED** | ❌ prevented | ✅ possible | ✅ possible |
| **REPEATABLE READ** | ❌ | ❌ prevented | ✅ possible |
| **SERIALIZABLE** | ❌ | ❌ | ❌ prevented (full isolation) |

`SERIALIZABLE` behaves *as if* transactions ran one after another — perfect correctness, most
contention. `READ UNCOMMITTED` allows everything — fastest, least safe.

## 🟦 SQL Server vs 🐘 PostgreSQL — the crucial defaults

This is one of the **most important conceptual differences** between the two engines:

| | 🟦 SQL Server | 🐘 PostgreSQL |
|--|--------------|---------------|
| **Default level** | **READ COMMITTED** (lock-based) | **READ COMMITTED** (MVCC-based) |
| How reads behave | Readers can **block** on writers' locks (default) | Readers **never block** writers (MVCC — see [MVCC vs Lock-Based](04.MVCC-vs-Lock-Based.md)) |
| Optimistic option | `READ_COMMITTED_SNAPSHOT` / `SNAPSHOT` isolation (opt-in, uses row versions in tempdb) | MVCC is the *only* mode — always versioned |
| `REPEATABLE READ` impl. | Locks read rows | Snapshot at first statement |
| `SERIALIZABLE` impl. | Range locks (can deadlock/block heavily) | **SSI** (Serializable Snapshot Isolation — optimistic, may abort with a serialization error) |
| Extra level | `SNAPSHOT` (transaction-level versioning) | (MVCC gives snapshot semantics natively) |

> **The headline:** by default, **🟦 SQL Server uses locking** so a reader can be *blocked* by an
> uncommitted writer (unless you enable `READ_COMMITTED_SNAPSHOT`, which many shops do). **🐘
> PostgreSQL uses MVCC** so **readers never block writers and writers never block readers** — each
> transaction sees a consistent snapshot. This shapes how the two engines feel under load.

## 💻 Setting the isolation level

```sql
-- 🟦 SQL Server
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;
    SELECT ...;
COMMIT;
-- Enable optimistic read-committed for the whole database (common best practice):
ALTER DATABASE MyDb SET READ_COMMITTED_SNAPSHOT ON;
```
```sql
-- 🐘 PostgreSQL (per transaction)
BEGIN ISOLATION LEVEL SERIALIZABLE;
    SELECT ...;
COMMIT;
-- or:
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

> 🐘 quirk: `READ UNCOMMITTED` is **treated as `READ COMMITTED`** — PostgreSQL never actually does
> dirty reads (its MVCC design makes them impossible). So you effectively have three levels there.

## 💻 The `SNAPSHOT` family (optimistic reads)

Snapshot isolation gives each transaction a **consistent point-in-time view** without blocking
writers — readers see data as it was when their transaction/statement began.

- **🟦:** opt-in via `SNAPSHOT` (transaction-level) or `READ_COMMITTED_SNAPSHOT` (statement-level).
  Uses **row versions stored in tempdb**. Hugely reduces reader/writer blocking — a popular setting.
- **🐘:** this *is* the default behavior (MVCC). Every `READ COMMITTED` statement sees a fresh
  snapshot; `REPEATABLE READ`/`SERIALIZABLE` freeze the snapshot for the whole transaction.

## ⚖️ Choosing a level

| Need | Use |
|------|-----|
| Max concurrency, dirty reads OK (rough estimates, dashboards) | `READ UNCOMMITTED` (🟦) — rarely worth it |
| Sensible default for most OLTP | **`READ COMMITTED`** (the default — usually right) |
| Re-read the same rows and need stable values within a txn | `REPEATABLE READ` |
| Critical correctness (financial postings, inventory invariants) | `SERIALIZABLE` (accept retries/contention) |
| Reduce 🟦 reader/writer blocking | enable `READ_COMMITTED_SNAPSHOT` |

**Default to `READ COMMITTED`** (it's the default for a reason); raise the level only for specific
transactions that need stronger guarantees, and prefer **optimistic/snapshot** approaches for
read-heavy workloads.

## 🚫 Common mistakes

```sql
-- ❌ Using READ UNCOMMITTED / WITH (NOLOCK) "for speed" everywhere (🟦)
SELECT * FROM orders WITH (NOLOCK);   -- dirty reads: can see uncommitted/rolled-back/duplicated/missing rows
-- ✅ enable READ_COMMITTED_SNAPSHOT for non-blocking reads WITHOUT dirty-read anomalies

-- ❌ Cranking everything to SERIALIZABLE "to be safe" → heavy blocking/deadlocks (🟦), serialization aborts (🐘)
-- ✅ READ COMMITTED default; SERIALIZABLE only where truly needed, with retry logic

-- ❌ 🐘: not handling serialization_failure under SERIALIZABLE → transaction aborts unhandled
-- ✅ catch SQLSTATE 40001 and RETRY the transaction

-- ❌ Assuming PostgreSQL can do dirty reads (it can't — READ UNCOMMITTED = READ COMMITTED)
```

## 🌍 Real-World Use

- **OLTP apps:** `READ COMMITTED` (with `READ_COMMITTED_SNAPSHOT` on 🟦) covers the vast majority of
  workloads.
- **Reports/analytics:** snapshot/MVCC reads run without blocking the busy write path.
- **Money & inventory:** `SERIALIZABLE` for the few transactions where a phantom or write-skew would
  be catastrophic — with retry-on-conflict logic.
- **The `NOLOCK` debate:** widely overused on 🟦; the right fix is usually snapshot isolation, not
  dirty reads.

## 🎯 Practice (with full solutions)

### 1. Match the anomaly to the level — `Easy`
**Task:** Which standard level is the lowest that prevents (a) dirty reads, (b) non-repeatable reads,
(c) phantom reads?
**Solution:** (a) **READ COMMITTED**, (b) **REPEATABLE READ**, (c) **SERIALIZABLE**.
**Why it matters:** picking the *lowest* level that prevents the anomaly you care about maximizes
concurrency while staying correct.

### 2. Non-blocking reads on SQL Server — `Medium`
**Task:** Reports are blocking the OLTP write path because readers wait on writers' locks. Fix it
without resorting to `NOLOCK`/dirty reads.
**Solution:**
```sql
-- 🟦 SQL Server: turn on optimistic read-committed (row-versioned reads)
ALTER DATABASE MyDb SET READ_COMMITTED_SNAPSHOT ON;
-- Now readers see a consistent committed snapshot via row versions and DON'T block on writers,
-- with NO dirty-read anomalies. (PostgreSQL already behaves this way by default — MVCC.)
```
**Why it works:** `READ_COMMITTED_SNAPSHOT` makes 🟦 readers use row versions (like 🐘's MVCC) instead
of taking shared locks — eliminating reader/writer blocking while keeping committed-read correctness.
It's the proper alternative to the overused `WITH (NOLOCK)`.

## ✅ Key Takeaways

- **Isolation level** trades correctness for concurrency: **READ UNCOMMITTED → READ COMMITTED →
  REPEATABLE READ → SERIALIZABLE** prevents progressively more anomalies (dirty/non-repeatable/
  phantom reads).
- Both default to **READ COMMITTED**, but **🟦 is lock-based** (readers can block on writers) while
  **🐘 is MVCC** (readers never block writers).
- **🟦's `READ_COMMITTED_SNAPSHOT`/`SNAPSHOT`** brings optimistic, non-blocking reads (row versions in
  tempdb); **🐘 does this natively**.
- Default to **READ COMMITTED**; use `SERIALIZABLE` only where needed (with **retry** logic for 🐘's
  serialization failures); avoid `NOLOCK` — use snapshot reads instead.
- 🐘 has no real dirty reads (`READ UNCOMMITTED` = `READ COMMITTED`).
