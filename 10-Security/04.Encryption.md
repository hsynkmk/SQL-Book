# Encryption

## 🧠 Intuition

Encryption protects data from being read by someone who shouldn't — in three places: **in transit**
(traveling over the network), **at rest** (sitting on disk), and **in use / column-level** (specific
sensitive fields, even from the DBA). Each defends against a different threat: a network sniffer, a
stolen disk/backup, and an over-privileged insider, respectively.

> 💡 **Analogy — protecting a letter.** In transit = a sealed, tamper-proof envelope (nobody reads it
> en route). At rest = a locked mailbox (a thief who grabs the mailbox can't read the letters). In
> use / column = the letter itself written in a code only the sender and recipient know (even the
> postal worker holding it can't read the secret parts).

## 📐 The three layers

| Layer | Protects against | Mechanism |
|-------|------------------|-----------|
| **In transit** | Network eavesdropping | **TLS/SSL** on connections |
| **At rest** | Stolen disk / backup files | **TDE** (transparent disk encryption) |
| **Column / in use** | Over-privileged insiders, app-side secrets | Column encryption / Always Encrypted / pgcrypto |

## 💻 In transit — TLS/SSL (do this always)

Encrypt the connection so credentials and data can't be sniffed:

```text
-- 🟦 SQL Server connection string
Server=...;Database=...;Encrypt=True;TrustServerCertificate=False;   -- require a valid cert in prod
```
```conf
# 🐘 PostgreSQL: enable SSL in postgresql.conf, require it in pg_hba.conf
# postgresql.conf:  ssl = on
# pg_hba.conf:      hostssl  all  all  0.0.0.0/0  scram-sha-256
```
```text
-- 🐘 connection string: sslmode=require  (or verify-full to also check the cert/hostname)
postgresql://app:...@host/shop?sslmode=verify-full
```

> ⚠️ `TrustServerCertificate=True` (🟦) / `sslmode=require` without `verify-full` (🐘) encrypts but
> **doesn't verify the server's identity** — vulnerable to man-in-the-middle. In production use a
> **valid certificate** and `verify-full` / `TrustServerCertificate=False`.

## 💻 At rest — TDE (Transparent Data Encryption)

TDE encrypts the **data files and backups** on disk transparently — the database decrypts on read, so
applications need no changes. It defends against someone stealing the physical disk or backup files.

```sql
-- 🟦 SQL Server: TDE (built-in, Enterprise/Standard)
CREATE DATABASE ENCRYPTION KEY WITH ALGORITHM = AES_256 ENCRYPTION BY SERVER CERTIFICATE MyTDECert;
ALTER DATABASE shop SET ENCRYPTION ON;
```

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Built-in TDE | **Yes** (TDE feature) | **No** (community PostgreSQL) |
| At-rest options | TDE; or OS/disk encryption | **Filesystem/disk encryption (LUKS/BitLocker)**; or enterprise distros (EDB) / cloud-managed TDE |
| Cloud-managed | Azure SQL TDE (default on) | RDS/Aurora/Cloud SQL encryption at rest (default on) |

> A real dialect gap: **community PostgreSQL has no built-in TDE.** You get at-rest encryption via
> **filesystem/disk encryption** (LUKS, BitLocker), **managed cloud** (RDS/Aurora/Cloud SQL encrypt by
> default), or **enterprise distributions** (EnterpriseDB) that add TDE. SQL Server has TDE built in.

## 💻 Column-level & in-use encryption

For specific sensitive fields (SSNs, card numbers, tokens), encrypt the **column** so even a DBA or a
stolen database can't read the plaintext.

```sql
-- 🟦 SQL Server: Always Encrypted — encryption/decryption happens in the CLIENT driver;
-- the server only ever sees ciphertext. Even sysadmins can't read it.
-- (Configured via column master/encryption keys; the app's driver handles crypto transparently.)

-- 🐘 PostgreSQL: pgcrypto extension for column encryption (app supplies the key)
CREATE EXTENSION IF NOT EXISTS pgcrypto;
INSERT INTO users (ssn_enc) VALUES (pgp_sym_encrypt('123-45-6789', :key));
SELECT pgp_sym_decrypt(ssn_enc, :key) FROM users;   -- decrypt with the key
```

| Approach | 🟦 SQL Server | 🐘 PostgreSQL |
|----------|--------------|---------------|
| Client-side, server-blind | **Always Encrypted** (server never sees plaintext) | (app-side encryption + a KMS) |
| Column functions | `ENCRYPTBYKEY`/`DECRYPTBYKEY` (cell-level) | **pgcrypto** (`pgp_sym_encrypt`, etc.) |

> **Always Encrypted (🟦)** is special: the **client driver** encrypts/decrypts, so the **database
> server never sees plaintext** — protecting against a malicious DBA or a fully-compromised server.
> PostgreSQL achieves similar by encrypting in the application before storing (with a key the DB
> doesn't hold).

## ⚖️ Key management is the hard part

Encryption is only as strong as **key management**. If the key sits next to the data, encryption adds
little. Best practice: store keys in a dedicated **Key Management Service / HSM** (Azure Key Vault,
AWS KMS, HashiCorp Vault), rotate them, and never hard-code keys in source/config. Losing the key =
losing the data; leaking the key = leaking the data.

## 🚫 Common mistakes

```text
❌ Encrypting at rest but transmitting in plaintext → sniffable credentials/data. ✅ TLS always.
❌ TLS without certificate verification (TrustServerCertificate=True / sslmode=require) → MITM risk.
   ✅ verify-full / valid cert in production.
❌ Assuming community PostgreSQL has TDE → it doesn't. ✅ disk encryption / managed cloud / EDB.
❌ Storing the encryption key alongside the encrypted data → defeats the purpose.
   ✅ KMS/HSM, key rotation, no keys in source.
❌ Encrypting a column then trying to index/search it efficiently → encrypted data isn't range-searchable.
   ✅ accept the query limitations; encrypt only what truly needs it.
```

## 🌍 Real-World Use

- **TLS** on every connection — non-negotiable.
- **TDE / disk encryption** for compliance (PCI, HIPAA, GDPR) — protects stolen backups/disks.
- **Always Encrypted (🟦) / app-side encryption (🐘)** for the most sensitive fields (PII, payment data)
  where even the DBA shouldn't see plaintext.
- **KMS/HSM** for keys; **cloud-managed** databases encrypt at rest by default and integrate with the
  cloud's key vault.

## 🎯 Practice (with full solutions)

### 1. Secure the connection — `Easy`
**Task:** Ensure the app's connection is encrypted and the server's identity verified, in both engines.
**Solution:**
```text
-- 🟦 SQL Server
Server=...;Database=shop;Encrypt=True;TrustServerCertificate=False;   -- requires a valid cert
-- 🐘 PostgreSQL
postgresql://app:...@host/shop?sslmode=verify-full                    -- encrypt + verify cert/hostname
```
**Why it works:** `Encrypt=True`/`sslmode=verify-full` encrypt the traffic **and** verify the server's
certificate, defeating both eavesdropping and man-in-the-middle (which plain `require`/`TrustServer­
Certificate=True` would not).

### 2. Protect a sensitive column from the DBA — `Medium`
**Task:** Store SSNs so that even a database administrator can't read the plaintext.
**Solution:**
- **🟦:** use **Always Encrypted** — configure column keys; the **client driver** encrypts before
  sending, so the server (and any DBA querying it) only sees ciphertext.
- **🐘:** encrypt in the **application** (or with `pgcrypto` using a key the DB doesn't store) before
  inserting; decrypt only in the app with a key from a **KMS**.
```sql
-- 🐘 conceptual (key supplied by the app from a vault, never stored in the DB):
INSERT INTO people (ssn_enc) VALUES (pgp_sym_encrypt(:ssn, :app_key));
```
**Why it works:** when encryption/decryption happens **client-side** with a key the database never
holds, the server stores only ciphertext — so a malicious or compromised DBA can't read the SSNs.

## ✅ Key Takeaways

- Encrypt in **three places**: **in transit (TLS — always)**, **at rest (TDE/disk)**, and
  **column/in-use** for the most sensitive fields.
- **TLS:** require it *and* **verify the certificate** (`verify-full` / valid cert) to stop MITM.
- **At rest:** **🟦 has built-in TDE**; **community 🐘 does not** — use disk encryption, managed cloud,
  or an enterprise distro.
- **Column/in-use:** **🟦 Always Encrypted** keeps plaintext from the server entirely; **🐘** uses
  **pgcrypto**/app-side encryption.
- **Key management** (KMS/HSM, rotation, no keys in source) is what makes encryption actually
  protective.
