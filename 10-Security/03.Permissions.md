# Permissions

## 🧠 Intuition

**Permissions** answer "**what are you allowed to do?**" — the *authorization* half of security. You
`GRANT` privileges (SELECT, INSERT, EXECUTE…) on **securables** (tables, views, schemas, procedures)
to principals (roles/users), `REVOKE` to take them away, and — on SQL Server — `DENY` to explicitly
block. The guiding principle is **least privilege**: grant only what's needed, nothing more.

> 💡 **Analogy — keys to specific rooms.** Authentication got you in the building; permissions are the
> set of keys you carry. A good security model gives each role only the keys it needs — the accountant
> can't open the server room, the cleaner can't open the vault. Hand out the minimum keys.

## 💻 GRANT / REVOKE / DENY

```sql
-- GRANT: allow an action on a securable
GRANT SELECT ON products TO sales_readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_rw;
GRANT EXECUTE ON PROCEDURE place_order TO app_rw;     -- 🟦: GRANT EXECUTE ON dbo.PlaceOrder TO app_rw;

-- REVOKE: remove a previously-granted permission
REVOKE INSERT ON orders FROM app_rw;

-- DENY (🟦 only): explicitly block, overriding any grant (even via role membership)
DENY SELECT ON salaries TO interns;     -- interns can NEVER select salaries, even if a role grants it
```

| Statement | Effect |
|-----------|--------|
| `GRANT` | Allow the action |
| `REVOKE` | Remove a grant (neutral — neither allowed nor denied) |
| `DENY` (🟦) | **Explicitly forbid** — overrides grants; the strongest |

> **🐘 PostgreSQL has no `DENY`** — it's grant-based only. To "deny," you `REVOKE` the grant (and don't
> grant it elsewhere). 🟦's `DENY` is an explicit override that wins over any grant, useful for "this
> role can do X *except* on this sensitive table."

## 💻 Permission levels — granularity

You can grant at different scopes; granting at a higher level cascades to its contents:

```sql
-- Column-level (grant SELECT on only some columns)
GRANT SELECT (name, city) ON customers TO support_role;   -- not their credit_card column

-- Table-level
GRANT SELECT ON customers TO reporting;

-- Schema-level (all current AND future objects in the schema)
GRANT SELECT ON SCHEMA::Sales TO reporting;               -- 🟦
GRANT SELECT ON ALL TABLES IN SCHEMA sales TO reporting;  -- 🐘 (existing tables)
ALTER DEFAULT PRIVILEGES IN SCHEMA sales GRANT SELECT ON TABLES TO reporting;  -- 🐘 future tables
```

**Schemas as a security boundary** is a powerful pattern: organize objects into schemas by sensitivity
(`Sales`, `HR`, `Audit`), then grant at the schema level. One grant covers the whole group, and new
tables are automatically covered (with `ALTER DEFAULT PRIVILEGES` on 🐘).

## 💻 Procedures as a controlled gateway (ownership chaining)

A powerful least-privilege technique: grant `EXECUTE` on a **stored procedure** without granting
direct table access. The procedure runs with its owner's rights (**ownership chaining** 🟦 /
`SECURITY DEFINER` 🐘), so the caller can do *exactly* what the procedure allows — and nothing else.

```sql
-- 🐘 PostgreSQL: SECURITY DEFINER runs with the function owner's privileges
CREATE FUNCTION place_order(...) RETURNS ... LANGUAGE plpgsql SECURITY DEFINER AS $$ ... $$;
GRANT EXECUTE ON FUNCTION place_order TO app_user;   -- app_user can place orders without table grants

-- 🟦 SQL Server: ownership chaining — grant EXECUTE on the proc, not the underlying tables
GRANT EXECUTE ON dbo.PlaceOrder TO app_user;
```

This lets you expose *operations* (place an order) instead of *raw tables* — the app can't run
arbitrary SQL against the tables, only the vetted procedures.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Grant/revoke | `GRANT`/`REVOKE` | `GRANT`/`REVOKE` |
| Explicit deny | **`DENY`** (overrides grants) | ❌ (revoke only) |
| Schema-level grant | `GRANT ... ON SCHEMA::name` | `GRANT ... ON ALL TABLES IN SCHEMA` + `ALTER DEFAULT PRIVILEGES` |
| Schema usage required? | implied | **`GRANT USAGE ON SCHEMA`** also required |
| Run-as-owner | ownership chaining; `EXECUTE AS` | `SECURITY DEFINER` functions |
| Column-level grants | yes | yes |
| `WITH GRANT OPTION` | yes (let grantee re-grant) | yes |

> 🐘 gotcha (again): table grants need **schema `USAGE`** too, and new tables aren't covered unless you
> set **default privileges**. 🟦's schema-level grant covers existing + future objects more directly.

## ⚖️ Least-privilege design

1. **Default deny** — start with no access; grant explicitly.
2. **Grant to roles, not individuals** ([Logins, Users & Roles](02.Logins-Users-Roles.md)).
3. **Use schemas** to group by sensitivity and grant at the schema level.
4. **Expose procedures, not tables**, where you want to constrain operations (ownership chaining /
   `SECURITY DEFINER`).
5. **Column/row scoping** for sensitive data (column grants here; rows in [RLS](05.Row-Level-Security-Masking-Auditing.md)).
6. **Review grants periodically** — privileges accrete; prune what's unused.

## 🚫 Common mistakes

```text
❌ Granting broad permissions (db_owner / superuser / ALL) for convenience → huge blast radius.
✅ grant the specific privileges on the specific securables.

❌ Granting to individual users → unmanageable sprawl.
✅ grant to roles.

❌ 🐘: granting table SELECT but forgetting GRANT USAGE ON SCHEMA → "permission denied for schema".
✅ grant schema USAGE + table privileges; set default privileges for future tables.

❌ Exposing raw tables to the app when only a few operations are needed.
✅ EXECUTE on vetted procedures (ownership chaining / SECURITY DEFINER).

❌ 🐘: SECURITY DEFINER function with a mutable search_path → privilege escalation risk.
✅ set a fixed search_path on SECURITY DEFINER functions.
```

## 🌍 Real-World Use

A typical setup: a `reporting` role with `SELECT` on a reporting schema (or replica); an `app_rw`
role with `SELECT/INSERT/UPDATE/DELETE` on the app's tables (or just `EXECUTE` on procedures);
column-level grants hiding sensitive fields from support staff; `DENY` (🟦) blocking a sensitive table
even for broad roles. Schemas partition `HR`/`Finance`/`Public` and permissions are granted per
schema. Audits review who-can-do-what.

## 🎯 Practice (with full solutions)

### 1. Scope a support role away from sensitive columns — `Medium`
**Task:** Support staff need to read customers' `name` and `city` but **not** `credit_card`.
**Solution:**
```sql
-- Column-level grant (both engines)
GRANT SELECT (name, city) ON customers TO support_role;
-- Do NOT grant SELECT on the whole table; credit_card stays inaccessible.
-- 🟦 alternative with DENY (if a broader grant exists elsewhere):
DENY SELECT ON customers (credit_card) TO support_role;
```
**Why it works:** column-level grants expose only the permitted columns; `credit_card` is never
selectable by `support_role`. On 🟦, `DENY` on the column is a belt-and-suspenders override if a wider
grant exists.

### 2. Expose an operation, not the table — `Medium`
**Task:** The app should be able to place orders but **not** run arbitrary SQL against `orders`/`stock`.
**Solution:**
```sql
-- 🐘 PostgreSQL: SECURITY DEFINER function + EXECUTE grant (no table grants to the app)
CREATE FUNCTION place_order(p_customer_id INT, p_product_id INT, p_qty INT)
RETURNS INT LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$ ... $$;
GRANT EXECUTE ON FUNCTION place_order TO app_user;

-- 🟦 SQL Server: ownership chaining — grant EXECUTE on the proc only
GRANT EXECUTE ON dbo.PlaceOrder TO app_user;
-- app_user has NO direct SELECT/INSERT on orders or stock.
```
**Why it works:** the app can only invoke the vetted procedure, which performs exactly the intended
operation with the owner's rights — it can't read or modify the tables directly, drastically reducing
what a compromised app account (or SQL injection) could do.

## ✅ Key Takeaways

- **Permissions = authorization.** `GRANT` to allow, `REVOKE` to remove; **🟦 `DENY`** explicitly
  blocks (overrides grants); **🐘 is grant-only** (revoke to deny).
- Grant at the right **granularity** (column / table / schema); **schemas are a security boundary** —
  grant per schema.
- **Expose procedures, not raw tables** (ownership chaining / `SECURITY DEFINER`) to constrain
  operations.
- **Least privilege**: default deny, grant to roles, scope sensitive columns/rows, review regularly.
- 🐘 gotchas: **schema `USAGE`** is required, and use **default privileges** for future tables; set a
  **fixed `search_path`** on `SECURITY DEFINER` functions.
