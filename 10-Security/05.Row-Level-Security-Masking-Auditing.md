# Row-Level Security, Masking & Auditing

## 🧠 Intuition

Three advanced controls that go beyond "who can access this table":

- **Row-Level Security (RLS)** — filter *which rows* a user sees, automatically, based on who they are
  (a salesperson sees only their region's orders). Both engines support it natively.
- **Dynamic Data Masking** — show *obscured* values (`****-1234`) to users without unmask rights, while
  the real data stays in the table (🟦 feature; 🐘 via views/functions).
- **Auditing** — record *who did what, when* for compliance and forensics.

> 💡 **Analogy — a shared report with personalized redaction.** RLS is everyone opening the "same"
> report but each only seeing their own section's rows. Masking is the sensitive numbers printed as
> `XXXX` unless you have clearance. Auditing is the sign-in sheet recording everyone who opened the
> report and what they touched.

## 💻 Row-Level Security (RLS)

RLS attaches a **policy** (a predicate function) to a table so every query is automatically filtered —
the application can't forget to add `WHERE tenant_id = ...`, because the database enforces it.

### 🐘 PostgreSQL

```sql
-- Enable RLS and define a policy
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.current_tenant')::int);   -- which rows are visible

-- The app sets the tenant per session/transaction:
SET app.current_tenant = '42';
SELECT * FROM orders;     -- automatically returns ONLY tenant 42's orders
```

`USING` filters reads; `WITH CHECK` constrains writes (so a user can't insert a row for another
tenant). Policies can be `PERMISSIVE` (OR'd) or `RESTRICTIVE` (AND'd).

### 🟦 SQL Server

```sql
-- A predicate function decides visible rows
CREATE FUNCTION dbo.fn_tenant_predicate(@tenant_id INT)
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS ok WHERE @tenant_id = CAST(SESSION_CONTEXT(N'tenant_id') AS INT);
GO
-- A security policy binds the predicate to the table
CREATE SECURITY POLICY TenantFilter
    ADD FILTER PREDICATE dbo.fn_tenant_predicate(tenant_id) ON dbo.orders
    WITH (STATE = ON);
-- App sets session context: EXEC sp_set_session_context 'tenant_id', 42;
```

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Mechanism | Security policy + predicate function | `CREATE POLICY ... USING / WITH CHECK` |
| Read filter | FILTER PREDICATE | `USING` |
| Write constraint | BLOCK PREDICATE | `WITH CHECK` |
| Per-user context | `SESSION_CONTEXT` | `current_setting()` / `current_user` |

**RLS is the robust way to do multi-tenancy** — the tenant filter lives in the database, so a forgotten
`WHERE` in application code can't leak another tenant's rows. Pair with a **[filtered/partial
index](../06-Indexing-and-Performance/03.Covering-Filtered-Included.md)** for performance.

## 💻 Dynamic Data Masking

Show masked values to non-privileged users without changing the stored data:

```sql
-- 🟦 SQL Server: built-in masking (the data is real; unprivileged users see a mask)
ALTER TABLE customers ALTER COLUMN email ADD MASKED WITH (FUNCTION = 'email()');
ALTER TABLE customers ALTER COLUMN credit_card ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)');
-- Users WITHOUT the UNMASK permission see 'aXXX@XXXX.com' / 'XXXX-XXXX-XXXX-1234'
GRANT UNMASK TO finance_role;   -- finance sees the real values
```

```sql
-- 🐘 PostgreSQL: no built-in masking — use a VIEW (or the PostgreSQL Anonymizer extension)
CREATE VIEW customers_masked AS
SELECT customer_id, name,
       regexp_replace(email, '(.).*(@.*)', '\1***\2') AS email,
       'XXXX-XXXX-XXXX-' || right(credit_card, 4) AS credit_card
FROM customers;
GRANT SELECT ON customers_masked TO support_role;   -- support reads the masked view, not the table
```

> ⚠️ Masking is a **display** convenience, **not** strong security — a user who can run arbitrary
> queries (e.g. `WHERE credit_card LIKE '4%'`) can sometimes infer masked values. For real protection
> of sensitive data, use **[column encryption](04.Encryption.md)** + **RLS** + restricted permissions.

## 💻 Auditing

Record who did what for compliance/forensics:

```sql
-- 🟦 SQL Server: SQL Server Audit (server/database-level, writes to a file/log)
CREATE SERVER AUDIT MyAudit TO FILE (FILEPATH = 'D:\audit\');
CREATE DATABASE AUDIT SPECIFICATION ShopAudit FOR SERVER AUDIT MyAudit
    ADD (SELECT, INSERT, UPDATE, DELETE ON SCHEMA::Sales BY public) WITH (STATE = ON);
```
```sql
-- 🐘 PostgreSQL: pgAudit extension (logs statements by class), plus log_statement, or trigger-based audit
-- postgresql.conf:  shared_preload_libraries = 'pgaudit';  pgaudit.log = 'write, ddl';
```

| Approach | 🟦 SQL Server | 🐘 PostgreSQL |
|----------|--------------|---------------|
| Built-in audit | **SQL Server Audit** (Extended Events based) | **pgAudit** extension; `log_statement` |
| Change history | **temporal tables** ([Temporal & Vector](../08-Specialized-Data/06.Temporal-and-Vector-Data.md)) | trigger-based audit / temporal pattern |
| Trigger-based | DML triggers writing to an audit table | DML triggers ([Triggers](../04-Programmable-SQL/03.Triggers.md)) |

## ⚖️ Combining the controls

These layers complement each other:
- **RLS** scopes *rows* per user (multi-tenancy, regional data) — enforced by the DB, not the app.
- **Masking** hides *values* from casual viewers (display-layer; not strong on its own).
- **Encryption** protects values from theft and DBAs (strong).
- **Auditing** records *access and changes* (accountability/compliance).
- **Permissions** ([Permissions](03.Permissions.md)) gate *what operations* are allowed.

A regulated app might use all five: permissions + RLS for tenant isolation + column encryption for PII
+ masking for support staff + audit for compliance.

## 🚫 Common mistakes

```text
❌ Relying on the app to add WHERE tenant_id = ... → one forgotten filter leaks data.
✅ enforce tenant isolation with RLS in the database.

❌ Treating masking as real security → inference attacks can reveal masked data.
✅ encrypt + restrict permissions for true protection; masking is display-only.

❌ No auditing on sensitive tables → can't answer "who accessed this?" during an incident.
✅ SQL Server Audit / pgAudit on sensitive schemas.

❌ RLS without a supporting index on the filter column → every query scans. ✅ index/partial-index it.

❌ 🐘: superusers and table owners BYPASS RLS by default → confirm policies apply to the roles you think.
```

## 🌍 Real-World Use

- **Multi-tenant SaaS:** RLS for tenant isolation is the standard, robust approach — the filter can't
  be forgotten.
- **Support/helpdesk views:** masking so agents see `****-1234` not full card numbers.
- **Compliance (GDPR/HIPAA/PCI/SOX):** auditing access to sensitive tables; temporal tables for change
  history; encryption for PII.
- **Healthcare/finance:** the full stack — permissions + RLS + encryption + masking + audit.

## 🎯 Practice (with full solutions)

### 1. Tenant isolation with RLS — `Medium`
**Task:** Ensure every query against `orders` returns only the current tenant's rows, enforced by the
database.
**Solution:**
```sql
-- 🐘 PostgreSQL
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
    USING (tenant_id = current_setting('app.current_tenant')::int)
    WITH CHECK (tenant_id = current_setting('app.current_tenant')::int);  -- also blocks cross-tenant inserts
-- App: SET app.current_tenant = '42';  then normal queries are auto-filtered.

-- 🟦 SQL Server: predicate function + SECURITY POLICY (as shown above), app sets SESSION_CONTEXT.
```
**Why it works:** the policy applies the tenant filter to **every** query automatically, so a missing
`WHERE` in app code can't leak another tenant's data; `WITH CHECK` also prevents writing rows for the
wrong tenant.

### 2. Mask card numbers for support — `Easy`
**Task:** Support staff should see `XXXX-XXXX-XXXX-1234` instead of full card numbers.
**Solution:**
```sql
-- 🟦 SQL Server: dynamic data masking
ALTER TABLE customers ALTER COLUMN credit_card
    ADD MASKED WITH (FUNCTION = 'partial(0,"XXXX-XXXX-XXXX-",4)');
-- support_role (no UNMASK) sees the masked value; GRANT UNMASK TO finance_role for full view.

-- 🐘 PostgreSQL: a masked view
CREATE VIEW customers_support AS
SELECT customer_id, name, 'XXXX-XXXX-XXXX-' || right(credit_card,4) AS credit_card FROM customers;
GRANT SELECT ON customers_support TO support_role;   -- support reads the view, not the base table
```
**Why it works:** 🟦's built-in masking hides the value for roles lacking `UNMASK`; 🐘 achieves it with a
view exposing only a masked column. (For real protection, combine with encryption + restricted
permissions — masking alone is display-only.)

## ✅ Key Takeaways

- **RLS** filters *which rows* a user sees, enforced by the database — the robust way to do
  **multi-tenancy** (🟦 security policy + predicate; 🐘 `CREATE POLICY USING/WITH CHECK`). Pair with a
  filtered index.
- **Dynamic Data Masking** obscures *values* for unprivileged users (🟦 built-in `MASKED WITH`; 🐘 via
  views/Anonymizer) — **display-only, not strong security**.
- **Auditing** records who-did-what (🟦 SQL Server Audit; 🐘 **pgAudit**; or triggers/temporal tables).
- **Combine** with permissions + encryption for defense in depth; superusers/owners may **bypass RLS**
  (🐘) — verify.
