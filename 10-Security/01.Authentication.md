# Authentication

## 🧠 Intuition

**Authentication** answers "**who are you?**" — proving identity before the database lets you in.
(Authorization, "what are you allowed to do?", comes next in [Permissions](03.Permissions.md).) Both
engines support OS-integrated identity (no password stored in the app) and database-native logins,
but they package and configure it very differently.

> 💡 **Analogy — the door of a building.** Authentication is the security guard checking your ID at
> the entrance. They don't yet care which rooms you can enter (that's authorization) — first they
> confirm you are who you claim to be. The strongest ID is one you don't carry a copy of (OS/managed
> identity) vs a password you might lose.

## 📐 Authentication modes

| Mode | Means | Best for |
|------|-------|----------|
| **OS / integrated** | The OS (Windows AD / Kerberos) vouches for you — no DB password | Enterprise SSO, no secrets in app config |
| **Database-native** | A login + password stored/managed by the database | Cross-platform, apps without AD |
| **Token / managed identity** | A cloud identity provider issues a token; no password at all | Cloud apps (Azure AD / IAM) — the modern best practice |

## 💻 🟦 SQL Server

SQL Server has two authentication modes (set at install: "Windows" or "Mixed"):

```sql
-- Windows Authentication (integrated — no password in the app; uses the OS/AD identity)
CREATE LOGIN [DOMAIN\AppServiceAccount] FROM WINDOWS;

-- SQL Authentication (login + password managed by SQL Server)
CREATE LOGIN app_login WITH PASSWORD = 'Strong_P@ssw0rd!', CHECK_POLICY = ON;

-- Azure AD / Microsoft Entra (token-based, passwordless — Azure SQL)
CREATE USER [app@contoso.com] FROM EXTERNAL PROVIDER;
```

- **Windows Authentication** is preferred on-prem — the OS/AD proves identity, so no password lives in
  connection strings.
- **SQL Authentication** (mixed mode) is needed for non-Windows clients; enforce `CHECK_POLICY` for
  password complexity/expiry.
- **Azure SQL** supports **Microsoft Entra (Azure AD)** + **Managed Identity** — the passwordless,
  modern path.

## 💻 🐘 PostgreSQL — `pg_hba.conf` is the gatekeeper

PostgreSQL authentication is configured in a file: **`pg_hba.conf`** (host-based authentication). Each
line says: for *this connection type* from *this address* to *this database* as *this user*, use
*this auth method*.

```conf
# pg_hba.conf  —  TYPE  DATABASE  USER  ADDRESS        METHOD
local           all       all                          peer        # local OS-user identity
host            shop      app_user  10.0.0.0/24        scram-sha-256 # password (hashed) from this subnet
hostssl         all       all       0.0.0.0/0          cert          # require client certificate over SSL
host            all       all       0.0.0.0/0          reject        # deny everything else
```

```sql
-- Create a role with a password (roles serve as both "logins" and "users" in PostgreSQL)
CREATE ROLE app_user WITH LOGIN PASSWORD 'Strong_P@ssw0rd!';
```

Common 🐘 methods: **`scram-sha-256`** (modern password hashing — use this, not the old `md5`),
**`peer`** (local OS user), **`cert`** (client certificate), **`gss`/`ldap`** (Kerberos/LDAP/AD
integration). After editing `pg_hba.conf`, reload the config.

## 🟦 SQL Server vs 🐘 PostgreSQL

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Config location | Server property (Windows/Mixed mode) | **`pg_hba.conf`** (per-rule, host-based) |
| OS-integrated | **Windows Authentication** (AD/Kerberos) | `peer` (local), `gss`/`ldap` (AD/Kerberos) |
| Native password | SQL login + password | role with `LOGIN` + password (`scram-sha-256`) |
| Login vs user | **Login** (server) → **user** (database), separate | **Role** (one concept; can log in or not) |
| Cloud passwordless | Azure AD / Managed Identity | Cloud IAM (e.g. IAM auth on RDS/Cloud SQL) |
| Password hashing | managed internally | **`scram-sha-256`** (configure, avoid `md5`) |

> Two big conceptual differences: **🐘 unifies "login" and "user" into one thing — a role** (more in
> [Logins, Users & Roles](02.Logins-Users-Roles.md)); and **🐘 controls *where* connections are allowed
> from via `pg_hba.conf`**, which has no direct 🟦 equivalent (🟦 relies on firewall + server config).

## ⚖️ Best practices

- **Prefer OS/managed identity** (Windows Auth, Azure AD/Managed Identity, IAM) — no password to leak,
  steal, or rotate. This is the single biggest auth improvement.
- **Always require TLS/SSL** for connections (encrypt credentials in transit) — see
  [Encryption](04.Encryption.md).
- **Enforce strong passwords** where native auth is used (`CHECK_POLICY` 🟦 / `scram-sha-256` 🐘); avoid
  weak/legacy hashing (`md5`).
- **Restrict by network** — 🐘 `pg_hba.conf` rules + firewall; 🟦 firewall + disable unneeded protocols.
- **No shared accounts** — each app/service gets its own identity for auditing.

## 🚫 Common mistakes

```text
❌ Storing a SQL/role password in plaintext config or source → leak waiting to happen.
✅ OS/managed identity (passwordless), or a secrets manager/vault for native passwords.

❌ 🐘: a wide-open pg_hba.conf line (host all all 0.0.0.0/0 trust) → anyone connects with NO auth!
✅ specific subnets + scram-sha-256/cert; reject the rest.

❌ Using SQL Authentication when Windows/Azure AD is available → unnecessary password to manage.
✅ integrated/managed identity where possible.

❌ 🐘: using md5 auth → upgrade to scram-sha-256.
❌ Allowing unencrypted connections → credentials sniffable in transit. ✅ require SSL/TLS.
```

> ⚠️ The `trust` method in `pg_hba.conf` means **no authentication at all** — never use it for
> anything beyond a locked-down local dev box.

## 🌍 Real-World Use

Enterprise apps authenticate via **Windows/AD** (🟦) or **Kerberos/LDAP** (🐘); cloud apps use
**Managed Identity / Azure AD / IAM** (passwordless) — the gold standard. `pg_hba.conf` is the first
thing a PostgreSQL DBA hardens (restrict addresses, enforce `scram-sha-256`/`cert`, reject the rest).
Every connection should be TLS-encrypted.

## 🎯 Practice (with full solutions)

### 1. Passwordless app auth — `Medium`
**Task:** An app connects to the database with a plaintext password in its config. Make it
passwordless on each engine.
**Solution:**
- **🟦:** run the app under a **Windows service account** and `CREATE LOGIN [DOMAIN\AppSvc] FROM
  WINDOWS;` — the OS proves identity, no password in config. (Azure SQL: use **Managed Identity** +
  `CREATE USER [...] FROM EXTERNAL PROVIDER`.)
- **🐘:** use **`gss`** (Kerberos/AD) or, on cloud, **IAM authentication** so a short-lived token
  replaces the password; or at minimum store the password in a **secrets manager**, not config.
**Why it works:** integrated/managed identity removes the stored secret entirely — nothing to leak or
rotate, and connections are tied to a real, auditable identity.

### 2. Harden pg_hba.conf — `Medium`
**Task (🐘):** A server has `host all all 0.0.0.0/0 trust`. Fix it.
**Solution:**
```conf
# Replace the dangerous trust-everyone line with least-privilege rules:
hostssl  shop  app_user  10.0.0.0/24   scram-sha-256   # the app subnet, hashed password, over SSL
local    all   all                     peer             # local admin via OS identity
host     all   all       0.0.0.0/0     reject           # deny everything else
```
Then reload the config.
**Why it works:** `trust` allowed *anyone* to connect with no authentication; the new rules limit
connections to a known subnet using `scram-sha-256` over SSL and explicitly reject the rest.

## ✅ Key Takeaways

- **Authentication = "who are you?"** Prefer **OS/managed identity** (Windows Auth, Azure AD/Managed
  Identity, IAM) — **passwordless** beats a stored secret.
- **🟦:** Windows vs Mixed mode; **login** (server) → **user** (database) are separate concepts.
- **🐘:** **roles** unify login/user; **`pg_hba.conf`** controls *who can connect from where* with what
  method — use **`scram-sha-256`**/`cert`, never `trust` in production.
- **Always require TLS**, enforce strong passwords for native auth, restrict by network, no shared
  accounts.
