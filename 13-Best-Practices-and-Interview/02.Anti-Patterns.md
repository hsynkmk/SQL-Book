# SQL Anti-Patterns

## 🧠 Intuition

An **anti-pattern** is a tempting solution that seems to work but causes pain — slow queries, wrong
results, security holes, or unmaintainable code. Learning to *smell* them is as valuable as learning
the right way: you'll spot the trap in a code review and refactor before it bites production. This is
the rogues' gallery of SQL mistakes, across **both engines**, each with the fix.

> 💡 **Analogy — a "what not to do" driving manual.** Knowing the rules of the road is half of it; the
> other half is recognizing the dangerous habits (tailgating, blind-spot lane changes) before they
> cause a crash. These are SQL's dangerous habits.

## 🚫 1. `SELECT *`

```sql
-- ❌ ships every column, breaks on schema change, defeats covering indexes, fragile to column order
SELECT * FROM orders;
-- ✅ name exactly what you need
SELECT order_id, customer_id, order_date FROM orders;
```
**Why it's bad:** extra I/O/network, brittle when columns change, and the optimizer can't use a
covering index. **Fix:** explicit column lists.

## 🚫 2. RBAR / cursors (Row By Agonizing Row)

```sql
-- ❌ a cursor looping to update each row one at a time → slow, serial
-- ✅ one set-based statement
UPDATE order_items SET line_total = quantity * unit_price;
```
**Why it's bad:** SQL engines are optimized for **set** operations; row-at-a-time loops are orders of
magnitude slower and can't parallelize. **Fix:** rewrite as set-based SQL (see
[Cursors](../04-Programmable-SQL/06.Cursors-and-Why-to-Avoid-Them.md)).

## 🚫 3. Non-SARGable predicates

```sql
-- ❌ function on the indexed column → forces a scan
WHERE YEAR(order_date) = 2025
WHERE UPPER(email) = 'A@B.COM'
WHERE total + 0 > 100
-- ✅ keep the column bare so an index can seek
WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'
WHERE email = 'a@b.com'          -- (or a case-insensitive collation / expression index)
WHERE total > 100
```
**Why it's bad:** wrapping the column in a function/expression prevents index seeks → full scans.
**Fix:** rewrite to expose the bare column; or build an **expression/computed index** (see
[SARGability](../06-Indexing-and-Performance/05.SARGability.md)).

## 🚫 4. Implicit conversions

```sql
-- ❌ comparing a varchar column to an N'unicode' literal, or string to int → conversion may scan + wrong results
WHERE phone = 5551234            -- phone is varchar → implicit convert, no seek
WHERE varchar_col = N'value'     -- 🟦: varchar vs nvarchar can force a scan
-- ✅ match types exactly
WHERE phone = '5551234'
```
**Why it's bad:** type mismatches make the engine convert column values (non-SARGable) and can yield
surprising results or precision loss. **Fix:** match literal/parameter types to the column.

## 🚫 5. N+1 queries (the ORM classic)

```text
❌ 1 query to get 100 orders, then 100 more queries (one per order) to get each customer → 101 round-trips.
✅ a single JOIN (or eager-load / batched IN) to fetch it all in one query.
```
**Why it's bad:** per-row round-trips dominate latency. **Fix:** JOIN or eager-load; inspect the SQL
your ORM generates (see [Application Integration](../12-DataWarehousing-BI-and-Ecosystem/08.Application-Integration.md)).

## 🚫 6. String-concatenated SQL (injection)

```csharp
// ❌ SQL injection + no plan reuse
var sql = "SELECT * FROM users WHERE name = '" + name + "'";
// ✅ parameterize
cmd.CommandText = "SELECT * FROM users WHERE name = @name";
cmd.Parameters.AddWithValue("@name", name);
```
**Why it's bad:** the #1 web vulnerability; also defeats the plan cache. **Fix:** **parameters,
always** (see [Dynamic SQL](../04-Programmable-SQL/05.Dynamic-SQL-and-Control-Flow.md)).

## 🚫 7. Misunderstanding NULL

```sql
-- ❌ NULL is never = or != anything; these silently drop/mismatch rows
WHERE status = NULL                 -- never true
WHERE status <> 'shipped'           -- excludes NULL status rows too!
-- ✅
WHERE status IS NULL
WHERE status <> 'shipped' OR status IS NULL
```
**Why it's bad:** three-valued logic silently produces wrong results. **Fix:** `IS [NOT] NULL`, and
account for NULL in negations (see [Working with NULL](../01-Querying-Basics/02.Working-with-NULL.md)).

## 🚫 8. Over-indexing (and under-indexing)

**Bad both ways:** no index on a hot filter/join → scans; an index on every column → every
`INSERT/UPDATE/DELETE` maintains them all, wasting space and slowing writes. **Fix:** index for **real
query patterns**, drop unused indexes (check usage DMVs / `pg_stat_user_indexes`).

## 🚫 9. Wildcard-leading `LIKE`

```sql
-- ❌ leading wildcard can't use a normal B-tree index → scan
WHERE name LIKE '%smith%'
-- ✅ trailing wildcard is seekable; for full text, use a full-text / trigram index
WHERE name LIKE 'smith%'
```
**Fix:** trailing-only wildcard for prefix search; **full-text** (🟦 FTS / 🐘 `tsvector`) or **trigram**
(`pg_trgm`) indexes for "contains" search (see [Full-Text Search](../08-Specialized-Data/05.Full-Text-Search.md)).

## 🚫 10. God-queries & magic numbers

A 400-line query with nested subqueries nobody can read; hard-coded IDs/statuses scattered around.
**Fix:** decompose with **CTEs** (see [CTEs](../02-Advanced-Querying/02.CTEs-and-Recursion.md)) or
views; lift constants into parameters/lookup tables; comment the *why*.

## 🚫 11. `OR` on different columns / functions defeating indexes

```sql
-- ❌ OR across columns can prevent good index use
WHERE customer_id = 5 OR employee_id = 5
-- ✅ often a UNION of two SARGable, separately-indexable queries is faster
SELECT ... WHERE customer_id = 5
UNION
SELECT ... WHERE employee_id = 5;
```

## 🚫 12. Relying on insertion order / no `ORDER BY`

A query without `ORDER BY` has **no guaranteed order** (it can change with plans, parallelism, page
layout). **Fix:** specify `ORDER BY` whenever order matters; for pagination use **keyset** ordering on
a unique key (see [Pagination](../01-Querying-Basics/08.Pagination.md)).

## 🟦 / 🐘 dialect-specific traps

```text
🟦 SQL Server:
  ❌ WITH (NOLOCK) everywhere to "fix" blocking → dirty reads (uncommitted/duplicated/missing rows)
  ✅ enable READ_COMMITTED_SNAPSHOT for non-blocking consistent reads
  ❌ scalar UDFs in WHERE/SELECT over big sets → per-row, can serialize (pre-2019) → slow
  ✅ inline TVFs / set-based; SQL Server 2019+ inlines some scalar UDFs

🐘 PostgreSQL:
  ❌ ignoring autovacuum on high-churn tables → bloat, slow scans
  ✅ tune autovacuum; watch n_dead_tup
  ❌ huge OFFSET for deep pagination → scans and discards OFFSET rows
  ✅ keyset pagination (WHERE id > :last ORDER BY id LIMIT n)
  ❌ thousands of direct connections (each a process) → use PgBouncer
```

## 🌍 Real-World Use

Most "the database is slow" incidents trace to a handful of these: a non-SARGable predicate, a missing
index, `SELECT *` pulling huge rows, N+1 from an ORM, or a long transaction blocking everything. A
reviewer who recognizes the smell fixes it in minutes; unrecognized, it becomes a production fire.

## 🎯 Practice (with full solutions)

### 1. Spot and fix three anti-patterns — `Medium`
**Task:** Critique: `SELECT * FROM orders WHERE YEAR(order_date)=2025 AND status<>'cancelled';`
**Solution:** Three issues: (1) **`SELECT *`** → name columns; (2) **non-SARGable** `YEAR(order_date)`
→ range predicate; (3) **NULL trap** — `status <> 'cancelled'` silently drops rows where `status IS
NULL`.
```sql
SELECT order_id, customer_id, order_date, status
FROM orders
WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'
  AND (status <> 'cancelled' OR status IS NULL);
```
**Why it works:** explicit columns reduce I/O and enable covering indexes; the date range is seekable;
the `OR status IS NULL` restores the rows three-valued logic would have silently excluded.

### 2. Kill the N+1 — `Medium`
**Task:** Code fetches 50 orders, then loops issuing one query per order to get the customer name. Fix
it in SQL.
**Solution:**
```sql
SELECT o.order_id, o.order_date, c.name AS customer
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.order_id IN (/* the 50 ids */);     -- or eager-load in the ORM
```
**Why it works:** one JOIN returns orders **with** their customer in a single round-trip instead of
1 + 50 = 51 queries — eliminating the per-row network latency that makes N+1 slow.

## ✅ Key Takeaways

- The usual suspects: **`SELECT *`**, **RBAR/cursors**, **non-SARGable** predicates, **implicit
  conversions**, **N+1**, **string-concatenated SQL**, **NULL** misuse, over/under-indexing,
  **leading-wildcard `LIKE`**, god-queries, **no `ORDER BY`**.
- Dialect traps: **🟦 `NOLOCK`/scalar UDFs**; **🐘 autovacuum neglect / huge `OFFSET` / connection
  floods**.
- Each has a clean fix — explicit columns, set-based logic, seekable predicates, type matching, joins/
  eager-loading, parameters, `IS NULL`, intentional indexing, keyset paging.
- Learning the **smell** lets you catch these in review before they reach production.

**Self-check:**
1. Why is `YEAR(order_date) = 2025` slower than a date range, and what's the fix?
2. How does N+1 arise and how do you eliminate it?
3. Why is `WITH (NOLOCK)` (🟦) a dangerous "fix," and what's the right one?
