# Study Plan & Roadmap

## 🧠 Intuition

You've got ~80 topics across 14 modules. This chapter is the **map**: the order to learn them, how
long to spend, what "I actually know this" looks like at each stage, and a spaced-repetition checklist
so it sticks. Follow the numbered modules — they're deliberately sequenced so each builds on the last.

> 💡 **Analogy — learning an instrument.** You don't start with concertos. Scales → simple tunes →
> technique → repertoire → performance. This roadmap is the same: query basics → modify → program →
> correctness → speed → specialization → mastery. Skip the foundation and the advanced stuff collapses.

## 📐 The four stages

| Stage | Modules | You can… | Rough time* |
|-------|---------|----------|-------------|
| **1. Beginner** | 00 Foundations · 01 Querying Basics | model data, write SELECT/JOIN/GROUP BY, handle NULL, paginate | 2–3 weeks |
| **2. Intermediate** | 02 Advanced Querying · 03 Modifying & DDL · 04 Programmable SQL | window functions, CTEs, DML/DDL, upsert, procs/functions/triggers | 3–4 weeks |
| **3. Advanced** | 05 Concurrency · 06 Indexing & Performance · 07 Partitioning & Scale | transactions/isolation, read plans, tune indexes, SARGability, scale-out | 4–6 weeks |
| **4. Expert** | 08 Specialized Data · 09 Internals · 10 Security · 11 Operations · 12 BI/Ecosystem | JSON/spatial/FTS/vector, engine internals, secure & operate, warehouse/BI | 6–8 weeks |

\* *Self-paced estimates for steady part-time study; compress or stretch freely. Throughout, finish
each topic's **Practice** before moving on, and revisit 13 Best Practices / Anti-Patterns continuously.*

## 📐 Milestone checks ("can I really do this?")

- **After Stage 1:** write a 3-table JOIN with filtering, grouping, and correct NULL handling from
  scratch; explain a primary vs foreign key; paginate results both ways.
- **After Stage 2:** solve a "top-N per group" with a window function; write a recursive CTE for a
  hierarchy; write an idempotent upsert in both dialects; write a stored proc with error handling.
- **After Stage 3:** read an execution plan and identify a scan vs seek; make a slow query SARGable;
  explain isolation levels and pick one for a scenario; design indexes for a given workload.
- **After Stage 4:** query JSON in both engines; explain MVCC/VACUUM and Always On vs streaming
  replication; set up RLS; choose a backup/PITR strategy; design a star schema and an ETL flow.

## 📐 Spaced-repetition checklist

Review on an expanding schedule (day 1 → 3 → 7 → 14 → 30). Tick what you can explain **and** write
without looking:

```text
CORE SQL
[ ] SELECT / WHERE / ORDER BY / DISTINCT
[ ] All JOIN types + when each (incl. self-join, anti-join via NOT EXISTS)
[ ] GROUP BY / HAVING / aggregates / GROUPING SETS / ROLLUP
[ ] NULL & three-valued logic; COALESCE / NULLIF / ISNULL(🟦)
[ ] Subqueries: scalar, correlated, EXISTS vs IN
[ ] Set ops: UNION (ALL) / INTERSECT / EXCEPT
[ ] Pagination: OFFSET/FETCH (🟦) vs LIMIT/OFFSET; keyset paging

ADVANCED QUERY
[ ] Window functions: ROW_NUMBER/RANK/DENSE_RANK, LAG/LEAD, running totals, frames
[ ] CTEs + recursion
[ ] PIVOT/UNPIVOT (🟦) vs crosstab/FILTER (🐘); CASE

MODIFY / PROGRAM
[ ] INSERT/UPDATE/DELETE; OUTPUT(🟦)/RETURNING(🐘)
[ ] Upsert: MERGE (🟦) vs INSERT … ON CONFLICT (🐘)
[ ] Identity/sequences; views vs materialized views
[ ] Stored procs, functions, triggers, error handling, dynamic SQL (parameterized!)

CONCURRENCY
[ ] ACID; the 4 isolation levels + snapshot
[ ] Locking/blocking/deadlocks; MVCC vs lock-based; VACUUM (🐘)
[ ] Optimistic (rowversion/xmin) vs pessimistic (FOR UPDATE)

PERFORMANCE
[ ] B-tree index; clustered vs heap; covering/INCLUDE vs partial/filtered
[ ] Read an execution plan (seek vs scan); SARGability; statistics
[ ] Index maintenance (rebuild/REINDEX/VACUUM); specialized indexes (columnstore, GIN/GiST/BRIN)
[ ] Partitioning; scaling out (replicas, sharding/Citus)

DEPTH
[ ] JSON in both engines; spatial; full-text; temporal; vector (pgvector / VECTOR)
[ ] SQL Server vs PostgreSQL architecture; storage/WAL; the optimizer; HA/replication
[ ] AuthN/Z, roles, permissions, encryption, RLS/masking/auditing
[ ] Backup/restore/PITR; monitoring (DMVs/Query Store vs pg_stat_*); automation
[ ] DW/star schema, SCD; ETL (SSIS / COPY/FDW/dbt); Power BI Import vs DirectQuery

HABITS
[ ] Best practices by reflex; smell the anti-patterns; parameterize everything
```

## ⚖️ How to study (so it sticks)

- **Do the practice, don't just read.** Type every query against the [sample database](../SAMPLE-DATABASE.md)
  in both engines. Reading SQL ≠ writing SQL.
- **Explain out loud** (rubber-duck). If you can't explain MVCC or a covering index simply, you don't
  own it yet — that's the self-check questions' job.
- **Run real plans.** Nothing teaches indexing like `EXPLAIN ANALYZE` (🐘) / actual execution plan (🟦)
  on your own slow query.
- **Build one small project** end-to-end: schema + constraints → seed → queries → a proc/trigger → an
  index tuning pass → a backup. Integrates everything.
- **Spaced repetition** over cramming; revisit the checklist on the expanding schedule.

## 🌍 Real-World Use

This roadmap mirrors how SQL competence actually grows on the job: you start querying, then modifying,
then you hit a concurrency bug and a slow query, then you're asked to secure and operate the database,
then to feed the BI stack. Following the order means each real-world problem lands *after* you've got
the foundation to solve it.

## 🎯 Practice

### 1. Build the capstone — `Project`
**Task:** Using the [sample database](../SAMPLE-DATABASE.md), build end-to-end in **both** engines: (a)
create the schema with full constraints, (b) seed it, (c) write 5 analytical queries (incl. a window
function and a recursive CTE over `employees.manager_id`), (d) add a stored proc that places an order
transactionally, (e) add an index that turns one query's scan into a seek (prove it with the plan), (f)
take a backup.
**Why it works:** it exercises Foundations → Querying → Advanced → Programmable → Concurrency →
Performance → Operations in one connected piece — the fastest way to convert "I read it" into "I can
do it," and a portfolio artifact you can talk through in an interview.

### 2. Self-test against the cheat sheet — `Easy`
**Task:** Close the notes and reproduce the [Interview Cheat Sheet](../INTERVIEW_CHEATSHEET.md) sections
from memory; fill gaps by revisiting that topic's module.
**Why it works:** active recall on the highest-yield facts surfaces exactly what you don't yet own, and
sends you back to the precise chapter to close the gap.

## ✅ Key Takeaways

- Follow the **numbered modules in order** — four stages (**Beginner → Intermediate → Advanced →
  Expert**), each building on the last.
- Hit the **milestone checks** before advancing; use the **spaced-repetition checklist** (expanding
  schedule, explain + write from memory).
- **Do the practice in both engines**, run real **execution plans**, and build one **end-to-end
  capstone** to integrate everything.
- The order mirrors real-world skill growth: **query → modify → program → make correct → make fast →
  specialize → operate → BI**.
