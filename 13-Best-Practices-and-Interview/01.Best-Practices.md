# SQL Best Practices

## 🧠 Intuition

Good SQL isn't just correct — it's **readable, fast, safe, and maintainable**. The same query can be
written a dozen ways; the best version makes intent obvious, lets the optimizer do its job, resists
injection, and survives schema changes. This chapter distills the habits that separate solid SQL from
fragile SQL — across **both engines**.

> 💡 **Analogy — writing clear prose.** Anyone can scribble a sentence that technically parses. A good
> writer chooses words so the reader understands instantly and nothing is ambiguous. Good SQL is the
> same: explicit, set-based, and unsurprising.

## 📐 The core habits

### 1. Think in **sets**, not loops
SQL is declarative — describe *what* you want and let the engine figure out *how*. A single set-based
statement almost always beats row-by-row (cursor/loop) processing.

```sql
-- ❌ RBAR (Row By Agonizing Row): a cursor/loop updating one row at a time
-- ✅ one set-based statement the engine optimizes and parallelizes:
UPDATE order_items SET line_total = quantity * unit_price WHERE line_total IS NULL;
```

### 2. **Name explicit columns**, never `SELECT *`
List the columns you need. `SELECT *` breaks when columns change, ships unneeded data, and defeats
covering indexes.

```sql
-- ❌ SELECT * FROM customers;
-- ✅ SELECT customer_id, name, email FROM customers;
```

### 3. **Always parameterize**
Never concatenate input into SQL. Parameters stop injection *and* enable plan reuse (see
[Application Integration](../12-DataWarehousing-BI-and-Ecosystem/08.Application-Integration.md)).

### 4. Write **SARGable** predicates
Don't wrap the indexed column in a function — it blocks index seeks (see
[SARGability](../06-Indexing-and-Performance/05.SARGability.md)).

```sql
-- ❌ WHERE YEAR(order_date) = 2025          -- function on the column → scan
-- ✅ WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'   -- seekable range
```

### 5. Use **explicit JOIN syntax** and qualify columns
ANSI `JOIN ... ON`, not comma-joins with `WHERE`. Alias tables and qualify ambiguous columns so intent
(and join conditions) are unmistakable.

```sql
-- ✅ explicit, aliased, qualified
SELECT o.order_id, c.name
FROM orders o JOIN customers c ON c.customer_id = o.customer_id;
```

### 6. Be explicit about **NULL** and **types**
Handle three-valued logic deliberately (`IS NULL`, `COALESCE`); avoid implicit conversions that cause
wrong results or non-SARGable scans (see [Working with NULL](../01-Querying-Basics/02.Working-with-NULL.md)).

### 7. **Constrain the data**
Push correctness into the schema: `NOT NULL`, `FK`, `UNIQUE`, `CHECK`, defaults. The database is the
last line of defense for integrity — don't rely only on app code.

### 8. **Keep transactions short**
Acquire locks late, hold them briefly, commit promptly. Long transactions cause blocking (🟦) and block
vacuum → bloat (🐘) (see [MVCC vs Lock-Based](../05-Transactions-and-Concurrency/04.MVCC-vs-Lock-Based.md)).

### 9. **Index intentionally**
Index for your real query patterns (filters, joins, sorts); don't over-index (every index slows
writes). Verify with execution plans, not guesses.

### 10. **Format and comment for the next human**
Consistent casing, indentation, one clause per line for complex queries, and a comment on the *why*
(not the obvious *what*).

## 📐 Naming conventions

- **Consistent and lowercase-friendly:** PostgreSQL folds unquoted identifiers to lowercase, so prefer
  `snake_case` and avoid quoted mixed-case names (`"OrderID"`) that force quoting forever. SQL Server is
  case-insensitive by default but `snake_case` or `PascalCase` consistently is fine — **pick one**.
- **Tables:** clear nouns (`customers`, `order_items`). Be consistent on singular vs plural.
- **Keys:** `customer_id` (not just `id`) reads better in joins; name FKs/constraints explicitly
  (`fk_orders_customer`) so errors are legible.
- **No reserved words / special chars** as identifiers; no spaces.

## 🟦 SQL Server vs 🐘 PostgreSQL — practice notes

| Habit | 🟦 SQL Server | 🐘 PostgreSQL |
|-------|--------------|---------------|
| Null-coalesce | `ISNULL(x, y)` (2-arg) or `COALESCE` | `COALESCE(x, y)` (standard) |
| Prefer the standard | `COALESCE`, `CASE` portable over `ISNULL` | same |
| Identifier case | case-insensitive; pick a convention | folds to lowercase → use `snake_case` |
| Get inserted key | `OUTPUT INSERTED.id` | `RETURNING id` |
| Concurrency default | consider `READ_COMMITTED_SNAPSHOT` ON | MVCC already |
| Limit rows | `TOP` / `OFFSET…FETCH` | `LIMIT … OFFSET` |

> Lean on **standard SQL** (`COALESCE`, `CASE`, ANSI joins, window functions) wherever possible — it's
> portable across both engines and clearer to readers who know SQL generally.

## ⚖️ Readability vs performance

Default to the **clear** version; optimize only what a plan/measurement proves slow. Premature micro-
optimization (cryptic query tricks) usually costs maintainability for no real gain. But know the
high-impact levers (SARGability, the right index, set-based logic, short transactions) — those are both
fast *and* usually clean.

## 🌍 Real-World Use

Code review checklists encode these: "explicit columns? parameterized? SARGable? indexed for this
filter? transaction scope tight? constraints in place? standard SQL where possible?" Teams that bake
them into review and CI (linting, plan checks) ship SQL that stays fast and safe as the system grows.

## 🎯 Practice (with full solutions)

### 1. Refactor a fragile query — `Medium`
**Task:** Improve: `SELECT * FROM orders o, customers c WHERE o.customer_id = c.customer_id AND
YEAR(o.order_date) = 2025;`
**Solution:**
```sql
SELECT o.order_id, o.order_date, c.name
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.order_date >= '2025-01-01' AND o.order_date < '2026-01-01';
```
**Why it works:** explicit columns (no `SELECT *`), **explicit ANSI JOIN** (not a comma-join), and a
**SARGable** date range instead of `YEAR(order_date)` so an index on `order_date` can seek. Clearer
intent, smaller result, faster plan — on both engines.

### 2. Push correctness into the schema — `Easy`
**Task:** App code keeps inserting orders with NULL customers and negative totals. Stop it at the
database.
**Solution:**
```sql
ALTER TABLE orders ALTER COLUMN customer_id INT NOT NULL;   -- 🟦 (PG: ALTER COLUMN ... SET NOT NULL)
ALTER TABLE orders ADD CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id);
ALTER TABLE orders ADD CONSTRAINT ck_orders_total CHECK (total >= 0);
```
**Why it works:** `NOT NULL` + `FK` + `CHECK` make invalid rows **impossible to insert**, regardless
of which app or script writes them — integrity enforced by the database, the one place every write
passes through.

## ✅ Key Takeaways

- **Set-based, not RBAR**; **explicit columns**, not `SELECT *`; **always parameterize**; keep
  predicates **SARGable**; use **explicit ANSI joins** and qualify columns.
- Be deliberate about **NULL** and **types**; push correctness into **constraints**; keep
  **transactions short**; **index intentionally** and verify with plans.
- **Name consistently** (`snake_case` is safest cross-engine — PostgreSQL folds case); prefer
  **standard SQL** (`COALESCE`, `CASE`, window functions) for portability.
- Default to **readable**; optimize what's **measured** slow. Encode the habits in **code review/CI**.
