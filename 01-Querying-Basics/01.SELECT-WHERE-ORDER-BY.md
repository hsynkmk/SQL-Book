# SELECT, WHERE, ORDER BY

## 🧠 Intuition

`SELECT` is how you ask the database for data. Three clauses cover the vast majority of queries:
**`SELECT`** chooses *which columns*, **`WHERE`** filters *which rows*, and **`ORDER BY`** decides
*the order*. Everything else in SQL builds on this trio.

> 💡 **Analogy — a librarian request.** "Give me the **title and author** (`SELECT`) of every book
> **published after 2000** (`WHERE`), **sorted by newest first** (`ORDER BY`)." You describe the
> result; the librarian (database) fetches it.

## 🎯 The Problem

```sql
-- ❌ The lazy query that haunts production
SELECT * FROM products;
```

`SELECT *` pulls **every column of every row** — wasteful over the network, breaks when columns are
added, and signals you didn't think about what you actually need. Real queries ask for *specific
columns* and *filter* down to the rows that matter.

## 📐 How It Works — logical order of evaluation

SQL is written `SELECT ... FROM ... WHERE ... ORDER BY`, but the database *evaluates* it in a
different order. Understanding this explains many "why doesn't that work?" moments:

```mermaid
graph LR
    A[FROM: pick the table] --> B[WHERE: filter rows]
    B --> C[SELECT: choose columns]
    C --> D[ORDER BY: sort the result]
```

1. **FROM** — start with the table's rows.
2. **WHERE** — keep only rows matching the condition.
3. **SELECT** — project the chosen columns (and compute expressions/aliases).
4. **ORDER BY** — sort the final result.

This is why you **can't use a `SELECT` alias in `WHERE`** (WHERE runs before SELECT) but **can use
it in `ORDER BY`** (ORDER BY runs after SELECT). More on that below.

## 💻 The essentials (identical on both engines)

```sql
-- Specific columns, filtered, sorted
SELECT name, unit_price
FROM products
WHERE unit_price > 5.00
ORDER BY unit_price DESC;

-- Multiple conditions
SELECT name, city, country
FROM customers
WHERE country = 'Germany' AND city = 'Berlin';

-- Ranges, lists, patterns
SELECT name, unit_price FROM products WHERE unit_price BETWEEN 2 AND 10;
SELECT name FROM customers WHERE country IN ('Germany','UK');
SELECT name FROM products WHERE name LIKE 'C%';        -- starts with C

-- Column aliases and computed columns
SELECT name, unit_price * units_in_stock AS inventory_value
FROM products
ORDER BY inventory_value DESC;

-- Sort by multiple keys
SELECT name, country, city FROM customers ORDER BY country ASC, city ASC;
```

### Limiting rows — the classic dialect split

```sql
-- 🟦 SQL Server
SELECT TOP 5 name, unit_price FROM products ORDER BY unit_price DESC;
```
```sql
-- 🐘 PostgreSQL
SELECT name, unit_price FROM products ORDER BY unit_price DESC LIMIT 5;
```

(Full paging — `OFFSET/FETCH` vs `LIMIT/OFFSET` — is in [Pagination](08.Pagination.md).)

## 🟦 SQL Server vs 🐘 PostgreSQL — small but real differences

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Limit rows | `SELECT TOP n` | `LIMIT n` |
| String compare | **Case-insensitive** by default (collation) | **Case-sensitive** by default |
| Case-insensitive `LIKE` | default behavior | `ILIKE`, or `LOWER(col) LIKE LOWER(...)` |
| Identifier quoting | `[Order Date]` (brackets) | `"Order Date"` (double quotes) |
| String concat | `+` or `CONCAT()` | `||` or `CONCAT()` |

> ⚠️ The **case sensitivity** difference bites people: `WHERE city = 'berlin'` returns Berlin rows
> on a default 🟦 install but **nothing** on a default 🐘 install. Use `ILIKE` / `LOWER()` in 🐘 (or
> set a case-insensitive collation) when you want case-insensitive matching.

## ⚡ Under the Hood / Performance

- **`SELECT` only what you need** — fewer columns = less I/O and network, and lets a covering
  [index](../06-Indexing-and-Performance/03.Covering-Filtered-Included.md) satisfy the query
  without touching the table.
- **`WHERE` filters at the database** — never pull all rows to the app and filter there (the
  classic [anti-pattern](../13-Best-Practices-and-Interview/02.Anti-Patterns.md)).
- **`ORDER BY` may need a sort** — sorting a large result is expensive unless an index already
  provides the order. The optimizer shows this in the [execution plan](../06-Indexing-and-Performance/04.Reading-Execution-Plans.md).

## 🚫 Common mistakes

```sql
-- ❌ SELECT * in production code
SELECT * FROM orders;
-- ✅ name your columns
SELECT order_id, customer_id, order_date FROM orders;

-- ❌ Using a SELECT alias in WHERE (alias doesn't exist yet — WHERE runs before SELECT)
SELECT unit_price * 1.2 AS price_with_tax FROM products WHERE price_with_tax > 10;  -- ERROR
-- ✅ repeat the expression, or use a subquery/CTE
SELECT unit_price * 1.2 AS price_with_tax FROM products WHERE unit_price * 1.2 > 10;

-- ❌ ORDER BY a column number and then refactoring the SELECT list silently re-sorts
ORDER BY 2          -- fragile
-- ✅ ORDER BY the column name
ORDER BY unit_price

-- ❌ Assuming case-insensitive matching on PostgreSQL
WHERE city = 'berlin'    -- returns nothing on 🐘 for 'Berlin'
-- ✅ WHERE city ILIKE 'berlin'   (🐘)
```

## 🌍 Real-World Use

Every list screen, search box, dashboard tile, and report begins as a `SELECT ... WHERE ...
ORDER BY`. Getting these three right — specific columns, server-side filtering, index-friendly
sorts — is 80% of day-to-day SQL.

## 🎯 Practice (with full solutions)

### 1. Filtered, sorted listing — `Easy`
**Task:** From the [sample DB](../SAMPLE-DATABASE.md), list the `name` and `unit_price` of all
products priced over $3, most expensive first.
**Solution:**
```sql
SELECT name, unit_price
FROM products
WHERE unit_price > 3.00
ORDER BY unit_price DESC;
```
**Why it works:** filters at the database, returns only the two needed columns, sorted as asked.

### 2. Top-N both ways — `Easy`
**Task:** Return the 3 cheapest products, in both dialects.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT TOP 3 name, unit_price FROM products ORDER BY unit_price ASC;
```
```sql
-- 🐘 PostgreSQL
SELECT name, unit_price FROM products ORDER BY unit_price ASC LIMIT 3;
```
**Why it works:** `ORDER BY ... ASC` puts cheapest first; the dialect-specific clause keeps the
first 3.

### 3. Case-insensitive search — `Medium`
**Task:** Find customers in a city the user typed as `'BERLIN'`, regardless of case, on PostgreSQL.
**Solution:**
```sql
-- 🐘 PostgreSQL
SELECT name, city FROM customers WHERE city ILIKE 'berlin';
-- (🟦 SQL Server: WHERE city = 'berlin' already works case-insensitively by default)
```
**Why it works:** `ILIKE` is PostgreSQL's case-insensitive match; on SQL Server the default
collation makes plain `=` case-insensitive already. Same intent, dialect-aware execution.

## ✅ Key Takeaways

- **`SELECT`** (columns) → **`WHERE`** (rows) → **`ORDER BY`** (sort) cover most queries.
- The **logical evaluation order** (FROM → WHERE → SELECT → ORDER BY) explains why aliases work in
  `ORDER BY` but not `WHERE`.
- Avoid **`SELECT *`**; name your columns.
- Row-limiting differs: **🟦 `TOP n`** vs **🐘 `LIMIT n`**; string matching is **case-insensitive by
  default on 🟦, case-sensitive on 🐘** (`ILIKE`/`LOWER` to bridge).
- Filter and sort **in the database**, not in your app.
