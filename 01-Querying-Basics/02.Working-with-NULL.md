# Working with NULL

## 🧠 Intuition

`NULL` means **"unknown" or "missing"** — *not* zero, not an empty string, not false. A customer's
`phone` is `NULL` because we don't know it, not because it's blank. This single idea causes more
beginner bugs than anything else in SQL, because `NULL` follows **three-valued logic**: a
comparison can be `TRUE`, `FALSE`, or **`UNKNOWN`**.

> 💡 **Analogy — a sealed box.** `NULL` is a box you can't see inside. Is the box equal to 5? You
> *don't know* — so the answer isn't "yes" or "no," it's "unknown." And `WHERE` only keeps rows
> where the condition is **true**, so "unknown" rows are silently dropped. That's the trap.

This behavior is **identical on SQL Server and PostgreSQL** — it's core SQL.

## 🎯 The Problem

```sql
-- ❌ "Find employees who don't have a manager"
SELECT name FROM employees WHERE manager_id = NULL;     -- returns ZERO rows!
```

Every comparison **with** `NULL` using `=` yields `UNKNOWN`, never `TRUE` — so `WHERE manager_id =
NULL` keeps nothing, even though Dana Director genuinely has `manager_id = NULL`. The fix is the
special operator **`IS NULL`**.

## 📐 How It Works — three-valued logic

| Expression | Result |
|------------|--------|
| `5 = 5` | TRUE |
| `5 = 6` | FALSE |
| `5 = NULL` | **UNKNOWN** |
| `NULL = NULL` | **UNKNOWN** (two unknowns aren't "equal") |
| `NULL <> 5` | **UNKNOWN** |

And `WHERE` / `JOIN ... ON` keep a row **only when the condition is TRUE** — `UNKNOWN` is treated
like `FALSE` for filtering. So you must test for null with dedicated operators:

```sql
SELECT name FROM employees WHERE manager_id IS NULL;      -- ✅ the boss
SELECT name FROM employees WHERE manager_id IS NOT NULL;  -- ✅ everyone with a manager
```

### NULL in logic (AND/OR)

```sql
TRUE  AND UNKNOWN = UNKNOWN
FALSE AND UNKNOWN = FALSE      -- false "short-circuits"
TRUE  OR  UNKNOWN = TRUE       -- true "short-circuits"
NOT UNKNOWN       = UNKNOWN
```

### NULL in aggregates — they're *skipped*

```sql
-- COUNT(*) counts rows; COUNT(column) skips NULLs
SELECT COUNT(*)          AS all_employees,      -- 4
       COUNT(manager_id) AS have_manager        -- 3 (the boss's NULL is skipped)
FROM employees;

-- AVG/SUM ignore NULLs too (AVG divides by the COUNT of non-nulls)
SELECT AVG(salary) FROM employees;   -- average of present salaries only
```

> This is usually what you want — but be aware `AVG` over a column with NULLs averages only the
> non-null values, which can surprise you.

## 💻 Handling NULL — `COALESCE`, `NULLIF`, and friends

```sql
-- COALESCE: first non-null argument (ANSI standard — works on BOTH engines)
SELECT name, COALESCE(city, 'Unknown') AS city FROM customers;

-- NULLIF: returns NULL if the two args are equal (great for avoiding divide-by-zero)
SELECT revenue / NULLIF(orders, 0) AS avg_order_value FROM stats;
```

### 🟦 SQL Server vs 🐘 PostgreSQL

| Need | 🟦 SQL Server | 🐘 PostgreSQL | Portable |
|------|--------------|---------------|----------|
| Replace NULL with a fallback | `ISNULL(col, 'x')` | *(no `ISNULL`)* | **`COALESCE(col, 'x')`** ✅ |
| First non-null of many | `COALESCE(a,b,c)` | `COALESCE(a,b,c)` | `COALESCE` |
| Null if equal | `NULLIF(a,b)` | `NULLIF(a,b)` | `NULLIF` |

> **Prefer `COALESCE`** — it's the SQL standard, works on both engines, and takes many arguments.
> 🟦's `ISNULL` is a non-standard two-argument shortcut that doesn't exist in 🐘.

## ⚖️ NULL and uniqueness / sorting (engine differences)

- **`UNIQUE` constraints:** the SQL standard says multiple `NULL`s are allowed (they're "unknown,"
  so not duplicates). 🐘 follows this. 🟦 SQL Server is **stricter** — a `UNIQUE` index allows only
  **one** NULL by default. (Use a filtered index `WHERE col IS NOT NULL` on 🟦 to allow many.)
- **Sorting:** `ORDER BY` must place NULLs somewhere. 🟦 sorts **NULLs first** (ascending);
  🐘 sorts **NULLs last** (ascending). Both let you override with **`NULLS FIRST` / `NULLS LAST`**
  (🐘 natively; 🟦 emulate with a `CASE` or `ORDER BY col IS NULL`).

```sql
-- 🐘 PostgreSQL: explicit null placement
SELECT name, city FROM customers ORDER BY city ASC NULLS LAST;

-- 🟦 SQL Server: emulate "NULLs last"
SELECT name, city FROM customers ORDER BY CASE WHEN city IS NULL THEN 1 ELSE 0 END, city;
```

## 🚫 Common mistakes

```sql
-- ❌ Comparing to NULL with = / <> → always UNKNOWN → silently wrong results
WHERE col = NULL
WHERE col <> NULL
-- ✅
WHERE col IS NULL
WHERE col IS NOT NULL

-- ❌ NOT IN with a NULL in the list → returns NOTHING
WHERE id NOT IN (SELECT manager_id FROM employees)   -- manager_id has a NULL → whole thing UNKNOWN
-- ✅ use NOT EXISTS (null-safe) or filter the NULLs out
WHERE NOT EXISTS (SELECT 1 FROM employees e2 WHERE e2.manager_id = employees.id)

-- ❌ Assuming AVG includes NULLs as zero
SELECT AVG(rating) ...   -- divides by count of NON-null ratings, not all rows
-- ✅ decide explicitly: AVG(COALESCE(rating, 0)) if NULL should count as 0
```

The **`NOT IN` + NULL** trap is one of the nastiest bugs in SQL — covered again in
[Subqueries](05.Subqueries.md). Prefer `NOT EXISTS`.

## 🌍 Real-World Use

`NULL` represents genuinely-missing data everywhere: an optional middle name, a not-yet-shipped
order's `shipped_date`, a survey question left blank. Handling it correctly is the difference
between a report that's right and one that quietly omits or miscounts rows.

## 🎯 Practice (with full solutions)

### 1. Find the unmanaged — `Easy`
**Task:** List employees with no manager.
**Solution:**
```sql
SELECT name FROM employees WHERE manager_id IS NULL;
```
**Why it works:** `IS NULL` is the only correct way to test for missing values; `= NULL` would
return nothing.

### 2. Safe display fallback — `Easy`
**Task:** List every customer's name and city, showing `'(unknown)'` where city is missing —
portably across both engines.
**Solution:**
```sql
SELECT name, COALESCE(city, '(unknown)') AS city FROM customers;
```
**Why it works:** `COALESCE` is the ANSI-standard fallback that works on SQL Server and PostgreSQL
alike (unlike 🟦-only `ISNULL`).

### 3. Avoid the NOT IN trap — `Medium`
**Task:** Find products that have **never** been ordered. `order_items.product_id` is always
non-null, but write it the *safe* way regardless.
**Solution:**
```sql
SELECT p.name
FROM products p
WHERE NOT EXISTS (
    SELECT 1 FROM order_items oi WHERE oi.product_id = p.product_id
);
```
**Why it works:** `NOT EXISTS` is null-safe — even if the subquery column could contain NULLs, it
behaves correctly, unlike `NOT IN`, which returns nothing the moment a NULL appears in its list.

## ✅ Key Takeaways

- `NULL` = **unknown/missing**, not zero or empty. Comparisons with it yield **`UNKNOWN`**.
- Test with **`IS NULL`** / **`IS NOT NULL`** — never `= NULL`.
- **`COALESCE`** (portable) replaces NULLs; **`NULLIF`** guards divide-by-zero. Avoid 🟦-only
  `ISNULL`.
- Aggregates **skip NULLs**; `COUNT(col)` ignores them while `COUNT(*)` counts rows.
- Engine differences: 🟦 allows **one** NULL in a `UNIQUE` index and sorts **NULLs first**; 🐘 allows
  **many** NULLs and sorts **NULLs last** (both support `NULLS FIRST/LAST`).
- Prefer **`NOT EXISTS`** over **`NOT IN`** to dodge the NULL trap.
