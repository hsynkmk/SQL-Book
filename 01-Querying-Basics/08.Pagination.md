# Pagination

## 🧠 Intuition

You rarely want *all* rows — you want "page 3 of the results, 20 per page." **Pagination** returns
a slice. The naive way (`OFFSET`) skips N rows and returns the next M; it's simple but gets slow on
deep pages. The fast way (**keyset / "seek" pagination**) remembers the last row you saw and
continues *after* it, using an index — constant time no matter how deep.

> 💡 **Analogy — reading a book.** `OFFSET` pagination is "count 2,000 pages from the start, then
> read 20" — you re-count from page 1 every time. Keyset pagination is a **bookmark**: "continue
> from where I left off." The bookmark is instant; recounting is not.

## 🎯 The Problem

```sql
-- ❌ Page 50,000 with OFFSET — the database reads and THROWS AWAY a million rows first
-- 🟦 SQL Server
SELECT * FROM orders ORDER BY order_id OFFSET 1000000 ROWS FETCH NEXT 20 ROWS ONLY;
-- 🐘 PostgreSQL
SELECT * FROM orders ORDER BY order_id LIMIT 20 OFFSET 1000000;
```

`OFFSET 1000000` makes the engine scan and discard a million rows just to return 20. Deep pages get
linearly slower. For "load more" / infinite scroll on big tables, that's a real problem.

## 💻 OFFSET pagination (simple, fine for shallow pages)

The two engines differ in syntax but do the same thing:

```sql
-- 🟦 SQL Server (ANSI OFFSET/FETCH — needs an ORDER BY)
SELECT order_id, customer_id, order_date
FROM orders
ORDER BY order_id
OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY;     -- page 3, 20 per page (skip 2×20)
```
```sql
-- 🐘 PostgreSQL (LIMIT/OFFSET)
SELECT order_id, customer_id, order_date
FROM orders
ORDER BY order_id
LIMIT 20 OFFSET 40;
```

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Skip + take | `OFFSET n ROWS FETCH NEXT m ROWS ONLY` | `LIMIT m OFFSET n` |
| Take only (first page) | `OFFSET 0 ROWS FETCH NEXT m ROWS ONLY` or `TOP m` | `LIMIT m` |
| Requires `ORDER BY`? | **Yes** (OFFSET/FETCH) | Recommended (else order is undefined) |

> ⚠️ **Always `ORDER BY` a unique, stable key** when paginating. Without a deterministic order, the
> "same" page can return different rows between requests — rows shift, duplicate, or vanish.

## 💻 Keyset (seek) pagination — fast at any depth

Instead of "skip N rows," remember the **last value you saw** and fetch rows *after* it:

```sql
-- First page (no bookmark yet)
-- 🟦 SQL Server
SELECT TOP 20 order_id, order_date FROM orders ORDER BY order_id;
-- 🐘 PostgreSQL
SELECT order_id, order_date FROM orders ORDER BY order_id LIMIT 20;

-- Next page: continue AFTER the last order_id from the previous page (say 1040)
-- 🟦 SQL Server
SELECT TOP 20 order_id, order_date FROM orders WHERE order_id > 1040 ORDER BY order_id;
-- 🐘 PostgreSQL
SELECT order_id, order_date FROM orders WHERE order_id > 1040 ORDER BY order_id LIMIT 20;
```

The `WHERE order_id > 1040 ORDER BY order_id` uses the **index** to jump straight to the right
spot — **O(log n)**, identical cost on page 1 and page 1,000,000.

### Keyset with a non-unique sort key

If you sort by something non-unique (e.g. `order_date`), include a tiebreaker (the PK) so the
bookmark is exact:

```sql
-- "after (order_date, order_id)" — compound keyset
-- 🐘 PostgreSQL (row-value comparison — clean)
SELECT order_id, order_date FROM orders
WHERE (order_date, order_id) > ('2025-05-02', 1040)
ORDER BY order_date, order_id
LIMIT 20;

-- 🟦 SQL Server (expand the comparison; row-value '>' isn't supported the same way)
SELECT TOP 20 order_id, order_date FROM orders
WHERE order_date > '2025-05-02'
   OR (order_date = '2025-05-02' AND order_id > 1040)
ORDER BY order_date, order_id;
```

> 🐘 supports **row-value comparison** `(a, b) > (x, y)` directly — elegant. 🟦 needs the expanded
> `OR` form. Same logic, different syntax.

## ⚖️ OFFSET vs Keyset

| | OFFSET / FETCH-LIMIT | Keyset / Seek |
|--|----------------------|---------------|
| Code complexity | Simple | Slightly more (track last key) |
| Speed on deep pages | **Degrades linearly** (scans skipped rows) | **Constant** (index seek) |
| "Jump to page 500" | Easy | Hard (no random page numbers) |
| Stable under inserts/deletes | No (rows shift between pages) | **Yes** (anchored to a key) |
| Best for | Small datasets, admin grids with page numbers | Infinite scroll, APIs, large tables |

**Rule of thumb:** page-numbered admin UIs over modest data → `OFFSET`. Infinite scroll / "load
more" / large tables / public APIs → **keyset**.

## ⚡ Under the Hood / Performance

- `OFFSET n` still **reads and discards** the first `n` rows — cost grows with `n`.
- Keyset turns paging into a **range seek** on an index (`WHERE key > @last ORDER BY key`) — make
  sure the sort/seek columns are **indexed**, ideally matching the `ORDER BY` exactly so no extra
  sort is needed. See [Indexing](../06-Indexing-and-Performance/01.How-Indexes-Work.md).

## 🚫 Common mistakes

```sql
-- ❌ Pagination without ORDER BY → nondeterministic pages
SELECT * FROM orders OFFSET 20 ROWS FETCH NEXT 20 ROWS ONLY;   -- order undefined!
-- ✅ always order by a stable, unique key
... ORDER BY order_id OFFSET 20 ROWS FETCH NEXT 20 ROWS ONLY;

-- ❌ Deep OFFSET on a large table for infinite scroll → slower with every page
-- ✅ keyset: WHERE order_id > @lastSeen ORDER BY order_id

-- ❌ Sorting by a non-unique column without a tiebreaker → rows can repeat/skip across pages
ORDER BY order_date            -- ties are unstable
-- ✅ ORDER BY order_date, order_id
```

## 🌍 Real-World Use

Every "next page," "load more," and infinite-scroll feed is pagination. High-traffic APIs almost
always use **keyset** (often exposing the bookmark as an opaque "cursor" token) because OFFSET
melts under deep paging. Admin back-office grids with explicit page numbers use OFFSET because users
want to jump to page 7.

## 🎯 Practice (with full solutions)

### 1. Page 2, 3 per page — `Easy`
**Task:** Return the second page of products (3 per page) ordered by `product_id`, in both dialects.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT product_id, name FROM products ORDER BY product_id
OFFSET 3 ROWS FETCH NEXT 3 ROWS ONLY;
-- 🐘 PostgreSQL
SELECT product_id, name FROM products ORDER BY product_id
LIMIT 3 OFFSET 3;
```
**Why it works:** skip the first page (3 rows), take the next 3, with a stable `ORDER BY`.

### 2. Convert to keyset — `Medium`
**Task:** The previous page ended at `product_id = 3`. Fetch the next 3 products via keyset.
**Solution:**
```sql
-- 🟦 SQL Server
SELECT TOP 3 product_id, name FROM products WHERE product_id > 3 ORDER BY product_id;
-- 🐘 PostgreSQL
SELECT product_id, name FROM products WHERE product_id > 3 ORDER BY product_id LIMIT 3;
```
**Why it works:** `WHERE product_id > 3` seeks straight into the index past the last seen id — no
rows scanned-and-discarded, so it's just as fast on page 1 or page 10,000.

### 3. Stable sort by a non-unique column — `Medium`
**Task:** Page orders newest-first by `order_date`, with a tiebreaker so pages are stable.
**Solution:**
```sql
-- 🐘 PostgreSQL (row-value keyset, descending)
SELECT order_id, order_date FROM orders
WHERE (order_date, order_id) < ('2025-05-02', 4)     -- "before" this bookmark, since DESC
ORDER BY order_date DESC, order_id DESC
LIMIT 20;
-- 🟦 SQL Server: expand to
-- WHERE order_date < '2025-05-02' OR (order_date = '2025-05-02' AND order_id < 4)
```
**Why it works:** adding `order_id` as a tiebreaker makes the sort total and the bookmark exact, so
no row repeats or disappears between pages even when many share an `order_date`.

## ✅ Key Takeaways

- Pagination returns a slice: **🟦 `OFFSET ... FETCH NEXT`** vs **🐘 `LIMIT ... OFFSET`**.
- **Always `ORDER BY` a unique, stable key** — otherwise pages are nondeterministic.
- **`OFFSET` degrades on deep pages** (scans skipped rows); **keyset/seek** stays constant by
  continuing after the last key via an index.
- Use OFFSET for small/page-numbered grids; **keyset for infinite scroll, APIs, and big tables**.
- 🐘 supports clean **row-value keyset** `(a,b) > (x,y)`; 🟦 expands it to `OR` conditions.
