# Aggregation: GROUP BY & HAVING

## 🧠 Intuition

Aggregation **collapses many rows into a summary**: total sales, average salary, count of orders
per customer. `GROUP BY` says *what to summarize by* (one result row per group), aggregate
functions (`SUM`, `COUNT`, `AVG`, `MIN`, `MAX`) say *how to summarize*, and `HAVING` filters the
*groups* after they're computed.

> 💡 **Analogy — sorting receipts into piles.** `GROUP BY customer` makes one pile per customer.
> `SUM(amount)` adds up each pile. `HAVING SUM(amount) > 1000` then throws away the small piles.
> `WHERE` filters individual receipts *before* you pile them; `HAVING` filters the *piles* after.

Aggregation is **standardized** — both engines behave the same (with a couple of function-name
notes).

## 🎯 The Problem

```sql
-- ❌ "How much has each customer spent?" — you can't answer this row-by-row
SELECT customer_id, order_id FROM orders;   -- raw rows, no totals
```

You need to *group* orders by customer and *sum* their values — that's aggregation.

## 📐 How It Works

Aggregation runs **after** `WHERE` and **before** `ORDER BY`:

```mermaid
graph LR
    A[FROM/JOIN] --> B[WHERE: filter rows]
    B --> C[GROUP BY: form groups]
    C --> D[aggregates computed per group]
    D --> E[HAVING: filter groups]
    E --> F[SELECT + ORDER BY]
```

**The golden rule:** every column in `SELECT` must either be **in the `GROUP BY`** or **wrapped in
an aggregate**. Otherwise the database can't decide which row's value to show for the group.

## 💻 The essentials

```sql
-- The five core aggregates
SELECT COUNT(*)            AS num_products,
       SUM(units_in_stock) AS total_stock,
       AVG(unit_price)     AS avg_price,
       MIN(unit_price)     AS cheapest,
       MAX(unit_price)     AS priciest
FROM products;

-- GROUP BY: one summary row per group
SELECT category_id, COUNT(*) AS product_count, AVG(unit_price) AS avg_price
FROM products
GROUP BY category_id;

-- WHERE filters rows BEFORE grouping; HAVING filters groups AFTER
SELECT category_id, COUNT(*) AS in_stock_count
FROM products
WHERE units_in_stock > 0          -- per-row filter
GROUP BY category_id
HAVING COUNT(*) >= 2;             -- per-group filter

-- Aggregation over a join: spend per customer
SELECT c.name, SUM(oi.quantity * oi.unit_price) AS total_spent
FROM customers c
JOIN orders      o  ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
GROUP BY c.name
ORDER BY total_spent DESC;

-- COUNT variants
SELECT COUNT(*)                AS all_rows,        -- counts rows (incl. NULLs)
       COUNT(employee_id)      AS handled_orders,  -- non-null employee_id
       COUNT(DISTINCT customer_id) AS unique_customers
FROM orders;
```

## 🟦 SQL Server vs 🐘 PostgreSQL

Aggregation is nearly identical. A few notes:

| Concept | 🟦 SQL Server | 🐘 PostgreSQL |
|---------|--------------|---------------|
| Core aggregates (`SUM/COUNT/AVG/MIN/MAX`) | identical | identical |
| String aggregation | `STRING_AGG(name, ', ')` | `string_agg(name, ', ')` |
| `GROUP BY` non-aggregated column rule | **strict** (must list all) | **strict** (must list all) — *but* 🐘 relaxes it when grouping by a PK |
| Conditional count | `COUNT(CASE WHEN ... THEN 1 END)` | `COUNT(*) FILTER (WHERE ...)` *(cleaner)* or the same CASE |

```sql
-- 🐘 PostgreSQL: the FILTER clause (elegant conditional aggregation)
SELECT category_id,
       COUNT(*) FILTER (WHERE units_in_stock > 0) AS in_stock,
       COUNT(*) FILTER (WHERE units_in_stock = 0) AS out_of_stock
FROM products
GROUP BY category_id;

-- 🟦 SQL Server (and portable): use CASE inside the aggregate
SELECT category_id,
       SUM(CASE WHEN units_in_stock > 0 THEN 1 ELSE 0 END) AS in_stock,
       SUM(CASE WHEN units_in_stock = 0 THEN 1 ELSE 0 END) AS out_of_stock
FROM products
GROUP BY category_id;
```

> 🐘's **`FILTER (WHERE ...)`** is a clean way to do "count/sum only the rows matching X" without a
> `CASE`. 🟦 doesn't have it — use the `CASE` form (which also works on 🐘).

## ⚡ Under the Hood / Performance

- Aggregation may use a **hash aggregate** (group via a hash table) or a **stream aggregate**
  (requires sorted input). An index on the `GROUP BY` columns can enable the cheaper stream path.
- `COUNT(*)` is generally the fastest count — don't write `COUNT(1)` thinking it's faster (it
  isn't; both count rows).
- Filtering early with `WHERE` shrinks the data *before* grouping — always prefer it over `HAVING`
  for per-row conditions.

## 🚫 Common mistakes

```sql
-- ❌ Selecting a non-aggregated, non-grouped column
SELECT category_id, name, AVG(unit_price) FROM products GROUP BY category_id;  -- which "name"? ERROR
-- ✅ either group by it, or aggregate it
SELECT category_id, AVG(unit_price) FROM products GROUP BY category_id;

-- ❌ Using HAVING for a per-ROW filter (works, but filters too late / slower)
SELECT category_id, COUNT(*) FROM products GROUP BY category_id HAVING units_in_stock > 0;  -- ERROR: units_in_stock not grouped/aggregated
-- ✅ per-row condition belongs in WHERE
SELECT category_id, COUNT(*) FROM products WHERE units_in_stock > 0 GROUP BY category_id;

-- ❌ Expecting COUNT(column) to count rows with NULLs
SELECT COUNT(employee_id) FROM orders;   -- skips NULL employee_id
-- ✅ COUNT(*) counts all rows
```

## 🌍 Real-World Use

Every dashboard number is an aggregate: revenue per region, signups per day, average response time
per endpoint, orders per customer. `GROUP BY` + `HAVING` answers "which groups exceed a threshold"
— top customers, overloaded servers, categories with low stock.

## 🎯 Practice (with full solutions)

### 1. Spend per customer — `Easy`
**Task:** Total amount spent by each customer (quantity × unit_price across their order items),
highest first.
**Solution:**
```sql
SELECT c.name, SUM(oi.quantity * oi.unit_price) AS total_spent
FROM customers c
JOIN orders      o  ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
GROUP BY c.name
ORDER BY total_spent DESC;
```
**Why it works:** join down to line items, group by customer, sum the line totals.

### 2. Categories with 2+ products — `Easy`
**Task:** List category IDs that contain at least 2 products, with the count.
**Solution:**
```sql
SELECT category_id, COUNT(*) AS product_count
FROM products
GROUP BY category_id
HAVING COUNT(*) >= 2;
```
**Why it works:** group by category, then `HAVING` keeps only groups whose count meets the
threshold — a per-group filter.

### 3. Shipped vs total orders per customer — `Medium`
**Task:** For each customer, show total orders and how many are `'Shipped'`.
**Solution:**
```sql
-- portable (works on both engines)
SELECT c.name,
       COUNT(*) AS total_orders,
       SUM(CASE WHEN o.status = 'Shipped' THEN 1 ELSE 0 END) AS shipped_orders
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.name;
```
```sql
-- 🐘 PostgreSQL, cleaner with FILTER
SELECT c.name,
       COUNT(*) AS total_orders,
       COUNT(*) FILTER (WHERE o.status = 'Shipped') AS shipped_orders
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.name;
```
**Why it works:** conditional aggregation counts only the matching rows within each group — `CASE`
portably, or `FILTER` on PostgreSQL.

## ✅ Key Takeaways

- Aggregates (**`SUM/COUNT/AVG/MIN/MAX`**) collapse rows; **`GROUP BY`** defines the groups.
- **Golden rule:** every `SELECT` column is grouped or aggregated.
- **`WHERE`** filters rows *before* grouping; **`HAVING`** filters groups *after*.
- `COUNT(*)` counts rows; `COUNT(col)` skips NULLs; `COUNT(DISTINCT col)` counts uniques.
- 🐘's **`FILTER (WHERE ...)`** does conditional aggregation cleanly; the portable form is
  `SUM/COUNT(CASE WHEN ...)`.
