# Subqueries

## 🧠 Intuition

A **subquery** is a query nested inside another query — you use the result of one `SELECT` as input
to another. "Find products priced above the average" needs two steps: compute the average (one
query), then compare each product to it (the outer query). A subquery wires those together.

> 💡 **Analogy — a question inside a question.** "Who earns more than the company average?" contains
> a sub-question: "what *is* the average?" You answer the inner one first, then use it to answer the
> outer one. SQL lets you write both in a single statement.

Subqueries are **fully standardized** — identical on SQL Server and PostgreSQL.

## 📐 The flavors

| Kind | Returns | Used in | Example need |
|------|---------|---------|--------------|
| **Scalar** | One value | anywhere a value fits (`SELECT`, `WHERE`) | "above the average price" |
| **Multi-row** | A column of values | `IN`, `ANY`, `ALL` | "in these categories" |
| **Correlated** | Re-runs per outer row (references it) | `WHERE`, `SELECT` | "their most recent order" |
| **`EXISTS`** | TRUE/FALSE (does any matching row exist?) | `WHERE` | "customers who have ordered" |
| **Derived table** | A whole result set | `FROM` (as a temp table) | pre-aggregate, then join |

## 💻 The essentials

```sql
-- Scalar subquery: products priced above the overall average
SELECT name, unit_price
FROM products
WHERE unit_price > (SELECT AVG(unit_price) FROM products);

-- Multi-row subquery with IN: products in 'Beverages' or 'Snacks'
SELECT name
FROM products
WHERE category_id IN (
    SELECT category_id FROM categories WHERE name IN ('Beverages','Snacks')
);

-- EXISTS: customers who have placed at least one order (null-safe, often fastest)
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);

-- NOT EXISTS: customers who have NEVER ordered (the anti-join, null-safe)
SELECT c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);

-- Correlated subquery: each customer's most recent order date
SELECT c.name,
       (SELECT MAX(o.order_date) FROM orders o WHERE o.customer_id = c.customer_id) AS last_order
FROM customers c;

-- Derived table (subquery in FROM): pre-aggregate then filter
SELECT category_id, avg_price
FROM (
    SELECT category_id, AVG(unit_price) AS avg_price
    FROM products GROUP BY category_id
) AS cat_avgs
WHERE avg_price > 5;
```

### Scalar vs correlated — the key distinction

- A **scalar** subquery `(SELECT AVG(unit_price) FROM products)` runs **once** and plugs its single
  value in.
- A **correlated** subquery references the outer row (`WHERE o.customer_id = c.customer_id`), so it
  conceptually **re-runs for each outer row**. Powerful, but watch performance on large tables.

## ⚡ Under the Hood / Performance

- The optimizer often **rewrites** subqueries into joins or semi-joins automatically — a correlated
  `EXISTS` typically becomes an efficient *semi-join*, not a literal loop. Check the
  [execution plan](../06-Indexing-and-Performance/04.Reading-Execution-Plans.md) to see what it did.
- **`EXISTS` short-circuits** — it stops at the first matching row, so it's usually faster than
  `IN` for "does any match exist," and it's **null-safe** (unlike `NOT IN`).
- **`NOT IN` + NULL = nothing.** If the subquery can return a NULL, `NOT IN` returns no rows at all.
  Prefer **`NOT EXISTS`** (see [Working with NULL](02.Working-with-NULL.md)).
- A **correlated subquery in `SELECT`** that re-runs per row can be slow; a `LEFT JOIN` +
  `GROUP BY`, a [window function](../02-Advanced-Querying/01.Window-Functions.md), or a derived
  table is often faster.

## ⚖️ Subquery vs JOIN vs CTE

Many subqueries can be written as joins or [CTEs](../02-Advanced-Querying/02.CTEs-and-Recursion.md) —
choose for clarity:
- **`EXISTS`/`NOT EXISTS`** for "does a related row exist?" (semi/anti-join) — clear and fast.
- **`IN`** for small static lists or simple membership.
- **Derived table / CTE** when you need to pre-aggregate, then join or filter — far more readable
  than deeply nested subqueries.
- **JOIN** when you actually need columns *from* the other table in the output.

## 🚫 Common mistakes

```sql
-- ❌ NOT IN with a nullable subquery column → returns NOTHING if any NULL appears
SELECT name FROM products
WHERE product_id NOT IN (SELECT product_id FROM order_items WHERE quantity IS NULL);
-- ✅ NOT EXISTS is null-safe
SELECT p.name FROM products p
WHERE NOT EXISTS (SELECT 1 FROM order_items oi WHERE oi.product_id = p.product_id);

-- ❌ Scalar subquery that returns more than one row → runtime error
WHERE unit_price = (SELECT unit_price FROM products WHERE category_id = 1);  -- many rows!
-- ✅ use IN, or aggregate to one value
WHERE unit_price IN (SELECT unit_price FROM products WHERE category_id = 1);

-- ❌ Forgetting to alias a derived table
SELECT * FROM (SELECT category_id, COUNT(*) FROM products GROUP BY category_id);  -- ERROR (needs alias)
-- ✅ name it
SELECT * FROM (SELECT category_id, COUNT(*) AS n FROM products GROUP BY category_id) AS t;
```

## 🌍 Real-World Use

Subqueries answer comparative and existence questions everywhere: "products above average price,"
"customers with no recent activity," "employees earning more than their department's average,"
"orders containing a discontinued product." `EXISTS` powers permission checks ("does this user have
any active subscription?") cleanly and fast.

## 🎯 Practice (with full solutions)

### 1. Above-average products — `Easy`
**Task:** List products priced above the average product price.
**Solution:**
```sql
SELECT name, unit_price
FROM products
WHERE unit_price > (SELECT AVG(unit_price) FROM products);
```
**Why it works:** the scalar subquery computes one average; each product is compared to it.

### 2. Customers who ordered in May 2025 — `Medium`
**Task:** Names of customers with at least one order dated in May 2025.
**Solution:**
```sql
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.order_date >= '2025-05-01' AND o.order_date < '2025-06-01'
);
```
**Why it works:** `EXISTS` stops at the first qualifying order per customer — efficient and
null-safe. (Note the SARGable date range instead of a function on `order_date` — see
[SARGability](../06-Indexing-and-Performance/05.SARGability.md).)

### 3. Each product with its category's average — `Medium`
**Task:** Show each product's price next to the average price *of its category*.
**Solution:**
```sql
-- Correlated subquery
SELECT p.name, p.unit_price,
       (SELECT AVG(p2.unit_price) FROM products p2 WHERE p2.category_id = p.category_id) AS cat_avg
FROM products p;

-- Often clearer/faster as a window function (see Advanced Querying):
SELECT name, unit_price, AVG(unit_price) OVER (PARTITION BY category_id) AS cat_avg
FROM products;
```
**Why it works:** the correlated subquery computes the average within the *same* category for each
product. The window-function version does the same in one pass — a preview of
[Window Functions](../02-Advanced-Querying/01.Window-Functions.md).

## ✅ Key Takeaways

- A **subquery** nests one query inside another: **scalar** (one value), **multi-row** (for `IN`),
  **correlated** (references the outer row), **`EXISTS`** (membership), **derived table** (in `FROM`).
- **`EXISTS`/`NOT EXISTS`** are the null-safe, usually-fastest way to test for related rows — prefer
  them over `IN`/`NOT IN`.
- The optimizer often rewrites subqueries into joins; check the plan.
- For pre-aggregate-then-use, a **derived table or CTE** beats deeply nested subqueries for clarity.
- Correlated subqueries in `SELECT` can be slow — a join or window function is often better.
